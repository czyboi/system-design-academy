The same-row write and pointer invalidation in the reference solution address both orders of a completion racing with an edit or revocation once approval is version-scoped. If the change commits first, the updated row fails the predicate. If publication commits first, the later change clears the pointer. The authoritative fetch and private object storage bound revocation to new access checks. PostgreSQL 18 is scoped to an update of the same target row at Read Committed. The catalogue design is an illustration, with no executable SQL or database test result. [PostgreSQL 18 §13.2.1](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED) · [RFC 9111 §5.2.2.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5)

The contracts at `modules/m03/integrated/solution-rubric.md:18–22,32` distinguish durable catalogue admission, renderer acceptance and eventual completion. Catalogue retries return the existing authorized job for the same key and inputs even if the version moved. The renderer atomically records acceptance by a stable unique ID in one store shared by eligible endpoints. A repeated ID returns the matching record, while a changed request is rejected. Retention spans the stated retry and restart window. The processing path separately requires repeat-safe outputs and completion. These are application contracts. HTTP `202` and the RPC stub support the interaction without guaranteeing execution or providing deduplication. [RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) · [gRPC Core concepts, RPC life cycle](https://grpc.io/docs/what-is-grpc/core-concepts/#rpc-life-cycle) · [Amazon Builders’ Library, Reducing client complexity, Late arriving requests and Same client request ID, different intent](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

The brief at `modules/m03/integrated/brief.md:11` and solution at `modules/m03/integrated/solution-rubric.md:26–32` use the same cycle budget. Taking the full 30 ms delay after a 120 ms timeout starts the second attempt at 150 ms with 150 ms left. Its 60 ms response arrives at 210 ms and leaves 90 ms. Both no acceptance and committed acceptance with a lost reply can look like a timeout. Reusing the same ID under the durable contract handles both branches. The single retry owner, at most two attempts per cycle, concurrency cap, maximum cache age, and expiry-bounded later dispatch are consistent with M03-L03. The later dispatch uses the same ID and therefore needs no inference of non-application from a missing status.
