# Source evidence for M03-INTEGRATION

Checked 2026-11-11. Confidence is verified for the scoped claim in each row. Scenario inputs, calculations and design judgments are original illustrative assumptions.

| Claim | Supported statement | Primary evidence and version | Scope and limits |
| --- | --- | --- | --- |
| LAYER-1 | Logical presentation, business and data layers can share deployment units; physical tiers mark runtime/network boundaries. | [Microsoft Azure Architecture Center, N-tier architecture (living)](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier) | Architecture distinction. A design may scale application replicas and use clear in-process modules. |
| LAYER-2 | Microservices can deploy and scale independently where boundaries and ownership permit. They introduce distributed calls, failure modes, service operations and data-consistency work. | [Microsoft Azure Architecture Center, Microservices architecture style (living)](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices) | Architecture guidance. Independence depends on API/data ownership and release coupling. No guaranteed latency or productivity gain. |
| LAYER-3 | A saga uses local transactions with explicit compensations where feasible rather than providing one shared transaction boundary. | [Microsoft Azure Architecture Center, Saga distributed transactions pattern (living)](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga) | Compensations are business operations, can fail and cannot generally undo external observations. The lesson can retain closely coupled invariants inside a single transactional owner. |
| API-1 | REST constrains client/server separation, stateless interaction, caching, uniform interfaces and layering, with optional code on demand. The uniform interface includes resource identity, manipulation through representations, self-description and hypermedia. | [Roy Fielding, Architectural Styles and the Design of Network-based Software Architectures §§5.1 and 5.2.1 (2000)](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm) | REST is an architectural style. HTTP JSON endpoints do not automatically satisfy every constraint. |
| API-2 | An RPC client stub encodes a procedure and arguments, the server dispatches and the response flows back; gRPC supports schema-generated stubs and unary/streaming shapes. | [IETF RFC 5531 §4 (2009), gRPC Core concepts (living)](https://datatracker.ietf.org/doc/html/rfc5531#section-4) | See [gRPC core](https://grpc.io/docs/what-is-grpc/core-concepts/). ONC RPC and gRPC are distinct implementations. A stub cannot give local-call failure semantics. |
| API-3 | Protobuf field-number rules affect wire compatibility, deadlines bound caller wait and idempotence concerns intended repeated effects. | [Protobuf proto3 guide, gRPC Deadlines, IETF RFC 9110 §9.2.2 (living; 2022)](https://protobuf.dev/programming-guides/proto3/#updating) | See [gRPC deadlines](https://grpc.io/docs/guides/deadlines/) and [HTTP idempotence](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2.2). Application semantics and durable deduplication remain explicit design choices. |
| API-4 | HTTP 202 reports acceptance for processing. The response can provide a way to monitor status. | [IETF RFC 9110 §15.3.3 (2022)](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) | Processing can still fail. Persisting the job and idempotency record before responding is the catalogue’s application contract. |
| DISC-1 | A Consul agent can register a service with address, port and health checks; health API results can filter passing instances. DNS SRV carries priority, weight, port and target. | [HashiCorp Consul Agent Service and Health APIs (living), IETF RFC 2782 (2000)](https://developer.hashicorp.com/consul/api-docs/agent/service#register-service) | See [Consul health](https://developer.hashicorp.com/consul/api-docs/health#list-nodes-for-service) and [SRV](https://datatracker.ietf.org/doc/html/rfc2782). Health and TTL are separate signals. Client support for SRV is needed. |
| DISC-2 | etcd leases tie key lifetimes to keepalive; ZooKeeper ephemeral nodes last for a session; Consul also exposes a separate general KV feature. | [etcd 3.6 API, ZooKeeper 3.9.4 Programmer's Guide, Consul KV overview (living)](https://etcd.io/docs/v3.6/learning/api/#lease-api) | See [ZooKeeper ephemeral nodes](https://zookeeper.apache.org/doc/r3.9.4/zookeeperProgrammers.html#Ephemeral+Nodes) and [Consul KV](https://developer.hashicorp.com/consul/docs/automate/kv). KV-based products need a registration/watch/health design. Do not infer identical expiry or secret-management semantics. |
| DISC-3 | A stable service address can shift endpoint selection behind an intermediary. Retries across several layers can multiply; use remaining deadline, capped attempts, backoff and jitter. | [Kubernetes Service concepts and AWS Builders' Library, Timeouts, retries, and backoff with jitter (living)](https://kubernetes.io/docs/concepts/services-networking/service/) | See [AWS retry guidance](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/). The routing model varies by implementation. Timeout after commit is ambiguous; retry only under a suitable application contract. |
