# Reference design and rubric

## Ownership and deployment

Keep items, approval and publication in the catalogue's transactional boundary. Give the renderer its own deployment and CPU capacity. It takes immutable input for an item version, owns rendering progress, and returns an output reference with the work ID and version. Keep current version, approved version and public pointer on the same authoritative item row. An approval records the reviewed version only if it is still current. Publish with one guarded row update that requires both versions to equal the rendered version. An edit advances the current version and clears the approval and pointer in the same update. A revocation clears the approval and pointer together. If either commits before publication, the guard rejects the result. If publication commits first, the edit or revocation clears the pointer when it commits. This preserves the invariant in both orders. When immediate revocation is required, keep preview objects private and gate each public fetch on the authoritative pointer. Avoid a public object URL or cached authorization that can outlive revocation. A separate check followed by an unconditional write can race even inside a transaction. PostgreSQL 18 Read Committed is one implementation where a concurrent UPDATE rechecks the same target row after the competing update commits. [PostgreSQL 18 §13.2.1](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)

A modular application with isolated worker capacity is viable if it meets all four targets without separate release or data ownership. An entity-per-service split adds remote dependencies to metadata and moves a publication invariant across interfaces. Compare viable options under the same workload and fault schedule, including metadata p99, CPU saturation and preview completion lag. Low admitted-response latency cannot compensate for rejecting original requests.

## Public and internal contracts

| Contract | Behavior |
| --- | --- |
| `POST /items/{item}/previews` | Authorize the editor and uniquely claim (editor, operation, key). In one transaction persist the key, immutable item/version/options, stable job and work IDs, and pending dispatch before sending. On conflict compare saved inputs: matching retries return the same job link, even after an edit; mismatches are rejected. Restart resumes the saved dispatch. Return `202 Accepted` with the job link after commit. |
| `GET /preview-jobs/{id}` | Authorize access and return a private representation with `pending`, `ready`, `superseded` or `failed`. Expose a result link only when eligible. Preserve status meanings and required links. Add optional fields only where old clients tolerate unknown fields; use an opt-in representation for strict clients. New clients must tolerate old responses without the addition. Test both directions. |
| `StartRender(work_id, item_version, input_ref, options)` | The dispatcher's stub marshals the operation. The transport carries it to the selected renderer, where the server stub decodes and dispatches it. The renderer atomically inserts a durable record under a unique work ID and returns that ID through the reverse path. All eligible endpoints share that acceptance store. Concurrent attempts with the same ID and matching immutable inputs return the existing record. A reused ID with changed inputs is rejected. An accept reply confirms a work record, while a later state change confirms completion. |

The catalogue dispatcher resumes pending dispatch after a restart. The renderer resumes accepted work and stores a recoverable completed-result reference by work ID. A lost completion notification is recovered by replay or authoritative lookup; the catalogue applies the ready transition idempotently and still performs the version guard. Retain deduplication and result records through the retry and recovery window. At expiry, surface unresolved acceptance for reconciliation; retain the identity until authoritative terminal evidence establishes the original cannot apply. A superseded job can be shown as such and a new version requested. [Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#using-an-outbox-table-with-a-relational-database)

## Discovery and failure trace

For one catalogue caller, let its dispatcher select from a watched, locally cached renderer pool. Use registration, readiness, removal or expiry, and a maximum age for using the list during registry failure. An intermediary could instead centralize selection for several caller stacks. It adds another dependency to size and monitor. The retry owner and the discovery owner may be different components, but their deadline and attempt contracts must agree.

1. At 0 ms the dispatcher calls a renderer listed as ready. If the stopped instance never accepted the call, the alternate can create the job. If the first renderer accepted the work and its reply was lost, the alternate must reuse the committed record. In either case an unanswered attempt can consume the full 120 ms limit. The caller treats the outcome as unknown until it has an authoritative result.
2. Exclude the suspect endpoint for this retry. Wait at most 30 ms, then call a distinct eligible endpoint with the same work ID. At 150 ms there are 150 ms left. A 60 ms response arrives at 210 ms, leaving 90 ms. The receiver returns the existing record if acceptance happened on the first attempt.
3. The dispatcher owns a maximum of two attempts in this cycle. Disable independent intermediary retries or coordinate them within that cap. For illustration, two dispatcher replicas each allow 16 caller-tracked in-flight calls, including retries: together they can offer 32 calls, not 16. At saturation, pending dispatch remains in a bounded durable queue; reject or defer admission when its configured bound is reached and count rejected originals against the SLO. Use a cached list for at most five seconds after its last successful refresh; then pause sends until refresh. Resume pending work under the same ID with backoff while its window remains; surface expiry for reconciliation.

Independently, the renderer admits at most 40 active render executions across its workers and uses a bounded durable accepted-work queue. Before applying new-work admission, look up the work ID: matching accepted or completed duplicates return the existing record even at saturation; new work is deferred or rejected when full. Protect acceptance handlers separately with a receiver-side limit of 64 live handlers across workers and a bounded request queue; when full, reject or defer calls without accepting new work. These are independent from caller slots and active renders. A caller timeout does not prove the handler stopped or cancel committed render work. Propagate remaining attempt time where supported, cancel unnecessary handler work on timeout, and reconcile the durable work ID before retrying. Explicit cancellation marks obsolete work and stops execution where possible, but the publication guard remains necessary. Measure live handlers, active renders and queue depths separately from caller in-flight calls, including during timeout and worker loss. Values are test assumptions, not observed capacity. [gRPC deadlines](https://grpc.io/docs/guides/deadlines/#deadlines-on-the-server)

The durable record covers acceptance of the logical job. If processing restarts, make the render output and completion handler repeat-safe for the same work ID. [AWS Builders' Library, making retries safe](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## Illustrative drill procedure

This is a test plan, not a result or a capacity claim. For each viable boundary, generate evenly spaced arrivals at 900 metadata operations/s and 30 previews/s over [0, 60 s), with unique original IDs and fixed approved versions. Assume two dispatcher replicas, two renderer workers each capable of 20 concurrent executions, and a deterministic one-second render service time per execution when healthy; configure each durable queue with 2,000 entries. Measure actual metadata service time and admission/dispatch overhead in the test environment, or state explicit values in a simulation. These inputs do not establish that a target passes.

At t=10 s stop one renderer worker for 10 s, including any recovery of its accepted work. At t=25 s interrupt discovery for 10 s; arrange the last successful refresh at t=25 s so the five-second cache cutoff is crossed, then restore discovery at t=35 s. Repeat with the same inputs for each alternative. Record first submissions, commits, client responses, authorized ready observations, queue depth and age, endpoint age, active renderer executions, caller-tracked calls and retries. Follow each original to its individual one-second or 120-second cutoff, including the final preview near t=180 s. Calculate each proportion and the specified p99 from those records; report results as measured or, for a model, projected with its assumptions. Run separate cancellation, timeout and race cases; if any assumption or measurement is unavailable, report the target as unverified.

## Self-evaluation

Score each row and each operational subcheck independently: 2 for the stated evidence, 1 for incomplete evidence, 0 for missing or contradictory evidence. A justified design must meet all four numerical targets and independently pass the safety checks; one passing metric cannot offset another failure. A model gives projected evidence only, not a measured benchmark.

| Criterion | Evidence for full credit |
| --- | --- |
| Boundary and invariant | Compare alternatives using the scenario’s CPU constraint and the delay allowance. Name the state owner and show how the publication guard serializes with concurrent version changes and approval revocations. |
| Interface trace | Specify the scoped unique key, input comparison, atomic identity and pending dispatch, restart recovery, completion replay or lookup, and guarded idempotent ready transition. Test old and new representations in both directions, including strict clients. |
| Failure policy | Trace elapsed and remaining time, retry and discovery ownership, stable identity, replica-wide offered calls and independent receiver active-work limits. Give bounded queue/admission, timeout, cancellation and saturation behavior, cache age, deferral and expiry reconciliation. |
| Test plan | Specify a reproducible arrival pattern, service/capacity assumptions and timed faults, track original IDs through individual deadlines, and report observed or explicitly projected results for viable alternatives under the same schedule. Measure both caps, queues, retries and endpoint age, including timeout and worker loss. |
| Metadata success | Independently show at least 99% of original valid metadata operations receive a successful response within 1 s of first submission, including all rejected, failed, missing and late operations in the denominator. |
| Metadata latency | Independently show p99 at most 200 ms from first submission among successful responses received within 1 s, including retries and waits; report population size. |
| Preview admission | Independently show at least 99% of original valid preview submissions commit durable catalogue admission within 1 s of first submission; record client acknowledgement/link separately. Later failure does not undo a timely admission success. |
| Preview readiness | Independently show at least 99% of original valid preview submissions reach an authorized usable result through catalogue status within 120 s of first submission. Include rejected, failed, expired, unexpected cancellations, unresolved and late work. |
| Safety | Independently test concurrent matching creates, restart before first dispatch, lost acceptance and lost completion; verify one logical job and recovered result. In separate cancellation tests force both publication/edit and publication/revocation orders: obsolete work never becomes ready for the changed version, and revocation prevents publication or clears the pointer. Approve v1, edit to v2, and verify v2 remains private until approved. Equivalent mechanisms and tests earn credit. |

Other choices earn credit if they protect the current-version invariant and bound work within the stated failure policies. An authoritative accepted record resolves whether the renderer accepted the work ID. An absent or pending record leaves room for an earlier attempt to apply. Preserve the covered work ID or require authoritative terminal evidence of non-application before assigning a fresh one.
