# Source evidence for M03-L02

Checked 2026-11-11. Confidence is verified for the scoped claim in each row. Scenario inputs, calculations and design judgments are original illustrative assumptions.

| Claim | Supported statement | Primary evidence and version | Scope and limits |
| --- | --- | --- | --- |
| API-1 | REST constrains client/server separation, stateless interaction, caching, uniform interfaces and layering, with optional code on demand. The uniform interface includes resource identity, manipulation through representations, self-description and hypermedia. | [Roy Fielding, Architectural Styles and the Design of Network-based Software Architectures §§5.1 and 5.2.1 (2000)](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm) | REST is an architectural style. HTTP JSON endpoints do not automatically satisfy every constraint. |
| API-2 | An RPC client stub encodes a procedure and arguments, the server dispatches and the response flows back; gRPC supports schema-generated stubs and unary/streaming shapes. | [IETF RFC 5531 §4 (2009), gRPC Core concepts (living)](https://datatracker.ietf.org/doc/html/rfc5531#section-4) | See [gRPC core](https://grpc.io/docs/what-is-grpc/core-concepts/). ONC RPC and gRPC are distinct implementations. A stub cannot give local-call failure semantics. |
| API-3 | Protobuf field-number rules affect wire compatibility, deadlines bound caller wait and idempotence concerns intended repeated effects. | [Protobuf proto3 guide, gRPC Deadlines, IETF RFC 9110 §9.2.2 (living; 2022)](https://protobuf.dev/programming-guides/proto3/#updating) | See [gRPC deadlines](https://grpc.io/docs/guides/deadlines/) and [HTTP idempotence](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2.2). Application semantics and durable deduplication remain explicit design choices. |
| API-4 | Choosing resource or operation contracts changes round trips, payload shaping, tooling, debugging and caches for specific workloads. | [Fielding §5.1 and gRPC core concepts, plus original Academy design analysis](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm) | Illustrative cases must explain their actual contract and consequence without generic performance claims. Service-discovery failure preview resolves within this milestone. |
| API-5 | HTTP/1.1 uses a Host field and octet-based Content-Length framing in the shown messages. A clocked origin sends Date on this 202. HTTP 202 reports acceptance and can link to a monitor. | IETF RFC 9112 [§2.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-2.1), [§3.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-3.2), [§6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3) and RFC 9110 [§6.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-6.6.1), [§10.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.2), [§15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) (2022, checked 2026-11-13). | The relative Location identifies the status resource by this API's contract. The illustrative bodies contain 41 and 63 UTF-8 octets. Acceptance does not establish completion. |
| API-6 | Cache directives apply to the response that carries them. An optional JSON response field is compatible here only under the client contract and validator behavior. | IETF RFC 9111 [§5.2.2.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5), [§5.2.2.7](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.7) (2022), [JSON Schema Draft 2020-12 Core §10.3.2.3](https://json-schema.org/draft/2020-12/json-schema-core#section-10.3.2.3) and [Google AIP-180](https://google.aip.dev/180#adding-components) (checked 2026-11-13). | Apply the chosen policy to create, status and file responses and authorize each endpoint. The original progressPercent example assumes old clients accept unknown fields and new clients handle missing progress. |
| API-7 | A committed dispatch intent can survive an API restart. A timed-out RPC can still have applied, so covered replays use the same operation ID and immutable input. | [AWS transactional outbox, Motivation](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#motivation), [AWS Builders' Library, making retries safe](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) and [gRPC RPC termination](https://grpc.io/docs/what-is-grpc/core-concepts/#rpc-termination) (living sources, checked 2026-11-13). | The export record is the scenario's durable intent. The dispatcher retries within its recovery policy. The worker's shared durable acceptance and recorded outcome are application choices. |
