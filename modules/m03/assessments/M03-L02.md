## Practical exercise

EX-1. A public catalogue serves multiple mobile app versions. A user submits a request to reserve a limited-edition item, and an internal inventory service processes the reservation. Clients can disconnect after the server receives a request. Inventory instances are replaced during deployments. The reservation must be applied at most once per user request. A separate public listing of past reservations can contain thousands of results.

Propose a public resource contract and an internal operation contract. Trace one accepted request and the reverse response through the RPC path. Explain how the caller selects an inventory endpoint, handles a stale endpoint and bounds its total wait. Define the duplicate and unknown-outcome policy, pagination and one compatibility concern. State the assumptions under which your design meets the reservation requirement.

## Knowledge checks

### Q1

In the export example, what does the client receive while work is still running, and how can it discover the next action?

Answer: It receives an accepted response and a representation with a status URI or link.

Explanation: The URI identifies the export and the link tells the client how to check its state without waiting for the report to finish.

### Q2

Trace the `StartExport` request from caller to implementation and back to the caller.

Answer: The client stub marshals the operation and arguments, transport sends them, and the server stub unmarshals and dispatches. The result or error returns in reverse through transport to the client stub.

Explanation: Stubs supply the interface and serialization around the network exchange. Network and server errors still need handling.

### Q3

An export client has a 300 ms total deadline. A stale worker fails after 40 ms, and the client waits another 20 ms before selecting a second worker. What time remains?

Answer: 240 ms.

Explanation: Both the first attempt and the delay consume the original deadline. The second attempt may use at most the remaining 240 ms.

### Q4

A public API returns JSON and HTTP status codes. Which REST interface constraints still require examination?

Answer: Resource identification, representation-based manipulation, complete self-descriptive messages and hypermedia transitions all need examination.

Explanation: JSON and a status code alone do not show how a client identifies a resource, processes a representation or discovers its available transitions.

### Q5

Why can a timeout followed by a create retry with a new key create two exports?

Answer: The first operation may have committed before the reply was lost, and a new key can be treated as a different operation.

Explanation: A timeout reports the caller's observation. A durable same-key and same-payload contract lets the server recognize a retry within the documented retention period.

### Q6

An older client receives a large report and uses only two fields. Compare a composite response with paginated or narrower resources.

Answer: A composite response can reduce round trips but transfers unused data and has a broader contract. Narrower or paginated resources can limit payload size but may require more requests.

Explanation: The appropriate shape depends on client access patterns, latency, cache behavior and compatibility requirements.

## Answer key / rubric

One viable answer creates a reservation resource with authenticated caller and idempotency key, returns a status URI, and stores a durable association between that key and the reservation. It rejects reuse with a different item or quantity. The inventory operation receives the same stable reservation ID. Its client stub marshals the request, sends it to a chosen endpoint, and the server stub dispatches it. The result returns in reverse. The inventory service atomically checks and records that ID with the reservation effect so a retry within the documented retention window can return the existing outcome. This at-most-once claim depends on that atomic durable implementation and the stated key lifetime.

An inventory client may select from a refreshed cached list or call a stable intermediary. It limits total attempts and applies a shared deadline. When a stale endpoint fails, it tries another only within that budget and with the same operation identity. It does not infer a failed reservation from a lost response. Reservation history can use a bounded cursor with documented concurrent-update behavior. An explicit compatibility policy covers old client versions and new response fields. Other resource and RPC choices receive credit when their contracts and failure behavior satisfy the requirements.

Score 10 points. Award 2 for public and internal contract design, 2 for the complete RPC trace, 2 for discovery and deadline ownership, 3 for durable duplicate and unknown-outcome handling, and 1 for pagination and client compatibility.
