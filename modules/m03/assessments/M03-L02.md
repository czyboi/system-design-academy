# Companion assessment — REST, RPC and interface contracts


## Practical exercise

EX-1. A public catalogue serves mobile app v1 and v2; v1 will remain deployed for six months and expects the existing reservation fields. A user requests up to three limited-edition items. The API has a 400 ms deadline for its internal inventory call. Clients can disconnect after the server receives a request, and inventory instances are replaced during deployments. The reservation must apply at most once per user request. History may contain 10,000 results, each between 1 KB and 100 KB.

Propose public and internal contracts and trace one request and the reverse RPC response. Define endpoint selection, stale-endpoint recovery and deadline, plus the duplicate policy when inventory commits but its reply is lost. Specify pagination and response-size policy and evolve the contract while v1 remains active. Compare an alternative and identify production signals and a failure test. State the assumptions behind at-most-once effects.

## Knowledge checks

### Q1

In the export example, what does the client receive while work is still running, and how can it discover the next action?

Answer: It receives an accepted response and a representation with a status URI or link.

Explanation: The URI identifies the export and the link tells the client how to check its state without waiting for the report to finish.

### Q2

Trace the `StartExport` request from caller to implementation and back to the caller.

Answer: The client stub marshals the operation and arguments, transport sends them, and the server stub unmarshals and dispatches. The result or error returns in reverse through transport to the client stub.

Explanation: Stubs supply the interface and serialization around the network exchange. Network and server errors still need handling.

### Q3

An export client has a 300 ms total deadline. A stale worker fails after 40 ms, and the client waits another 20 ms before selecting a second worker. What time remains?

Answer: 240 ms.

Explanation: Both the first attempt and the delay consume the original deadline. The second attempt may use at most the remaining 240 ms.

### Q4

A public API returns JSON and HTTP status codes. Which REST interface constraints still require examination?

Answer: Resource identification, representation-based manipulation, complete self-descriptive messages and hypermedia transitions all need examination.

Explanation: JSON and a status code alone do not show how a client identifies a resource, processes a representation or discovers its available transitions.

### Q5

Why can a timeout followed by a create retry with a new key create two exports?

Answer: The first operation may have committed before the reply was lost, and a new key can be treated as a different operation.

Explanation: A timeout reports the caller's observation. A durable same-key and same-payload contract lets the server recognize a retry within the documented retention period.

### Q6

An older client receives a large report and uses only two fields. Compare a composite response with paginated or narrower resources.

Answer: A composite response can reduce round trips but transfers unused data and has a broader contract. A narrower representation can limit the bytes sent. Pagination caps item count and can require more requests, while a byte limit needs its own rule.

Explanation: The appropriate shape depends on client access patterns, latency, cache behavior and compatibility requirements.

## Answer key / rubric

One viable answer atomically claims the unique authenticated caller and idempotency key and stores the input and one pending reservation ID before dispatching to inventory. Concurrent requests resolve to that same record. Return its status URI on a payload match and reject a mismatch. After an API restart, resume pending dispatch with the stored reservation ID. The inventory operation receives that same ID. Its client stub marshals the request, sends it to a chosen endpoint, and the server stub dispatches it. The result returns in reverse. The inventory service atomically checks and records that ID with the reservation effect so a retry within the documented retention window can return the existing outcome. Retain the unique operation identity or tombstone at both boundaries after the response cache expires. Use it to return status or reject the replay.

An inventory client may select from a refreshed cached list or call a stable intermediary, accepting that the latter adds a dependency. It limits total attempts within the 400 ms deadline. After a lost reply, retain a pending state and retry the same ID only under the durable contract; do not infer failure. History can use a cursor and a 50-item maximum, with documented concurrent-update behavior; 50 items can still be 5,000 KB, so separately constrain representations or bytes. Keep v1 fields and semantics for six months, introduce v2 fields compatibly and test both versions before retiring v1. Track version use, response bytes, deadline failures, pending age and duplicate effects; inject a lost inventory reply and verify one effect and recoverable status. Other contracts receive credit when their failure and compatibility behavior satisfy the requirements.

Score 10 points. Award 1 for public and internal contracts, 1 for the complete RPC trace, 2 for discovery, deadline and a justified alternative, 3 for the atomic caller/key claim before dispatch, payload comparison and durable lost-reply recovery, 2 for item and byte limits and old-client evolution, and 1 for production signals and a failure test. A plausible choice earns partial credit. Full credit requires the mechanism and its consequence or verification. Accept equivalent contracts that meet the stated assumptions.
