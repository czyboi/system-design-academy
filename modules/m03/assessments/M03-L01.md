# Companion assessment — Application layers and microservices

## Practical exercise

EX-1. A ticketing application accepts a reservation only when the requested seats remain available and the reservation is recorded atomically. It also generates a PDF receipt after a reservation. During sale bursts, PDF generation exhausts CPU needed by the interactive reservation flow. A receipt may appear one minute later. A proposal creates separate synchronous services for seats, reservations and customers, plus a PDF service.

Trace the request through the web, application and data responsibilities. Choose deployment and ownership boundaries, including the reservation invariant and PDF processing. Describe one remote failure and a recovery or user-visible state. Compare your proposal with the entity-per-service proposal and explain what evidence you would collect.

## Knowledge checks

### Q1

Which layer applies a rule that a catalogue item may only be published after an ownership check?

Answer: The application layer applies and coordinates the business rule.

Explanation: The web layer handles the request boundary, and the data layer persists or retrieves state used by the rule.

### Q2

Can the web, application and data responsibilities appear in a single deployable application?

Answer: Yes.

Explanation: A logical layer describes responsibility, while a deployment tier describes where components run and communicate.

### Q3

In the media example, which owner validates and records the conversion result before publication state changes?

Answer: The catalogue owner.

Explanation: The processor performs conversion, while the catalogue retains the publication decision and its state.

### Q4

Why might an entity-per-service design increase the failure surface for one metadata request?

Answer: A request requiring several synchronous service calls depends on each called service and network path.

Explanation: A stalled or failed required dependency can delay or fail the request.

### Q5

When is a separate media processor a defensible choice in the worked example?

Answer: When conversion CPU is the measured constraint and delayed completion is acceptable.

Explanation: The processor can receive its own capacity allocation, while the design must handle the additional coordination and intermediate state.

### Q6

Why does a saga need an explicit recovery plan for a failed compensation?

Answer: A compensation is another business operation and can itself fail.

Explanation: Cross-service local transactions do not provide one automatic atomic rollback of the whole workflow.

## Answer key / rubric

One viable answer has the web boundary accept the reservation, an application module enforce availability, and a data layer atomically update seats and reservation within one owner's transaction. A separately deployed PDF processor is allocated CPU independently. The reservation owner records pending receipt work in the reservation transaction and returns `receipt pending`. A worker can resume that durable work after restart. A later result changes the receipt to ready. If the processor is unavailable, the application keeps the reservation and displays pending until recovery. The entity-per-service proposal adds synchronous dependencies and would need a cross-service invariant and recovery design. Measure reservation latency, PDF CPU saturation, processing lag and failure recovery before and after the split. A modular monolith can instead reserve CPU for the interactive pool and cap receipt-worker CPU. This alternative earns credit when it addresses the measured contention and defines completion state.

Score 10 points. Award 2 for the layer trace, 3 for keeping the seat invariant with a transactional owner, 2 for an independently bounded PDF workload and failure state, 2 for comparing network and consistency costs, and 1 for appropriate observations.
