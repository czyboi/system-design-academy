# Companion assessment — Service discovery and resilient calls

## Practical exercise

EX-1. A checkout API calls a read-only pricing service through a shared proxy. At peak, the proxy receives 1,000 calls per second and has capacity allocated for at most 100 pricing attempts in flight. It caches three addresses for 30 seconds; one instance stops just after refresh. The API has a 500 ms end-to-end deadline and permits three total attempts; the proxy permits two upstream attempts for each API attempt. The registry then becomes unavailable for two minutes.

Trace the stale-address failure and calculate the maximum upstream attempts. Choose discovery ownership and compare an alternative. Set numeric retry, concurrency, deadline and stale-cache budgets; explain overload and registry-outage fallback and recovery signals. State how the design changes for a charge whose response is lost after commit. Identify a production test that checks the policy.

## Knowledge checks

### Q1

Why can a registry return an address for a worker that has already terminated?

Answer: Failure detection and removal have not necessarily completed, and consumers may use an older cached list.

Explanation: Probes, lease expiry and client refresh occur on separate schedules.

### Q2

A caller has 300 ms in total. Its first attempt and backoff take 60 ms. What is the maximum remaining time for the next attempt?

Answer: 240 ms.

Explanation: The deadline covers the complete operation, including previous attempts and delay.

### Q3

What extra data can a DNS SRV answer provide beyond a host-address record, if the caller supports it?

Answer: A target host and port with priority and weight.

Explanation: A and AAAA provide addresses for host names, while SRV adds service-location selection information.

### Q4

Compare two total attempts at each of two nested call layers with one layer owning two total attempts.

Answer: Nested layers can make up to four downstream attempts, while one retry owner caps them at two for the same single request.

Explanation: Every outer attempt may trigger the inner attempt budget.

### Q5

When does an intermediary improve discovery ownership, and which new cost must the design address?

Answer: It can centralize selection across heterogeneous clients. It adds a request-path component that needs capacity and failure protection.

Explanation: The intermediary must remain available enough to route calls and requires its own operational attention.

### Q6

A caller times out after issuing a create request. Why is repeating it with a fresh operation key unsafe?

Answer: The server may have committed the first operation, so the second key can create another effect.

Explanation: A timeout describes the caller's observation. Retry with the same key only if a durable deduplication contract covers it. An authoritative committed record confirms the effect; an absent, stale, or pending status alone leaves it unknown. Use a fresh key only after authoritative terminal evidence establishes that the original operation did not and cannot apply.

## Answer key / rubric

One viable answer retains the proxy as discovery owner to apply one selection policy across clients, accepting that the proxy adds a capacity and availability dependency. It detects the connection failure, excludes the stopped address locally and refreshes its endpoint list. Three API attempts multiplied by two proxy attempts can produce **six upstream attempts**. Change to one proxy retry owner with at most two total attempts, each capped at 180 ms and separated by up to 20 ms jittered backoff, all within the 500 ms deadline. Count all attempts against 100 in-flight slots and reject excess calls promptly; do not retry overload blindly. Use cached healthy candidates for at most 60 seconds since the last successful refresh; after that, return a controlled failure while discovery is unavailable, rather than serving stale prices without an agreed contract. Monitor rejection rate, in-flight calls, latency, attempt rate, cache age and successful refreshes; restore traffic gradually after refresh and successful calls recover, retaining the cap. Test at the stated peak while killing an instance and interrupting registry access, checking the caps, fallback and recovery signals. These budgets are proposed assumptions requiring measurement, not guaranteed capacity.

For a charge, reuse the same operation key only if a durable deduplication contract covers it. An authoritative committed record confirms the charge; an absent, stale, or pending status alone leaves the outcome unknown. Use a fresh key only after authoritative terminal evidence establishes that the original charge did not and cannot apply. An equally explicit client-side discovery design is acceptable if it justifies the ownership choice and accounts for client updates, traffic isolation and discovery failure.

Score 10 points: 1 for stale-address trace and six-attempt calculation; 1 for reasoned discovery ownership and its alternative; 2 for numerical deadline and retry budgets; 2 for a numerical concurrency cap and overload behavior; 1 for maximum staleness and outage fallback; 1 for recovery signals and a production failure test; 2 for the ambiguous charge outcome and safe retry contract. Full credit in each criterion requires a coherent mechanism and consequence or verification; an unqualified plausible choice earns at most half. Accept other justified budgets and either ownership model when they respect the given constraints.
