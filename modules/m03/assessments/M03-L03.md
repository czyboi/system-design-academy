# Companion assessment — Service discovery and resilient calls

## Practical exercise

EX-1. A checkout API calls a read-only pricing service through a shared proxy. The proxy caches three addresses for 30 seconds. One instance stops just after the proxy refreshes its list. The API has a 500 ms end-to-end deadline. The API permits three total attempts and the proxy permits two upstream attempts for each API attempt.

Trace the stale-address failure and calculate the maximum upstream attempts. Propose discovery ownership, a refresh and stale-cache policy, and an end-to-end retry/deadline policy. State how your design changes if this call instead creates a charge and the response is lost after the charge commits. Include a fallback for unavailable discovery.

## Knowledge checks

### Q1

Why can a registry return an address for a worker that has already terminated?

Answer: Failure detection and removal have not necessarily completed, and consumers may use an older cached list.

Explanation: Probes, lease expiry and client refresh occur on separate schedules.

### Q2

A caller has 300 ms in total. Its first attempt and backoff take 60 ms. What is the maximum remaining time for the next attempt?

Answer: 240 ms.

Explanation: The deadline covers the complete operation, including previous attempts and delay.

### Q3

What extra data can a DNS SRV answer provide beyond a host-address record, if the caller supports it?

Answer: A target host and port with priority and weight.

Explanation: A and AAAA provide addresses for host names, while SRV adds service-location selection information.

### Q4

Compare two total attempts at each of two nested call layers with one layer owning two total attempts.

Answer: Nested layers can make up to four downstream attempts, while one retry owner caps them at two for the same single request.

Explanation: Every outer attempt may trigger the inner attempt budget.

### Q5

When does an intermediary improve discovery ownership, and which new cost must the design address?

Answer: It can centralize selection across heterogeneous clients. It adds a request-path component that needs capacity and failure protection.

Explanation: The intermediary must remain available enough to route calls and requires its own operational attention.

### Q6

A caller times out after issuing a create request. Why is repeating it with a fresh operation key unsafe?

Answer: The server may have committed the first operation, so the second key can create another effect.

Explanation: A timeout describes the caller's observation. A durable deduplication contract with the same key, or a status lookup, addresses the unknown outcome.

## Answer key / rubric

One viable answer retains the proxy as discovery owner, detects the connection failure, excludes the stopped address locally and refreshes its endpoint list. Three API attempts multiplied by two proxy attempts can produce **six upstream attempts**. Configure a single retry owner with a small total cap, backoff and jitter, a concurrency bound, and attempt timeouts within the 500 ms overall deadline. Define a maximum stale period and return a controlled failure if discovery remains unavailable after the permitted stale interval. For a charge, use the same durable operation key and a documented deduplication or status-query contract before retrying. An equally explicit client-side design is acceptable if it accounts for client updates, traffic isolation and discovery failure.

Score 10 points. Award 3 for the stale-address trace and six-attempt calculation, 3 for deadline and retry ownership, 2 for refresh and unavailable-discovery policy, and 2 for the ambiguous charge outcome and safe retry contract.
