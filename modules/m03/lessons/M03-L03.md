# Service discovery and resilient calls

## Learning outcomes

- M03-L03-LO1: Trace how a caller finds an instance and handles stale membership within a deadline.
- M03-L03-LO2: Defend discovery ownership and a bounded retry policy for a stated failure and workload.

## Problem and motivation

A report API sends jobs to a changing pool of export workers. Deployments replace worker addresses, and a terminated worker may remain in a caller's cached membership list. The caller needs a usable destination, a way to recognize failure, and a limit on the work created by recovery attempts.

## Core concepts and mechanisms

### Registration, health and membership

A registry maps a logical service to instance addresses and ports. An instance or its platform registers on startup, supplies health information, and removes or lets its entry expire on termination. Consumers obtain and cache eligible endpoints, then refresh or watch membership changes. A health endpoint reports the service's ability to handle a request, while a lease limits how long a registration survives without renewal. Probes, lease expiry and consumers' refreshes occur at different times, so an eligible entry can still refer to a stopped worker.

DNS can publish names for a service. A and AAAA records resolve host names to addresses, while an SRV record can also provide a target host, port, priority and weight when callers support SRV. Resolver TTL and application caches influence how long an answer is retained. Consul's agent service registration API accepts an address, port and checks, and its health API can request passing instances. These are examples of mechanisms whose configuration must be inspected for a particular deployment. [RFC 2782](https://datatracker.ietf.org/doc/html/rfc2782), [Consul service registration](https://developer.hashicorp.com/consul/api-docs/agent/service#register-service), [Consul health API](https://developer.hashicorp.com/consul/api-docs/health#list-nodes-for-service)

Consul provides service registration and discovery as well as a separate key-value (KV) store for configuration. etcd 3.6 offers leased keys, while ZooKeeper 3.9.4 offers session-bound ephemeral nodes. A registry built on those coordination primitives still needs an explicit membership schema, health policy and consumer refresh strategy. A configuration key can hold a setting such as a request limit, but configuration storage alone does not determine whether a worker is healthy. [Consul KV overview](https://developer.hashicorp.com/consul/docs/automate/kv), [etcd 3.6 Lease API](https://etcd.io/docs/v3.6/learning/api/#lease-api), [ZooKeeper 3.9.4 ephemeral nodes](https://zookeeper.apache.org/doc/r3.9.4/zookeeperProgrammers.html#Ephemeral+Nodes)

### Ownership and failure controls

In client-side discovery, the caller keeps an endpoint list and chooses an instance. Each caller needs compatible discovery and balancing logic, but can use local observations. In server-side discovery, the caller connects to a stable intermediary, which selects an eligible instance. This centralizes selection and adds an intermediary that needs capacity and failure protection. A Kubernetes Service is one example of a stable service abstraction whose backing endpoints can change. [Kubernetes Service concepts](https://kubernetes.io/docs/concepts/services-networking/service/)

A deadline limits the time the caller is willing to wait for the whole operation. Cap each attempt by the remaining deadline and any tighter per-attempt limit. Set a maximum attempt count, choose one retry-owning layer where practical, and use backoff with jitter to spread eligible retries. A timeout may occur after a server applied a write. Retry a write only when the operation's contract makes repeated attempts safe, for example through durable deduplication keyed to the same operation. Isolation can cap concurrent calls to a failing dependency so it cannot consume every request slot. Cached discovery avoids requiring a registry lookup for every request, with an explicit refresh and maximum-staleness policy for registry outages. [AWS Builders' Library, timeouts, retries and backoff](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

## Worked example: stale endpoint and deadline failure trace

Assume a client caches workers A and B. Worker A terminates immediately after the last successful health observation. A registry probe has not yet removed A, and the client has not refreshed. A read-only export-status request has a 300 ms total deadline, and this client owns at most two attempts.

1. At 0 ms the client selects A from its cached list. The attempt ends in a connection error at 40 ms. No response was received.
2. The client marks A suspect locally and selects B from the cached list. After a 20 ms jittered backoff, the second attempt starts at 60 ms with at most 240 ms remaining. B responds at 120 ms, leaving 180 ms before the original deadline.
3. A registry update eventually removes A, and the next successful refresh replaces the cached membership. If B also fails or the deadline expires, the client returns a failure instead of making unlimited attempts. A failed cache refresh needs a configured maximum-staleness and fallback decision.

If both a gateway and client independently allow two attempts per request, one user request can create up to four downstream attempts. Give the retry policy one owner or coordinate an end-to-end budget. For a create operation, a timeout can leave the outcome unknown even if the worker committed. The caller can retry under the same operation identity if the durable deduplication contract covers it. An authoritative committed record for that identity confirms the effect; an absent, stale, or pending status alone leaves the outcome unknown. Use a fresh identity only after authoritative terminal evidence establishes that the original operation did not and cannot apply. [AWS, Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## Trade-offs and failure modes

Client selection removes an intermediary from the request path but distributes configuration and balancing behavior to every caller. An intermediary can apply one policy consistently but adds another capacity and availability dependency. A longer cache lifetime tolerates more registry outages while increasing exposure to stale endpoints. A shorter lifetime increases refresh load and still cannot make detection instantaneous.

Retrying helps selected transient failures when remaining time and capacity exist. It can magnify overload, so limit concurrent work, attempts and elapsed time. A healthy registry response does not prove that a particular subsequent connection will succeed. Failure isolation needs monitoring and a recovery path so a dependency can be tried again after it improves.

For example, a proxy can cap outstanding pricing attempts at 100 including retries, reject excess work and pass the remaining deadline to pricing. A receiver can continue working after the proxy stops waiting. Measure active receiver work separately and bound it at the receiver when needed. Watch rejections, attempt rate, latency and discovery-cache age, and ramp traffic after successful refreshes and calls signal recovery. The cap is a scenario assumption to verify under load. [gRPC deadlines, server handling and propagation](https://grpc.io/docs/guides/deadlines/#deadlines-on-the-server)

## Decision framework

Choose the owner of endpoint selection from client capabilities and operating costs. Define registration, address and port data, health eligibility, refresh behavior, maximum staleness and registry-outage behavior. Then specify the end-to-end deadline, retry owner, attempt cap, idempotency contract and concurrency bound. Test a worker disappearing while a cached endpoint is in use.
