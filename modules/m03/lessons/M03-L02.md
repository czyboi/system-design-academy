# REST, RPC and interface contracts

## Learning outcomes

- M03-L02-LO1: Trace resource and remote-procedure interactions, including endpoint selection and an ambiguous response, for a report export.
- M03-L02-LO2: Choose and defend interface and discovery contracts using client compatibility, workload and failure criteria.

## Problem and motivation

A reporting product accepts exports from browser and mobile clients and delegates work to an internal worker pool. Clients need stable ways to request and observe an export, while workers change addresses during deployment. The interface must describe how to request work, interpret results and recover when a response is lost. Endpoint selection and retry ownership must also be clear.

## Core concepts and mechanisms

### Resource interfaces and REST constraints

A resource is an identified concept such as an export. A URI can identify `/exports/42`, while a representation describes its current status and allowed next actions. A client manipulates a resource by exchanging representations under a shared interface. A representation is a message about the resource, so it can have multiple formats or change over time while its identity remains stable.

REST is an architectural style with client-server separation, stateless interactions, cache constraints, a uniform interface and a layered system. Statelessness means each request contains the context needed for that interaction, including relevant authentication. It does not prevent the server from retaining the export resource or a durable operation record. A response declares whether it can be cached, rather than making every response cacheable. Intermediaries can serve or forward interactions without the client knowing the final component. Code on demand is an optional constraint. [Fielding, §§5.1–5.2](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm)

The uniform interface has four constraints. **Identification** gives the resource a stable identity. **Manipulation through representations** uses a submitted representation to request a change. **Self-descriptive messages** supply the method, media type, relevant headers and semantics needed for processing, together with an interpretable response. A status code alone does not describe a whole message. **Hypermedia** gives the client links or controls in representations to discover available transitions, such as a status link followed later by a download link. It is a constraint on application interaction, not a requirement that a browser render the representation. An HTTP JSON API does not automatically meet all REST constraints. [Fielding, §§5.1.5 and 5.2](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm)

## RPC path and interface choices

A remote procedure call (RPC) exposes an operation such as `StartExport(request)`. The client invokes a client stub, which marshals the operation and arguments into a request. A transport sends it to a server, whose server stub unmarshals and dispatches it to the implementation. The result or error follows the reverse path and the client stub decodes it. A timeout, connection failure or lost reply remains observable even when the call looks like a local function. An RPC may use generated schemas and stubs. For example, gRPC describes unary and streaming methods, while ONC RPC is a different implementation of the model. [RFC 5531, §4](https://datatracker.ietf.org/doc/html/rfc5531#section-4), [gRPC core concepts](https://grpc.io/docs/what-is-grpc/core-concepts/)

An SDK can package authentication, serialization and error handling for known client platforms. This can simplify a consistent client experience, but clients must obtain a compatible library and understand its versioning and failure behavior. Adding an operation can require a new contract and client release. A binary operation and generated stub can need protocol-aware tracing to diagnose compared with inspecting an HTTP message. RPC response caching needs an explicit cache design and appropriate keys because generic HTTP caches do not automatically understand an arbitrary operation's semantics. These are costs to evaluate for the chosen stack, rather than fixed properties of every deployment.

A resource interface can fit clients that navigate stable entities and benefit from shared HTTP semantics. An operation interface can fit a focused internal capability or stream, especially when the organization controls generated clients. For a nested view, separate requests for a report, its sections and their attachments increase round trips. A composite representation can reduce requests at the cost of larger payloads, cache invalidation and a broader contract. Pagination bounds each response under a server page-size policy and can require more trips to read the whole collection. Adding fields can increase bytes received by older clients that do not use them. A query for records updated after a cursor can be modeled as a collection with query parameters, though a highly specialized event-oriented query may be clearer as an operation. Measure the actual request shapes, payloads and clients before choosing either interface.

## Compatibility and safe retries

For public clients that update on different schedules, document optional fields, supported media types, pagination cursor behavior and how long old contracts remain available. A cursor identifies the continuation position. A server-enforced page-size limit bounds each response. Specify whether it represents a stable snapshot when concurrent writes matter. For Protocol Buffers proto3, adding fields can be wire-safe, but application assumptions can still break. Reusing an old field number is unsafe. A wire-compatible schema alone does not prove that two application versions interpret the data alike. [Protocol Buffers, updating a message type](https://protobuf.dev/programming-guides/proto3/#updating)

A deadline limits the caller's total wait, including attempts and delays. A timeout after sending a create can mean the server committed the operation while the response was lost. An application can define a durable idempotency key scoped to an authenticated caller and payload. The server atomically records the key and created operation, returns the existing result for the same request, and rejects a key reused with a different payload. State how long the caller can replay the request and how the server handles expiry. If an operation must never run twice under the same identity, keep that identity with an outcome or tombstone even after the response body expires. Return the known status or reject the replay. An idempotent method has the same intended effect on repetition, though responses can differ. [gRPC deadlines](https://grpc.io/docs/guides/deadlines/), [RFC 9110, §9.2.2](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2.2)

## Worked example

Assume an export can take minutes, clients may retry after a network loss, and an export result is private. A public client sends `POST /exports` with report filters, authorization and an idempotency key. The API validates access, atomically reserves the caller/key and creates export `42`. It returns `202 Accepted`, a status URI and a representation containing a link to check status. A repeated request with the same key and filters returns the recorded operation, while the same key with different filters is rejected. When the job finishes, the status representation offers a time-limited download link. The private response needs an explicit cache policy.

The API uses an internal `StartExport(export_id, filters)` RPC to the worker service. The client stub serializes the request, sends it to an endpoint, and the server stub dispatches to the worker. A successful response carries the accepted export ID back through those layers. The design assigns each export ID to a durable operation and makes worker processing deduplicate that ID. If the API times out after the worker accepts it, a retry with that same identity can recover without creating a second logical export, provided both the API and worker implement their stated durable contracts. A lost response alone does not reveal whether the worker accepted it.

The API can select a worker using a cached instance list, or call a stable intermediary that selects the worker. That endpoint decision is independent of whether the internal interface is RPC. As a preview of the next lesson's discovery trace, a cached worker A has terminated. Its read-only status call fails at 40 ms, waits 20 ms, then starts at worker B with 240 ms remaining in a 300 ms deadline. B responds at 120 ms. With a create, an unanswered attempt has an unknown outcome and needs the same operation identity and durable deduplication before retry. [M03-L03, stale endpoint and deadline failure trace](M03-L03.md#worked-example-stale-endpoint-and-deadline-failure-trace)

## Applying the decision to other workloads

The following original examples use the same public-interface, internal-operation and discovery decisions in different systems. Each internal caller needs a current endpoint or intermediary and an explicit failure policy.

| Workload | Contract and decision |
| --- | --- |
| Shared snippets | A public client creates a snippet resource and receives its URI. An internal storage operation writes by stable snippet ID, so an ambiguous reply can be resolved against that ID. |
| Activity feed | A public feed collection uses a cursor and describes its pagination behavior. An internal timeline operation reads a bounded page, with a deadline so a slow dependency cannot occupy the entire request budget. |
| Web crawler | A public crawl-job resource exposes progress. An internal scheduling operation accepts a job ID and a worker endpoint selected by discovery, so a new worker can replace a stopped one. |
| Financial aggregation | A public account-summary representation exposes a timestamp and currency. An internal aggregation call scopes inputs to an authorized account and reports partial results explicitly when a dependency fails. |
| Social graph | A public connections collection paginates results. An internal `GetConnections` operation bounds page size to avoid a traversal request returning an unbounded graph. |
| Query cache | A public search resource identifies the query and its filters. An internal `Lookup` operation includes tenant and query parameters in its cache identity to avoid mixing results across callers. |
| Sales ranking | A public category-ranking resource states its reporting window. An internal `GetRanking` operation carries the same window so callers do not confuse rankings for different periods. |
| Scaling an application | A public catalogue resource provides a stable client contract while an internal inventory call moves to a separately deployed service. The caller's discovery owner and timeout policy must change along with that deployment boundary. |

These are interface sketches. Their security, consistency and capacity assumptions require further design for a particular system.

## Trade-offs and failure modes

A uniform HTTP interface can support heterogeneous clients and intermediaries, while carefully designed links and representations add contract work. A generated RPC SDK can simplify operation calls and streaming for supported platforms, while coupling clients to schema and release practices. Neither choice by itself determines latency, compatibility, caching or reliability. Compare workload-specific measurements and operator visibility.

Deadlines without a shared attempt budget can still allow retry amplification across layers. Endpoint discovery can return an instance that fails immediately after a health observation. A create must have an explicit duplicate and unknown-outcome policy, including key retention, regardless of interface style. Authentication and authorization must protect both resource access and internal operations.

## Decision framework

List the clients and their update cadence, then state resource or operation semantics, data shape, pagination, streaming and compatibility requirements. For each remote call, specify endpoint-selection ownership, a deadline, retry owner and behavior for an unknown result. Choose a representation and SDK strategy that the clients can support, then observe real payloads, round trips and failure traces.
