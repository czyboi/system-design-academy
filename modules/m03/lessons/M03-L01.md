# Application layers and microservices

## Learning outcomes

- M03-L01-LO1: Trace request responsibilities and data ownership through a layered application and a proposed service split.
- M03-L01-LO2: Defend a deployment boundary using workload, invariants and operational costs.

## Problem and motivation

An image catalogue handles small interactive metadata requests alongside CPU-intensive image conversions. Interactive latency degrades when conversion jobs consume the same worker capacity. The team needs to isolate the constrained resource while keeping publication rules understandable and enforceable.

## Core concepts and mechanisms

### Logical layers and deployment tiers

The web layer receives HTTP requests, authenticates users at the boundary and translates requests into application calls. The application layer applies business rules and coordinates work. The data layer persists and retrieves state using its storage contracts. A public request can pass through all three even when they run in a single deployment. A layer names a responsibility, while a tier identifies a deployment boundary that may cross a network. [Azure Architecture Center, N-tier architecture](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier)

A modular monolith keeps domain modules with explicit interfaces in one deployable application. Teams can scale its replicas and keep tightly coupled state transitions within a single transactional owner. A microservice boundary gives a service control over a capability and its owned data through an interface, with separate deployment and capacity when dependencies permit. That autonomy depends on contracts and ownership, not simply running each class in another process. [Azure Architecture Center, Microservices architecture style](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices)

### Costs of a remote boundary

A remote call consumes connections and network time, can time out after the receiver acted, and needs observable failure handling. A request that synchronously fans out across several required services can fail or slow down when any required call fails or stalls. Each service also needs deployment, capacity, logging, security and on-call ownership. Independent releases provide value only if compatibility and shared dependencies let a service evolve independently.

If an invariant spans services, one local database transaction no longer covers the entire workflow. A saga can coordinate local transactions with explicit compensating business actions where these exist, plus recovery when a step or compensation fails. Compensation does not erase all external observations. If a rule needs an immediate atomic change and no acceptable recovery exists, keep that decision and state in one transactional owner. [Azure Architecture Center, Saga distributed transactions pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)

Two buyers can both read that a seat is free before either writes. The reservation owner can claim each requested seat with a write that succeeds only while the seat is still available. Roll back the whole reservation if any claim fails. Commit the seat claims, reservation and pending receipt work before acknowledging success. PostgreSQL 18 at Read Committed illustrates the guard for an update to a predetermined row by re-evaluating the update predicate after a competing update commits. Other engines need a mechanism with equivalent concurrency behavior. [PostgreSQL 18 §13.2.1](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)

## Worked example

Assume a user can publish a catalogue item only after its owner and publication state pass one consistency check. Image conversion can complete later, and the interface can show `processing` until a result is ready. The bottleneck is conversion CPU, while ordinary metadata reads have spare capacity.

1. A browser submits an image through the web layer. The application layer checks ownership and records the item and processing request. The data layer persists the item state and pending processing request in the catalogue owner's transaction. A dispatcher can resume pending work after a process restart.
2. A separately deployed media processor performs conversion and returns a result to the catalogue through an agreed interface. The catalogue owner validates and records the result before changing publication state. Conversion instances can receive a different capacity allocation from the interactive application.
3. Compare a split into separate user, image, item and publication services. If every metadata view synchronously calls all four, the request gains several remote dependencies. A publication decision that needs owner and publication data also crosses boundaries, so its failure and recovery policy becomes more complex.

The media boundary addresses the stated CPU pressure and accepts delayed completion and new coordination work. Splitting every entity has additional operating cost without an identified independent scaling or ownership need. Both choices still require load and failure observations before their capacity behavior can be established.

Give each processing request a stable identity across the catalogue and processor. Write output under that identity so repeating the same work after a crash has the same effect. Persist the completed output reference by work ID before replying. After a lost reply the catalogue can retrieve that reference by retry or status lookup, then apply the completion transition idempotently. Keep the item in `processing` until a confirmed result is recorded and retain the result for the supported recovery window. [AWS Builders' Library, retries and semantic equivalence](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## Trade-offs and failure modes

Keeping modules together simplifies local calls and shared transactions. A shared deployment can also couple releases and resource allocation, and teams must preserve module boundaries as the application grows. Separating a service can target scaling, ownership or release cadence, but network calls, compatibility, monitoring and cross-boundary state transitions add cost. A failure in a remote dependency can affect callers unless timeouts, capacity limits and a suitable fallback are designed.

Asynchronous processing is useful when the user can accept delayed completion and the workflow can show and recover an intermediate state. It introduces completion tracking and recovery work. A synchronous call can be appropriate for a small, bounded operation whose result is required before responding, provided its failure and deadline are part of the contract.

## Decision framework

Identify the constraint, the operations that must change atomically, and the team that owns each capability. Start with a module boundary and establish the cost of shared deployment. Consider a service boundary when independent capacity, ownership or release needs justify its network, consistency and operational costs. Trace the normal request and a failed call before committing to the split.
