# Companion assessment for M06-L02

## Practical exercise

**EX-1.** A community centre stores room status at version 3. A reader starts a miss and loads version 3. An editor commits version 4 while the reader is still running. Trace plain commit-then-delete, a versioned fill, and a write-behind design that acknowledges acceptance while the store is still at 3. Compare cache failure before the flush with failure during cache publication after a synchronous store commit. Choose a display policy that permits brief lag and a reservation-check path that needs authoritative availability.

## Knowledge checks

### Q1

How can a stale fill occur after commit-then-delete?

**Answer.** The reader loaded old data before commit and filled after deletion. Its write puts the old value back under the same key.

### Q2

What changes on a read-through miss?

**Answer.** The cache interface owns the loader and fill. An overlapping write can still require a fill guard.

### Q3

When can write-behind lose an acknowledged update?

**Answer.** After accepting it in volatile dirty state but before storing it durably. The store still holds the preceding revision after cache loss.

### Q4

When can eager write-through waste memory?

**Answer.** When writes populate keys that receive no reads before eviction or expiry.

### Q5

Why is a failed cache refresh a capacity concern?

**Answer.** It uses origin work even if the refreshed value never serves a request. Retry within the same origin budget.

### Q6

When is a TTL insufficient to promise time since the last authoritative change?

**Answer.** A late fill or lagging origin can restart a TTL on an old value. Tie reuse to the source observation or retained revision and define how readers verify freshness.

## Sample solution and rubric

With one unversioned key, the late version 3 fill survives the version 4 deletion. With a revision captured from the source snapshot, the late fill writes the version 3 key and a post-commit authoritative revision check selects version 4. A volatile write-behind buffer can lose 4 before flush. A durable pending record and idempotent, revision-guarded replay preserve accepted changes. A write-through cache failure after store commit leaves version 4 durable and the reply uncertain. Resolve at the store by the same operation ID. Use repaired cache-aside for display and the reservation authority for a decision under concurrent bookings.

| Criterion | Points | Full credit |
| --- | ---: | --- |
| Race and fence | 3 | Traces the late fill and names the source snapshot and lookup contract. |
| Crash outcomes | 4 | Separates lost dirty writes from uncertain replies after a durable commit and gives recovery for both. |
| Policy choice | 3 | Chooses a defensible display policy and protects the authoritative reservation decision. |

Accept alternatives that satisfy the same constraints. Award partial credit for a correct trace with an incomplete justification.
