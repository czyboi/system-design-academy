# Companion assessment for M06-L02

## Practical exercise

**EX-1.** A community centre stores room status at version 3. A reader captures version 3 before an editor commits version 4. The display may use a primary observation at most 5 s old. Reservations must use current authoritative state. For cache-aside, write-through, write-behind and refresh-ahead, trace what an overlapping reader can see and how the system recovers after cache loss. Include a write-through crash after store commit and a write-behind crash after applying 4 but before recording the flush. For refresh-ahead, let the old read complete after a cache restart and after its observation deadline. Choose a policy for display and specify what the user sees if fresh data is unavailable.

## Knowledge checks

### Q1

How can a stale fill occur after commit-then-delete?

**Answer.** The reader loaded old data before commit and filled after deletion. Its write puts the old value back under the same key.

### Q2

A read-through loader captures version 3. The source commits 4 and the cache restarts before the loader returns. How can the next reader avoid 3?

**Answer.** The loader writes under the captured version 3. The next lookup checks the current revision at the source, selects key 4 and loads it on a miss. A cache-only version comparison loses its history on restart.

### Q3

When can write-behind lose an acknowledged update?

**Answer.** After accepting it in volatile dirty state but before storing it durably. The store still holds the preceding revision after cache loss.

### Q4

When can eager write-through waste memory?

**Answer.** When writes populate keys that receive no reads before eviction or expiry.

### Q5

Why can refresh-ahead reduce capacity when it predicts a read that never arrives?

**Answer.** The refresh uses origin work without avoiding any demand fill. Bound it alongside demand fills.

### Q6

When is a TTL insufficient to promise time since the last authoritative change?

**Answer.** A late fill can restart an insertion-based TTL on an old value. Use the original fresh primary observation to set a reuse deadline and check it before returning the result. Account for lag if using a replica.

## Sample solution and rubric

With cache-aside, the late version 3 fill can follow deletion and restore the old unversioned key. Cache loss causes bounded origin reads. On a hardened path the fill stays under version 3, while a fresh authoritative lookup selects 4. With write-through, a normal hit between the store commit and cache publication may still return 3. A crash there leaves 4 durable and the reply uncertain. Resolve the input-bound receipt committed with the write and repair from the latest source revision without repeating the mutation.

With write-behind, an accepted dirty 4 can be visible in cache before the store changes. Volatile loss before flush can lose 4. Durable pending work permits replay and helps readers that promise accepted state. If 4 was committed before the flusher lost its progress marker, its applied receipt prevents a second application. An older whole-value replay also cannot overwrite 5 under the revision guard. With refresh-ahead, a reader sees eligible 3 and triggers a reload. If it loaded 3 before the edit, it can only fill key 3 after restart, and its expired deadline prevents serving it. A post-commit authority lookup selects 4 on the hardened path. Use a deadline anchored to the primary observation for cached displays. If no eligible result can be fetched in time, return unavailable. The authority decides reservations.
