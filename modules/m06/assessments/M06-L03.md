# Companion assessment for M06-L03

## Practical exercise

**EX-1.** A public library search has capacity for three entries in each local cache. A node sees store P, store Q, store R, read P, store S, and then update R. The fleet routes clockwise on a ring with X=15, Y=45, Z=75. Query keys are P=9, Q=35, R=60 and S=95. Q is the hottest search; measured one-off scans frequently evict reusable searches and cause refills. Y goes down while a new library record joins Q's page and a ranking revision deploys. Trace the local operations independently of the routing exercise, and trace Q's owner and the miss path afterward. Assume query data and catalogue generation are committed together and a stale display is usable only within its existing observation deadline. Assume a request coalesces under generation 7 and rank R1, but its primary snapshot sees generation 8 and the available worker only supports R2. Trace the mismatch. Recommend a layout and an eviction or admission policy using the observed reuse, and explain costs and failure controls.

## Knowledge checks

### Q1

What breaks if updating an existing key inserts a second list node?

**Answer.** The map and list no longer have a one-to-one correspondence. Evicting the orphan can remove the map entry for the surviving node.

### Q2

What are the final keys after inserting A, B and C, reading A and inserting D at capacity three?

**Answer.** D, A, C from most to least recent. The hit moved A ahead of B and C, so B was evicted.

### Q3

Can invalidation based only on IDs already present in a result handle a newly matching record?

**Answer.** No. A new record can enter an old result without having appeared in it. Change the affected catalogue generation or invalidate by a dependency that covers new membership.

### Q4

What happens when a source fetch returns the old generation after a newer generation becomes current?

**Answer.** If the request was routed under a different generation, discard the mismatched fill and reselect the full key and owner, then re-coalesce within the original request deadline and shared retry and fill budgets. A correctly matched old-generation fill retains its source observation deadline; a newer lookup cannot reuse it.

### Q5

Can consistent hashing alone spread a single hot query across many nodes?

**Answer.** One key still maps to one primary owner. Add controlled copies or a shared local tier and keep per-key fills and invalidation coordinated.

### Q6

What differs between a successful Redis Cluster promotion missing a recent fill and a failed promotion?

**Answer.** An eligible replica authorized by a majority of voting primaries can be promoted yet lack recent fills because replication is asynchronous. Without an eligible replica or voting majority, promotion cannot complete. Redis slot ownership is separate from the illustrative successor ring.

## Sample solution and rubric

Local order ends P, R, Q after the hit, S, P, R after inserting S and evicting Q, and R, S, P after reusing node R. Remove the evicted Q from the map. The standalone ring places Q at Y, then at Z when Y is removed. A catalogue change and rank deployment select a new composite key, which can hash to a different position. Z is the successor for the old Q key; route the new key from its actual hash. Reject ineligible older copies. The 7/R1 attempt cannot publish 8/R2 under the old key: discard it, select a supported ranking version and fresh primary generation, hash the full tuple, reroute and re-coalesce under its owner within the original deadline and shared retry and fill budgets. Bind the actual rank implementation and primary snapshot generation to the resulting key; preserve its source-observation deadline and recheck each waiter. If no eligible result can be obtained in budget, return unavailable. Every eligible request also makes authorization and primary generation checks, even on hits. Measure and budget those checks and retries separately from expensive fill starts, accounting for their shared primary capacity; unavailable checks produce unavailable responses. Replicate a consistently hot key or use a small eligible local tier, paying extra memory and routing work. Bound cold origin starts and retry work during failover. Since scans displace reused results, frequency-based admission or eviction can protect the hot working set at metadata and complexity cost; LRU remains defensible if measurements show recency predicts reuse or the added cost outweighs saved refills.
