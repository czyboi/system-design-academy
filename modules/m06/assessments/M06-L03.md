# Companion assessment for M06-L03

## Practical exercise

**EX-1.** A public library search has capacity for three entries in each local cache. A node sees store P, store Q, store R, read P, store S, and then update R. The fleet routes clockwise on a ring with X=15, Y=45, Z=75. Query keys are P=9, Q=35, R=60 and S=95. Q is the hottest search. Y goes down while a new library record joins Q's page and a ranking revision deploys. Trace the local operations independently of the routing exercise, and trace Q's owner and the miss path afterward. Assume query data and catalogue generation are committed together and a stale display is usable only within its existing observation deadline. Recommend a layout and explain its costs and failure controls.

## Knowledge checks

### Q1

What breaks if updating an existing key inserts a second list node?

**Answer.** The map and list no longer have a one-to-one correspondence. Evicting the orphan can remove the map entry for the surviving node.

### Q2

What are the final keys after inserting A, B and C, reading A and inserting D at capacity three?

**Answer.** D, A, C from most to least recent. The hit moved A ahead of B and C, so B was evicted.

### Q3

Can invalidation based only on IDs already present in a result handle a newly matching record?

**Answer.** No. A new record can enter an old result without having appeared in it. Change the affected catalogue generation or invalidate by a dependency that covers new membership.

### Q4

What happens when a source fetch returns the old generation after a newer generation becomes current?

**Answer.** It may only fill its actual generation and original deadline. A newer lookup selects the new generation, so it cannot reuse the earlier result.

### Q5

Can consistent hashing alone spread a single hot query across many nodes?

**Answer.** One key still maps to one primary owner. Add controlled copies or a shared local tier and keep per-key fills and invalidation coordinated.

### Q6

What evidence would distinguish restarting an empty sharded cache from promoting a Redis Cluster replica?

**Answer.** Check the actual membership and configured replica topology and inspect valid entry coverage after failure. Asynchronous failover can preserve some entries while losing recent fills.

## Sample solution and rubric

Local order ends P, R, Q after the hit, S, P, R after inserting S and evicting Q, and R, S, P after reusing node R. Remove the evicted Q from the map. The standalone ring places Q at Y, then at Z when Y is removed. A catalogue change and rank deployment select a new composite key, which can hash to a different position. Z is the successor for the old Q key; route the new key from its actual hash. Reject ineligible older copies and coalesce a fill under the new key within a shared budget. Load from a source snapshot that includes the required catalogue state, fill under the observed generation and verify the observation deadline before returning. Replicate a consistently hot key or use a small eligible local tier, paying extra memory and routing work. Bound cold origin starts and retry work during failover.

| Criterion | Points | Full credit |
| --- | ---: | --- |
| Local invariants | 3 | Derives the order and eviction and maintains map/list identity on update. |
| Routing and coherence | 4 | Traces old ownership, considers new namespace routing, blocks old fills from contaminating new results and names the observation cutoff. |
| Layout and recovery | 3 | Explains hot-key and replica trade-offs, coalescing, and a bounded origin fallback. |

Accept alternatives that satisfy the same constraints. Award partial credit for a correct trace with an incomplete justification.
