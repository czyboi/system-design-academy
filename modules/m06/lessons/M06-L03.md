# Bounded LRU and distributed query cache

A parts directory ranks matching listings for a search. Demand repeats across users, but a large catalogue scan generates many one-off queries. Choose which entries to evict, where to route the next hit and what to do when the owner of a popular result disappears.

- **M06-L03-LO1.** Trace a bounded local LRU, result lookup and invalidation through a query change and loss of a shard.
- **M06-L03-LO2.** Defend an eviction policy and cache layout using reuse, stale-data risk, failover load and memory.

## Maintain a map and a recency list

A hash map sends each full key to its one list node. A doubly linked list holds the same nodes, from most recent at the head to least recent at the tail. Each node stores its key, result and links. Keep a one-to-one correspondence between the map and the list, repair both directions of each changed link and hold the size within capacity. Serialize a lookup-plus-move, insert or eviction with respect to competing operations.

- On a hit, detach the existing node and move it to the head. An absent or expired key is a miss. Remove an expired node from both structures.
- On an existing-key write, replace the value and move that same node to the head. A new node for the same key would leave two list entries and only one addressable by the map.
- On a new-key write, insert at the head and evict from the tail if over capacity. Remove the evicted node's key from the map. At zero capacity, skip storing the entry.

With good hash dispersion and bounded key-processing cost, lookup is expected constant time and list edits are constant time. A growing hash table can rehash, so insertion is amortized expected constant time unless provisioned to avoid growth. A byte budget instead may require several evictions for a large value. [Java SE 25 LinkedHashMap](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/LinkedHashMap.html), [HashMap growth](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/HashMap.html).

With capacity three and no expiry in this trace, follow five accesses:

| Access | Result | Most recent → least recent |
| --- | --- | --- |
| Store A | Insert A | A |
| Store B | Insert B | B, A |
| Store C | Insert C | C, B, A |
| Read A | Hit, move A | A, C, B |
| Store D | Insert D and evict B | D, A, C |

A subsequent update of C should produce C, D, A without evicting another entry. A scan of many distinct keys can push out reusable results. Use LRU when recent access predicts reuse. Consider frequency-based admission or eviction when measured scans dominate evictions and cause repeated refills. [Redis, eviction policies](https://redis.io/docs/latest/develop/reference/eviction/#eviction-policies).

## Trace a query from lookup to invalidation

A request to `GET /search?q=bolts&locale=en&page=1` resolves a canonical tuple containing the parsed query, locale, page, authorized visibility scope, ranking version and catalogue generation. Hash the tuple for routing and use the full canonical key for matching. A hit returns the ordered IDs and summaries only if its visibility and freshness rules still hold. On a miss, coalesce same-key work within a declared shared scope, admit the leader within an origin rate budget, run the source query and fill with the captured generation and source observation deadline. Waiters recheck that their result remains eligible before returning it. An unavailable owner or exhausted budget can yield an explicit unavailable response.

Changing the query text selects another key. A listing added to the catalogue can change earlier pages even though its ID is absent from those pages. Bump the affected catalogue generation. The authoritative rollout policy selects the required ranking version for each request. In this design the authority updates catalogue data and generation together. The PostgreSQL 18 primary is the generation authority and query origin. Each eligible request checks authorization and uses a fresh primary statement to check generation before consulting the result cache. A fill reads data and generation together in a fresh primary statement; its key must also name the ranking implementation actually used.

Suppose a request routes and coalesces under generation 7 and required rank R1. The source snapshot sees generation 8 and the available worker supports only R2. Discard the mismatched attempt. Retry on a worker that supports the same required rank, R1, or return unavailable. Use R2 only if a fresh authoritative rollout decision requires R2 and the request contract permits the change. On retry, obtain a fresh generation, recompute the complete key with the required rank, hash it to select the owner, and join the group that coalesces fills for that key. Keep the original request deadline and charge retries and origin work to the same shared budgets. Waiters independently recheck eligibility. Each result keeps the deadline set by its source observation.

A response whose check overlapped a catalogue change may still reflect the earlier generation within the source-age bound. Enforcement of restrictions stays on the authorization path. Result-cache hits still cause generation and authorization checks: measure and budget those requests and retries at the pre-cache boundary separately from expensive fill starts at the admission boundary. Provision both against their respective authority capacity, including the primary shared by checks and fills. If authorization or generation cannot be checked within budget, return unavailable rather than serving an unchecked result. [M06-L02](M06-L02.md), [PostgreSQL 18, statement snapshots](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED).

## Route to the cache and lose an owner

| Layout | Routing and cost | What one failed cache node changes |
| --- | --- | --- |
| Independent | Each app caches its own traffic. Capacity is divided between local working sets with overlapping copies. | One empty or replaced process loses its warm state. Other local copies stay warm. |
| Replicated | A cache fleet can route reads for the same key to several copies. Each additional full replica needs the same entry memory again. | A surviving copy may be hot. Check its generation and observation age before reuse. |
| Sharded | Route each key to one owner. Spread different keys across aggregate memory. Replicate particular shards or hot results where needed. | Keys whose owner failed need another route, a usable replica or a refill. A single hot key can still overload one shard. |

Use a clockwise consistent-hash ring with nodes N1 at 20, N2 at 50 and N3 at 80. From a key's position pick the next node, wrapping at the end. For key positions A=10, B=40, C=65, D=90, the owners are N1, N2, N3, N1. When the routing membership removes N2, B moves to N3 and A, C and D keep their owners. The routing change moves ownership. Any data on a failed node must be refilled or obtained from an eligible copy. In a partition, inconsistent membership views can cause duplicate fill attempts. Use a shared origin admission budget across routing views and bound retries. Watch per-node demand and evictions. If B alone is hot, add a small replica tier for that key, validate replicas with the same key generation and deadline, and coalesce initial fills across the replicas. [Karger et al., Consistent Hashing and Random Trees §4](https://www.akamai.com/site/en/documents/research-paper/consistent-hashing-and-random-trees-distributed-caching-protocols-for-relieving-hot-spots-on-the-world-wide-web-technical-publication.pdf#page=6), [Dynamo §4.2, clockwise successor](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf#page=5), [Scaling Memcache at Facebook §3.2.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf#page=4).

In the Memcached baseline, clients can choose a server by key and the servers do not replicate among themselves. The built-in proxy, introduced in Memcached 1.6.23, can also own routing. Redis Open Source Cluster assigns hash slots separately from the illustrative ring. Promotion requires an eligible replica and authorization from a majority of voting primaries; it does not move the failed node’s slots to the next ring node. Replication is asynchronous, so a successfully promoted copy may lack a recently filled entry. Without an eligible replica or voting majority, promotion cannot complete. Redis LRU under the maxmemory policies uses approximation rather than a single exact recency list. Ask where routing and invalidation live, how much usable memory one failure leaves and what limits cold-refill load under the selected deployment. [Memcached design](https://docs.memcached.org/#how-does-it-work), [Memcached built-in proxy](https://docs.memcached.org/features/proxy/), [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/), [Redis approximated LRU](https://redis.io/docs/latest/develop/reference/eviction/#approximated-lru-algorithm).
