# Cache update and coherence policies

A venue directory stores opening hours. A reader wants the current hours, while editors want to know what a successful write promises. Each cache policy places different work on the read or write path. Trace which copy is authoritative and when a failure can separate the copies.

- **M06-L02-LO1.** Trace one overlapping read and write and one cache failure under each policy.
- **M06-L02-LO2.** Choose a policy and explain the write latency, freshness and durability it can support.

## Order the cache-aside update

The application looks in cache. A miss adds a cache lookup before the database read and a fill before future hits. A write commits at the authority before deleting the cached value. If deletion comes first, a reader can miss, read old version 7 and refill it before version 8 commits. With commit first, a related race remains. Reader R misses and reads version 7, writer W commits 8 and deletes the key, then R fills 7 after the delete. A crash between commit and deletion can also strand an old hit until repair or expiry. A cache crash alone loses reusable copies. Reads fall back within the origin's capacity. [Microsoft Cache-Aside](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside#solution), [Scaling Memcache at Facebook §3.2.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf#page=4).

A read-through cache owns the miss loader, so the caller asks only the cache. The same in-flight fill can race a write unless the design fences it. If the read-through service crashes, provide a bounded bypass or treat the route as unavailable until recovery. Read-through can pair with any explicit write policy. [Oracle Coherence 14.1.2, Read-Through Caching](https://docs.oracle.com/en/middleware/fusion-middleware/coherence/14.1.2/develop-applications/caching-data-sources.html).

## Fence a late fill

For this example, the source transaction updates the hours and the venue revision together. Every hit checks the current revision at the same authority. A miss loads revision and value in one snapshot and writes under that revision. An R snapshot at revision 7 can complete late under key `venue:7`. A read whose revision check starts after W commits selects key `venue:8`. It cannot reuse `venue:7`. An earlier overlapping read can still return 7. The extra authority check makes this design worthwhile only if loading or assembling the result costs appreciably more. For public data that can lag, M06-L01 separates commit and generation advance with a recoverable outbox. Its delay becomes part of the freshness budget. In either design, a TTL measured from a late fill does not give the same bound as a TTL measured from the source observation. [PostgreSQL 18, transactions and statement snapshots](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED).

## Trace write-through, write-behind and refresh-ahead

Use the same starting state, store and cache at 7, and a concurrent write to version 8. These are explicit application designs.

| Policy | Overlapping read and write | Cache failure and repair |
| --- | --- | --- |
| Write-through | W commits 8 at the store, publishes 8 in cache and reports success after both steps. A reader on an ordinary cache path between commit and publication may see 7. A hardened read checks the current authority revision and can fill key 8 without waiting for W's cache step. | If the cache dies after the store commit, the change survives despite an uncertain reply. Retry against the durable receipt and repair the cache from the current source revision. After restart, untouched keys remain cold until loaded. Eager writes can also populate unread entries. |
| Write-behind | W records full value 8 as dirty and acknowledges acceptance before flushing. A cache reader can see 8 while a direct store reader sees 7. All writers of this key use one revision order. | Losing the only volatile dirty copy before flush loses the accepted change. Journal the input, operation ID and revision durably before acceptance. A read that promises accepted state consults the journal or waits for rebuild. Reject new work if safe buffering is unavailable. |
| Refresh-ahead with cache-aside writes | R hits 7 near expiry and triggers a background read. W commits 8 and invalidates 7. A refresh that read 7 can finish late. The hardened path writes only to key 7 and checks the authority revision at lookup. | A cache restart can erase the guard if it was only the current cached value. With revision keys, even a refresh that survives the restart can write only key 7. New readers checking revision 8 ignore it. Refill under the miss budget. Failed or unused refreshes cost origin work. |

On the write-through path, commit the request-bound receipt and version 8 in the same authority transaction. After a lost reply, the same operation ID and input recover the recorded store outcome. If the cache is still unavailable, report store commitment and incomplete cache publication separately. If version 9 is already current, repair under key 9. An emptied cache cannot persuade a reader checking the authority to look up 8. A read-through loader can use the same hardened lookup and write under the revision it actually loaded from the authority. [AWS Builders' Library, Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), [Meta, Cache made consistent](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/).

For write-behind, suppose the flusher conditionally installs full value 8 and commits its applied receipt, then crashes before marking the journal entry complete. After 9 has been installed, replay finds 8's receipt and retires the journal entry without changing the store. A conditional update also rejects an older full replacement based on the current committed revision. For an additive operation, every required delta must be applied once logically in the required order. A higher revision alone cannot excuse skipping a delta. [PostgreSQL 18, conditional updates in Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED), [Oracle Coherence 14.1.2, Write-Behind Caching and Write-Behind Requirements](https://docs.oracle.com/en/middleware/fusion-middleware/coherence/14.1.2/develop-applications/caching-data-sources.html).

## Choose by the promises clients need

For venue hours, suppose the display may use a source observation up to 5 s old. Use a fresh PostgreSQL primary statement and tag the result with a deadline 5 s after a trusted timestamp captured just before the statement. Assume comparable clocks and reserve margin for uncertainty. Carry the original deadline through fills and refreshes. Check it before returning either a hit or a new result. A read begun at time 10 that completes at 16 cannot populate a usable entry or answer from it. If invalidation fails at time 12, an earlier observation at 10 remains eligible only until its deadline at 15. After that, use an eligible primary result within the request budget or report the display unavailable. A replica would need demonstrated source visibility and a bound covering its lag. [PostgreSQL 18, Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED), [hot standby visibility](https://www.postgresql.org/docs/18/hot-standby.html#HOT-STANDBY-USERS).

Choose lazy cache-aside with this cutoff and repairable invalidation for the display. Add refresh-ahead for predictable keys only if unused refresh work fits the origin budget. Write-through pays store latency plus the cache step. Write-behind can acknowledge durable acceptance from a journal and makes replay part of correctness before the store converges. Keep reservation or permission decisions at the authority. Monitor miss latency, observation age, invalidation lag and oldest pending write.
