# Cache update and coherence policies

A venue directory stores opening hours. A reader wants the current hours, while editors want to know what a successful write promises. Each cache policy places different work on the read or write path. Trace which copy is authoritative and when a failure can separate the copies.

- **M06-L02-LO1.** Trace one overlapping read and write and one cache failure under each policy.
- **M06-L02-LO2.** Choose a policy and explain the write latency, freshness and durability it can support.

## Order the cache-aside update

The application looks in cache. A miss adds a cache lookup before the database read and a fill before future hits. A write commits at the authority before deleting the cached value. If deletion comes first, a reader can miss, read old version 7 and refill it before version 8 commits. With commit first, a related race remains. Reader R misses and reads version 7, writer W commits 8 and deletes the key, then R fills 7 after the delete. A crash between commit and deletion can also strand an old hit until repair or expiry. A cache crash alone loses reusable copies. Reads fall back within the origin's capacity. [Microsoft Cache-Aside](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside#solution), [Scaling Memcache at Facebook §3.2.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf#page=4).

A read-through cache owns the miss loader, so the caller asks only the cache. The same in-flight fill can race a write unless the design fences it. If the read-through service crashes, provide a bounded bypass or treat the route as unavailable until recovery. Read-through can pair with any explicit write policy. [Oracle Coherence 14.1.2, Read-Through Caching](https://docs.oracle.com/en/middleware/fusion-middleware/coherence/14.1.2/develop-applications/caching-data-sources.html).

## Fence a late fill

For this example, the source transaction updates the hours and the venue revision together. Every hit checks the current revision at the same authority. A miss loads revision and value in one snapshot and writes under that revision. An R snapshot at revision 7 can complete late under key `venue:7`. A read whose revision check starts after W commits selects key `venue:8`. It cannot reuse `venue:7`. An earlier overlapping read can still return 7. The extra authority check makes this design worthwhile only if loading or assembling the result costs appreciably more. For public data that can lag, M06-L01 separates commit and generation advance with a recoverable outbox. Its delay becomes part of the freshness budget. In either design, a TTL measured from a late fill does not give the same bound as a TTL measured from the source observation. [PostgreSQL 18, transactions and statement snapshots](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED).

## Trace write-through, write-behind and refresh-ahead

Use the same starting state, store and cache at 7, and a concurrent write to version 8. These are explicit application designs.

| Policy | Overlapping read and write | Cache failure and repair |
| --- | --- | --- |
| Write-through | W commits 8 at the store, publishes 8 in cache and reports success after both steps. A reader between commit and publication may see 7. Guard cache publication so a slower update or fill cannot replace a newer value. | If the cache dies after the store commit, the write may have taken effect despite no success reply. Resolve retries by operation ID at the store and rebuild from committed values. After restart, untouched keys are cold until loaded. Eager writes can also populate entries nobody reads. |
| Write-behind | W records 8 as dirty and acknowledges acceptance before flushing. A cache reader can see 8 while a direct store reader sees 7. Flush in revision order or apply guarded versioned writes so replay of 8 cannot undo 9. | Losing the only dirty copy before flush loses the acknowledged change. Persist pending work before acceptance, replay unapplied IDs after a crash and consult pending state for reads that promise accepted changes. Reject new work when safe buffering is unavailable. |
| Refresh-ahead with cache-aside writes | R hits 7 near expiry and triggers a background read. W commits 8 and invalidates 7. A refresh that read 7 may finish afterward. Guard refresh and ordinary fill with the same captured revision or token. | A cache crash loses the refresh and warm entries. Refill on demand within the miss budget. Failed or unused refreshes cost origin work. Keep expiry anchored to the applicable freshness contract. |

[Oracle Coherence 14.1.2, caching strategies](https://docs.oracle.com/en/middleware/fusion-middleware/coherence/14.1.2/develop-applications/caching-data-sources.html).

## Choose by the promises clients need

For venue hours that can briefly lag, choose lazy cache-aside with repairable invalidation. Measure invalidation lag and the age of stale values. Add refresh-ahead for predictably popular keys if unused refreshes fit the origin budget. Write-through pays store latency plus the cache step and can suit frequently reread updates. Write-behind can acknowledge durable acceptance from a journal, but store visibility comes later and replay becomes part of correctness. Where a permission or safety decision needs authoritative state, check that state on the request path. Track miss latency, stale responses, oldest pending write and recovery load to see where a policy is failing.
