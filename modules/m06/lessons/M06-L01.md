# Where and what to cache

A museum catalogue serves the same exhibit searches all day. The database has warm pages, yet the application still repeats filtering and ranking. Decide which work can be reused and which requests are allowed to share it.

- **M06-L01-LO1.** Trace a fill across cache boundaries and estimate its memory and origin load.
- **M06-L01-LO2.** Defend a cache location, granularity and update policy using permissions, reuse and failure behavior.

## Put reuse at the right boundary

| Location | What a hit avoids | What the design must preserve |
| --- | --- | --- |
| Browser | The network request when direct HTTP reuse is permitted without validation | Use the unqualified `private` directive to restrict user-specific responses to private caches. Use `no-store` where storage itself is unacceptable. |
| CDN edge | A trip to the backend | Shared responses need deliberate cacheability. Keep language or encoding variants distinct with the applicable key and `Vary`. |
| Web server or reverse proxy | Application rendering and calls below it | A shared cache of rendered pages must separate every response-changing variant and enforce access before reuse. |
| Application cache | Expensive queries or object construction | Check permissions and use the tenant or authorized audience in the key when reuse is safe within that scope. |
| Database buffer cache | Some storage I/O | In PostgreSQL 18, `shared_buffers` holds database buffers and the OS cache also matters. A cached page can still require query execution. An external RAM cache can reuse the finished result. |

A shared HTTP cache may reuse a response to a request carrying `Authorization` only when the response explicitly permits shared caching under the applicable rules. A login cookie alone does not generally prohibit shared HTTP caching. A stored response requiring revalidation can still cause a network trip. An application cache needs its own guard at lookup. A correct hash of an incomplete key still leaks data. [RFC 9111 §§3.5, 4.1, 4.2 and 5.2.2](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5), [PostgreSQL 18 resource consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html#GUC-SHARED-BUFFERS).

## Pick the unit of reuse

| Unit | Read and fill | What changes invalidate it |
| --- | --- | --- |
| Row | Load an exhibit row by ID and reuse it in different reads. | An edit or deletion of that row. |
| Serializable object | Assemble an exhibit card from its row, localized labels and opening hours. Store the compact card by exhibit, locale and schema version. | A source change that alters the assembled card, including a label or hours update. Assembling a result can still require fetching many cards. |
| Query result | Cache the IDs and ranks returned for a canonical query. Include normalized filters, locale, page, visibility scope and ranking version in the tuple before hashing. Use collision-safe key encoding or verify the stored tuple on lookup. | A matching edit, an exhibit newly entering the result, or a ranking change. Invalidating just queries whose old payload contains the edited ID misses new membership. A dependency index by affected filter domain or a versioned namespace can invalidate broadly at a cost. |
| Rendered HTML | Cache completed markup to skip lookup, assembly and rendering for a reused page. | Underlying data, presentation version and response variants can all change the output. |

## Size the catalogue and trace a miss

Suppose 24,000 reusable query keys average 3 KiB each, including key and per-entry overhead. The working set is 72,000 KiB, about 70.3 MiB. With a 96 MiB cache and 20% held for headroom, 76.8 MiB is available for entries. Measure actual key and value sizes and allocator overhead before treating this estimate as capacity.

At 2,000 catalogue requests per second reaching the application cache and a measured 90% hit ratio there, 200 requests per second miss. With no intermediate result cache, coalescing or retry, each miss makes one origin query. For an uncached `ceramics,en,page=1`, authorize access, find no result, query PostgreSQL, encode the result with its expiry and return it. A subsequent request with the same key can skip query execution. If the hit rate falls to 80%, origin demand doubles to 400 queries per second under those assumptions. Use the origin's capacity to set a minimum useful hit rate. [Microsoft Cache-Aside pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside#solution).

A TTL determines when normal reuse ends. Capacity eviction can remove an entry sooner. When a popular key expires, many callers can try the same expensive fill. Coalesce them at the shared scope to send one in-flight lookup for that key while waiters stay within their deadlines. A per-process coalescer still permits one fill per process. Spread independent expiries with jitter and limit total origin fills during a cold start. A new app replica can hit an already-warm shared entry; it does not empty the shared cache. On shared expiry, one fleet-wide fill owner queries while other callers wait within deadlines. A fleet-wide rate limit with a defined burst allowance controls query starts; a separate concurrency cap bounds in-flight work. Excess or timed-out requests need an explicit error or permitted stale response. A file-local cache on an app instance starts empty on a new clone or contains whatever stale state the image carried. Keep it disposable with a safe warm-up path or put shared reuse in a separately managed cache. [AWS Builders' Library, caching challenges](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/), [AWS Cache Validity](https://docs.aws.amazon.com/whitepapers/latest/database-caching-strategies-using-redis/cache-validity.html), [Scaling Memcache at Facebook §3.2.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf#page=4).

## Combine granularity and update policy

For this example, cache only public catalogue results in a shared application query cache with lazy cache-aside fills. Read a shared generation before a fill, then run a fresh Read Committed statement on the PostgreSQL 18 primary; store the result under the generation captured before that statement. A committed change advances the affected generation asynchronously. Once it advances, a new fill's primary statement begins after the commit; a late old-generation fill remains under its old key. A lagging replica or an older snapshot could otherwise populate a new key with old data. Until advancement succeeds, old results may still be served. Persist a change event in the same transaction as the data and retry delivery to advance the generation after a crash; make processing safe for duplicate and out-of-order events. This recovery does not eliminate the delay. Check access revocation on an authoritative authorization path, independently of cached public data. [PostgreSQL 18 Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED), [hot standby visibility](https://www.postgresql.org/docs/18/hot-standby.html#HOT-STANDBY-USERS), [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#motivation).

If many distinct queries return the same exhibit cards and card rendering dominates, cache cards by ID and assemble results. Keeping card payloads out of query entries reduces duplicated invalidation for a label edit. Query membership and rank still need their own coherence policy.

| Policy | Update path and decision |
| --- | --- |
| Cache-aside | The application reads the cache and fills from the store on a miss; a write updates the store and separately invalidates or versions cached data. Lazy fills avoid work for unread keys, but a failed invalidation can leave stale data. |
| Write-through | A write updates the cache and backing store synchronously before success. Later reads can find the updated object, but writes wait for the store and partial failures need handling. |
| Write-behind | A write updates the cache and queues a later store write. Initial acceptance can be faster, but pending updates can be lost unless the queue is durable and recoverable. |
| Refresh-ahead | An access near expiry triggers an asynchronous reload from the store before the entry expires. It can keep popular data warm, but uses origin work on values that might not be read again. |

These paths are a preview; M06-L02 traces their failure windows in detail. In Redis Community Edition 7.4, a list can hold recent activity, a sorted set can hold an explicitly maintained score-ordered ranking, and RDB snapshots or AOF logging can be configured. Choose the data type for access and persistence for recovery. Check memory limits and eviction separately. [Oracle Coherence 14.1.2 cache strategies](https://docs.oracle.com/en/middleware/fusion-middleware/coherence/14.1.2/develop-applications/caching-data-sources.html), [Redis LPUSH](https://redis.io/docs/latest/commands/lpush/), [ZADD](https://redis.io/docs/latest/commands/zadd/), [7.4.0 configuration](https://github.com/redis/redis/blob/7.4.0/redis.conf).

| Workload | Useful reuse and boundary |
| --- | --- |
| Shared text paste and public landing page | Cache public rendered content at the edge. Check expiry and deletion behavior across all copies. |
| Timeline and relationship traversal | Cache recent activity or adjacency objects scoped to the viewer's authorized access. Keep visibility changes in the invalidation contract. |
| Web crawl and search | Reuse URL metadata by normalized URL. Reuse popular search results separately by query and index or ranking generation. |
| User session | Reuse a session object only for its authenticated session, never across users. Invalidate it on logout or revocation and check authorization on the authoritative path. |
| Personal finance overview | Cache computed account summaries behind authorization and scope keys to the account. Keep an authoritative balance check on the transaction path. |
| Sales ranks and autoscaled web tier | Cache a published ranking by reporting window or generation. Share expensive results across app replicas and keep instance-local copies disposable. |

Decline a shared cache when callers cannot safely share the value or when most keys are one-off. Measure origin demand on warm and cold paths before making the cache a capacity dependency.
