# Read architecture families critically

A new team wants a nightly 20 GiB report to run before 06:00. Someone recommends reproducing Google's 2004 MapReduce cluster, another suggests a modern stream processor, and a third presents a decade-old company blog diagram as proof that a particular managed database guarantees global correctness. None of those references, alone, proves that the new workload needs the same architecture. A paper is evidence for **a mechanism under stated historical assumptions**; it is not an unconditional current product SLA, benchmark or procurement decision.

- **M13-L01-LO1:** classify processing, storage, file-system and coordination architecture families by the invariants and failure mechanisms they actually provide.
- **M13-L01-LO2:** inspect primary sources by date/section/conditions and adapt two historical patterns to a smaller original workload, discarding unsupported or unnecessary components.

## Classify by contract, not recognizable product name

Use the family's **problem boundary** to narrow source research:

| Family | Historical/current examples to investigate | Core question | Mechanism lesson to revisit |
| --- | --- | --- | --- |
| Batch/distributed dataflow | MapReduce, Spark | How is finite work partitioned, retried and recomputed? | [M07-L03](../../m07/lessons/M07-L03.md), [M10-L03](../../m10/lessons/M10-L03.md) |
| Stateful event/stream processing | Storm, event logs and processors | What is event-time/order, checkpoint and replay contract? | [M07-L03](../../m07/lessons/M07-L03.md) |
| Sorted/column-family storage | Bigtable, HBase, Cassandra | How are keys partitioned and read/write semantics scoped? | [M04-L02](../../m04/lessons/M04-L02.md), [M05-L02](../../m05/lessons/M05-L02.md) |
| Availability-oriented key-value/document | Dynamo (2007), modern DynamoDB, MongoDB | Which writes remain available under partition and how are versions reconciled? | [M05-L01](../../m05/lessons/M05-L01.md), [M11-L09](../../m11/lessons/M11-L09.md) |
| Globally coordinated transactional data | Spanner | Where is ordering/commit authority and what clock assumptions matter? | [M09-L03](../../m09/lessons/M09-L03.md) |
| Memory KV/cache | Redis, Memcached | Can an acknowledged value vanish? Who repairs misses? | [M11-L09](../../m11/lessons/M11-L09.md) |
| Distributed file systems | GFS, HDFS | What is block/chunk placement, append and recovery model? | [M04-L01](../../m04/lessons/M04-L01.md) |
| Coordination, tracing and logs | Chubby, ZooKeeper, Dapper, Kafka | Which state transitions need fencing/metadata, which are observability, which are retained data? | [M07-L03](../../m07/lessons/M07-L03.md), [M09-L03](../../m09/lessons/M09-L03.md) |

These are **families for inquiry**, not declarations that listed products share identical semantics. For example, Dapper is tracing/observability, not a consensus or locking service. Kafka's retained log may coordinate consumer progress but is not a drop-in replacement for a lock authority. Redis and Memcached have very different persistence possibilities; GFS and HDFS were designed in distinct eras and operating environments. Record version and deployment mode whenever making a contemporary product claim.

## Read one primary mechanism in its own historical envelope

Google's [MapReduce paper (Dean and Ghemawat, OSDI 2004)](https://research.google/pubs/mapreduce-simplified-data-processing-on-large-clusters/) introduces `map` over input key/value pairs and `reduce` over grouped intermediate keys. Its runtime manages partitioning, machine failure and communication for large data-processing clusters. That is evidence for the **work decomposition** and reexecution model described in the 2004 paper, not evidence that our 20 GiB nightly job needs thousands of workers today.

The bounded mechanism is:

```text
immutable input -> map partitions -> intermediate key grouping/shuffle
                -> reduce partitions -> versioned output manifest
```

A failed map worker can recompute a deterministic map result from immutable input. An intermediate partition's output can be read more than once; downstream external side effects must not be blindly repeated. The client-visible result is not “all worker tasks returned success”: it is a **complete, correct versioned output readable before the report deadline**. If a reducer fails after writing half a report, publish a new immutable attempt output and atomically select the completed manifest rather than exposing mixed versions.

Next compare [Spark's RDD model](https://www.usenix.org/conference/nsdi12/technical-sessions/presentation/zaharia): an RDD records transformations/lineage for recomputing lost partitions and can keep reusable intermediate data in memory for repeated computations. Its appeal depends on **iterative reuse and memory envelope**, not the vague promise that Spark is always “faster than MapReduce.” A bounded nightly one-pass transformation might use a simpler SQL job or single-machine vectorized computation instead of either distributed engine.

Storm illustrates long-lived topology/event processing rather than a scheduled finite batch. Use the actual Storm version/documentation if choosing its acking or message guarantee; do not infer those from a twenty-year-old batch paper. See [Apache Storm documentation](https://storm.apache.org/releases/current/index.html) for a current reference to validate against a specific deployment. If the product needs fresh continuous updates, compare processing delay, checkpoint state, replay and late event handling; do not choose a streaming engine for a once-nightly finite report.

## Storage papers teach different failure boundaries

Google's [Bigtable paper (Chang et al., OSDI 2006)](https://research.google/pubs/bigtable-a-distributed-storage-system-for-structured-data/) describes a sorted persistent map indexed by row, column and timestamp, with data placement over many tablets and integration with supporting infrastructure. The lesson to transfer is that key design affects locality, partition splits and hotspot behavior; the publication's reported machine counts/latencies **are 2006 measurements**, not a 2026 guarantee for HBase, Cassandra or a managed Bigtable product. Check an actual product's current consistency and partition documentation before using it.

Amazon's [Dynamo paper (DeCandia et al., SOSP 2007)](https://www.amazon.science/publications/dynamo-amazons-highly-available-key-value-store) deliberately discusses a highly available key-value architecture that may sacrifice consistency during some failures and expose versions that application logic must reconcile. That historical Dynamo **is not synonymous with DynamoDB's current APIs or consistency modes**. Reusing its partition-tolerance reasoning can be valuable, but “DynamoDB permits concurrent versions exactly as Dynamo 2007” would require current API evidence and is not established by that paper.

Google's [Spanner paper (Corbett et al., OSDI 2012)](https://research.google/pubs/spanner-googles-globally-distributed-database/) describes a globally distributed database using TrueTime uncertainty bounds and coordination to support specific transaction and external consistency properties. Do not simplify its correctness to “wall-clock timestamps make transactions globally serializable.” The clock interface, uncertainty waits, replication and transaction protocol are part of the mechanism; copying just the timestamp idea cannot reproduce the guarantee. A local workload with no cross-region transaction requirement may avoid that coordination cost entirely.

MongoDB and Cassandra are not interchangeable with a single historical Dynamo or Bigtable model. Their current consistency and query guarantees need **version-scoped vendor documentation**. If an architecture recommendation names MongoDB aggregation, Cassandra consistency level or DynamoDB transactions, cite the exact product edition/version/configuration and official operation docs instead of guessing from family resemblance.

## File systems, coordination and tracing are different kinds of infrastructure

The original [Google File System paper (Ghemawat et al., SOSP 2003)](https://research.google/pubs/the-google-file-system/) describes assumptions including large files, failures as normal, and append-heavy workloads. These assumptions explain large-chunk placement, metadata ownership and relaxed file semantics in the historical design. They do **not** prove that a small team storing a nightly 20 GiB report needs a custom distributed filesystem today. Modern object storage might meet immutable-input/output needs with less operational complexity, subject to the actual service's documented durability, consistency and cost.

[ZooKeeper (Hunt et al., USENIX ATC 2010)](https://www.usenix.org/conference/usenix-atc-10/zookeeper-wait-free-coordination-internet-scale-systems) demonstrates a replicated coordination service with a small state interface and specified ordering properties. Chubby's Google paper explores a lock/metadata service for distributed clients [Chubby (Burrows, OSDI 2006)](https://research.google/pubs/the-chubby-lock-service-for-loosely-coupled-distributed-systems/). A lease leader is **not** by itself a safety guarantee: external resources still need epoch fencing if an old client resumes. Do not substitute a tracing system such as [Dapper](https://research.google/pubs/dapper-a-large-scale-distributed-systems-tracing-infrastructure/) for the state authority; Dapper collects request-path evidence. Kafka is a retained ordered-partition log under its actual version/configuration, not a universal serializable database [Kafka design docs](https://kafka.apache.org/documentation/#design).

## Work the small nightly workload backward

Assume **original synthetic** requirements: 20 GiB immutable daily source, 200 report transformations, one final signed report by 06:00, 60-minute overnight computation window, correct versioned output, no real-time event UI, one region initially, two failures of an ephemeral worker during the window. The team currently runs a relational store and object storage and can process data on a single adequate instance if measured CPU/memory allow.

Start with one scheduled job:
1. Pin input `date, dataset_version, checksum`, so a retry cannot silently read changed source.
2. Read partitions using bounded memory; stage attempt outputs at immutable temporary keys; write a manifest only after all required partitions validate.
3. Atomically publish the selected complete report revision. A repeated trigger with the same run ID retrieves the prior receipt or safely resumes; do not expose partial worker output.
4. If one process cannot meet measured CPU/I/O/deadline budget, partition input and distribute deterministic map tasks with an output merge step. Add workers, retry receipts and a bounded shuffle, not an entire historical cluster by default.

Suppose a synthetic trial of 30 nightly report runs has 27 correct complete reports published before 06:00, 2 missed deadline and 1 failed integrity check. On-time report success is **27/30=90%**, with all scheduled runs in the denominator. “Worker jobs succeeded” is not the product outcome. Measure actual per-run input bytes, output checksums, CPU and elapsed critical path. A new architecture is justified only when it addresses the proven bottleneck without weakening publication correctness.

A design using MapReduce patterns would add shuffle, task scheduling and distributed retry. A Spark-like in-memory lineage engine might help if the same source supports many iterative recomputations; it is unjustified for one simple pass without measured benefit. Stream infrastructure is unnecessary unless the workload's **freshness** changes. GFS/HDFS-style storage becomes a relevant comparison when native object-store access fails verified semantics or performance needs, not because a diagram included thousands of disks. Coordinate only the final manifest owner, not every intermediate computation.

## Use an evidence ledger before transferring a design

For every asserted property record: **source title, author/publisher, year, exact section/link, historical workload, mechanism, assumed failure class, current target product/version, evidence status and unresolved gap**. Label primary papers *historical*, contemporary vendor docs *version-specific* and blog catalogs *discovery only*. Never copy third-party diagrams without checking rights and attribution; draw a new diagram for the lesson's own domain instead. Even an official paper may have reuse restrictions; linking to it and independently describing an idea is different from reproducing its figures or code.

Before selecting a design, answer: What is the **smallest** mechanism that proves the required invariant? Which old assumption actually holds for the new workload? What observable failure would falsify the proposal? What source is still missing for a present-day guarantee? If those questions remain open, mark the recommendation conditional rather than filling the gap with product popularity.
