**Task:** `SD-DB01-WORKFLOW-PILOT`  
**Lesson reviewed:** DB-01 — Data Modeling and Relational Foundations  
**Sources checked:** 2026-11-09  
**Researcher scope:** Claim-level source support for the current draft. This report is not a technical, pedagogical, legal, or publication approval.

## Summary

- PostgreSQL 18 documentation supports the draft's explanations of primary keys, foreign keys, unique constraints, check constraints, and the missing default index on referencing columns. These are PostgreSQL-specific semantics and should not be presented as universal without qualification.
- A material cross-engine caveat affects the example DDL: MySQL 8.4 parses and ignores column-level inline `REFERENCES` specifications. The DB-01 schema uses that form for `orders.customer_id`, `order_items.order_id`, `order_items.product_id`, and `payments.order_id`. As written, those declarations do not create MySQL foreign keys. If MySQL is an intended target, rewrite them as table-level `FOREIGN KEY` constraints and name the engine/storage-engine assumptions, or explicitly scope the runnable example to PostgreSQL 18.
- The ER diagram states that every order contains one or more order items (`ORDERS ||--|{ ORDER_ITEMS`), while the DDL only enforces the child-to-parent foreign key. It does not enforce that an order must have at least one item. Confirm whether this is a required invariant; if so, explain the separate transactional/application or trigger mechanism, or adjust the conceptual cardinality.
- Several parts of the lesson are design heuristics rather than database guarantees: starting with access patterns, snapshotting the checkout price, and choosing natural versus surrogate keys. Teach them conditionally from explicit domain requirements and workload assumptions.
- The SQL is not executed in a declared engine/version. No executable-syntax or performance claim is verified by this evidence pack.

## Open questions for author/reviewers

1. Is PostgreSQL 18 the reference SQL engine for this lesson? If yes, label the sample accordingly. If portability is a learning objective, provide a separate MySQL 8.4 DDL variant using table-level foreign-key declarations and test both variants.
2. Is an order required to contain at least one item at creation, or only before confirmation? Align the ERD cardinality with the invariant and enforcement point.
3. Is `provider_ref` globally unique or unique per payment provider? If scoped per provider, the example's unique key needs to model that assumption.
4. Is the price snapshot tied to a stated business requirement to preserve the agreed checkout amount? Keep it as a conditional design choice.
5. The claim that access patterns should guide modeling is a useful course heuristic; add a vendor-independent data-modeling source if the lesson intends to present it as a general technical rule.
6. No SQL was executed, and no query plan or performance result was inspected. Keep the SQL example labeled illustrative until an engine/version and runnable lab are selected.
