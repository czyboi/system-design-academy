# Companion assessment

## Practical exercise

**EX-1.** A ticket service has six web instances, two in each of three availability zones, with a database pool capped at 30 connections per instance. The database supports 200 connections and 35 are reserved for other clients. After a zone loss, surviving and replacement instances can number up to 12, while the two failed instances can still hold their old database connections for up to 15 s. The database and session store remain reachable from the surviving zones. For this scenario, assume 8 database connections per serving web instance suffice for peak primary traffic.

At modeled peak load, measure valid ticket operations first submitted in the 60 seconds after zone loss. At least **99%** must return a successful result to the client within **one second of first submission**. Count each operation once across retries. A shed operation that never succeeds by its deadline, a timeout without a timely successful retry, and an unresolved outcome all use the 1% error budget. An operation is admitted if any attempt passes admission control before the deadline. Separately, p99 for admitted operations must be **below 250 ms**, measured from first submission through the final client outcome, including wait and retries. Use one second for admitted operations still unresolved at the deadline.

Trace ingress routing for `/tickets` and `/profiles`, including TLS and what happens to a local-only session after zone loss. Calculate the current pool exposure and choose a cap for the worst overlap. Specify what to do when pools fill and when a purchase reply is lost after the request is forwarded. Compare your policy with retaining the current pool size behind a shared connection limit. Design a failure test with separate pass criteria for capacity, the overall success budget, admitted latency and purchase correctness.

## Knowledge checks

### Q1

In the worked example, A fails before the proxy receives the catalogue response. Which backend and session store does the retry use?

**Answer:** The proxy can select B and B reads the shared session store.

**Explanation:** The retry is bounded and allowed for the stated read when no partial response has been sent. The session is stored outside A.

### Q2

An affinity cookie points at failed A. Why is choosing B insufficient if the session was only in A's memory?

**Answer:** B cannot recover that local session solely from the routing cookie.

**Explanation:** Affinity chooses a backend. It does not replicate application session state.

### Q3

A write times out after being sent to A. What remains unknown?

**Answer:** Whether A committed the write before its response was lost.

**Explanation:** A transport failure does not establish the application's outcome.

### Q4

Which routing layer can select an upstream using an HTTP path inside TLS, and what must happen first?

**Answer:** An L7 proxy can select by path after trusted TLS termination.

**Explanation:** The proxy must access the HTTP message to inspect its path.

### Q5

Why can least connections direct too much work to a backend?

**Answer:** Equal connection counts do not imply equal request cost.

**Explanation:** A long CPU-intensive request and an idle connection contribute differently to resource use.

### Q6

Why should a proxy not treat every forwarded IP header as a trustworthy client identity?

**Answer:** An untrusted client can supply or alter that header.

**Explanation:** Connection limits based on it require a trusted forwarding boundary and should account for shared client IPs.

## Answer key / rubric

Use reachable L7 ingress in multiple zones, terminate TLS at a trusted boundary and route by HTTP path. Store sessions in the surviving shared store so a rerouted user can continue. A cookie pointing to a lost instance cannot restore local-only session state.

Six pools can open 180 connections against a web budget of 165. If the cap is deployed before the incident, 14 potentially connected instances at 11 connections each can hold 154 connections, leaving 11 for headroom beyond the 35 reserved. The same cap meets the modeled eight-connection need per serving instance. If old instances can still hold 30 each, the cap of 11 for 12 live instances is unsafe until the old connections drain. A shared 165-connection limit could permit larger per-instance pools when peers are idle, but requests still need admission control so one instance or a retry burst cannot consume all available slots.

Bound pool wait inside the request deadline and shed work when the queue fills. Reserve serving capacity across zones and check whether the survivors can absorb enough peak traffic before replacements arrive. Give replay ownership to one application-aware caller. If a purchase outcome is unknown, resolve it by operation ID or replay the same input and ID within its durable deduplication contract and remaining deadline.

During a peak-load zone-loss drill, keep database connections within 200 including reserved clients. Record original operations at the load generator, match attempts by operation ID, and follow operations submitted near the end of the window through their deadlines. Verify at least 99% timely success across all valid operations and p99 below 250 ms across admitted operations. For example, if 970 of 1,000 valid operations succeed within one second, the drill fails even with an admitted p99 of 200 ms. Record pool wait and attempts per operation to diagnose misses. Drop a purchase response after commit and confirm that replay leaves a single purchase.

Score 10 points. Award 2 for the path, trust and session trace, 3 for overlap math and a viable cap or shared limiter with its trade-off, and 3 for bounded overload and safe purchase recovery. Award 1 point for measuring the 99% timely-success target over all original operations, and 1 for measuring the admitted-operation p99 separately. A cap that fits steady state but exceeds the failure budget earns at most 1 of the 3 capacity points. Other designs earn full credit when they satisfy the same constraints.
