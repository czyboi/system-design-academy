# Companion assessment

## Practical exercise

**EX-1.** A ticket service has six web instances, each with a database pool capped at 30 connections. The database budget is 200 connections and 35 are reserved for other clients. An ingress must route `/tickets` and `/profiles` to different services. Sessions are stored only in web-instance memory and a failed instance may have processed a purchase before its response is lost.

Propose ingress routing, a session strategy and a safe purchase retry policy. Calculate the present maximum web connections and a new equal per-instance pool cap that fits the remaining database budget. Describe what happens when one web instance and then one ingress instance fail. State any additional availability assumptions.

## Knowledge checks

### Q1

In the worked example, A fails before the proxy receives the catalogue response. Which backend and session store does the retry use?

**Answer:** The proxy can select B and B reads the shared session store.

**Explanation:** The retry is bounded and allowed for the stated read when no partial response has been sent. The session is stored outside A.

### Q2

An affinity cookie points at failed A. Why is choosing B insufficient if the session was only in A's memory?

**Answer:** B cannot recover that local session solely from the routing cookie.

**Explanation:** Affinity chooses a backend. It does not replicate application session state.

### Q3

A write times out after being sent to A. What remains unknown?

**Answer:** Whether A committed the write before its response was lost.

**Explanation:** A transport failure does not establish the application's outcome.

### Q4

Which routing layer can select an upstream using an HTTP path inside TLS, and what must happen first?

**Answer:** An L7 proxy can select by path after trusted TLS termination.

**Explanation:** The proxy must access the HTTP message to inspect its path.

### Q5

Why can least connections direct too much work to a backend?

**Answer:** Equal connection counts do not imply equal request cost.

**Explanation:** A long CPU-intensive request and an idle connection contribute differently to resource use.

### Q6

Why should a proxy not treat every forwarded IP header as a trustworthy client identity?

**Answer:** An untrusted client can supply or alter that header.

**Explanation:** Connection limits based on it require a trusted forwarding boundary and should account for shared client IPs.

## Answer key / rubric

A defensible answer uses L7 path routing with appropriate TLS termination. Six pools can open 6 × 30 = 180 connections. The web budget is 200 − 35 = 165, so a cap of 27 per instance permits at most 162 connections, leaving three unused. A lower cap is acceptable. Move the session to a suitably available shared store, and make purchase retries conditional on a durable application idempotency contract and a bounded deadline. A replacement web instance can resume only if that store remains reachable. Use at least two reachable ingress instances and explain the routing and shared dependencies needed for one to take over.

Score four equally weighted dimensions. Award up to 25% each for path-aware routing and trust boundary, correct pool arithmetic and budget, session and write-failure reasoning, and ingress failover with stated shared dependencies. Accept other defensible routing and state designs that meet the constraints.
