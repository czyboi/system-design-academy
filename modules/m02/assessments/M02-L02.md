# TCP, UDP and HTTP assessment

## Practical exercise

EX-1. An industrial dashboard displays a sensor's current temperature twice per second. Each newer reading supersedes older readings. The target is to display 95% of received current readings within 300 ms of their generation during a defined load test. The same dashboard creates maintenance tickets, where duplicates have an operational cost. A ticket request can reach the server, commit, and lose its response. The client has a two-second total ticket deadline and may make at most two attempts within it. The team can implement datagram ordering and congestion response, and operates an HTTP server with durable storage.

For the test, 400 clients each attempt a persistent connection. Assume each connection reserves 96 KiB and the server's buffer budget is 30 MiB. Calculate the buffer-only connection limit and explain what to do when demand exceeds it. Propose a delivery and retry contract for readings and tickets, including missing and delayed readings, a lost response after commit, a bounded wait and overload behavior. Compare one alternative transport or connection approach and its costs. State assumptions and identify measurements or tests for latency, saturation, retries and duplicate effects. Treat the numbers as scenario inputs rather than observed performance guarantees.

## Knowledge checks

### Q1

What does a cumulative TCP ACK with acknowledgment number N tell the sender, and what does it leave unknown about a transaction?

**Answer:** It indicates receipt of all bytes before N in sequence space, with N the next expected sequence number. It does not establish that the application committed the transaction.

**Explanation:** Transport progress and business-state changes occur at different layers.

### Q2

Why can later bytes received on a TCP connection wait behind an earlier lost segment?

**Answer:** The receiving application sees an ordered byte stream, so delivery can wait for the missing earlier bytes.

**Explanation:** Retransmission repairs the gap, but that repair takes time.

### Q3

Why might a UDP application add acknowledgments?

**Answer:** It may need evidence that a particular command or message arrived and may decide to resend it. An acknowledgment alone does not prevent duplicate effects if the acknowledgment is lost.

**Explanation:** UDP preserves datagram boundaries but supplies no delivery acknowledgment or retransmission.

### Q4

Why can a pool of 1,000 connections consume more memory than 100, and what else should a capacity estimate include?

**Answer:** Each connection uses state and possibly buffers. Include actual buffer use, idle connections and application memory.

**Explanation:** Multiplying an assumed per-connection reservation by pool size is only one part of the resource budget.

### Q5

A client repeats a DELETE after a timeout and receives a different status. Does that make the operation non-idempotent? Can a cache reuse this response for a later GET? How would a PATCH response qualify for reuse?

**Answer:** The DELETE can still have the same intended effect. Its response is ineligible for caching. A PATCH response can qualify for later GET or HEAD when it includes explicit freshness and a Content-Location matching the target URI.

**Explanation:** Idempotence describes effects. Cacheability depends on the method and response metadata, and a cached PATCH response does not execute another patch.

### Q6

A client times out after sending a ticket-creation POST. What must the application provide before a retry can safely avoid duplicate tickets?

**Answer:** It needs an explicit retry contract such as a durable request identifier and server-side deduplication, with defined repeat responses.

**Explanation:** The server may have committed the first request before its response was lost.

## Answer key / rubric

One solution sends numbered temperature datagrams, discards readings older than the latest received and does not retransmit obsolete readings. Loss can still prevent a current reading from reaching a client, and UDP does not guarantee the latency target. The application needs congestion response and suitable security. Alternatively, an HTTP stream over TCP can reuse existing infrastructure, but an earlier loss can delay later bytes and its connection state consumes memory. Either choice must be tested under the specified workload.

For tickets, the client uses an HTTP request with a caller-scoped identifier and the same input on both attempts. The server atomically records that identifier and input with the ticket, and returns the established outcome for a matching repeat within the documented retention period. A different input with the same identifier is rejected. An application acknowledgment may communicate acceptance or a committed result, according to its contract, but if it is lost the same-key durable deduplication prevents a second effect. A timeout remains an unknown outcome. Use no more than two attempts inside the two-second deadline, including waiting and any delay. If the deadline expires, report the unknown state and reconcile via the established operation identity rather than assume a failed creation.

The buffer-only maximum is floor((30 × 1,024) / 96) = **320 connections**. Demand for 400 exceeds this by 80. Bound the connection pool and waiting queue, reject or shed excess work explicitly, and avoid immediate unbounded retries. Multiplexing requests or reusing connections can reduce connection demand where supported. Actual capacity also depends on other connection state, application memory and queueing. During the 400-client test, measure reading age against the 300 ms target and report losses and discards separately so low measured latency cannot hide poor delivery. Record ticket latency, connection and memory use, queue depth, rejected work and retry rate. Drop a ticket response after commit and verify that retries produce one ticket.

Score the exercise out of 10 points.

- 2 points for a reading-delivery choice, loss behavior and justified alternative or trade-off.
- 3 points for an unknown ticket outcome, durable same-identity deduplication and a deadline-bounded retry.
- 2 points for the connection calculation and bounded behavior when demand exceeds capacity.
- 3 points for a test or measurement plan covering reading latency, resource saturation, retry behavior and duplicate effects.

A plausible transport and capacity choice earns the applicable design credit. Full credit also requires the failure and overload behavior, trade-offs and evidence for the target under the scenario. Accept other defensible designs that meet the stated constraints.
