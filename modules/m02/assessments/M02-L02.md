# TCP, UDP and HTTP assessment

## Practical exercise

EX-1. An industrial dashboard displays a sensor's current temperature twice per second. A later reading supersedes an earlier one. The same dashboard lets an operator create a maintenance ticket, where a duplicate ticket has an operational cost. A failed ticket response can be retried. The team can implement datagram ordering, acknowledgments and congestion response, and operates an HTTP server with durable storage. Each persistent connection reserves an assumed 96 KiB of memory. The budget for these buffers is 30 MiB.

Propose delivery behavior for the readings and ticket creation. Explain how each handles a missing message or lost response. Calculate the maximum whole number of connections under the stated buffer-only budget. Name one operational consideration outside this simplified calculation.

## Knowledge checks

### Q1

What does a TCP acknowledgment tell the sender, and what does it leave unknown about a transaction?

**Answer:** It indicates transport receipt of bytes. It does not establish that the application committed the transaction.

**Explanation:** Transport progress and business-state changes occur at different layers.

### Q2

Why can later bytes received on a TCP connection wait behind an earlier lost segment?

**Answer:** The receiving application sees an ordered byte stream, so delivery can wait for the missing earlier bytes.

**Explanation:** Retransmission repairs the gap, but that repair takes time.

### Q3

Why might a UDP application add acknowledgments?

**Answer:** It may need evidence that a particular command or message arrived and may decide to resend it.

**Explanation:** UDP preserves datagram boundaries but supplies no delivery acknowledgment or retransmission.

### Q4

Why can a pool of 1,000 connections consume more memory than 100, and what else should a capacity estimate include?

**Answer:** Each connection uses state and possibly buffers. Include actual buffer use, idle connections and application memory.

**Explanation:** Multiplying an assumed per-connection reservation by pool size is only one part of the resource budget.

### Q5

A client repeats a DELETE after a timeout and receives a different status. Does that make the operation non-idempotent? Can a cache reuse this response for a later GET? How would a PATCH response qualify for reuse?

**Answer:** The DELETE can still have the same intended effect. Its response is ineligible for caching. A PATCH response can qualify for later GET or HEAD when it includes explicit freshness and a Content-Location matching the target URI.

**Explanation:** Idempotence describes effects. Cacheability depends on the method and response metadata, and a cached PATCH response does not execute another patch.

### Q6

A client times out after sending a ticket-creation POST. What must the application provide before a retry can safely avoid duplicate tickets?

**Answer:** It needs an explicit retry contract such as a durable request identifier and server-side deduplication, with defined repeat responses.

**Explanation:** The server may have committed the first request before its response was lost.

## Answer key / rubric

One solution sends numbered temperature datagrams and discards readings older than the latest received. Lost readings need no resend under the stated freshness requirement. The application still needs congestion behavior and suitable security. Ticket creation uses an HTTP request with a caller-scoped identifier and durable deduplication. Commit the matching identifier and input together with the ticket in one transaction. A retry with the same identifier returns the established outcome rather than creating another ticket. Other choices are acceptable if they satisfy the stated loss and duplicate constraints.

The buffer-only maximum is floor((30 × 1,024) / 96) = **320 connections**. Actual capacity also depends on other connection state, application memory and queueing.

Score the exercise out of 10 points.

- 3 points for an appropriate reading delivery policy and its loss handling.
- 3 points for an explicit ticket retry and duplicate-control contract.
- 2 points for the connection calculation with units.
- 2 points for a relevant operational consideration and its effect.
