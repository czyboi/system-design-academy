# TCP, UDP and HTTP

## Learning outcomes

- M02-L02-LO1: Trace connection, delivery and request behavior for a workload using TCP, UDP and HTTP.
- M02-L02-LO2: Choose and defend transport and HTTP behavior using delivery, latency, resource and retry criteria.

## Problem and motivation

A service distributes downloadable files and also sends frequent game-position updates. Both use a network, but their useful delivery semantics differ. The file needs all bytes in order. An old position may have little value after a newer one arrives. Decide which failures the application can tolerate before choosing a transport, then budget connection resources and retries.

## Core concepts and mechanisms

### TCP connections, delivery and budgets

TCP establishes a connection using SYN, SYN-ACK and ACK, then exposes an ordered byte stream. Sequence numbers locate bytes in that stream. The receiver acknowledges progress and the sender retransmits missing data when needed. A checksum helps detect corruption. A cumulative ACK with acknowledgment number N indicates receipt of all bytes before N in sequence space and identifies N as the next expected sequence number. It does not establish that the application committed a transaction. A separate application response communicates the business outcome. Closing normally exchanges FINs and acknowledgments. A reset can terminate a connection abruptly. [RFC 9293 §§3.5–3.6](https://datatracker.ietf.org/doc/html/rfc9293#section-3.5)

The receiver's advertised window limits data in flight to protect its receive capacity. Congestion control also limits transmission according to network conditions. These controls serve different constraints. Ordered delivery means missing earlier bytes can hold later bytes at the receiver even if they have arrived. This head-of-line delay matters when unrelated application messages share one TCP stream. [RFC 9293 §3.8](https://datatracker.ietf.org/doc/html/rfc9293#section-3.8), [RFC 5681 §3](https://datatracker.ietf.org/doc/html/rfc5681#section-3)

A connection pool can avoid repeated setup, but every connection has state and buffers. For a hypothetical budget of 1,000 connections at 128 KiB of reserved state per connection, the estimate is 125 MiB. Actual memory depends on implementation, buffer use and workload. Limit pool size, include idle connections and measure real memory and queueing rather than assuming more connections improve throughput.

### UDP datagrams and application responsibility

UDP sends datagrams that retain message boundaries. A receiver can see loss, duplication or reordering. An application that needs delivery evidence can add sequence numbers and acknowledgments, decide which missing messages to resend, and discard stale updates. Checksums detect some corruption but do not repair loss. A UDP application also needs congestion control appropriate to its traffic. DHCP bootstrap is an example that can use local IPv4 broadcast before a client has a configured address. UDP does not itself guarantee a low latency or avoid congestion. [RFC 768](https://datatracker.ietf.org/doc/html/rfc768), [RFC 8085 §§3.1–3.3](https://datatracker.ietf.org/doc/html/rfc8085#section-3.1), [RFC 2131 §4.1](https://datatracker.ietf.org/doc/html/rfc2131#section-4.1)

### HTTP requests and method semantics

An HTTP request contains a method, target and fields, and may include content. A response carries a status, fields and optional content. A persistent HTTP/1.1 connection can carry multiple requests over time. HTTP/2 can multiplex exchanges over TCP, where lost TCP bytes can still delay streams sharing that connection. HTTP/3 maps HTTP to QUIC over UDP. QUIC implements streams, recovery and congestion control, so using HTTP/3 does not mean application messages are delivered with raw UDP semantics. TLS 1.3 supplies security properties within its connection and authentication assumptions. [RFC 9112 §9.3](https://datatracker.ietf.org/doc/html/rfc9112#section-9.3), [RFC 9113 §5](https://datatracker.ietf.org/doc/html/rfc9113#section-5), [RFC 9114 §2](https://datatracker.ietf.org/doc/html/rfc9114#section-2), [RFC 8446 §1](https://datatracker.ietf.org/doc/html/rfc8446#section-1)

**Safety** concerns the effect requested by the client. **Idempotence** concerns whether repeating the same request has the same intended effect as one request. The responses can differ. **Cacheability** asks whether a cache can store the response and use it again under the applicable rules.

| Method | Requested effect | Safe | Idempotent | Response cacheability |
| --- | --- | --- | --- | --- |
| GET | Retrieve a representation of the target. | Yes | Yes | Eligible for caching subject to cache controls and reuse rules. |
| POST | Ask the target to process the submitted content. | No | No | Requires explicit freshness and a Content-Location matching the target URI. An eligible cached response can serve a later GET or HEAD for that target. |
| PUT | Create or replace the state of the target with the supplied representation. | No | Yes | The PUT response is ineligible for caching. |
| PATCH | Apply changes described by a patch document. | No | Depends on the operation | Requires explicit freshness and a Content-Location identifying the target. An eligible cached response can serve a later GET or HEAD for that target. |
| DELETE | Remove the association between the URI and its current functionality. | No | Yes | The DELETE response is ineligible for caching. |

POST and PATCH reuse in this table is for retrieval. A subsequent POST or PATCH still needs processing. A cache that receives a non-error response (2xx or 3xx) to an unsafe request invalidates stored responses for the target URI. Other caches may still hold an earlier representation. [RFC 9110 §§9.2–9.3](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2), [RFC 5789 §2](https://datatracker.ietf.org/doc/html/rfc5789#section-2), [RFC 9111 §4.4](https://datatracker.ietf.org/doc/html/rfc9111#section-4.4)

For a create request, a timeout can occur after the server commits but before its response arrives. Retrying an ordinary POST may create another item. If the product requires retryable creation, scope a request identifier to the caller and input, atomically record it with the new item, and define the response to a matching repeat. An HTTP method name alone cannot establish that application contract.

## Worked example

Assume a file download must reproduce every byte, while game positions arrive ten times per second and an older position is useless after a newer one. Both choices require observed network behavior and security appropriate to the application.

1. The download uses HTTP over a reliable transport. If a TCP segment is lost, later stream bytes wait for the missing sequence range. Retransmission delays progress, but the application receives an ordered stream. A dropped connection still requires application-level recovery of the download.
2. The game sends independently numbered position datagrams. If update 41 is lost and 42 arrives, the client displays 42 and does not wait for 41. An application acknowledgment can communicate receipt or a business result, depending on its contract. It cannot by itself prevent duplicate effects when the acknowledgment is lost and the command is retried. The command also needs a durable deduplication contract. Both traffic types need an appropriate congestion strategy.
3. A pool of 400 hypothetical TCP connections with 64 KiB reserved each consumes an estimated 25 MiB for those buffers. Queueing and other application memory are additional. Limit concurrent connections and bound waiting work when the budget is exhausted. Measure the deployed implementation, queue delay, request latency and retry rate before selecting the pool limit.

### Packet loss across multiplexed requests

Two independent responses A (a large image) and B (a small status) share a connection. The following is a mechanism trace, not a performance benchmark.

| Event | HTTP/2 over one TCP connection | HTTP/3 over QUIC |
| --- | --- | --- |
| Packet carrying data for A is lost | A gap appears in TCP's ordered byte stream. | A's QUIC stream has missing data. |
| Later bytes for B arrive | TCP cannot deliver them to HTTP/2 past the missing sequence range, so B is blocked even if its own data arrived. | B's independent QUIC stream can deliver its available ordered data without waiting for A's stream recovery. |
| Missing data is recovered | TCP retransmission closes the gap and delivery resumes for both streams. | QUIC recovers A's missing stream data; B does not have to wait for A. |

HTTP/3 does **not** eliminate retransmissions, congestion control, loss, or head-of-line blocking **within** a stream. Connection-wide congestion, server saturation and application dependencies can still delay B. Neither version establishes that a business transaction committed after a lost response: an application operation-ID and durable retry contract are still required. [RFC 9114 §§1.1–2](https://www.rfc-editor.org/rfc/rfc9114.html#section-2)

## Trade-offs and failure modes

TCP supplies ordered reliable transport while the connection operates, at the cost of connection state and possible delay behind lost bytes. An application can use UDP to choose which messages merit recovery and which may expire. It must implement and operate the needed reliability, congestion response and security. HTTP's method semantics help clients reason about retries, but a network failure leaves the outcome of a state-changing operation uncertain.

## Decision framework

State the unit that must arrive, ordering and deadline before selecting a transport. Choose reliable ordered delivery for a complete byte stream. Consider datagrams when newer independent updates can replace older ones and the team can supply the missing application behavior. For HTTP operations, record method semantics, cache policy, retry contract, pool budget and observed error signals.
