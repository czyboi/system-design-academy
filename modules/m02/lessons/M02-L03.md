# Load balancing and reverse proxies

## Learning outcomes

- M02-L03-LO1: Trace a request through an ingress, including backend selection, session lookup and a backend failure.
- M02-L03-LO2: Choose and defend ingress routing, state placement and retry policies using workload and failure constraints.

## Problem and motivation

A catalogue has several web instances. Requests need to reach a healthy instance and a signed-in user must retain their session when an instance fails. The ingress must also have capacity for connections and avoid becoming the service's only failure point.

## Core concepts and mechanisms

### Routing and backend selection

A load balancer distributes incoming work across eligible backends. A layer 4 (L4) balancer selects using network and transport information such as addresses and ports. A network address translation implementation can rewrite the destination address and port, while another L4 implementation proxies a transport connection. Either can route a TCP flow without inspecting its HTTP path. [NGINX stream proxy](https://nginx.org/en/docs/stream/ngx_stream_proxy_module.html), [RFC 3022 §2.2](https://www.rfc-editor.org/rfc/rfc3022.html#section-2.2).

A layer 7 (L7) proxy understands the application protocol. After terminating the relevant client connection, an HTTP proxy can select a backend using a host, path, header or cookie, and establish or reuse backend connections. Path routing requires access to the HTTP message, so encrypted traffic needs appropriate TLS termination before inspection. Termination creates certificate, CPU and connection-management work at ingress. It also creates a separate trust boundary to the backend. [NGINX HTTP proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass).

Among healthy candidates, **round robin** rotates selections. **Weighted** selection assigns larger shares to larger capacity, subject to actual workload and connection reuse. **Random** selection spreads selections probabilistically, while **least connections** uses active connections as an imperfect load signal. An idle connection and a CPU-heavy request may cost very different amounts. Health probes or observed failures can remove an unhealthy instance from selection, but a health check can miss a failing operation or lag a failure. [NGINX load-balancing methods](https://nginx.org/en/docs/http/load_balancing.html) · [NGINX random selection](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#random).

Cookie affinity can steer a client's subsequent requests to the same backend. It helps when state is local, but can concentrate a hot session, and the chosen backend can disappear. The client needs a new eligible backend and any required state must remain available. AWS Application Load Balancer documents one product-specific implementation of stickiness. [ALB target-group attributes](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html).

### Proxy work and horizontal scaling

A reverse proxy receives requests on behalf of servers and forwards selected work. It may terminate TLS, compress responses to save bandwidth, serve static files directly, buffer a slow client's response, and cache reusable responses. Each shifts work away from applications but consumes proxy CPU, memory, storage or connections. Cached data needs an explicit freshness and variation policy. The proxy hides internal backend addresses from ordinary clients, while network access controls still protect those backends. Per-client connection or IP limits can reduce one client's resource use. Trust the forwarding chain before using a forwarded IP and account for many users sharing one IP. [NGINX proxy buffering](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering), [gzip module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html), [static files](https://nginx.org/en/docs/beginners_guide.html#static), [connection limits](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html).

Horizontal scaling adds web instances. Stateless request handlers can run on any instance when durable business data and session state live in shared services. Shared state is itself a dependency with capacity and availability limits. More instances also multiply downstream connection pools. For example, 12 instances with a maximum of 20 database connections each can open 240 connections before other clients are counted. Size pools for the maximum overlap of active and draining instances. A shared cap can allocate spare connections across instances, but requests still need a bounded wait and a rejection policy. In a failover test, observe pool wait and rejected work alongside admitted latency so the latency result reflects how much traffic the service handled.

A load balancer describes the distribution role, and a reverse proxy describes accepting requests on behalf of backends. One component may perform both. Redundant ingress instances reduce reliance on one machine only if traffic can reach a surviving ingress and shared configuration, network and certificate dependencies also survive.

## Worked example

Assume a catalogue has two healthy ingress instances, web backends A and B, and a shared session store. An L7 proxy routes `/catalogue` to a web backend and `/media` to a separate service. TLS terminates at ingress and the backend connection is protected according to the deployment's trust boundary. A session cookie identifies the user's session in the shared store. The affinity cookie is only a routing preference, not the session record.

1. The proxy sends a catalogue read to A. A reads the session from the store and begins the response. A then fails before the proxy receives a response.
2. Failure detection removes A from new selections after the detection delay. For this idempotent read, the proxy can retry within a bounded deadline on B, provided it has not already sent a partial response to the client. B reads the same session and responds. If the store is unavailable, moving to B alone cannot restore the session.
3. A checkout timeout leaves the commit outcome unknown. The proxy returns the failure to the caller and does not automatically replay a non-idempotent checkout. An application-aware client can retry a checkout operation whose documented contract guarantees deduplication. Reuse the same operation ID and input within the remaining deadline and the deduplication window. [RFC 9110 §9.2.2](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2.2).

## Trade-offs and failure modes

L4 forwarding is appropriate when transport information is sufficient. L7 enables path-aware routing and application policies, at the cost of termination and per-request work. Affinity can support local state but makes failover and distribution harder. A central session store makes instances interchangeable while adding a shared failure and latency dependency. A single overloaded or failed balancer can interrupt every request, and redundant balancers can still share a faulty network or configuration. A reverse proxy can also bottleneck on TLS, compression, cache memory or buffering, and stale cached data can violate the chosen freshness requirement.

## Decision framework

1. Select L7 when a required decision depends on the HTTP message and arrange trusted TLS termination. Use L4 when a transport flow is enough.
2. Measure backend load and connection distribution before choosing a selection policy. Configure health checks around a meaningful readiness signal and tolerate detection delay.
3. Place session state deliberately. Budget aggregate downstream pools and ingress resources, then test the loss of a backend, a session store and an ingress instance.
4. Retry only operations whose semantics and response progress allow it, within a bounded deadline.
