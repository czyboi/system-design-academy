# DNS and endpoint discovery

## Learning outcomes

- M02-L01-LO1: Trace DNS resolution and model cached answers during an endpoint change.
- M02-L01-LO2: Choose and defend a DNS routing policy using traffic, geography and failure criteria.

## Problem and motivation

A service needs to move clients between two regions during maintenance. A healthy standby is one part of recovery. Clients also need a usable route to it. DNS can select an endpoint for a name, yet resolvers and clients can retain earlier answers after an operator changes a record. The [two-region failover trace](../../m01/lessons/M01-L04.md#trace-a-two-region-recovery) separates standby eligibility from traffic migration. Here the decision concerns how clients discover the endpoint.

## Core concepts and mechanisms

### Resolution and record roles

An application asks a **recursive resolver** for a name and type. If it has no usable cached answer, the resolver follows the DNS delegation hierarchy. A parent zone's NS records identify authoritative name servers for the child zone. An authoritative server supplies data for the zone it serves. The resolver returns the answer and can cache it for the record's remaining time to live (TTL). A resolver may reuse cached delegations and answers, so a lookup does not necessarily contact every level each time. [RFC 1034 §§4.3.2 and 5.3.3](https://datatracker.ietf.org/doc/html/rfc1034#section-5.3.3)

An A record carries one IPv4 address, and an AAAA record carries one IPv6 address. A name can have multiple records of either type. [RFC 1035 §3.4.1](https://www.rfc-editor.org/rfc/rfc1035.html#section-3.4.1) · [RFC 3596 §2](https://www.rfc-editor.org/rfc/rfc3596.html#section-2)

A CNAME makes an alias point to a canonical name whose address then needs resolution. NS identifies authoritative name servers. MX identifies mail exchangers and includes a preference. TXT carries text data used by applications such as domain verification. A CNAME owner cannot also contain ordinary data records, so plan aliases with the zone's record constraints in mind. [RFC 1035 §3.3](https://datatracker.ietf.org/doc/html/rfc1035#section-3.3), [RFC 3596 §2](https://datatracker.ietf.org/doc/html/rfc3596#section-2)

### Routing choices and cached answers

The authoritative service can choose which eligible answer to return. With weighted selection, weights of 3 and 1 target a three-to-one share of eligible answer selections. That can represent unequal cluster capacity or an A/B rollout. It does not promise that three quarters of HTTP requests reach one cluster. A recursive resolver can share an answer among many clients until its TTL expires. Observed distribution depends on resolver traffic and caching.

A latency-based policy chooses using the provider's latency data, while a geolocation policy groups queries by inferred location. These can favor a nearby regional endpoint but location inference and actual end-to-end latency can differ. A health-aware failover policy can stop returning an impaired endpoint for new answers. Health and fallback behavior depends on the DNS service and policy. Route 53 can select records marked unhealthy when all records in the group are unhealthy. [Route 53 health selection](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-how-route-53-chooses-records.html) Amazon Route 53 documents weighted, latency, geolocation and failover policies. [Route 53 routing policies](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy.html), [Route 53 weighted routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-weighted.html)

TTL controls DNS cache reuse rather than an application's existing connections. Lowering a TTL shortly before a change does not shorten answers already cached with a longer TTL. A resolver can also be configured to serve expired data when refresh fails under the serve-stale approach in RFC 8767. Resolver failure can stop new lookups even when both service regions work. A control-plane failure can prevent changing authoritative data even while cached clients continue using existing answers. [RFC 8767 §4](https://datatracker.ietf.org/doc/html/rfc8767#section-4)

## Worked example

A catalogue name initially resolves to region A. Region B has already passed its readiness check. Assume one cached A record with a 300-second TTL, clients honor the answer, resolvers do not serve stale answers, and each new request obtains a DNS result rather than reusing a connection.

1. At t = -240 s, resolver R1 receives region A with TTL 300 seconds. Its answer expires at t = 60 s.
2. At t = -30 s, resolver R2 receives region A with TTL 300 seconds. Its answer expires at t = 270 s.
3. At t = 0 s, the operator changes the authoritative answer to region B for new lookups. B is ready, but R1 and R2 retain their cached answers.
4. At t = 90 s, R1 refreshes and returns B. R2 can still return A until t = 270 s. A client using R2 can reach A even though B is ready.
5. After t = 270 s, R2's next successful refresh obtains B under the stated assumptions. An existing client connection, a failed refresh or a serve-stale policy can extend actual migration beyond this simplified timeline.

The operator should keep A serving during planned maintenance where feasible, observe traffic at both regions, and keep a rollback path. The exact recovery deadline requires evidence about resolver, client and connection behavior.

If an unplanned loss makes A unreachable and the recovery objective is shorter than a cached answer's remaining life, changing DNS alone cannot meet that objective for affected clients. A separately operated, stable ingress address could route cached-address traffic to B if its own failure path, capacity and client reachability meet the objective. This adds an ingress dependency. Measure successful requests and latency from affected client networks during a failure drill, including existing connections and stale-answer behavior.

## Trade-offs and failure modes

A longer TTL reduces repeat DNS lookups and can let cached clients continue through a brief authoritative outage. It also delays ordinary refresh after an endpoint change. A shorter TTL increases lookup traffic and speeds ordinary cache expiry, with no universal bound on client migration. Weighted answers suit coarse allocation where approximate proportions are acceptable. They do not provide per-request balancing or exact A/B assignment. A health-aware policy still depends on the quality and scope of its health check.

## Decision framework

Choose the routing policy against the actual decision. Use weights for an approximate allocation or staged maintenance, latency or geography when regional placement matters, and an explicitly configured failover policy when endpoint health should affect new answers. Before the change, record old and new TTLs, readiness checks, resolver failure behavior, connection reuse and how traffic at both endpoints will be observed.
