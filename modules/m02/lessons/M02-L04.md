# CDN push, pull and cache control

## Learning outcomes

- M02-L04-LO1: Trace edge hits, misses and content replacement using a stated cache key and freshness policy.
- M02-L04-LO2: Choose and defend a population and cache-control policy for a workload, including privacy and origin-failure constraints.

## Problem and motivation

A global image catalogue has users far from its origin. A popular image causes repeated long-distance requests and a burst can overwhelm the origin. Some image variants are public, while account-specific responses must not leak across users.

## Core concepts and mechanisms

### Population and placement

A content delivery network (CDN) serves eligible content from geographically distributed edge locations. In a **pull** design, a request reaches an edge and a cache hit is served locally. On a miss the edge fetches from an upstream cache or origin, then eligible later requests can reuse the stored response. A cold edge and an expired object can therefore send work upstream. AWS CloudFront documents this pull flow for its own service. [CloudFront delivery flow](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html).

In a **push or proactive population** design, the publisher uploads or distributes content before demand reaches an edge. This spends transfer and storage on content that may never be requested, but can reduce first-request origin work for a known release. Actual prepositioning controls and coverage depend on the chosen provider. Pull is useful when the catalogue is large and demand is uncertain, but a sudden cold-object burst needs origin capacity or request coalescing if the implementation supports it. Edge proximity can reduce network distance, while the path and the actual latency still need measurement.

### Cache keys, freshness and privacy

A cache key defines which requests can share a stored response. It must include every request dimension that changes a cacheable representation, such as a language or image-size variant, or the system needs another correct variant mechanism. For example, a public `/poster` response selected by `size` needs distinct keys for small and large versions. If a personalized response is shared under a key that omits identity, another user could receive it. Prefer a private or non-stored response for personalized data, and check the actual cache configuration rather than relying on a missing key to protect it. [RFC 9111 §4.1](https://datatracker.ietf.org/doc/html/rfc9111#section-4.1).

Freshness is determined by response age and the applicable freshness lifetime, often called a time to live (TTL). Under HTTP semantics, `Cache-Control: private` prevents a shared cache from storing that response, and `no-store` instructs caches not to store it. CloudFront's documented positive minimum TTL can override origin `private` and `no-store` directives, so verify the distribution policy as well as the origin headers. A cache key is not authorization. [RFC 9111 §5.2.2](https://datatracker.ietf.org/doc/html/rfc9111#section-5.2.2), [CloudFront cache policy](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cache-key-understand-cache-policy.html).

For replacement, versioned URLs such as `/poster-v2.jpg` give the new bytes a new identity. Update the referring page or metadata too, because clients can still have an old reference. An invalidation asks the CDN to remove selected cached objects, but it does not by itself remove copies in every browser or intermediary. Both choices need a plan for old references and propagation. [CloudFront object updates](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/UpdatingExistingObjects.html), [CloudFront invalidation](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html).

## Worked example

Assume a public image `/launch-v1.jpg` has a 10-minute freshness lifetime and a single representation. Two regions use independent cold edges and the origin can supply the image. At time 0, the first request at edge A misses and fetches v1. Later requests at A while the stored response is fresh can hit. The first request at edge B also misses, because A's copy does not establish a copy at B. Concurrent misses may create multiple upstream requests unless the CDN coalesces them.

At minute 3 the image must be replaced. The publisher uploads `/launch-v2.jpg` and changes the catalogue metadata to refer to it. A request that has the new URL misses at its edge and fetches v2. A client holding older metadata can still request v1 until its metadata changes. If the origin fails on a cold v2 miss, that edge cannot serve v2 from a copy it does not have. A previously stored, eligible response might be served stale during an origin error only if the applicable policy and implementation allow it. [RFC 5861 §4](https://datatracker.ietf.org/doc/html/rfc5861#section-4).

## Trade-offs and failure modes

Longer freshness can reduce upstream traffic but extends the time an older representation remains usable. Shorter freshness increases refresh traffic. Proactive placement uses capacity before demand, while pull exposes cold edges to origin latency and load. CDN transfer, storage and invalidation can add cost. A shared cache key or a provider policy that stores personalized responses can expose data. An edge miss during origin failure still needs a reachable upstream, and a cached stale response is only suitable when its content and age are acceptable.

## Decision framework

1. Classify each response as publicly shareable or personalized, then configure origin headers and CDN policy together.
2. Define the representation variants and cache key. Test two users and two variants against the actual distribution.
3. Choose pull for uncertain demand or proactive population for a predictable release where available. Budget cold misses and origin capacity.
4. Set freshness from the tolerated age. Use versioned URLs or invalidation for replacement, and test old metadata, cold edges and origin failure.
