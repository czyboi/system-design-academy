| CDN-1 | A pull CDN serves a cached hit or asks an upstream tier/origin for a miss. A proactive population design pays upload/prefill and distribution cost before demand. | [AWS CloudFront Developer Guide, How CloudFront delivers content (living)](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html) | The source covers the CloudFront pull example. | CDN-2 | The cache key identifies request variants; freshness depends on age and applicable TTL. private prohibits shared storage and no-store prohibits storage under HTTP semantics. | [IETF RFC 9111 §§2, 3.2, 4.1, 4.2, 5.2.2 (2022)](https://datatracker.ietf.org/doc/html/rfc9111#section-5.2.2) | See [variant matching](https://datatracker.ietf.org/doc/html/rfc9111#section-4.1) and [CloudFront cache policy](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cache-key-understand-cache-policy.html). Check actual CDN settings; positive minimum TTL can override origin directives in CloudFront. |
| CDN-3 | Versioned object URLs and invalidation address different replacement needs. Edge invalidation cannot promise eviction from browsers and intermediary caches. | [AWS CloudFront Developer Guide, Update existing objects and Invalidate files (living)](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/UpdatingExistingObjects.html) | See [Invalidation](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html). Publishing new asset links also requires a freshness plan for their referring metadata. |
| CDN-4 | stale-if-error can permit eligible stale content during a specified error window. | [IETF RFC 5861 §4 (2010, Informational)](https://datatracker.ietf.org/doc/html/rfc5861#section-4) | Requires a prior cached representation and support/policy. Use only for deliberately shareable content with a stated freshness tolerance. |
