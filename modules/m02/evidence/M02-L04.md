# Source evidence for M02-L04

Checked 2026-11-11. Confidence is verified for the scoped claim in each row. Scenario inputs, calculations and design judgments are original illustrative assumptions.

| Claim | Supported statement | Primary evidence and version | Scope and limits |
| --- | --- | --- | --- |
| CDN-1 | A pull CDN serves a cached hit or asks an upstream tier/origin for a miss. A proactive population design pays upload/prefill and distribution cost before demand. | [AWS CloudFront Developer Guide, How CloudFront delivers content (living)](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html) | The source covers the CloudFront pull example. Proactive population is an architecture alternative, without any claim of universal push or prewarm API. |
| CDN-2 | The cache key identifies request variants; freshness depends on age and applicable TTL. private prohibits shared storage and no-store prohibits storage under HTTP semantics. | [IETF RFC 9111 §§2, 3.2, 4.1, 4.2, 5.2.2 (2022)](https://datatracker.ietf.org/doc/html/rfc9111#section-5.2.2) | See [variant matching](https://datatracker.ietf.org/doc/html/rfc9111#section-4.1) and [CloudFront cache policy](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cache-key-understand-cache-policy.html). Check actual CDN settings; positive minimum TTL can override origin private, no-store and no-cache directives in CloudFront. |
| CDN-6 | For a conditional GET, a matching current ETag on an otherwise successful request yields a bodyless 304; a mismatch leaves normal GET handling. A cache updates eligible stored metadata and reuses the corresponding body after validation. Unqualified no-cache requires validation before reuse. | [IETF RFC 9110 §13.1.2 (June 2022)](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2), [§15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5); [IETF RFC 9111 §§4.3.1–4.3.4 and 5.2.2 (June 2022)](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.1) | Checked 2026-11-13; conditional GET for the same URI and selected variant; ordinary handling on mismatch is not a guarantee of success. |
| CDN-3 | Versioned object URLs and invalidation address different replacement needs. Edge invalidation cannot promise eviction from browsers and intermediary caches. | [AWS CloudFront Developer Guide, Update existing objects and Invalidate files (living)](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/UpdatingExistingObjects.html) | See [Invalidation](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html). Publishing new asset links also requires a freshness plan for their referring metadata. |
| CDN-4 | stale-if-error can permit eligible stale content during a specified error window. | [IETF RFC 5861 §4 (2010, Informational)](https://datatracker.ietf.org/doc/html/rfc5861#section-4) | Requires a prior cached representation and support/policy. Use only for deliberately shareable content with a stated freshness tolerance. |
| CDN-5 | Simultaneous misses for one key can share a fetch within a collapse domain. | [AWS CloudFront Developer Guide, request collapsing (living, checked 2026-11-13)](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html#request-custom-request-collapsing) | CloudFront documents simultaneous requests with the same key at an edge. Counts for independent domains and a shared upstream tier are illustrative path models. |
