# Source evidence for M02-L02

Checked 2026-11-11. Confidence is verified for the scoped claim in each row. Scenario inputs, calculations and design judgments are original illustrative assumptions.

| Claim | Supported statement | Primary evidence and version | Scope and limits |
| --- | --- | --- | --- |
| NET-1 | TCP provides a reliable ordered byte stream through sequence numbers, checksum validation, acknowledgments and retransmissions. Receive window, congestion window, connection establishment and closure solve distinct problems. | [IETF RFC 9293 §§2.2, 3.1, 3.5, 3.6, 3.8 and RFC 5681 §3 (2022, 2009)](https://datatracker.ietf.org/doc/html/rfc9293#section-3.5) | See [congestion algorithms](https://datatracker.ietf.org/doc/html/rfc5681#section-3). ACKs describe transport progress, not application persistence. Pool memory numbers require declared hypothetical inputs. |
| NET-2 | UDP preserves datagram boundaries and leaves delivery/order/recovery to the application. UDP applications need congestion controls appropriate to the use case. DHCP uses UDP and can use local IPv4 broadcast during bootstrap. | [IETF RFC 768, RFC 8085 §§3.1–3.3 and RFC 2131 §4.1 (1980, 2017, 1997)](https://datatracker.ietf.org/doc/html/rfc8085#section-3.1) | See [RFC 768](https://datatracker.ietf.org/doc/html/rfc768) and [DHCP](https://datatracker.ietf.org/doc/html/rfc2131#section-4.1). UDP itself supplies no deadline or bandwidth guarantee. Distinguish checksums from repair. |
| NET-3 | HTTP method safety, idempotence and cacheability are independent; PATCH semantics allow conditional requests and do not guarantee idempotence. | [IETF RFC 9110 §§9.2–9.3 and RFC 5789 §2 (2022, 2010)](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2) | See [PATCH](https://datatracker.ietf.org/doc/html/rfc5789#section-2). POST caching has explicit prerequisites, PUT/DELETE are idempotent in intended effects, status codes can differ. |
| NET-4 | HTTP/1.1 supports persistent connections, HTTP/2 multiplexes streams on TCP, and HTTP/3 uses QUIC streams over UDP. TLS 1.3 authenticates and encrypts within its connection assumptions. | [IETF RFC 9112 §9.3, RFC 9113 §5, RFC 9114 §2, RFC 9000 §2, RFC 8446 §1](https://datatracker.ietf.org/doc/html/rfc9114#section-2) | See [1.1](https://datatracker.ietf.org/doc/html/rfc9112#section-9.3), [2](https://datatracker.ietf.org/doc/html/rfc9113#section-5), [QUIC](https://datatracker.ietf.org/doc/html/rfc9000#section-2), [TLS](https://datatracker.ietf.org/doc/html/rfc8446#section-1). QUIC streams can still share congestion and application dependencies. |
| NET-5 | TCP delivers an ordered connection byte stream; QUIC delivers ordered bytes per stream. A lost QUIC packet can contain frames for multiple streams, and lost stream information is sent in new STREAM frames. HTTP/3 maps exchanges onto QUIC streams. | IETF [RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2) (2022), [RFC 9000 §§2.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-2.2), [13](https://www.rfc-editor.org/rfc/rfc9000.html#section-13), [13.3](https://www.rfc-editor.org/rfc/rfc9000.html#section-13.3) (2021), [RFC 9114 §6](https://www.rfc-editor.org/rfc/rfc9114.html#section-6) (2022); checked 2026-11-13. | Verified for the trace: A-only loss and contiguous B data allow B transport delivery without waiting for A on that QUIC connection. A gap in B still blocks B. Shared congestion and [QPACK dependencies](https://www.rfc-editor.org/rfc/rfc9204.html#section-2.1.2) can delay B; no latency guarantee is implied. |
| NET-6 | Retry reasoning depends on operation semantics and knowledge of application: an idempotent request can be retried after communication failure; a non-idempotent request needs appropriate knowledge or a safe replay contract. HTTP/3 retains HTTP retry conditions. | IETF [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2), [RFC 9114 §4.1.1](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.1.1) (2022); checked 2026-11-13. | Verified for HTTP semantics. The ticket POST’s durable same-ID deduplication is the scenario’s application contract for unknown outcomes; transport recovery alone does not prove commitment. |
