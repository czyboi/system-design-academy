# Companion assessment for M07-L01

## Practical exercise

**EX-1.** A document service generates an optional preview after save. A preview may take 5–20 seconds. The client can poll a job ID. Preview workers have a bounded concurrency and the service must reject new previews once its pending budget is full. Saved documents have a separate durability contract. A preview request may be retried after a lost response, and a worker may crash after making the preview visible but before acknowledging.

Draw the acceptance and completion paths. State which record owns status, when acceptance is returned and how a publish or worker retry finds the same operation. Trace a worker race and repeated invalid input. Explain which operations you would keep synchronous.

## Knowledge checks

### Q1

The API commits the job but dies before the relay first publishes. What must persist with the job?

**Answer.** The runnable intent must be committed in the same transaction, such as an outbox row. The relay can find it independently of the crashed API.

### Q2

A worker crashes after committing the result and before acknowledging. What should a new delivery do?

**Answer.** Read the stable job ID and its terminal result, and acknowledge without repeating the user-visible effect. Work committed and broker delivery completed are distinct events.

### Q3

How do two deliveries racing to finish one job avoid two public links?

**Answer.** Stage attempts privately and condition publication on a single valid state transition. The losing attempt observes the durable terminal state and can clean up only unreferenced staging.

### Q4

Why is a RabbitMQ publisher confirm insufficient evidence that a preview exists?

**Answer.** Confirmation covers the publisher-to-broker interaction. Worker execution and the job's durable output are separate events.

### Q5

Should a worker requeue a known invalid preview input without a limit?

**Answer.** No. Classify permanent errors as terminal and preserve diagnosis. Limit retryable failures as well so poison work cannot monopolize execution.

### Q6

Should a document service enqueue its cheap status read?

**Answer.** Usually no. The caller needs the status now and the read is cheap. Queueing the costly deferrable preview lets the save and status paths stay responsive.

## Sample solution and rubric

Save the document under its own contract and schedule preview work only for durable input. Atomically claim the caller's request key, reserve pending capacity and write the pending job and outbox together. Return the job ID after commit. A retried request with matching input returns that job even when admission is full. A relay sends the stable ID and retries uncertain publishes. Workers stage attempt-specific previews and use a conditional job transition to publish one output. Crashing before commit leaves it retryable. Crashing after commit leaves a result that redelivery can observe and acknowledge. A competing attempt can spend compute, but it cannot publish a second link. A known malformed input becomes durably failed. Bound transient retries, retain diagnostics and reconcile dead-lettered jobs. Keep document save and status lookup synchronous under their own timing and correctness requirements.
