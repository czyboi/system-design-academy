# Companion assessment for M07-L01

## Practical exercise

**EX-1.** A document service generates an optional preview after save. A preview may take 5–20 seconds. The client can poll a job ID. Preview workers have a bounded concurrency and the service must reject new previews once its pending budget is full. Saved documents have a separate durability contract. A preview request may be retried after a lost response, and a worker may crash after making the preview visible but before acknowledging.

Draw the acceptance and completion paths. State which record owns status, when acceptance is returned and how a publish or worker retry finds the same operation. Trace a worker race, repeated invalid input, and a DLQ message arriving while another attempt is live. Assume immutable input and an application deadline after which publication is ineligible. Explain which operations you would keep synchronous.

## Knowledge checks

### Q1

The API commits the job but dies before the relay first publishes. What must persist with the job?

**Answer.** The runnable intent must be committed in the same transaction, such as an outbox row. The relay can find it independently of the crashed API.

### Q2

A worker crashes after committing the result and before acknowledging. What should a new delivery do?

**Answer.** For the SQS Standard example, look up the stable job ID, observe the terminal result and delete using this receive’s receipt handle without repeating the effect. An older handle can fail to remove the message even if its delete call succeeds; redelivery is still possible after deletion.

### Q3

How do two deliveries racing to finish one job avoid two public links?

**Answer.** First stage durable, readable, immutable objects privately. Guard the transition from pending to succeeded so only one reference wins. A sweeper reads terminal status from the write authority and deletes a staged object only when it differs from the immutable winning reference; it must not sweep a pending job.

### Q4

A RabbitMQ 4.2 mandatory publish to a single intended route is misrouted, yet receives a positive confirm. Can the relay retire the outbox row, and does the confirm prove a preview exists?

**Answer.** No. Correlate the returned unroutable message and retain the outbox intent; mark it sent only after a positive confirm with no return under the configured routing and durability contract. A confirm also cannot prove worker execution or a durable output.

### Q5

A DLQ message arrives while another attempt is rendering the same job. Should the service immediately mark it failed?

**Answer.** No. A DLQ receive count is not a job-level failure proof. A permanent validation failure for the same immutable input or an elapsed application deadline may authorize a guarded failure from pending; a live eligible success can otherwise win. Preserve an existing terminal state and reconcile aged pending jobs even without a DLQ entry.

### Q6

Should a document service enqueue its cheap status read?

**Answer.** Usually no. The caller needs the status now and the read is cheap. Queueing the costly deferrable preview lets the save and status paths stay responsive.

## Sample solution and rubric

Save the document under its own contract and schedule preview work only for durable input. Atomically enforce a unique caller/key claim storing the input version and job ID, reserve a pending slot, and write the job and outbox together. Concurrent new claims cannot exceed the budget; roll back the claim when no slot is available. Return acceptance only after commit. A matching retry waits for or verifies the original transaction; if it aborted, retry the claim. A committed matching job is returned even at capacity, without another slot. Keep the mapping through the retry window; conflicting input is rejected.

A relay retries uncertain handoffs. For a single intended RabbitMQ route it uses mandatory publishing, correlates returns, and retires the intent only after a positive confirm without a return under the chosen durability contract. Workers upload durable, readable, immutable private objects, then guard the pending-to-succeeded transition and release the slot in the same transaction. A crash before commit leaves the job pending; a crash afterward leaves a terminal result that redelivery observes before deleting its current SQS receipt. Two workers can spend compute but only one publishes. A sweeper reads terminal state at the write authority and deletes only objects different from the immutable winning reference.

A DLQ copy may coexist with a live worker. Before the deadline, its receive count alone cannot fail the job: the eligible worker can succeed. Once the deadline has elapsed, a guarded failure from pending competes with success; whichever terminal transition committed first remains authoritative. The same guard allows failure on permanent validation of the same immutable input. Bound transient retries, retain diagnostics and reconcile aged pending jobs even when no DLQ message remains. Keep document save and status lookup synchronous under their own timing and correctness requirements.
