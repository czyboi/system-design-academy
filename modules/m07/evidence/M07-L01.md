# Source evidence for M07-L01

Checked 2026-11-14. The render job, status contract and application examples are original. The approved inventory and Story SDA-M07-L01 supply topic scope.

| Claim | Exact primary evidence | Applicability |
| --- | --- | --- |
| C1. SQS Standard can redeliver. The visibility timeout hides a received message for a period and a consumer deletes it upon success. A redrive policy can move repeatedly received messages to a DLQ; each receive has a receipt handle, and stale handles or post-delete redelivery require duplicate-safe handling. Queue retention can expire messages. | AWS SQS Developer Guide [at-least-once delivery](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html), [visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), [DLQ redrive policy](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html#policies-for-dead-letter-queues), [DeleteMessage](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_DeleteMessage.html). | Verified for SQS Standard service documentation on the checked date. Visibility is no exclusive lock. |
| C2. RabbitMQ publisher confirms and consumer acknowledgements cover different hops. Unacknowledged manual-ack deliveries requeue on channel or connection closure. An unroutable publish can receive a positive confirm; mandatory returns expose an unroutable message. | RabbitMQ 4.2, AMQP 0-9-1 [confirm and acknowledgement scope](https://www.rabbitmq.com/docs/4.2/confirms#relation), [automatic requeueing](https://www.rabbitmq.com/docs/4.2/confirms#automatic-requeueing), [when publishes are confirmed](https://www.rabbitmq.com/docs/4.2/confirms#when-publishes-are-confirmed), [routing](https://www.rabbitmq.com/docs/4.2/reliability#routing). | Verified for the stated protocol and ack mode. Queue and message settings determine broker-side durability. |
| C3. Redis OSS 6.2+ LMOVE atomically moves a list element to a processing list. Removing completed work and recovering old claims are application responsibilities in this pattern. | Redis [LMOVE, Pattern: reliable queue](https://redis.io/docs/latest/commands/lmove/#pattern-reliable-queue), [persistence modes](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). | Verified for the documented list pattern. Redis persistence, failure recovery and reaper logic require explicit configuration/design. |
| C4. Celery workers execute registered tasks. Default early ack differs from late ack, with documented process-termination exceptions. | Celery 5.6.0 [Tasks, introduction](https://docs.celeryq.dev/en/v5.6.0/userguide/tasks.html). | Verified for the documented Celery version. Broker transport and worker settings matter. |
| C5. A dual write can leave committed state without its corresponding published message. A transactional outbox persists the handoff intent with the source mutation. | AWS Prescriptive Guidance [Transactional outbox, motivation and considerations](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html). | Verified design pattern. The relay can publish again, so deduplication still matters. |
| C6. A unique caller/key and atomic mutation support safe retries; PostgreSQL conditional updates recheck their predicates after concurrent changes. | AWS Builders’ Library [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), PostgreSQL 17 [unique constraints](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS) and [Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED). | Verified design principles and PostgreSQL 17 behavior. Coordinated capacity reservation and guarded job states are scenario design choices. |
| C7. A successful object upload can be readable while deletion is a separate action. | Amazon S3 [data consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel); PostgreSQL 17 [Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED). | S3 is an example, not an assumed universal object-store contract. The terminal-state cleanup rule is an inference from the database/object-store race. |
