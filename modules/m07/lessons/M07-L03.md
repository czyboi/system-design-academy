# Event logs, ordering and replay

A museum's search index stopped processing catalogue changes. Notifications continued independently. To restore search, the indexer needs a known starting state and the missing changes in a usable order.

- **M07-L03-LO1.** Trace groups, positions and versioned effects while replaying a partitioned log into a search projection.
- **M07-L03-LO2.** Choose a queue or log and defend its ordering, retention and repair contract.

## Choose the delivery and ordering unit

A work queue routes a job to an eligible worker and uses acknowledgement or deletion to finish that delivery. A retained log stores records independently of any one group's progress. In standard Kafka 4.2 consumer groups, members of one group divide the partitions, with one assigned member per partition at a time. A second group reads the same log with its own positions. Search and notification groups can advance independently. A committed Kafka offset is the position of the next record to consume in that partition. It does not certify that an external search index changed. [Kafka 4.2, Consumer Position and Message Delivery Semantics](https://kafka.apache.org/42/design/design/).

Route by exhibit ID and keep a stable mapping from keys to partitions. Offsets order appends within a partition. If writers race or the relay retries, the partition's append order can differ from the order of source changes. A stable key gives one ordered append path for that exhibit. More consumers can cover other partitions, while preserving one key's serial processing requires preserving order on its path. Review reassignment when partition counts or partitioners change. Split a hot key only if the application can handle the resulting ordering and merge rules. [Kafka 4.2, load balancing and consumer position](https://kafka.apache.org/42/design/design/).

The 2011 Kafka paper describes logs with sequential partition reads and consumer-held offsets. The Kafka 4.2 case adds explicit product questions about acknowledgement and replica configuration, retention and checkpoints. Even with stronger producer settings, the destination needs its own replay-safe effects. [Kreps, Narkhede and Rao, Kafka §3](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/09/Kafka.pdf), [Kafka 4.2, Replication and Message Delivery Semantics](https://kafka.apache.org/42/design/design/).

## Replay into a new index

The source transaction writes the exhibit change and a durable outbox record together. Assume each record has a stable event ID, exhibit ID, monotonic source revision and a complete searchable value or a deletion. A relay sends each committed intent to the exhibit's partition. A crash after publish can produce a duplicate. A conditional apply in the index store keeps the highest applied source revision per exhibit, including a revision marker for a deletion. This works for complete replacements. Deltas would require enforcing their order and detecting missing changes. [AWS transactional outbox, issues and considerations](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#issues-and-considerations).

A saved index snapshot includes P0 through offset 19 and P1 through offset 6, plus each exhibit's revision marker. Restore that snapshot as a separate index generation with next positions `{P0:20, P1:7}`. The relevant retained records are:

| Partition and offset | Record | Rebuild effect |
| --- | --- | --- |
| P0:20 | Exhibit E revision 5, update title | Publish the new title in the rebuilt index. |
| P0:21 | Duplicate of E revision 5 | Keep the existing version. |
| P0:22 | Exhibit G revision 2, update location | Index G's new location. |
| P0:23 | E revision 6, delete | Remove E and retain its revision 6 marker. |
| P1:7 | Exhibit F revision 3, update hours | Publish F's hours independently. |

Apply durably before advancing the checkpoint to the next position. If the indexer dies after applying P0:20 but before saving its next offset, the restart repeats 20 and the revision guard preserves one logical effect. Saving position first could skip work after a crash. Never advance past an earlier unapplied record of that partition. In this trace the rebuilt index reaches `{P0:24, P1:8}`. To switch readers, pause updates to the old served index, capture its last applied vector, then verify the new generation covers those prefixes and passes correctness checks. Atomically switch the read alias and continue from the new generation's own next positions. Bound replay traffic separately if it competes with live indexing. [Kafka 4.2, Message Delivery Semantics](https://kafka.apache.org/42/design/design/), [M07-L02](M07-L02.md).

## Repair an incomplete history

Set a retention budget for detection, outage, restore and catch-up. Measure the oldest recoverable position as well as current lag. In Kafka 4.2, a delete policy can remove old segments under time or size limits. Compaction can remove obsolete values without changing surviving record offsets. A compacted topic can help restore current keyed state under its replay conditions, while a rebuild needing every transition requires retained transitions. Deletion markers have their own retention window. Check whether a rebuild can finish before needed markers disappear. [Kafka 4.2, topic configs and log compaction](https://kafka.apache.org/42/configuration/topic-configs/), [Kafka 4.2, Log Compaction](https://kafka.apache.org/42/design/design/#log-compaction).

If P0's earliest available offset is 23, the saved P0:20 cursor has fallen behind. Starting at 23 would miss G's location update even though the later delete supersedes E's earlier update. Take a newer snapshot with its corresponding source and log boundary, or reconcile against authoritative records, including removals, while capturing overlapping changes. Resume from the repaired generation's own cursor after proving coverage. Use deliberate offset handling so a restart exposes a missing position to operators. Compare source revisions and durable outbox progress with the serving index to find gaps before retention removes the needed history. [Kafka 4.2, auto.offset.reset](https://kafka.apache.org/42/configuration/consumer-configs/).
