# Event logs, ordering and replay

A museum's search index stopped processing catalogue changes. Notifications continued independently. To restore search, the indexer needs a known starting state and the missing changes in a usable order.

- **M07-L03-LO1.** Trace groups, positions and versioned effects while replaying a partitioned log into a search projection.
- **M07-L03-LO2.** Choose a queue or log and defend its ordering, retention and repair contract.

## Choose the delivery and ordering unit

A work queue routes a job to an eligible worker and uses acknowledgement or deletion to finish that delivery. A retained log stores records independently of any one group's progress. In standard Kafka 4.2 consumer groups, members of one group divide the partitions, with one assigned member per partition at a time. A second group reads the same log with its own positions. Search and notification groups can advance independently. A committed Kafka offset is the position of the next record to consume in that partition. It does not certify that an external search index changed. [Kafka 4.2, Consumer Position and Message Delivery Semantics](https://kafka.apache.org/42/design/design/).

Route by exhibit ID and keep a stable mapping from keys to partitions. Offsets order appends within a partition. If writers race or the relay retries, the partition's append order can differ from the order of source changes. A stable key gives one ordered append path for that exhibit. More consumers can cover other partitions, while preserving one key's serial processing requires preserving order on its path. Changing partition count or partitioner can remap keys; consumer group reassignment instead moves ownership of an existing partition. Split a hot key only if the application can handle the resulting ordering and merge rules. [Kafka 4.2, load balancing and consumer position](https://kafka.apache.org/42/design/design/).

The 2011 Kafka paper describes logs with sequential partition reads and consumer-held offsets. The Kafka 4.2 case adds explicit product questions about acknowledgement and replica configuration, retention and checkpoints. Even with stronger producer settings, the destination needs its own replay-safe effects. [Kreps, Narkhede and Rao, Kafka §3](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/09/Kafka.pdf), [Kafka 4.2, Replication and Message Delivery Semantics](https://kafka.apache.org/42/design/design/).

## Replay into a new index

The source transaction writes the exhibit change and a durable outbox record together. Assume each record has a stable event ID, exhibit ID, monotonic source revision and a complete searchable value or a deletion. The relay sends committed intents to a Kafka 4.2 delete-retention-only topic. It marks an intent sent only after the selected broker acknowledgement succeeds; failed or uncertain sends are retried with the same immutable event ID. For example, `acks=all` waits for the current in-sync replicas subject to `min.insync.replicas`; choose that minimum and replication factor for the failure model. If the broker accepts a send but the response is lost, the retry can append a duplicate. Producer idempotence does not deduplicate application re-sends after a relay crash or coordinate the source and index. [Kafka 4.2 producer](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html), [producer configs](https://kafka.apache.org/42/configuration/producer-configs/), [topic configs](https://kafka.apache.org/42/configuration/topic-configs/). A conditional apply in the index store keeps the highest applied source revision per exhibit, including a revision marker for a deletion. This works for complete replacements. Deltas would require enforcing their order and detecting missing changes. [AWS transactional outbox, issues and considerations](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#issues-and-considerations).

A saved index snapshot includes P0 through offset 19 and P1 through offset 6, plus each exhibit's revision marker. Restore that snapshot as a separate index generation with its own next-position checkpoint `{P0:20, P1:7}`. Disable auto-commit; on assignment seek to this generation’s stored positions, not the old group’s offsets. Apply serially per partition and fence workers that lose assignment. The relevant retained records are:

| Partition and offset | Record | Rebuild effect |
| --- | --- | --- |
| P0:20 | Exhibit E revision 5, update title | Publish the new title in the rebuilt index. |
| P0:21 | Duplicate of E revision 5 | Keep the existing version. |
| P0:22 | Exhibit G revision 2, update location | Index G's new location. |
| P0:23 | E revision 6, delete | Remove E and retain its revision 6 marker. |
| P1:7 | Exhibit F revision 3, update hours | Publish F's hours independently. |

Apply each required visible record durably before advancing that generation’s checkpoint. If the indexer dies after applying P0:20 but before saving its next offset, reopen the same generation and seek to its saved position; repeating 20 is harmless under the revision guard. Saving first could skip work. In this trace the generation reaches `{P0:24, P1:8}`. Positions cover all required visible records in the processed prefix, not necessarily every integer offset: Kafka positions can cross numeric holes. Check each saved position against the log start throughout replay; set `auto.offset.reset=none` so absent or out-of-range positions surface as errors. Numeric jumps alone do not prove a history gap.

For cutover, fence old index writers permanently and settle their in-flight effects. Assuming every served effect came from this log, capture a consumer-readable log-end vector after the fence as a barrier covering all previously visible effects. The replacement must durably process all required records before that vector and pass correctness checks before atomically switching the read alias. The source snapshot, this generation’s saved next positions and the old served barrier are different things. Continue using the replacement’s own positions and bound replay traffic. [Kafka 4.2 consumer positions and external offsets](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html), [consumer configs](https://kafka.apache.org/42/configuration/consumer-configs/), [M07-L02](M07-L02.md).

## Repair an incomplete history

Set a retention budget for detection, outage, restore and catch-up. The worked raw log uses delete-only retention, because its relay can append source revisions out of order. Kafka compaction keeps the later append for a key, not the highest source revision: if E revision 6 deletes E and a delayed revision 5 follows, compaction can leave 5 and a fresh index with no marker can resurrect E. A separate compacted state topic needs source-revision-ordered publication including retries, or a stateful filter that rejects stale revisions before publication. Kafka’s keyed null-value tombstone represents deletion in that log; its delete-retention window must cover a full consumer scan. It differs from the durable source revision marker retained in a snapshot. [Kafka 4.2 log compaction](https://kafka.apache.org/42/design/design/#log-compaction), [topic configs](https://kafka.apache.org/42/configuration/topic-configs/).

If P0’s earliest available offset is 23, starting at 23 would miss G’s update. One repair for this full-value model is: first record and protect the consumer-readable end position of each partition; then open a consistent PostgreSQL 17 Repeatable Read authority snapshot. The relay publishes only committed changes. Build a new generation from that snapshot, including durable revision markers for removed exhibits, and replay from the earlier end vector. Every record before that vector came from a source commit visible to the later snapshot; changes after the snapshot can only be published at or after the earlier vector. Overlap and delayed pre-snapshot publications are safe under the revision guard, including deletion markers. Protect the continuation from retention through catch-up; if a position becomes unavailable, repair again. Fence the old writers and validate the replacement through the cutover barrier above. An existing projection snapshot is another option only with a trustworthy retained continuation. This ordering is an application inference under these assumptions, not a cross-system atomic snapshot. [AWS outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [Kafka 4.2 endOffsets](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html), [PostgreSQL 17 Repeatable Read](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-REPEATABLE-READ).
