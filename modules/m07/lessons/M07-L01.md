# Message queues and task queues

A customer uploads a model and asks for a preview render. The render takes seconds and can be retried after the upload request ends. The API needs a durable acceptance contract and a separate completion contract.

- **M07-L01-LO1.** Trace enqueue, delivery, execution, acknowledgement and user-visible status through a worker crash.
- **M07-L01-LO2.** Choose synchronous work or a bounded asynchronous handoff using ownership, loss and duplication criteria.

## Separate acceptance, delivery and completion

The render API scopes a client-supplied request key to the caller. An atomically enforced unique caller/key claim stores the immutable input version and job ID. In the same transaction, a new request reserves pending capacity, creates the `pending` job and records an outbox row. If capacity is unavailable, roll back the claim and reject before acceptance. Concurrent new requests must coordinate the reservation; a count read followed by an insert is not enough. Release the reservation once on a terminal transition.

A matching retry resolves to the committed job without consuming another slot, even at capacity; different input for the key conflicts. When the original transaction is still in flight or its outcome is uncertain, wait for or verify that its job and outbox committed before returning acceptance. If it aborted, the retry may attempt a new claim and reservation. Keep the key mapping for the promised retry window. Return acceptance only after the transaction commits. Even if the process dies before publication, a relay can find the outbox row and try again. A crash after handoff but before recording success can cause duplicate publication. [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [safe idempotent retries](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), [PostgreSQL 17 unique constraints](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS).

The relay marks an outbox row sent only after confirmed handoff to its configured destination under its chosen durability contract; failed or uncertain handoffs retain the intent for retry. For a simple RabbitMQ 4.2 AMQP 0-9-1 topology with one intended route, publish as mandatory, correlate any `basic.return` to its publish, and mark sent only on a positive confirm with no return. An unroutable publish can receive a positive confirm, so a confirm alone is insufficient. Configure the destination and message durability to match the contract. [RabbitMQ confirms](https://www.rabbitmq.com/docs/4.2/confirms#when-publishes-are-confirmed), [routing](https://www.rabbitmq.com/docs/4.2/reliability#routing).

A message broker accepts and routes deliveries. Depending on its contract, it can retain them, redeliver them or move them to a dead-letter queue. A task executor maps a job type to code, controls worker concurrency and decides how work is retried or scheduled. The render service owns the input, terminal status and published result. A broker's publish acknowledgement concerns message acceptance at that hop. A worker's consumer acknowledgement concerns one delivery. The user sees completion by reading durable job status, which includes the output reference or the final failure. Ownership across service boundaries is developed in [M03-L01](../../m03/lessons/M03-L01.md). [RabbitMQ 4.2, confirmation and acknowledgement scope](https://www.rabbitmq.com/docs/4.2/confirms#relation).

## Trace the crash around acknowledgement

Assume the worked transport is SQS Standard. Each message carries a stable job ID for lookup; each receive also provides a receipt handle for that delivery. Delete with the current receive's handle after committing or observing a terminal result. An old handle can report success without deleting the message; even a successful delete can be followed by redelivery. [SQS DeleteMessage](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_DeleteMessage.html).

Assume each attempt uploads a durable, readable, immutable private object before trying to publish its reference. The user-visible effect is linking one preview from the job record. Both success and failure compete by guarded transitions from `pending`: success requires an unexpired application deadline; failure requires either permanent validation failure for the same immutable input or an elapsed deadline that ends publication eligibility. A committed terminal state and winning reference never change. The database commits the status, reference and capacity release together. A sweeper reads terminal status from the write authority and deletes a staged object only if it differs from the winning reference; it does not delete while the job remains pending. Otherwise a sweep can delete an unreferenced upload just before its worker publishes it. Object availability is a separate storage obligation. [PostgreSQL 17 Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED), [S3 consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

| Event | Durable outcome and next action |
| --- | --- |
| A worker receives job J and begins rendering. | The accepted job exists. Its message can become visible again after the visibility window. |
| The worker crashes before result commit. | No result is visible. Another attempt can render and try the guarded transition. |
| The worker commits the result and crashes before deletion. | The report already says `succeeded`. Redelivery observes it and deletes its delivery without rendering again. |
| Two live attempts race after a visibility timeout. | Both can stage bytes. One guarded transition publishes a result; the loser observes the terminal state before deleting its delivery. |
| A DLQ copy appears while another attempt is live. | A receive count alone cannot fail the job. If the application deadline has elapsed, a guarded failure can win; otherwise allow the eligible attempt to finish. If success already committed, preserve it. |

Early acknowledgement can lose an attempt if the worker dies before committing its effect. Late acknowledgement can repeat the delivery, so make the effect duplicate-safe. If the effect lives in another service, a local processed flag leaves a crash window between that service's effect and the flag. Use the destination's idempotency contract or a recoverable reconciliation protocol there. A DLQ tracks broker-message receives, not job-level completion; duplicate publishes can create separate messages and a live attempt can outlast visibility. Reconcile DLQ entries and aged pending jobs even without a DLQ entry, since messages can expire from the queue. Stop automatic retries at the application deadline, retain diagnosis and make manual replay explicit. [SQS Standard delivery](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html), [visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), [DLQ policy](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html#policies-for-dead-letter-queues).

## Compare broker and executor contracts

| Evidence case | Design implication |
| --- | --- |
| RabbitMQ 4.2 over AMQP 0-9-1 | Publisher confirms and consumer acknowledgements cover different hops. A channel or connection closing with unacknowledged manual-ack deliveries causes requeueing. A positive confirm can cover an unroutable publish; use the mandatory-return handling above and check queue and message durability. [RabbitMQ confirms and acknowledgements](https://www.rabbitmq.com/docs/4.2/confirms). |
| SQS Standard | A received message becomes temporarily invisible and the worker deletes it after successful handling. Redelivery is possible even when a visibility window was set. A redrive policy can move repeated failures to a DLQ. [Visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), [DLQs](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html). |
| Redis OSS 6.2+ list pattern | A destructive pop can lose work on a crash. `LMOVE` can atomically move an item into a processing list. Supply claim expiry, safe requeue and removal of completed items. Review persistence for server failure. [Redis LMOVE reliable queue pattern](https://redis.io/docs/latest/commands/lmove/#pattern-reliable-queue), [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). |
| Celery 5.6.0 | Celery supplies registered tasks and workers and uses a broker transport. The default early acknowledgement differs from `acks_late`, which still acknowledges on documented child-process termination cases unless settings change. Test the selected broker and settings against each crash window. [Celery Tasks](https://docs.celeryq.dev/en/v5.6.0/userguide/tasks.html). |

## Decide which work waits

Render asynchronously when clients accept a job ID and a later result, and the system can sustain that queue. Bound accepted pending work and worker concurrency using the coordinated reservation above. A matching accepted retry returns its existing job even when the budget is full; reject a new claim before acceptance when no slot remains and let callers retry under a bounded policy. A queue absorbs a transient mismatch and adds wait during a sustained capacity shortfall. M07-L02 derives the backlog and retry budgets.

Keep a cheap status read or input validation synchronous. For a paste service, keep the durable write that defines a successful save in the save contract and defer indexing. For a timeline, defer fan-out and notifications after recording the owned post. For a crawler, queue bounded URL fetches and deduplicate work. For financial imports, defer reconciliation and keep the transfer invariant on its authoritative path. Social graph snapshots, popular query warm-ups and sales-rank recomputations can similarly run in the background when their consumers tolerate known lag. In an autoscaled service, add workers only when the dependency and the execution budget have headroom. Otherwise admission control protects both the worker pool and its downstream services.
