# Message queues and task queues

A customer uploads a model and asks for a preview render. The render takes seconds and can be retried after the upload request ends. The API needs a durable acceptance contract and a separate completion contract.

- **M07-L01-LO1.** Trace enqueue, delivery, execution, acknowledgement and user-visible status through a worker crash.
- **M07-L01-LO2.** Choose synchronous work or a bounded asynchronous handoff using ownership, loss and duplication criteria.

## Separate acceptance, delivery and completion

The render API scopes a client-supplied request key to the caller. In one database transaction it claims that key, creates a job with a stable ID and status `pending`, and records an outbox row for publication. A retry with the same key and same input returns the same job ID. Reusing the key with different input yields a conflict. The API returns acceptance only after commit. Even if the process dies before publication, a relay can find the outbox row and try again. A crash after publish but before recording success can make the relay publish twice. [AWS transactional outbox pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

A message broker accepts and routes deliveries. Depending on its contract, it can retain them, redeliver them or move them to a dead-letter queue. A task executor maps a job type to code, controls worker concurrency and decides how work is retried or scheduled. The render service owns the input, terminal status and published result. A broker's publish acknowledgement concerns message acceptance at that hop. A worker's consumer acknowledgement concerns one delivery. The user sees completion by reading durable job status, which includes the output reference or the final failure. Ownership across service boundaries is developed in [M03-L01](../../m03/lessons/M03-L01.md). [RabbitMQ 4.2, confirmation and acknowledgement scope](https://www.rabbitmq.com/docs/4.2/confirms#are-publisher-confirms-related-to-consumer-delivery-acknowledgements).

## Trace the crash around acknowledgement

Assume rendered bytes can be staged privately under an attempt-specific path. The user-visible effect is linking one staged preview from the job record. A conditional update transitions the job to `succeeded` with the output link only while it is eligible to succeed. Keep the stable job ID through every retry. The database makes the result link and successful status visible together. Losing attempts leave private files eligible for cleanup. The cleanup process preserves the object referenced by any committed result.

| Event | Durable outcome and next action |
| --- | --- |
| A worker receives job J and begins rendering. | The accepted job exists. The delivery can become visible again after its visibility window. |
| The worker crashes before result commit. | No result is visible. Another attempt can render and try the same conditional update. |
| The worker commits the result and crashes before acknowledgement. | The report already says `succeeded`. Redelivery reads the terminal row and acknowledges without rendering again. |
| Two live attempts race after a visibility timeout. | Both can stage bytes. The conditional transition publishes one result. The other observes terminal state before acknowledging. |
| Input is malformed or the retry budget is exhausted. | Persist a terminal failure with a reason. Retain a diagnostic record for repair. Stop automatic retry. |

Early acknowledgement can lose an attempt if the worker dies before committing its effect. Late acknowledgement can repeat the delivery, so make the effect duplicate-safe. If the effect lives in another service, a local processed flag leaves a crash window between that service's effect and the flag. Use the destination's idempotency contract or a recoverable reconciliation protocol there. A DLQ alone never changes what job status says. Reconcile quarantined jobs to a terminal status and make manual replay an explicit operation. [SQS Standard delivery](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html), [SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), [SQS dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html).

## Compare broker and executor contracts

| Evidence case | Design implication |
| --- | --- |
| RabbitMQ 4.2 over AMQP 0-9-1 | Publisher confirms and consumer acknowledgements cover different hops. A channel or connection closing with unacknowledged manual-ack deliveries causes requeueing. Check queue type, routing and durability settings before relying on a confirm. [RabbitMQ confirms and acknowledgements](https://www.rabbitmq.com/docs/4.2/confirms). |
| SQS Standard | A received message becomes temporarily invisible and the worker deletes it after successful handling. Redelivery is possible even when a visibility window was set. A redrive policy can move repeated failures to a DLQ. [Visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), [DLQs](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html). |
| Redis OSS 6.2+ list pattern | A destructive pop can lose work on a crash. `LMOVE` can atomically move an item into a processing list. Supply claim expiry, safe requeue and removal of completed items. Review persistence for server failure. [Redis LMOVE reliable queue pattern](https://redis.io/docs/latest/commands/lmove/#pattern-reliable-queue), [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). |
| Celery 5.6.0 | Celery supplies registered tasks and workers and uses a broker transport. The default early acknowledgement differs from `acks_late`, which still acknowledges on documented child-process termination cases unless settings change. Test the selected broker and settings against each crash window. [Celery Tasks](https://docs.celeryq.dev/en/v5.6.0/userguide/tasks.html). |

## Decide which work waits

Render asynchronously when clients accept a job ID and a later result, and the system can sustain that queue. Bound accepted pending work and worker concurrency. If admission is full, reject new work before promising acceptance and let callers retry under a bounded policy. A queue absorbs a transient mismatch and adds wait during a sustained capacity shortfall. M07-L02 derives the backlog and retry budgets.

Keep a cheap status read or input validation synchronous. For a paste service, keep the durable write that defines a successful save in the save contract and defer indexing. For a timeline, defer fan-out and notifications after recording the owned post. For a crawler, queue bounded URL fetches and deduplicate work. For financial imports, defer reconciliation and keep the transfer invariant on its authoritative path. Social graph snapshots, popular query warm-ups and sales-rank recomputations can similarly run in the background when their consumers tolerate known lag. In an autoscaled service, add workers only when the dependency and the execution budget have headroom. Otherwise admission control protects both the worker pool and its downstream services.
