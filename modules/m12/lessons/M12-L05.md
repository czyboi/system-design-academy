# Deck composition and blackjack scoring as separate policies

A deck is a sequence of 52 distinct cards. A blackjack hand is **not** simply a list of cards with fixed integer values: an ace may count as 1 or 11, depending on the other cards in the hand. When a generic `Card` object permanently stores `ace.value=11`, a hand with two aces and a face card scores 32 and incorrectly busts, even though its best legal total is 12. This is a responsibility boundary: a card describes identity, a deck manages inventory and dealing, and a **game-specific scoring policy** interprets a hand.

- **M12-L05-LO1:** trace constructing, shuffling, dealing and exhausting a 52-card/four-suit deck under clear ownership and failure rules.
- **M12-L05-LO2:** compute valid blackjack hand totals with multiple aces and choose composition/testable randomness over embedded card scoring.

## Define identity, deck ownership and boundaries

Use four suits `clubs, diamonds, hearts, spades`, thirteen ranks `A,2…10,J,Q,K` per suit: 4×13=52 distinct immutable card identities. For the approved generic deck source, `Card(suit,rank)` does not know its game; `Deck(cards, next_index, rng)` owns a shuffled permutation and deals the next card; `Hand(cards)` aggregates cards without owning the global deck. `BlackjackScorer` is a separate policy that interprets a hand.

```text
Card { suit, rank }                 # immutable identity
Deck { cards[52], next_index, rng }
Deck.shuffle(seed_or_rng)           # allowed before dealing for this contract
Deck.deal() -> Card | exhausted
Hand.add(card)                      # caller owns dealt card
BlackjackScorer.totals(hand) -> set<int>
BlackjackScorer.best(hand) -> {score, bust}
```

The deck invariant: each original card identity appears exactly once in the deck's permutation; `0 <= next_index <= 52`; the dealt prefix and remaining suffix partition the original 52. `deal` returns the current next card and increments the index atomically within the deck owner. When index reaches 52, return an explicit exhausted outcome; do **not** wrap to card 0 or return an arbitrary sentinel that can be mistaken for a card.

Cards are values, not one mutable global instance reused for every player. A dealt card is no longer available for a different hand. In a multi-threaded game, deck mutation is serialized; two simultaneous `deal` calls cannot receive the same next index. This local OOD problem excludes anti-cheat server authority and distributed replay, covered separately by M11-L07.

## Shuffle without entangling game rules

Start with the ordered 52-card list. The Fisher–Yates algorithm visits indices from 51 down to 1, chooses a uniform integer `j in [0,i]`, and swaps cards at i and j. Under an unbiased independent random-number source, this generates each permutation with equal probability. This is an *algorithmic property under its randomness assumptions*, not evidence that one concrete RNG is unpredictable or that a live game shuffle is cryptographically fair. A deterministic injected seeded RNG makes unit tests repeatable; an adversarial, money-stakes game needs a separately validated security/fairness design.

```text
shuffle(cards, rng):
    for i = 51 down to 1:
        j = rng.uniform_integer(0, i)
        swap(cards[i], cards[j])
```

If `shuffle` is callable after some cards were dealt, decide the contract explicitly: either reject until a new round/reset, or shuffle **only remaining cards** while preserving the already dealt prefix. For simplicity, this lesson rejects mid-deal shuffle. A `reset` returns to a known all-cards state only when no old hand may continue to deal against the same logical deck; use a new round ID to distinguish them.

## Hand totals: an ace is an option, not a constant

For blackjack **in this bounded scoring example**, numeric cards count face value, J/Q/K count 10, an ace counts 1 or 11, and 21 is the maximum non-bust total. We do not model split, surrender, dealer standing rules, insurance or betting.

A simple robust approach initially counts **every ace as 1** and other ranks as usual, then upgrades a single ace by +10 if that keeps total at most 21. At most one upgrade can improve a non-bust total: upgrading two aces adds 20 to their base value and would reach at least 22 for two aces alone. For a hand with two aces and one face card: base = 1+1+10=12, and upgrading one yields 22, so **best legal score is 12**. For two aces alone, base=2 and one upgrade yields 12; for Ace+9+Ace, base=11 and upgrading one yields 21.

Trace:

| Hand | All aces counted as 1 | Upgrade one ace by +10? | Best non-bust score |
| --- | ---: | --- | ---: |
| A,A,K | 12 | No (22 busts) | 12 |
| A,A | 2 | Yes (12) | 12 |
| A,9,A | 11 | Yes (21) | 21 |
| A,9,9 | 19 | No (29 busts) | 19 |
| K,Q,2 | 22 | No ace; already bust | 22 (bust) |

The function may return an explicit `bust=true` with raw minimum total 22 when every possible total exceeds 21. Do not incorrectly return 21 as a cap or label a bust as a valid score. An alternative implementation enumerates all possible ace choices, deduplicates totals, then selects the greatest <=21 if present. The optimized method and enumeration should agree; enumeration serves as a simple reference oracle for testing.

## Trace the final deal and an exhausted deck

Assume the deck's `next_index=51` and all prior 51 cards have been dealt. The next `deal` returns the final unique card at index51 and updates `next_index=52`. A following `deal` reports `exhausted`, leaves index52 unchanged and does not mutate a hand. A retry of `deal` over a network requires a stable command/receipt outside this in-process API; replaying the method blindly would consume another card. Separate mechanism from distribution.

The composition model makes the failure evident: `Hand.add` is invoked only when `Deck.deal` succeeded. If a mutation can fail between deck removal and hand addition, the owning GameRound needs a transaction-like guard or explicit recovery. A card must not be both in the remaining-deck suffix and an active hand; nor can the same deal receipt place it in two hands.

## Choose OO boundaries and verify them

One giant `BlackjackDeck` class holding shuffle logic, blackjack scoring, players and turn state is easy to start but hard to extend: changing blackjack ace values modifies inventory code, and a second card game cannot reuse the basic 52-card deck. Composition isolates shared identity/inventory from varying scoring. A single immutable `Card` type with injected `Scorer` rules is easier to test than rank subclasses that override `getValue` based on hidden hand state.

For a five-minute synthetic cohort of 1,000 original valid deal requests, suppose 960 return the correct unique card in 50 ms, 10 return a legitimate exhaustion result, 15 fail, 10 time out and 5 complete late. A timely correct **decision** SLI counts the 960 successes plus 10 timely legitimate exhaustions **if** they were returned within deadline, yielding 970/1000; a successful-card-delivery SLI counts only 960. This distinction matters more than a method's average execution time in isolation.

Test distinctness and conservation over all 52 deals; ensure no 53rd card, test a known seeded shuffle permutation, check edge-case random bounds, deal concurrency, mid-deal shuffle rejection and no hand mutation on exhaustion. Test A,A,K; A,A; A,9,A; A,9,9; K,Q,2 against an independent exhaustive-ace enumerator. If a checker produces 32 for A,A,K it tested the wrong responsibility model, not a valid blackjack game.
