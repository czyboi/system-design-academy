# Parking allocation and contiguous resource ownership

A bus needs five adjacent large parking spots. A naive design loops over available spots, finds five anywhere on a level and calls the allocation successful. The lot later has an impossible occupancy layout—and on release it frees only the bus's first spot. This is an object-responsibility failure: the **allocation must be a contiguous, compatible set on one row**, and its identity must own the **entire** set for the lifetime of the parking session.

- **M12-L03-LO1:** trace bike/car/bus compatibility, contiguous allocation and complete release through parking-lot, level and spot responsibilities.
- **M12-L03-LO2:** select composition and rule extension boundaries while preserving atomic allocation, accurate counts and failure behavior.

## Specify the source contract and one owner of truth

The approved exercise uses multiple levels with motorcycle, compact and large spots. For this **original illustrative fit policy**, a motorcycle may fit any size; a car fits compact or large; a bus needs **exactly five consecutive large spots in one row**. Each spot belongs to exactly one level and one row and has a stable index within that row. A bus cannot combine the last three spots of row A with the first two of row B or spread across different levels. Inputs are assumed valid, but concurrent calls still need invariant-safe state transitions.

```text
ParkingLot(levels)           // chooses eligible level, returns receipt
Level(rows, spots, index)    // finds contiguous eligible run on one row
Spot(id, row, index, size, allocation_id?)
Vehicle(id, kind)
Allocation(id, vehicle_id, ordered_spot_ids, status)
FitPolicy.compatible(vehicle, spot) -> bool
```

`Spot` owns physical size and current allocation reference; `Allocation` owns a committed vehicle-to-spots association; `Level` owns the row topology and count/index updates. `ParkingLot` coordinates level selection, but it should not manually mutate five unrelated spot fields bypassing Level's commit operation. The key invariant is: each occupied spot belongs to exactly one active allocation; the allocation's stored spot set exactly matches all occupied spots referencing its ID.

A count is **derived evidence**: available-large count tells whether five might exist, not whether five are adjacent. A level with eight free large spots scattered as 2+3+3 has enough total but may still have no run of five. Scanning row-local contiguous runs (or maintaining a correct run index) is required.

## Trace a successful bus allocation

Consider level 2, row R7 with seven large spots indices 0–6. Indices 0 and 6 are already occupied by different cars; 1–5 are free. A bus `BUS-8` arrives and requests five consecutive large spots. The Level scans index order, recognizes [1,2,3,4,5] as one free and compatible run and generates allocation `AL-41`.

| Step | R7 occupancy, indices 0…6 | Stored state |
| --- | --- | --- |
| Before | C, ·, ·, ·, ·, ·, C | free large count=5 |
| Candidate | C, [1,2,3,4,5], C | no mutation yet |
| Commit AL-41 | C, B, B, B, B, B, C | each spot points to AL-41; allocation stores all five |
| Release AL-41 | C, ·, ·, ·, ·, ·, C | all five spots cleared together; count restored |

The critical transition is **validate candidate then commit as one unit**. If another car claims spot 3 between search and mutation, do not occupy 1,2,4,5 and report partial success. Under a single-process design, the Level can lock allocation-sensitive state around **revalidation and commitment**, or serialize all parking operations through its owner. Optimistic versioned conditional commit is another option if it guarantees the whole run changes together. A free-count cache is updated within the same transition, not before confirmation.

## Trace a failed allocation and a complete release

Now a different row has large spots [0…6] where indices 2 and 5 are occupied, leaving free groups [0,1], [3,4], [6]. The free count is 5 but there is **no five-spot consecutive run**. `allocateBus` returns a definite failure with no spot state change and no new active allocation. A fallback across rows would break the announced contract even if it satisfied the total count.

When BUS-8 exits, the caller presents `AL-41`, not a bare first spot ID. `release(AL-41)` validates current active allocation and its full set, frees each owned spot, updates counts and marks allocation released **as one operation**. A repeated release should be explicitly idempotent under the same allocation ID or rejected as already-released without increasing counts again. Releasing only spot 1 would leave four occupied ghosts and corrupt future placement. A car parked later in spot 1 must not be accidentally released by a delayed retry for the old bus: bind the release to the current allocation ID, not the vehicle's claimed location alone.

## Extend the fit rule without rewriting ownership

Assume a new product rule: **electric cars require a charging-capable compatible spot**, while existing cars can use non-charging spots and buses remain five contiguous large spots. Add `capabilities` to `Spot` and a fit predicate `supports(vehicle_requirements, spot)`; let Level still compute candidate runs and commit ownership. Do not introduce a subclass for every cross-product of motorcycle, compact, large, charging and accessibility flags. The allocation strategy decides adjacency, the fit rule decides **individual compatibility**, and the Level owns atomic mutation.

Inheritance may express stable vehicle kinds, but a bus is not five `Car` objects, and a level is not a subtype of a spot. Composition models containment; policies encapsulate potentially changing rules. A capability-based strategy can enforce a new row-local rule with no changes to the release invariant.

The main design trade-off is between **simple scanning** and maintained run indexes. Scanning N spots costs O(N) per bus attempt but is easy to reason about; an interval/run index may accelerate allocation for large, busy levels but must be kept synchronized on every spot claim/release. A stale index can tell you five are free when the source of truth disagrees. Begin with scan-and-lock for moderate lot sizes, add an index only against measured need.

## Failure and observability contract

For a synthetic five-minute cohort of 1,000 valid vehicle arrivals, 880 receive a compatible confirmed allocation within 200 ms, 70 fail legitimately for no fit, 30 time out and 20 get a late outcome. If the SLI promises **successful parking**, report 880/1,000=88%; if it promises a **correct decision**, a policy-consistent no-fit may count in the numerator when returned by deadline. Define both contracts and do not hide timeouts in an admitted-only denominator. All values are illustrative, not a real lot benchmark.

Check conservation after every operation: active allocated spot references equal the union of all active Allocation.spot IDs; free counts plus occupied counts equal physical spot counts per class; no bus spans a row or level; no partial booking is visible to callers. Test race between two buses selecting the same run, car claim between bus scan and commit, reallocation after partial failure, double release, delayed release of an old allocation, and new charging policy interactions. Passing a simple `park(bus)` unit test without asserting these invariants is not evidence the object model is safe.
