# Hash-table contracts, collision chains, and resizing

A small dictionary implementation seems correct until two different keys land in the same bucket. The developer replaces the bucket with the latest key and silently loses another customer's value. The root cause is not a poor hash function: **collisions are a normal, required case** for a finite table. The object contract must specify equality, bucket membership, replacement, removal and capacity before a caller can trust `get`.

- **M12-L01-LO1:** trace insert, update, get and middle-of-chain removal for integer keys in a fixed-capacity separate-chaining table.
- **M12-L01-LO2:** justify resizing, equality/hash stability and unordered versus ordered indexes under collisions, capacity and adversarial inputs.

## Begin from the bounded source contract

The approved source exercise models assumed-valid **integer keys**, key/value entries, an in-memory array of exactly four buckets, and separate chaining. It is an educational design, not a production concurrent map. Define `index(k) = ((k % 4) + 4) % 4`, which always yields a bucket in 0–3 even when a language uses signed remainder for negative integers. Entries in each bucket retain both key and value.

```text
Table.capacity = 4
buckets[i] = chain of Entry { key:int, value:V, next:Entry? }
size = count of distinct keys
```

If `insert(1,"A")`, `insert(5,"B")` and `insert(9,"C")` run in that order, all hash to bucket 1. Assuming front insertion, the chain is `(9,C) -> (5,B) -> (1,A)`. The table stores **three** entries, not one. Looking up 5 compares keys in this bucket until it finds equality and returns B. Looking up 13 walks the chain and returns a declared missing-key result—never a stale value from another key in the same bucket.

An interface should distinguish absent key from an explicitly stored null value. One simple API uses `lookup(key) -> {found:boolean, value}`; `remove(key) -> boolean`; `put(key,value) -> {inserted:boolean, previous?}`. Avoid a contract where missing and present-with-null both collapse silently to null unless the application explicitly permits that ambiguity.

## Work the middle deletion and update trace

Start from `9 -> 5 -> 1` in bucket 1. Call `put(5,"B2")`, then `remove(5)`.

| Operation | Bucket 1 chain (key:value) | size | Explanation |
| --- | --- | ---: | --- |
| Insert 1,5,9 | 9:C → 5:B → 1:A | 3 | Same bucket, distinct keys |
| `put(5,B2)` | 9:C → 5:B2 → 1:A | 3 | Equality match updates value; no new entry |
| `remove(5)` | 9:C → 1:A | 2 | Previous node 9's `next` now points to 1 |
| `lookup(9)` | 9:C → 1:A | 2 | Found C |
| `lookup(5)` | 9:C → 1:A | 2 | Missing |
| `remove(13)` | 9:C → 1:A | 2 | False, no mutation |

A linked deletion algorithm keeps `previous` and `current`. For the head, replace `buckets[i]` with `head.next`; otherwise link `previous.next = current.next`. Then detach the deleted node and decrement size **once**. Removing a missing key or changing an existing value never decrements/increments distinct-key count. If a caller holds node references, define whether those references are invalidated; this contract exposes only values, not internal mutable entries.

Replacing `buckets[1]` with a new entry for key 5 destroys 9 and 1. Conversely, treating equal-hash as equal-key changes someone else's value. Equality and hash are separate checks: *equal keys must hash to the same bucket for a given capacity, but collisions do not imply equal keys*. In Python, values that compare equal must have equal hashes and hashable keys need stable hashes during their lifetime in a mapping [Python data model, `__hash__`](https://docs.python.org/3/reference/datamodel.html#object.__hash__). Our fixed integer-key contract avoids mutable-key hazards, but a generalized API cannot.

## Add capacity: when and how to resize

A fixed table has load factor `alpha = size / capacity`. With 3 entries and 4 buckets, alpha=0.75. A bounded demonstration extends the table by doubling to 8 buckets when the next distinct insertion would exceed 0.75. For an insertion of key 13, the new size would be 4 and the old alpha becomes 1, so allocate eight empty buckets and **rehash every existing entry** using modulus 8. Old bucket 1 contained 1,5,9: now 1 and 9 map to bucket 1, 5 to bucket 5; the new 13 also maps to bucket 5. Preserve key/value mappings; chain order need not remain identical unless specified.

```text
put(key, value):
    locate by hash and key equality
    if existing: replace value, return old
    if (size + 1) / capacity > max_load:
        allocate new buckets; rehash all existing entries
    insert unique entry in new index; size++
```

Looking up first avoids resizing on an update. Rehashing costs O(n) for n entries in one event, although geometric growth can give amortized expected O(1) insertion under reasonable hashing and bounded load. Collisions can still create O(n) chains in the worst case. Do not promise worst-case constant time merely from “hash table.” Java HashMap documents both capacity/load factor and rehashing when threshold is exceeded; its exact collision handling differs from our educational list model [Oracle Java SE 26 HashMap](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/util/HashMap.html).

The source exercise is valid without resizing because its contract fixes capacity. This extension is required when the *product* needs growth. Choose the smallest mechanism that meets the declared scope; do not silently turn a four-bucket teaching example into an unbounded production service.

## Complexity, order and concurrency boundaries

For well-spread keys at bounded load, expected lookup/put/remove work is near O(1), plus a possible resize for insertion. A pathological collision chain is O(n). A balanced ordered tree can support range scans and sorted iteration in O(log n) update/lookup under its usual balancing assumptions, at a different constant/memory cost. Use a hash table for equality lookup and an ordered index for predecessor/successor, range query, or stable sorted traversal. Arbitrary bucket order must never be mistaken for chronological or lexical order.

Concurrency is **not** granted by the class design: two writers can both observe absence, insert duplicate keys and corrupt links or size. Make the whole structure single-thread-owned, guard mutations with appropriate locking, or choose a concurrently specified map. A thread-safe lookup function alone does not make resize safe if readers can traverse freed old chains. The contract also needs an unambiguous capacity and memory-pressure policy: reject new entries under a fixed-memory bound, evict under a separate cache contract, or allocate larger storage.

The original exercise should be tested under negative keys, collisions, update-without-growth, head/middle/tail deletion, missing remove, resize with collision redistribution and adversarial all-colliding keys. A functional pass is **not** evidence that performance is constant for hostile inputs. Its core invariant is simple: for every distinct stored key, exactly one reachable entry with matching equality lives in the key's current bucket and `size` equals the number of distinct reachable keys.
