# Chat domain models and permissioned relationship states

A user rejects a friend request. The sender retries a stale “approve” action, a shared group changes membership, and a message is posted based on an old client-side participant list. If the chat object trusts the request payload, it may accept a message from someone who is no longer in the group. This is a local domain modeling problem before it is a websocket delivery problem: **friendship, group membership and message ownership are separate state machines**, and authorization is checked against the authoritative current state at the write boundary.

- **M12-L06-LO1:** trace create/update/remove user responsibilities, friendship transitions, group membership and private/group message identity.
- **M12-L06-LO2:** defend lifecycle and permission policies under stale requests, rejected invitations, membership changes and history retention.

## Keep the source bounded and name state ownership

The approved OOD contract is an initially unscaled **text-only** chat. It includes user create/update/remove, friend invitations, friendship removal, private and group conversations, and message history. Message transport, device presence and global delivery belong to [M11-L02](../../m11/lessons/M11-L02.md), not this model.

Choose distinct aggregates:

```text
User { user_id, profile, status: active|deleted, revision }
FriendRequest { request_id, from_id, to_id, state: pending|approved|rejected, version }
Friendship { unordered_user_pair, state: active|removed, revision }
Conversation { id, kind: direct|group, membership_version, history_policy }
Membership { conversation_id, user_id, state: active|left|removed, revision }
Message { message_id, conversation_id, sender_id, payload, accepted_membership_version, created_seq }
```

The User service owns profile and deletion state; Relationship service owns requests and approved friendships; Conversation owns current membership and local message sequence. Message service enforces membership before accepting a new message and stores immutable sender/history identity. A friend request is not itself a conversation membership grant.

Define direct-chat eligibility as a product rule: for this exercise a direct conversation requires an active friendship, while a group member may send only while active in that group. Different products may allow messaging strangers; the enforcement location is the lesson, not the universal rule. A user-created group has a creator/admin who can invite under an explicit role policy. Invite acceptance is not equivalent to an unverified membership insert.

## Trace a rejected friend request

Alice sends request `FR-9` to Bob, initially pending. Bob rejects it; the owner commits version 2 and records a rejected receipt. Alice's app, still showing version1, tries `approve(FR-9, expected_version=1)`. It fails: only the recipient under the current pending state may approve; the stale version/rejected terminal state forbids a transition to approved.

| Event | Request state | Friendship | Correct outcome |
| --- | --- | --- | --- |
| Alice sends FR-9 | pending v1 | absent | receipt FR-9 |
| Bob rejects FR-9 | rejected v2 | absent | terminal rejection |
| Alice sends stale approve | still rejected v2 | absent | forbidden actor and stale state |
| Alice retries original create with same ID/input | rejected v2 | absent | replay request's existing receipt/current state, not a new approval |
| Alice sends a new FR-10 | pending v1 (subject to policy) | absent | new invitation, not resurrection of FR-9 |

A rejected request does not automatically block every future invitation; cooldown/abuse prevention is a distinct policy. Conversely, a removed friendship should not silently become active because an old pending invite or delivery callback arrives. Store versioned transitions, and bind retries to the request identity and canonical actor/input.

Deleting a user presents another ownership boundary. A naive `User.delete` that loops over every group and message object to mutate them synchronously couples domains and risks partial state. Set user `deleted` under its own authority and make future authorization deny new actions; coordinate relationship/membership cleanup through explicitly recoverable transitions. Decide whether history is retained, redacted, anonymized, or removed under the product's privacy/retention requirements. This lesson does not invent a global legal retention policy or promise physical erasure on a local deletion flag.

## Trace group membership and message acceptance

Group G7 has active members Alice, Bob and Cara at membership version 12. Alice is an admin, and David has a pending invitation but is **not yet active**. Cara leaves, producing membership version 13. Cara's device then sends `M44` with its stale local v12 participant list; the server reads authoritative membership at the acceptance boundary, finds Cara inactive and refuses M44. A client-provided membership version is an optimization or precondition, not an authorization source.

David accepts his invitation under the group owner policy, producing version14, and sends M45 as an active member. The conversation owner assigns unique `message_id`, `created_seq`, `sender_id`, immutable payload and accepted membership context. A same-ID retry replays the stored result without creating a second history entry. For readers, enforce history access by explicit policy: current membership does not automatically grant retrospective access to all pre-join private messages. A bounded example might grant messages from join sequence onward; a different group type may expose all history with consent. Encode this choice rather than inheriting it accidentally from a list.

The critical race is authorization versus membership removal. If a check at v12 occurs, Cara leaves at v13, then a later write accepts M44 without rechecking, a promise “removed members cannot send after confirmed removal” is violated. Guard membership eligibility *at the same authoritative message acceptance transition* or define a clearly weaker synchronization boundary. For separate storage domains, describe the reconciliation/ordering protocol rather than claiming one ordinary method call is an atomic cross-service transaction.

## Direct versus group composition

A direct conversation has two participants under the agreed friendship rule. A group has a membership set with role/admin policies and invitation state. Both share `Conversation` identity, a `Message` history model and send receipts, but their membership strategies differ. A `ConversationPolicy` object can decide whether an actor may invite, send or view history; it must inspect current authoritative context. Inheritance such as `GroupConversation extends DirectConversation` is semantically wrong because a group is not a specialized two-person relationship.

Maintain stable message identity separate from display order. One conversation-local sequence provides deterministic presentation/replay for accepted messages, but cross-conversation order is not guaranteed or needed. The source contract is text-only; file/media attachments, encryption key rotation and federated multi-device delivery introduce separate mechanisms and should not be implied by this OOD exercise.

Avoid a giant User object retaining every chat's mutable state. Prefer User ID references, conversation/membership indexes and clear owner boundaries. Indexing user-to-conversation relationships is a performance concern; the authoritative membership state still determines permissions, not an unvalidated search index.

## Verify authorization and lifecycle, not just method existence

A synthetic five-minute cohort receives 1,000 valid original send intents. Suppose 920 produce the correct accepted or authorized rejection decision within 100 ms, 40 time out, 25 fail and 15 complete late. Timely **decision** success is 920/1000=92%; the service should report accepted-message delivery separately, because a correct “not a member” rejection is not a delivered message. All figures are illustrative.

Test recipient-only friend approval, rejection then stale approval, duplicate invitation identity, removal and future re-invitation, group join/leave/send races, direct chat after friendship removal, user deletion with ongoing cleanup, history access after departure, and duplicate message retry with same/conflicting payload. The most important invariant is that each committed message was accepted under a documented authorization boundary and has a stable unique identity; present client state cannot confer rights on its own.
