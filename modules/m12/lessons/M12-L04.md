# Call-centre dispatch and escalation state machines

A call waiting for an operator is promoted to a supervisor after the operator cannot resolve it. At the same instant, a different operator becomes idle and grabs the same call from the queue. Both agents report ownership; when one ends the call, the scheduler marks the other agent available and assigns new work. This is not a failure to pick the right class inheritance hierarchy. It is a violation of **call state and assignment ownership**.

- **M12-L04-LO1:** trace dispatch, operator/supervisor/director escalation, queue and completion under explicit transition and rank rules.
- **M12-L04-LO2:** compare object inheritance and policy-based rank dispatch, making ownership, idempotency and invalid transitions defensible.

## Start with the approved policy, not an org chart

For the source exercise, rank order is `OPERATOR < SUPERVISOR < DIRECTOR`. An incoming ordinary call first seeks a free operator; if none exists it waits. When handling cannot finish, it can escalate one rank at a time. A director can handle any call, and no VIP scheduling/priority exists. The input domain is assumed valid; an actual telephony system adds authentication, recordings, legal constraints and network delivery, all outside this local OOD contract.

```text
Employee { id, rank, status: idle|busy, current_call_id? }
Call { id, state: waiting|assigned|escalating|completed, min_rank, owner_id?, version }
Dispatcher { waiting queues by min_rank, idle employees by rank }
Assignment { call_id, employee_id, assignment_version, status }
```

The **Call** object owns lifecycle truth; an **Assignment** is a versioned relation linking exactly one active employee and call; Dispatcher owns selection and queue placement. Employee owns only availability under dispatcher's coordination. An employee cannot become idle merely because an untrusted completion event names them; the current active assignment must match both IDs and its version.

One consistent dispatch rule: choose the lowest eligible available rank at or above `call.min_rank`, preferring earlier waiting calls at the same required rank. If no one is available, queue the call once in the proper rank queue. Never leave a call simultaneously in the waiting queue and assigned to an employee. Assignment and removal from queue commit together at the owner boundary.

## Trace queueing, escalation and free capacity

Three employees exist: O1 operator, S1 supervisor, D1 director. Initially O1 and S1 are busy on other calls; D1 is idle. New C9 arrives requiring operator. Under a strict **lowest-rank-first** policy, if no operator is idle but director is available, do we skip the queue and use D1? The answer depends on the **explicit dispatch policy**, not an assumed OO class model. For this lesson choose **immediate eligible assignment at higher rank** to minimize waiting, with a rank-preference that preserves lower-rank capacity when possible. C9 is assigned to D1 rather than queued. Under an alternative policy that reserves higher ranks for escalated calls, C9 would wait; the two are different valid products.

Now C10 arrives while all staff are busy: queue C10 once with `min_rank=OPERATOR`. O1 becomes idle while S1 is still busy, and C10 atomically leaves the queue and receives assignment `v1→O1`.

| Event | C10 state | Owner / queue | Guard |
| --- | --- | --- | --- |
| Arrival while all busy | waiting | operator queue | one queue membership |
| O1 finishes prior call | assigned | assignment v1→O1 | remove waiting item + claim O1 together |
| O1 cannot resolve C10 | escalating | no active O1 assignment | retire v1 and raise min_rank to supervisor |
| S1 becomes free | assigned | assignment v2→S1 | dispatch only after v1 retired |
| Duplicated O1 completion arrives | assigned | still v2→S1 | reject stale v1 mutation |
| S1 resolves C10 | completed | no active assignment | release S1 exactly once |

An escalation is **not** completion: it changes eligibility and retires the previous assignment while preserving call identity/history. The dispatcher cannot assign a waiting call to O1 *and* S1 because the claim compares the call's version/state to the current owner. A call that becomes unserviceable can wait, but must not retain an active assignment when the prior employee has already been released.

## Completion, queue draining and invalid transitions

Specify commands with stable identities:

```text
dispatch(call_id, expected_call_version)
escalate(call_id, expected_assignment_version, reason)
complete(call_id, expected_assignment_version, result)
employee_available(employee_id, expected_assignment_version)
```

On `complete`, guard `call.state == assigned` and the matching active assignment version. Atomically set completed, close assignment, clear `employee.current_call`, and enqueue a dispatch opportunity. If the same completion arrives twice with the same stable command ID, return the original receipt; if it arrives under a stale version, do not free whichever employee now occupies that slot. Multiple busy/free messages should be treated as observations reconciled against the authoritative Assignment, not unconditional toggles.

After a completion makes an employee available, drain one eligible queued call under the same state guard. For example, director D1 may take a waiting supervisor-ranked call if policy permits; an operator may not. A fairness policy must decide how long waiting calls are selected across rank queues; lowest eligible employee selection **alone** does not prove FIFO fairness under continuous load. The source has no VIP priority, but that does not remove queue starvation/overload risks if high-rank work continuously monopolizes all staff.

The invalid transitions `waiting→completed` without an assignment, `completed→assigned`, and `assigned v2→complete(v1)` must either reject with an explicit error or resolve via an idempotent receipt that refers to a genuinely completed earlier operation. No silent state mutation is permitted.

## Model policy separately from shared lifecycle

Inheritance can be useful if each rank has stable domain-specific behavior. But rank alone is a scalar capability: `Employee.rank` plus an injectable `DispatchPolicy` is usually easier than `Operator.handle` calling `Supervisor.handle` through a chain. Dispatch owns selection; Employee does not mutate other employees or global queues.

Policy alternatives are concrete:
- **Immediate higher-rank fallback:** shorter waits but may consume director capacity before escalations arrive.
- **Reserved specialist capacity:** protect escalations but can leave a director idle while ordinary callers wait.
- **Weighted queues and service levels:** useful for explicit business priorities, but outside this source's no-VIP baseline. Do not smuggle in VIP logic without authorization.

Because dispatch and completion change two or more objects, this is one in-memory **transactional state machine** under one owner/lock. If deployed across workers, the same invariant requires durable conditional transitions and recovery—mere eventual employee-availability updates can overassign. Keep this local lesson focused on responsibility and transition validity, not telephony infrastructure.

## Verification under a concrete workload

In an illustrative five-minute sample of 1,000 valid original calls, 810 receive a staffed connection within 30 seconds, 100 are rejected for capacity, 50 hang up waiting, 30 time out without confirmation and 10 connect late. Connection success by deadline is **810/1000=81%**. A system cannot improve this by counting only assigned calls; record queue age, escalations per call, time spent at each rank, and stale assignment commands. These are scenario assumptions, not industry benchmarks.

Exercise two simultaneous releases, a queued escalation racing with new availability, duplicate completion after a new call starts, staff disconnect, and a call escalated to director when no director is free. Assert: each active call has at most one active assignment, each employee at most one active call, queue and assignment membership are disjoint, completed calls cannot be dispatched, and every rank assignment satisfies required eligibility. When this model is correct, a later network/telephony adapter can deliver events without changing who owns truth.
