# LRU cache as cooperating objects

A cache holds `K1,K2,K3`; a `get(K1)` should make K1 the newest entry. After inserting K4 into a capacity-three cache, which key should disappear? A dictionary alone can find K1 quickly but does not by itself implement **recency ordering** as a separate updateable structure. A linked list alone can reorder nodes cheaply but needs an O(n) search by key. The object design combines the two under an invariant: **every map entry points to exactly one node in the recency list, and every list node is mapped by its key**.

- **M12-L02-LO1:** trace get, update, eviction and zero-capacity operations through a hash map and doubly linked list.
- **M12-L02-LO2:** design explicit class ownership and invariants; compare using hand-built nodes with an ordered container while diagnosing missing back-pointers and accidental fields.

## Define contracts and ownership before implementation

The approved source contract is a local, in-memory query cache with valid inputs; no networking or distributed coherence belongs here. [M06-L03](../../m06/lessons/M06-L03.md) owns cache policy and query-cache routing. Here `Cache` coordinates `Map<Key,Node>` and `RecencyList`; `Node` stores `key, value, prev, next`. The list owns the link/unlink operations and private sentinels; the cache owns capacity, map membership and the sequence of mutations.

```text
Cache.get(key) -> {hit, value}         # hit moves node to MRU
Cache.put(key,value) -> {inserted, evicted_key?}
Cache.remove(key) -> bool
Cache.capacity >= 0
List: head(MRU sentinel) <-> nodes ... <-> tail(LRU sentinel)
```

Sentinels carry no data keys, never appear in the map and make head/tail removal uniform. The core invariant at every public operation boundary is `map.size = list.data_node_count <= capacity`; for each `(k,node)`, node.key=k and node appears **once** between sentinels; `prev.next=node` and `next.prev=node`. A detached node must have `prev=next=null` and must no longer be in the map.

## Trace a collision-free sequence of object mutations

Start with capacity 3 and oldest-to-newest order `[A,B,C]`. A public get of A retrieves map[A] then unlinks and attaches that **same node** after the MRU head. The resulting newest-to-oldest list is `[A,C,B]`; B is now LRU. On `put(D,4)`, allocate a D node at MRU and, because capacity would become four, evict B at tail and remove **map[B]**.

| Call | MRU → LRU | Map keys | Why |
| --- | --- | --- | --- |
| Initial | C,B,A | A,B,C | three entries |
| get(A) | A,C,B | A,B,C | A moved, no duplicate |
| put(D,4) | D,A,C | A,C,D | B evicted |
| put(C,30) | C,D,A | A,C,D | existing node updated/moved; no new entry |
| remove(D) | C,A | A,C | unlink D and map.delete(D) |
| get(B) | C,A | A,C | miss does not change order |

It is a bug to allocate a *new* node on every successful get and leave the old one linked: the list then contains two copies, recency and eviction diverge from the map. It is also a bug to remove the LRU list node but leave its key in the map: a future lookup returns a detached/possibly reused object. **The node carries its key** specifically so eviction can remove the correct mapping in expected O(1); storing only value loses that back-reference unless another index exists.

### Implement link primitives as the only mutators

For node N currently in the list, `unlink(N)` writes `N.prev.next = N.next`, `N.next.prev = N.prev`, then clears N's links. `insert_after_head(N)` first requires N detached, sets N.prev=head and N.next=head.next, updates both neighboring links. `move_to_front(N)` calls both operations. These methods own pointer consistency; `Cache` never reaches into accidental attributes like `node.previous_key` that are absent from the class contract.

On new put, look up key first. If present, update its value and move it to MRU; capacity and node count remain unchanged. If absent and capacity zero, return without creating or retaining a node. If positive, insert node and mapping, then remove the LRU while over capacity. The order of internal mutations is protected by a single ownership/lock boundary so a concurrent reader never sees a map node detached from its list.

## Explain the zero-capacity and exception boundaries

At `capacity=0`, every `put` retains nothing and every `get` misses. It must not try to unlink a sentinel or enter a loop evicting a nonexistent data node. A negative capacity is invalid at constructor time. If value allocation or a user-defined callback can throw, do all validation before changing shared invariants, or use rollback/transaction-like guards: never expose half-updated map/list pointers to callers.

A local cache can be intentionally best-effort and single-thread-owned. If multiple threads access it, all operations that update recency (including `get`) are **writes**; a read lock that permits concurrent pointer updates is unsafe. Options include a coarse mutex for correctness, sharded caches with local locks for throughput, or a runtime-provided concurrent bounded cache. Define actual API behavior before optimizing.

## Compare implementations by pressure, not style

A composed map+doubly-linked-list gives expected O(1) lookup/move/eviction under normal hashing. It costs one node plus map entry per key, extra references, and tricky pointer invariants. An ordered map may implement efficient recency moves for you. Python's standard `OrderedDict` documents `move_to_end` and `popitem(last=False)`, which can express LRU without manual nodes [Python collections OrderedDict](https://docs.python.org/3/library/collections.html#ordereddict-objects). That is a language-specific API choice, not evidence that any `dict` has identical recency semantics.

LRU is not TTL: an entry frequently accessed can stay forever without expiry; a time-expired entry might be the most recently used but must still be treated as expired under a separate freshness policy. Nor does LRU solve multi-node key routing or stale invalidation (see M06-L03 and M11-L09). Use this lesson's design where demonstrating local object collaboration matters; use a mature library where production correctness, concurrency and policy breadth dominate.

Test every public operation against a simple reference model of unique key ordering. Include capacity 0 and 1, update-in-place, missing remove, double unlink, remove-tail then update another key, repeated get, randomized operation sequences and concurrent mutation under the declared lock. After every action assert both map-to-list and list-to-map bijection; a successful returned value alone is not proof the data structure remains safe.
