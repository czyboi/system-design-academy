# M12-L02 assessment — LRU object collaboration

## Knowledge checks

**Q1 (LO1).** Capacity 3, MRU→LRU is C,B,A. get(A), then put(D,4). Which item is evicted?

**Answer.** get(A) makes order A,C,B, so put(D) evicts B and yields D,A,C. A hit updates recency; it does not add another item.

**Q2 (LO1).** After put(C,30), is there a new C node? What is the new ordering?

**Answer.** No. The existing C node changes value and moves to MRU, producing C,D,A; the cache still has three unique keys.

**Q3 (LO1).** Capacity is zero. What must put(X,1) and get(X) do?

**Answer.** Put retains nothing; get misses. Do not evict a sentinel or manufacture a data node.

**Q4 (LO2).** Why must an evictable list node retain its key as well as its value?

**Answer.** After removing the LRU tail, the cache must remove the corresponding map entry in expected O(1). Without key/other reverse index it cannot identify mapping safely by node.

**Q5 (LO2).** A linked node N has neighbors P,Q. What pointer operations safely unlink N?

**Answer.** P.next = Q; Q.prev = P; then set N.prev=N.next=null. Map removal is the cache's responsibility at the corresponding public operation boundary.

**Q6 (LO2).** Why is concurrent get unsafe under a read-only lock?

**Answer.** A cache hit changes recency links, so get performs writes. Parallel pointer manipulations can corrupt list invariants unless serialized/otherwise made safe.

## EX-1 — Trace and repair a local query LRU

**Scenario.** A capacity-two LRU stores key/value pairs with a hashmap and doubly linked list with head/tail sentinels. A faulty implementation stores only value in nodes, creates a second node on every hit, and removes a tail node without deleting the map entry. Operations: put(A,1), put(B,2), get(A), put(C,3), put(A,10), remove(C), get(B). Another tenant configures capacity zero.

**Task.** Give class interfaces/responsibilities, expected MRU→LRU order after each call, locate the three implementation defects, describe link/unlink operations, handle zero capacity and compare a standard ordered-map implementation. State a concurrency contract and invariant-based test plan.

### Reference solution

Expected sequence: [A], [B,A], [A,B], [C,A] (B evicted), [A,C] (A updated), [A] (C removed), [A] (B misses). Map keys always match list nodes, counts never exceed two; capacity zero retains no entries. Include node.key and map.delete(node.key) on eviction; move existing hit node instead of duplicating; link/unlink through list-owned primitives. A coarse lock is acceptable for concurrent access because get changes recency, while an explicitly single-writer cache is also correct under its contract. Python OrderedDict-style move_to_end/pop oldest can replace hand-written nodes; explain the API semantics rather than assuming any map offers them.
