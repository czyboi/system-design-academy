# M12-L06 assessment — Chat domain and relationships

## Knowledge checks

**Q1 (LO1).** Alice sent FR-9 and Bob rejected it at version2. Alice sends approve(FR-9, expected_version1). Is friendship created?

**Answer.** No. Approval requires authorized recipient and current pending state. FR-9 is already rejected at version2; a stale/unauthorized attempt must not create friendship.

**Q2 (LO1).** What are distinct owners for user profile, friend request, conversation membership and message history?

**Answer.** User owns profile/deletion, Relationship owns pending/approved/rejected friendship transitions, Conversation owns active membership/role/version and Message owns accepted immutable message history/sequence under authorization. One User should not directly mutate all aggregates.

**Q3 (LO1).** Does deleting a user guarantee historical group messages vanish?

**Answer.** No. Immediate authorization revocation and deferred group cleanup are separate from history retention/redaction/erasure policy. Define the latter explicitly and recoverably.

**Q4 (LO2).** Cara leaves G7 at membership version13, then sends using stale v12 list. Does client v12 authorize sending?

**Answer.** No. The authoritative active membership at message acceptance decides. A supplied v12 list is not an access grant.

**Q5 (LO2).** David has a pending group invitation but has not accepted. Can he send a group message?

**Answer.** Not under the lesson's policy; pending invite is not active membership. Join commits versioned membership before send.

**Q6 (LO2).** What is wrong with a simple read of current membership followed by an unrelated later message write?

**Answer.** Membership may be removed between check and write. Enforce the declared no-post-removal boundary at the write's authoritative serialization point or honestly state a weaker consistency contract.

## EX-1 — Membership under stale clients

**Scenario.** Text-only chat has active users Alice, Bob and Cara, rejected friend request FR-9, group G7 with members A/B/C at v12 and pending invite for David. Cara leaves at v13. David joins at v14. Cara's stale device sends M44 after removal; David sends M45 after join; Alice retries an earlier accepted message after lost response. Bob also removes Alice as a friend while a private-chat send is in flight.

**Task.** Design User, FriendshipRequest, Friendship, Conversation, Membership and Message responsibilities; show legal transition table, authorization and message IDs/receipt; trace FR-9, G7 v12–v14 and direct-chat race; specify history access policy and deletion/retry behavior. Give five falsification tests and success denominator.

### Reference solution

FR-9 rejected remains terminal; a stale approval cannot create friendship and a same-ID retry replays receipt rather than create another request. Cara at v13 is inactive and M44 rejects; David at v14 is active and M45 may commit with immutable ID, sender and sequence. Alice's identical accepted message retry returns prior receipt with no duplicate. Direct send after confirmed friend removal is denied under the chosen policy; the acceptance write must check the current friend relation at a coherent boundary. Prior in-flight authorization must have an explicit ordering rule. Group history visibility to new members is configured (e.g. from join sequence forward), not implied. Deleted users cannot authorize new commands; cleanup of dependent aggregates and historical data follows explicit recoverable policy. Test stale approval, join/send race, leave/send race, same message ID changed payload, deletion with outstanding sends, and history read after membership removal.
