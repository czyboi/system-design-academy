# M12-L01 assessment — Hash-table contracts

## Knowledge checks

**Q1 (LO1).** A four-bucket table maps integers by floor-mod 4. Insert 1,5,9 at the head of a chain. What is bucket 1, and why does one colliding key not replace another?

**Answer.** 9→5→1. Collision selects a shared bucket; equality selects the actual key within that chain. Replacing the bucket wholesale loses distinct keys.

**Q2 (LO1).** Starting with 9→5→1, update 5 and then remove it. What links and size changes occur?

**Answer.** Updating changes only 5's value and leaves size 3. Removing middle 5 sets 9.next to 1, detaches 5 and decrements size to 2 once; 9 and 1 remain accessible.

**Q3 (LO1).** How should a caller distinguish a stored null from an absent key?

**Answer.** Return a found flag or optional result with explicit presence. A raw null cannot distinguish them under the selected contract.

**Q4 (LO2).** Three entries fill 4 buckets at alpha=.75. What happens to key 13 when max_load=.75 and the table doubles for new distinct insertion?

**Answer.** It expands to 8 before inserting the fourth entry; rehash keys 1,5,9 and 13 with modulus 8. 1 and 9 map to index1, while 5 and 13 map to index5. The table retains four unique values and size 4.

**Q5 (LO2).** Does bounded average load guarantee O(1) worst-case lookup?

**Answer.** No. A pathological collision chain contains n entries, yielding O(n) search. Expected O(1) depends on distribution assumptions; resizing cannot fix equal bucket hashes on its own.

**Q6 (LO2).** Why might a balanced ordered tree be preferable to a hash table?

**Answer.** Sorted range scans and predecessor/successor operations require order; hash buckets do not preserve key ordering. A balanced tree offers O(log n) typical worst-case operations under balancing invariants at additional structural cost.

## EX-1 — Implement the contract, not the syntax

**Scenario.** An in-memory integer-key map uses separate chaining, capacity 4, floor-mod indexing, max load .75, inserts at head, and an explicit found flag on lookup. Perform put(1,A), put(5,B), put(9,C), put(5,B2), remove(5), put(13,D), remove(42), then put(17,E). A second engineer proposes replacing the head on every collision and claiming O(1) worst case.

**Task.** Trace buckets and size after each operation; specify node, map and API responsibilities, including head/middle/tail deletion and missing-vs-null. Explain if/when resize occurs, list old/new indices, challenge the engineer's performance claim, compare a balanced ordered alternative, and give a mutation/concurrency test plan.

### Reference solution

The first three insertions produce bucket1: 9:C→5:B→1:A, size3. Updating 5 yields B2 but does not change size. Removing 5 produces 9:C→1:A, size2. Inserting 13 makes size3 and chain13:D→9:C→1:A at capacity4. Removing 42 returns false, no change. Inserting 17 would make size4 and exceed 0.75; resize to capacity8 first, rehash existing 13,9,1, then insert17. At modulus8, 1,9,17 share index1 and 13 belongs in index5. No distinct key may be lost and size becomes4. If the implementation instead resizes on the *first* fourth insertion, the trace must honor that actual step; in this sequence that occurs only at key17.

Explicitly verify that key5 stays absent, values for 1/9/13/17 survive and negative integer index is nonnegative. Bucket replacement fails this invariant. Worst-case key lookup is O(n) under a long collision chain, not O(1); key ordering needs a tree or separate ordered structure. Under concurrency, synchronize mutations including resize or declare single-writer ownership.
