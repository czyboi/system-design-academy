# M12-L03 assessment — Parking-lot objects

## Knowledge checks

**Q1 (LO1).** A row has seven large spots; 0 and 6 are occupied. Can a bus needing five consecutive large spots park?

**Answer.** Yes, indices 1–5 form one contiguous run on the same row. Reserve/commit all five under one allocation ID and decrement the free-large count by five.

**Q2 (LO1).** A level has five free large spots in runs of 2,2,1. Is total free count sufficient?

**Answer.** No. Five *adjacent* large spots on one row are required; total free count is a necessary filter, not a proof of a valid run.

**Q3 (LO1).** On bus release, why must the caller use allocation ID rather than the first parking spot?

**Answer.** Allocation stores all five owned spots and prevents leaving ghosts; a stale release must not free a new vehicle's occupancy if spot ownership has changed.

**Q4 (LO2).** Two buses discover the same free run concurrently. What must be guarded?

**Answer.** Revalidate compatibility and availability and commit the whole five-spot set atomically under serialization/lock or a transactionally coherent conditional allocation. Locking only the candidate search is insufficient.

**Q5 (LO2).** A new EV requirement means an electric car needs charging capability. Where should this live?

**Answer.** In a compatibility/fit policy over spot capabilities; keep Level responsible for candidate selection/commit and Allocation for vehicle/spot ownership. Avoid subtype explosion.

**Q6 (LO2).** What is the cost of a maintained interval index for free contiguous spots?

**Answer.** Faster searches can come at consistency/update complexity: every claim and release must update the index with the authoritative spot state. A stale index can propose occupied spans.

## EX-1 — Extend parking without partial ownership

**Scenario.** A two-level lot has motorcycle/compact/large spots, cars, motorcycles and buses. A bus needs five consecutive large spots on one row. Level A has large free runs 2+3; Level B has a run [2,3,4,5,6] of five. An electric car arrives with a charging-only requirement. During a bus search another car can park; after bus release a delayed duplicate release can arrive.

**Task.** Draw classes and ownership, specify allocation/release APIs and row-local candidate search, trace bus placement and an unsuccessful second bus, add charging fit rule with minimal change, and prove no partial occupancy or double-free under concurrency. Compare scanning with a maintained run index. Define tests and success population.

### Reference solution

Lot delegates to each Level's atomic candidate-and-commit method. Level A cannot fit the bus despite 5 free large spots; Level B can commit [2…6] under one Allocation receipt. A second bus cannot reuse the run until release. After release, all five spots are cleared and the free count restored in the same guarded transition. Duplicate `release(allocation_id)` must not double-increment counts or free newly reassigned spots. Charging is a spot capability tested by a FitPolicy; the atomic spot ownership transition remains unchanged. O(N) scan is a correct initial baseline; a run index requires update on each claim and release. Test two concurrent buses, partial failure rollback, stale release after reuse, cross-row temptation, incompatible charging space, and count conservation.
