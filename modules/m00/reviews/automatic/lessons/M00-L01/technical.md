## Technical findings

- **M00-L01-T1 · minor · open.** In lesson line 29 and evidence row R4, “manually acknowledged delivery” can imply that the broker accepted the acknowledgement. The worker and Q3 scenarios correctly place the crash after the receipt commit and before the broker receives the acknowledgement. Use “unacknowledged delivery in manual acknowledgement mode” and say that the broker requeues it on channel or connection closure. [RabbitMQ 4.2, When Consumers Fail or Lose Connection](https://www.rabbitmq.com/docs/4.2/confirms#automatic-requeueing)
- **M00-L01-T2 · minor · open.** Evidence row R1 says automatic retry of a non-idempotent method “requires” one of two conditions. RFC 9110 gives clients a SHOULD NOT recommendation with exceptions for known idempotent semantics or known non-application. Proxies have a separate MUST NOT rule. In lesson line 26, tie the stable key and application contract explicitly to the charge request with an unknown result. The existing example uses a fresh transaction and a business invariant, which remain appropriate in that scenario. [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)
- **M00-L01-T3 · minor · open.** Lesson line 27 presents commit durability without naming the configuration. The transaction example assumes a locally durable commit. State that it uses PostgreSQL 18's default synchronous commit, because an asynchronously acknowledged transaction can still be lost before WAL flush. The separate-attempt reasoning and Q1 remain valid under the example's durable-commit assumption. [PostgreSQL 18 §3.4, Transactions](https://www.postgresql.org/docs/18/tutorial-transactions.html) · [PostgreSQL 18 §28.4, Asynchronous Commit](https://www.postgresql.org/docs/18/wal-async-commit.html)

The charge trace separates response loss from rollback and transaction atomicity from the application invariant that covers two attempts. PostgreSQL unique constraints can enforce the key for modeled non-null request IDs. The receipt example scopes duplicate prevention to an atomic database effect and gives external effects their own contract. Q1–Q3 follow the same failure boundaries. [PostgreSQL 18 §5.5.3, Unique Constraints](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS) · [RabbitMQ 4.2, Data Safety on the Consumer Side](https://www.rabbitmq.com/docs/4.2/reliability#consumer)

The study-route guidance limits the research claims to the experimental memory tasks and treats the schedule as an instructional choice. The Netflix case accurately identifies video-play measures in a simulated regional failure exercise in 2015. No executable code or performance claims occur in the pair. [Karpicke and Roediger, Experiments 1–2](https://learninglab.psych.purdue.edu/downloads/2007/2007_Karpicke_Roediger_JML.pdf) · [Cepeda et al., abstract](https://www.evullab.org/pdf/CepedaVulRohrerWixtedPashler-PS-2008.pdf) · [Netflix, Chaos Kong and footnote 1](https://netflixtechblog.com/chaos-engineering-upgraded-878d341f15fa)
