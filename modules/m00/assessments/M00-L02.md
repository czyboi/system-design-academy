# M00-L02 companion assessment

## Practical exercise

EX-1. A team shares inspection reports through links. Owners create and revoke links. Recipients read reports. A read begun after a successful revoke response must be denied. Assume 20 reads and 2 link changes per second at peak, and a store whose updates and checks of the same link state share a linearizable order.

Produce a short design record containing the actors, use cases, one assumption, one non-goal, the create/read/revoke paths, and two architecture choices. A new requirement says reads must continue after one application host fails. Select a candidate and identify the checks needed to validate it. Include a representative load-test plan and one unresolved risk. Specify a fixed host-loss observation window, an original valid-read denominator, a client send-to-full-body deadline and a timely-success threshold. Explain how rejected, failed, timed-out and late original reads count. Describe survivor capacity, successful-read latency and revoked-link probes separately. You may choose justified targets.

## Knowledge checks

### Q1

Which part of the stated service scope is an assumption that needs confirmation?

Answer: The peak estimate of 20 link reads and 2 link changes per second.

Explanation: It is a provisional workload input. The team should compare it with observed or otherwise justified demand.

### Q2

Trace the status decision for a read begun after a successful revoke response under the example's store contract.

Answer: The application checks the authoritative status operation and denies the read when it sees the revoked state.

Explanation: The assumed linearizable operation places the completed revoke before the later read. The contract is an explicit store assumption.

### Q3

The service has an application and an authoritative store. What does each do when an owner creates a link?

Answer: The application receives and authorizes the owner's request, then writes the link association and active status in the store.

Explanation: The application implements the operation and the store retains the state used by later reads.

### Q4

What new requirement makes a design with one application host unable to satisfy the requirement during that host's outage?

Answer: Reads must continue when that application host fails.

Explanation: During the host outage, no application host remains to serve those reads. A candidate with multiple hosts needs its own routing, capacity, and failure checks.

### Q5

A load test indicates long waits for store connections while application CPU is low. What should the team do before adding hosts?

Answer: Profile connection-pool waits and store behavior, change a demonstrated constraint, and repeat the same test.

Explanation: The signal points to the status-store path but does not by itself establish the bottleneck or the effect of more hosts.

### Q6

What should a time-bounded review communicate after comparing the one-host and two-host options?

Answer: The choice, the requirement it addresses, its costs, remaining risks, and the evidence needed to revisit it.

Explanation: Those elements connect the proposed architecture to its constraints and make the uncertain parts testable.

## Answer key / rubric

A sample design gives the owner create and revoke operations and the recipient a read operation. It records the peak as an assumption and report editing as a non-goal. The application writes active status on create, checks authoritative status on read, and commits revoked status before confirming revocation. Two application hosts are a candidate for surviving one host failure. Validate routing around a failed host, surviving capacity at the specified peak, continued access to the store, and the store's status semantics.

For a hypothetical acceptance test, offer 20 original valid reads per second for 10 minutes beginning when a host is removed. The denominator is all 12,000 original reads sent in that window, including requests the survivor never receives. Set a target of at least 99% receiving the full requested report within two seconds of the original client send. Count rejected, failed, timed-out and late reads as unsuccessful, including late retry completions. For example, 11,760 timely responses give 98%, which fails the target. Test the stated read/change mix and representative payloads and distribution. Measure survivor capacity and successful-read latency separately, and count deliberately revoked-link probes separately to check denial after confirmation. A remaining risk is shared-store failure. These are test inputs, with no test performed here.

Score EX-1 out of 5 points. Award one point each for scope and assumptions, correct operation paths and revoke ordering, comparison and candidate choice, a representative load and failure test with an explicit window, original-operation denominator, end-to-end deadline, threshold and treatment of unsuccessful reads, plus separate survivor capacity, successful-read latency and revoked-probe checks, and an unresolved risk. Accept a different architecture when it explicitly meets the stated constraints and explains its evidence and trade-offs.
