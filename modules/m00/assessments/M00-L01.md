# M00-L01 companion assessment

## Practical exercise

EX-1. An engineer has a short study period. They correctly explain an HTTP timeout and a hash collision, but believe a lost response proves that the first database transaction rolled back. They are preparing to discuss a service that receives requests and queues receipts.

Produce a study route that identifies the blocking gap, orders the first study actions, includes some varied practice and a later retrieval attempt, and states one way to evaluate a historical architecture's failure evidence. Explain one cost of your route. Assume the service uses a stable request key.

## Knowledge checks

### Q1

A database transaction commits a charge and the response is lost. The client retries. What information remains unknown to the client?

Answer: Whether the first attempt took effect, unless the application exposes a way to retrieve that result.

Explanation: Losing the response can occur after commit. A stable request key and a durable application rule can connect the retry to the original result.

### Q2

In a chained hash table, two different request keys select the same bucket. How does lookup distinguish them, and what scope does an in-memory table have?

Answer: It compares candidate keys in the bucket. The table is local to the process that holds it.

Explanation: A shared bucket is a collision. Another process or a restart does not automatically share that memory.

### Q3

A RabbitMQ 4.2 worker commits a receipt record and crashes before the broker receives its manual acknowledgement. What can happen, and what application property limits duplicate records?

Answer: The delivery can be requeued. A durable receipt key enforced atomically with the write can prevent a second record.

Explanation: The first durable effect precedes the failed acknowledgement. A later delivery may execute the worker again.

### Q4

An engineer understands the request trace but cannot explain transaction commit and rollback. Which topic should their next study block target?

Answer: Transaction commit, rollback, and the relationship between separate attempts.

Explanation: That gap prevents the engineer from reasoning about whether a retry repeats a committed effect.

### Q5

Two engineers have similar prerequisites. One has a short period and the other a long period. How can their practice plans differ while each keeps a broad first pass?

Answer: The first can repair a blocking gap and solve some varied cases. The second can deepen decisions and failure analysis and solve most selected cases across workloads.

Explanation: The routes trade case variety and depth against the time available. Both use feedback on actual reasoning.

### Q6

An architecture diagram labels a service as resilient. Name two pieces of evidence to seek before applying its design elsewhere.

Answer: The failure scenario and a user-relevant observation from that scenario, along with the workload or constraints.

Explanation: The scenario and observation explain which behavior was measured and under what conditions.

### Q7

During a first pass over an architecture, a team sees that its database is slow while its application instances have spare capacity. Compare adding application clones with investigating the database path. What observation would guide the next study or design step?

Answer: Adding clones shares application request handling but leaves the shared database on the path. Profile the database path to identify the source of the delay, then study or test a change aimed at that constraint. For a read-heavy bottleneck, investigate whether a cache could reduce repeated reads and what freshness the service requires.

Explanation: A mechanism helps when it changes work at the constrained part of the path. An asynchronous worker may move suitable work out of the request, but completion and failure still need tracking. Evidence about the workload and waits guides which option to examine.

## Answer key / rubric

The engineer first traces rollback before commit and then commit followed by a lost response. They check how a durable uniqueness rule treats the same request key in a later transaction. They make a broad pass through the request and queue path, solve some cases with changed failure ordering, and later reconstruct the trace before consulting the solution. For a historical architecture, they identify the failure exercised and the user-facing signal observed. The route leaves less time for an extensive range of cases.

Score EX-1 out of 4 points. Award one point each for identifying the transaction gap, a targeted repair with a correct failure trace, varied practice plus later retrieval, and a historical-evidence criterion with a stated time trade-off. Accept another defensible sequence that covers the same elements.
