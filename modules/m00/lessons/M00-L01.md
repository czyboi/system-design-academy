# How to learn and check readiness

## Learning outcomes

- M00-L01-LO1: Trace the HTTP, transaction, hash lookup, and queue-consumer mechanisms in a repeated-request scenario.
- M00-L01-LO2: Choose and defend a study route and a way to evaluate an architecture using observed gaps, available time, and failure evidence.

## Problem and motivation

A workshop service receives a request to charge a registration fee. The client times out and retries. A diagram containing an API, a database, and a queue leaves open a consequential question. Could the participant be charged twice? Trace each boundary and write what is known before choosing more infrastructure. Assume the charge in this example is a database record and the service uses a stable request key. An external payment provider introduces its own contract and needs separate analysis.

## Core concepts and mechanisms

1. **HTTP request.** The client sends a request to the service, which processes it and sends a response. A connection can fail after the operation takes effect and before the client receives that response. The retry therefore needs an application contract for identifying the same intended operation. HTTP method idempotence concerns the intended effect of repeated identical requests. RFC 9110 recommends care when automatically retrying non-idempotent methods. [IETF, RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)
2. **SQL transaction.** Suppose the first attempt writes the charge and its request-key result in one PostgreSQL 18 transaction. A rollback cancels those updates. A commit makes them durable as a unit within the database. If the response is then lost, a second transaction can perform another charge unless a durable uniqueness rule and the application handling that rule make the request key identify the original result. A transaction's atomicity applies to its own changes. The relationship between separate attempts is an application design decision. [PostgreSQL 18, §3.4 Transactions](https://www.postgresql.org/docs/18/tutorial-transactions.html)
3. **Hash lookup.** For an abstract chained hash table, the hash selects a bucket and lookup compares candidate keys in that bucket. Different keys can share a bucket, so equality checks resolve collisions. Good hash distribution supports expected fast lookup. A lookup in one process's memory cannot by itself coordinate concurrent requests reaching another process or survive a restart. [Sedgewick and Wayne, Algorithms, §3.4 lecture](https://algs4.cs.princeton.edu/lectures/keynote/34HashTables-2x2.pdf)
4. **Queue consumer.** Assume a worker writes a receipt record and then acknowledges its delivery. If the worker crashes after committing but before the broker receives its acknowledgement, RabbitMQ 4.2 can requeue that manually acknowledged delivery. A durable receipt key and an atomic check-and-write can prevent another receipt record when the message is processed again. This is a modeled application policy, and any external side effect needs its own duplicate-handling contract. [RabbitMQ 4.2, Consumer Acknowledgements, When Consumers Fail or Lose Connection](https://www.rabbitmq.com/docs/4.2/confirms#automatic-requeueing)

Each step isolates a prerequisite. If the retry is unclear because commit and rollback are confused, study transactions first. If the transaction trace is sound but collision handling is unclear, repair hash lookup instead. Record the exact point where the explanation stops.

## Choose a study route

Use a breadth-first pass to build a map of a request, stored state, and failure boundaries. A first pass through the [Harvard 2019 scalability lecture](https://cs50.harvard.edu/summer/web/2019/lectures/10/) can supply vocabulary and candidate questions. Pause to sketch a flow and name one constraint and failure, then check the material. Follow with a written architecture case and revisit the specific components that determine its behavior. Later practice should change a workload or failure and require a new decision.

| Available time and observed readiness | Route | Cost and decision |
|---|---|---|
| Short time, a prerequisite gap | Repair the blocking gap, make a broad first pass, and solve **some** varied cases. | Fewer cases limit exposure to unfamiliar situations. Choose cases that exercise the repaired boundary. |
| Medium time, prerequisites mostly sound | Make a broad pass, deepen the weakest areas, and solve **many** varied cases with feedback. | More feedback reveals recurring mistakes, while deep work on every technology would reduce variety. |
| Long time, experienced with the basics | Cover the map, investigate decisions and failure modes in depth, and solve **most** of the selected practice cases across several workloads. | Broad practice costs time. Skip repeated introductory repair once a trace demonstrates that the prerequisite is sound. |

These are planning options, rather than measured completion times. Deliberate practice targets a specific gap, produces an answer before reading the explanation, and uses feedback to revise it. Return later and reconstruct the trace from memory, then vary the failure. Retrieval and spacing improved later retention in the cited memory experiments. Their results do not specify an optimal schedule for system-design transfer. [Karpicke and Roediger, 2007, Experiments 1–2](https://learninglab.psych.purdue.edu/downloads/2007/2007_Karpicke_Roediger_JML.pdf) · [Cepeda et al., 2008, abstract](https://pubmed.ncbi.nlm.nih.gov/19076480/#abstract)

## Worked example and historical architecture

An engineer correctly traces the HTTP timeout and hash lookup but assumes that a timed-out client means the first database transaction rolled back. Give transaction repair priority. First trace a rollback before commit, then trace a successful commit followed by a lost response. Add the stable request key to both attempts and explain how a durable uniqueness rule lets the second transaction return the prior result. After feedback, revisit the trace later with a worker crash between receipt commit and acknowledgement. A learner with little time could perform those two changed traces and one unrelated case. With more time, they can repeat the method across a larger mix of failures and constraints.

Read an architecture diagram with four annotations at each important boundary. State the workload it serves, the decision made, what failure changes the behavior, and the evidence offered for the claimed outcome. For historical context, Netflix described a simulated regional failover and used aggregate and regional video-play observations to assess its effect. The report illustrates how an operational signal connects to a failure decision. Its observations describe that exercise in 2015 and need separate evidence before being applied to another deployment. [Netflix Technology Blog, 2015, Chaos Kong and footnote 1](https://netflixtechblog.com/chaos-engineering-upgraded-878d341f15fa)

## Trade-offs and failure modes

Repair a prerequisite when it prevents a causal trace. Move on once the learner can explain the boundary and apply it to a changed failure. Spend the next study block on the highest-impact uncertainty visible in a design decision. A diagram can guide questions, while its labels alone leave capacity, correctness, and failure behavior to be established.
