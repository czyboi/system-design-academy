# From requirements to a defensible design

## Learning outcomes

- M00-L02-LO1: Trace requirements through the initial components, interfaces, and read and write paths of a link-sharing service.
- M00-L02-LO2: Choose and defend an architecture change using explicit constraints, estimates, failure behavior, and evidence.

## Problem and motivation

A team needs to share laboratory inspection reports. An early diagram places a cache in front of a database, but nobody has said when a revoked link must stop working. That missing requirement changes which data the service must check on a read. Start with the user-visible behavior and carry it through the system before deciding how to scale.

## Core concepts and mechanisms

### Frame the design

Identify actors, operations, constraints, assumptions, and non-goals. An actor is a person or external system using the service. A use case names an action and its result. A constraint is a required condition, such as a deadline or failure behavior. An assumption is a provisional input that needs confirmation. A non-goal bounds the current design. NASA's systems engineering guidance uses stakeholder needs, assumptions, interfaces, and constraints to derive technical requirements. [NASA Systems Engineering Handbook, SP-2016-6105 Rev. 2, §§4.1–4.2](https://www.nasa.gov/reference/4-0-system-design-processes/)

For the example, the report owner creates and revokes links. A recipient opens a link to read a report. Assume only owners can create or revoke their links. A confirmed constraint is that a read begun after a successful revoke response must be denied. A working assumption is a peak of 20 link reads and 2 link changes per second. We must validate the traffic estimate. Editing reports and searching their contents are non-goals for this design.

### Draw the paths and choose a deep dive

Start with a client, an application service, and an authoritative store holding report content and link status. The owner sends a create request to the application, which writes an active link record. A recipient sends a read request carrying a link identifier. The application checks the link status in the store and, when permitted, returns the report. A revoke request changes that status and returns success after the write commits. HTTP GET requests a representation and POST asks the target resource to process submitted data according to its semantics. The endpoint shapes and authorization policy here are design choices. [IETF, RFC 9110 §§9.3.1 and 9.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.1)

The revoke constraint warrants a focused deep dive. Assume the authoritative store offers a linearizable status operation and the application performs that check for every read. For a revoke that completes before a later read starts, the check observes the revoked state and the application denies the read. A response already in flight when revocation completes needs its own policy. A replica or cache that may return stale status needs a mechanism that meets the same requirement before it can replace the authoritative check. This is an abstract store contract, and the selected product and deployment must be checked against it.

### Estimate, measure, and revise

Use the provisional peak to size a test and state the response target and error criteria with it. A useful test includes the request mix, payload sizes, key distribution, duration, and failure conditions. Measure traffic, successful response latency, errors, and resource saturation. Profile the constrained path to distinguish, for example, application CPU from database waits. Google describes using load tests for capacity planning and these operational signals for diagnosis. [Google, Site Reliability Engineering, Capacity Planning](https://sre.google/sre-book/service-best-practices/#capacity-planning) · [The Four Golden Signals](https://sre.google/sre-book/monitoring-distributed-systems/#the-four-golden-signals)

Change one identified bottleneck, rerun the same workload and failure criteria, and compare the results. The estimate chooses what to test. The test supports a capacity decision only for the tested setup and workload. Future growth and a different mix need another evaluation.

## Worked example

Start with one application host and one store. For an illustrative request, the owner creates link L7 for report R4; the application records the association and active status. A reader requests L7, the application checks active status, and the store returns R4 for the response. The owner then revokes L7. After the successful revoke response, a new read checks the status and is denied. This is a design trace using the stated linearizable-status assumption, rather than a tested implementation.

Compare two alternatives against the same requirement:

| Option | Decision and consequence |
|---|---|
| One application host, authoritative status check | Fewer moving parts for the estimated workload. The host is a single point of failure, and recovery time is unknown until tested. |
| Two application hosts, shared authoritative status check | Either host can serve requests if routing, store access, and remaining capacity work. The store and routing path still need their own availability analysis, and the extra host adds operational cost. |

If stakeholders add a requirement that reads continue when one application host fails, the first option cannot meet that requirement during that host's outage. The second is a candidate that needs a host-failure test and enough capacity on the survivor. The new condition changes the design choice. The original estimated peak alone does not establish which option meets it.

For a hypothetical load test, suppose the application spends most request time waiting for status-store connections while application CPU remains low. That observation motivates profiling pool waits and store behavior. If the profile identifies an undersized connection pool and the store has headroom, adjust that pool and repeat the test. A different profile may call for a different change. These observations and outcomes are examples for reasoning, with no test performed here.

## Trade-offs and failure modes

An authoritative check supports the stated revocation contract but puts store availability and latency on the read path. Caching report content may reduce content retrieval work, while the status decision still needs the required freshness. Adding application hosts can reduce exposure to one host failure, but a shared store or routing failure can still stop reads. Unknown recovery time, real traffic peaks, authorization boundaries, and store semantics belong in the decision record and test plan.

## Time-bounded design review

In a 20-minute review, spend five minutes confirming actors, use cases, constraints, and non-goals. Use five minutes to walk the read and write paths, five to inspect the revocation and host-failure decisions, and five to compare alternatives and agree on the next measurement. This timebox is a planning example. Close with the chosen option, the requirement it addresses, costs, unresolved risks, and evidence needed to revisit it. Decision criteria should distinguish mandatory constraints from preferences and make uncertainty visible. [NASA Systems Engineering Handbook, SP-2016-6105 Rev. 2, §6.8 Decision Analysis](https://www.nasa.gov/reference/6-8-decision-analysis/)
