# Companion assessment for M04-L05

## Practical exercise

**EX-1.** A merchant endpoint returns the most recent 20 invoices and attaches adjustment counts that do not change order or eligibility. Both variants include invoices with zero adjustments. A hypothetical baseline plan runs an inner lookup with an average of two emitted rows per loop over 3,000 invoices. A candidate plan limits first and runs the lookup 20 times. For those 20 newest invoices, assume its lookup independently averages three emitted rows per loop. In a ten-minute test, there are 1,000 original valid list requests per variant. The baseline returns 970 correct responses within 250 ms of arrival. The candidate returns 985 on time, rejects five, times out five and returns five late. The target is 99% within 250 ms, with retries counted under the original request. The candidate also increases write WAL in the model.

Compare the plan work and timely success. Propose an index and preserve output semantics for invoices with zero adjustments. Give one schema change and explain what to verify. Compare tuning with replicas and sharding for this diagnosis, and describe a repeatable test before rollout.

## Knowledge checks

### Q1

What does `actual rows=2 loops=3000` imply about output from that node?

**Answer.** About 6,000 emitted rows. The per-loop value is an average, and this is not necessarily the number of rows scanned.

### Q2

Why can the endpoint limit invoice headers before enriching with adjustment counts?

**Answer.** The counts do not affect eligibility or ordering. Retain zero-count rows and order by the same keys.

### Q3

What does planner cost say about elapsed milliseconds?

**Answer.** It is an internal estimate in planner cost units. Use measured execution and request telemetry for time.

### Q4

Would date partitioning help a query filtering only by merchant ID?

**Answer.** It cannot prune on a date condition the query does not provide. It may still touch many partitions.

### Q5

What can an added composite index cost the write path?

**Answer.** Extra maintenance, WAL and memory or storage. Measure it with representative write traffic.

### Q6

Can the team use MySQL 5.7 query cache settings on MySQL 8.0?

**Answer.** The server feature was removed in 8.0. An application cache has separate keys and invalidation semantics.

## Sample solution and rubric

The baseline inner node emits about 6,000 rows and the candidate about 60, using each population's stated average. These node outputs and loop counts describe part of the plans. They do not establish total work or latency without additional observations. Start with a merchant-leading index ordered by descending time and invoice ID, and retain an invoice-leading adjustment index. Use a left join and count non-null adjustment IDs, or an equivalent bounded lookup, to preserve zero counts. Repeat the time and invoice-ID ordering in the outer enriched query. If adding a non-null merchant key, backfill and verify existing records before enforcing it. Measure new index and constraint impact under the same load.

Timely success changes from 97% to 98.5%, still below 99%. Keep all 15 misses in the denominator. Measure write commit time, WAL, buffer reads, plan shapes, and successful request latency under the same parameters, arrival pattern and fault window. Tune first because the plan shows unnecessary read work. Replicas are a later option for stale-tolerant read pressure and leave writes on the leader. Shard only after showing an owner-level write or storage constraint and a key that preserves the transaction rules.

| Criterion | Points | Full credit |
| --- | ---: | --- |
| Plan and semantics | 3 | Computes 6,000 and 60 node outputs from the separate averages, recognizes their measurement limit and preserves final ordering and zero counts. |
| Schema and index | 2 | Proposes compatible access and type/constraint changes with verification and write costs. |
| Measured result | 3 | Computes 97% and 98.5%, includes every miss and designs a repeatable read/write comparison. |
| Scaling decision | 2 | Justifies tuning and identifies the conditions for replica or shard adoption. |

Award partial credit for correctly explained mechanisms with incomplete traces. Accept alternatives that meet the same constraints.
