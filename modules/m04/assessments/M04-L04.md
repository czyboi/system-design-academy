# Companion assessment for M04-L04

## Practical exercise

**EX-1.** A merchant portal shows open refunds by merchant. Its ledger permits refunds only up to the remaining refundable amount. A separate read model serves the portal. In a ten-minute drill, track all 200 original relevant ledger commits and observe each for five seconds after its commit. Success means the read model can return that merchant's committed version or a newer complete version within five seconds. In the drill, 194 reach it on time, three arrive late and three never arrive within the observation horizon. The target is 99%.

Compare a live join, an in-transaction summary and an asynchronous view. Choose a design for a read-heavy portal that can label stale results. Trace a relay failure after the ledger commits, duplicate and reversed delivery of versions 12 and 13, and a rebuild following loss of event retention. Compute the measured freshness result and state which copy controls refund eligibility.

## Knowledge checks

### Q1

Which copy enforces remaining refundable amount?

**Answer.** The authoritative ledger transaction. A view can lag and is intended for display.

### Q2

A refund commits and the separate summary write fails. What does a reader see?

**Answer.** The authoritative refund exists, while the summary can return an older value until repaired.

### Q3

Version 13 is applied before a duplicate of version 12. What does the complete-snapshot projector do?

**Answer.** It keeps version 13 because the conditional update requires a greater version. The older snapshot would otherwise regress the view.

### Q4

When can an in-transaction summary be preferable?

**Answer.** When readers require the new summary at commit and the extra update cost and contention fit the source transaction budget.

### Q5

Does a healthy global lag reading prove a given merchant's view includes version 12?

**Answer.** No. Compare the actual row version or read the authority under the operation's freshness contract.

### Q6

Why start a rebuild with a snapshot and change position?

**Answer.** The position identifies which later updates must be applied. A mismatched starting position can omit committed updates or replay against the wrong state.

## Sample solution and rubric

Keep refund eligibility in the ledger. For a portal allowed to label stale data, save each ledger change and complete versioned summary event in one transaction. If the relay fails after commit, the durable outbox remains available. Apply version 13 if newer and skip any later delivery of 12. Advance the consumer's checkpoint only after the relevant durable writes or verified skips. Route freshness-critical reads to the ledger or report the documented stale or unavailable result.

A live join avoids the extra projection write, while an in-transaction summary makes its write and possible hot-row contention part of ledger latency. For the async design the observed freshness result is 194/200, or 97%, so it misses 99%. Keep all six misses in the denominator. Rebuild from a new consistent snapshot and change boundary, retain subsequent events, validate coverage and move readers only after the rebuilt projection is caught up with the serving projection and future changes have an unbroken replay path.

| Criterion | Points | Full credit |
| --- | ---: | --- |
| Authority and design | 3 | Enforces refunds at the source and compares all three options by latency, freshness and write cost. |
| Delivery trace | 3 | Shows atomic source plus outbox, durable replay, duplicate and reverse-order behavior with complete snapshots, and safe checkpointing. |
| Freshness | 2 | Computes 97% with the stated cohort and timing and makes a precise route or stale-result choice. |
| Repair | 2 | Rebuilds from an aligned snapshot and change position, verifies coverage and explains safe cutover. |

Award partial credit for correctly explained mechanisms with incomplete traces. Accept alternatives that meet the same constraints.
