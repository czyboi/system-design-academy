# Federation, sharding and consistent hashing

An accounts database handles billing updates and profile reads. Profiles are growing quickly, and one tenant accounts for most profile writes. A split by business capability and a split by row ownership answer different questions. Decide which workload gets separate capacity and which queries will cross the resulting boundary.

- **M04-L03-LO1.** Trace domain boundaries, partition routing and primary ownership on a hash ring.
- **M04-L03-LO2.** Choose and migrate a partition key using locality, skew, invariants and failure behavior.

## Split by domain or by row

Federation here means dividing data by business function. Billing owns invoices and payment status. Profiles owns contact and display data. Each domain scales and changes its schema independently. The admin page that combines both now reads two authorities or a derived view with an explicit freshness contract. A cross-domain write needs a coordinated protocol or an application process with recovery and partial states. Keep operations with a strict shared invariant under one transactional owner where practical. [Azure Architecture Center, microservice data considerations](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/data-considerations).

Sharding divides one logical dataset across owners with the same logical role. A directory can route `tenant_id=71` to its assigned profile shard. The tenant's update and tenant-scoped list stay local. A global search without a routing key must query several shards and combine results, or use an independently maintained index. A slow or failed shard can make an all-shard answer slow or incomplete. An unrelated billing split cannot reduce write load on the profile shard that serves tenant 71. [Azure Architecture Center, sharding pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/sharding).

## Choose the unit of routing

Range partitioning sends an interval of ordered keys to one shard. It preserves range locality, but a timestamp-leading range can send the latest writes to one owner. Hash partitioning spreads distinct inputs and usually requires fan-out for an original-key range. Hashing tenant ID keeps one tenant local. A tenant generating 70% of writes still sends that 70% to one owner. Hash by a more granular key such as profile ID for that tenant when its writes are independent by profile. A tenant-wide list now reads every assigned bucket, and a uniqueness rule spanning those buckets still needs an explicit owner or coordination. [Azure Architecture Center, sharding strategies](https://learn.microsoft.com/en-us/azure/architecture/patterns/sharding#sharding-strategies).

## Trace movement on a ring

Map keys and ownership tokens onto a circle of positions 0 through 99. The first token clockwise owns the key, wrapping at 99. A token owns the interval that excludes its predecessor and includes itself. With A at 20, B at 50 and C at 80, key 30 maps to B and key 90 wraps to A. Add D at 35. Only keys in (20, 35] change primary owner, from B to D. Key 30 moves and keys 50 and 90 stay put.

Give each physical node several virtual tokens to divide ownership into more intervals. A new physical owner can acquire intervals from several owners. Token distribution can improve average balance across many keys. It cannot divide a single popular key, and copying data and changing replica placement still consume capacity. Measure per-shard request rates, bytes and tail latency alongside the key distribution. [DeCandia et al., Dynamo §4.2 and Figure 2](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf#page=5).

## Move data with one writable owner

Assume profiles for tenant 71 are keyed by profile ID and each profile can be written independently. Place its profiles in four buckets. Copy a consistent snapshot from the old shard and record its change position. Replay newer changes in order while the old shard remains the only writer. To cut over, fence or pause new writes at the old shard, drain admitted writes and record the final position. Catch the destination up through that position and verify counts, record versions and required invariants. Only then publish the new directory epoch and open the new owner. Reject or refresh stale routes at the old shard. A failed cutover before the switch can continue from the old owner. After the new owner has accepted writes, rollback requires copying its changes back under a new fenced transition. [Vitess 24 sharding and resharding](https://vitess.io/docs/24.0/reference/features/sharding/).

Watch migration lag, stale-route rejections, per-bucket write rates and tenant-list fan-out. Co-locate writes that must commit together. Splitting one hot entity or a cross-profile invariant needs a separate design even if moving other profiles reduces shard pressure.
