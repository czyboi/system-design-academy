# Denormalisation and derived views

A support dashboard joins order headers, line items and refund records to show open orders and balances per customer. That query runs on every refresh. The team can store a customer summary so reads take one keyed lookup. The design now has to explain how a committed refund becomes visible and how the summary is repaired after a partial failure.

- **M04-L04-LO1.** Trace a normalized read, materialized summary and recovery from a missed or repeated projection update.
- **M04-L04-LO2.** Choose a derived view design based on freshness, write cost and the authority that enforces business rules.

## Keep the ledger authoritative

The source transaction owns order and refund facts. A current summary can be computed by joining and aggregating those facts on demand. A stored summary moves that join and aggregation out of the read path. The dashboard can fetch one row by customer key, but there is now another state to maintain. The refund workflow still reads authoritative facts and enforces its invariant there. It must never use a stale summary to decide that another refund is safe.

A PostgreSQL 18 materialized view stores the query results. Reads use the stored rows and refresh recomputes them. A periodic refresh trades bounded scheduling intent for actual data lag, which also includes refresh time and failed refreshes. A concurrent refresh can keep readers from being locked out and requires a qualifying unique index on a populated view. PostgreSQL permits one refresh at a time for each view. A synchronous summary update in the source transaction is another option when both live in the same database. It makes freshness part of the commit path and can add contention on a popular customer's summary row. [PostgreSQL 18 materialized views](https://www.postgresql.org/docs/18/rules-materializedviews.html), [REFRESH MATERIALIZED VIEW](https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html).

## Trace the failed second write

Customer 17 has two open orders totaling 90 units at version 7. A 20-unit refund commits in the ledger, giving version 8 and a balance of 70. An application that commits the refund and then writes the summary can crash between the writes. It leaves the ledger at 70 and the dashboard at 90 indefinitely unless another process repairs it. The refund is valid because its commit occurred at the ledger. The dashboard cannot call its old total current.

In an asynchronous design, every mutation contributing to a customer's summary first locks that customer's serialization row, before reading or changing contributing facts. Under PostgreSQL 18 Read Committed, once a waiting writer gets the lock, its subsequent read sees prior committed changes as well as its own transaction's writes. It computes a complete summary, advances the customer version and commits the source mutation and outbox record atomically. For example, if A and B both read a balance of 90 before taking the lock, A could publish 70 and B could later publish a higher version computed from the stale 90. The higher version would lose A's refund. Locking before either read makes B compute from A's committed result. [PostgreSQL 18 row locks](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS), [Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED), [AWS relational outbox pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#using-an-outbox-table-with-a-relational-database).

A relay publishes each committed outbox record and can repeat it after a crash. It retires a publication only after the broker durably acknowledges the handoff. The projector independently replaces the stored summary only when the incoming version is greater than the recorded version, atomically writing both payload and version. If version 9 arrives first, applying its complete state and skipping version 8 is safe because version 9 includes the earlier committed changes. An incremental delta would need ordered application and gap handling. The projector acknowledges its input after durable apply or a safe skip. A cumulative checkpoint can advance only through the contiguous prefix with every earlier record complete in that cursor's scope. [Debezium outbox event keys](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html#basic-outbox-table), [Kafka 4.1 consumer positions](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html).

## Measure freshness and rebuild

For a read that carries required version 8, compare it with the projection's version. Wait within the request deadline, route to the authority, or return a response explicitly labeled stale or unavailable under the API contract. A global queue lag metric cannot prove one customer's row has caught up. To measure a time-based target in a drill, pair each relevant source commit with the first time its version or a newer complete snapshot is readable. Count commits that never appear within the deadline as misses.

If the projection is corrupted or retained events cannot cover a gap, build a new generation from a consistent source snapshot paired with its exact change position. Capture and retain the stream starting immediately after that position. Apply changes and persist a gap-free checkpoint for the new generation. A source snapshot and stream must describe the same boundary. A connector's consistent snapshot and continuation can provide this alignment. [Debezium PostgreSQL snapshots](https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-snapshots).

For a concrete drill, assume one comparable source cursor. The old consumer's contiguous checkpoint is 90, while retention has removed later records it needs. A new snapshot covers the source through 120, and its retained stream begins at 121. The old projector may already have applied an out-of-order record at 130 despite its checkpoint of 90. Fence and drain that projector, record the greatest source boundary represented by anything it can serve, and choose a source cutover boundary at or beyond both that coverage and 120. If that boundary is 140, apply every record 121–140 or a verified safe skip to the new copy and persist its gap-free checkpoint at 140. Validate coverage, atomically switch readers, and resume the new generation at the first unapplied record, 141. The old checkpoint at 90 cannot establish this coverage. If the new stream has a gap, repair it or take another aligned snapshot before cutover.

This example uses a single source cursor for snapshot, coverage and replay. With partitioned streams, track gap-free progress per partition and an explicit mapping from the source snapshot boundary to each partition's continuation. A maximum offset from one partition cannot certify another. Retaining the required history, new storage and replay capacity are part of the design cost. [Kafka 4.1 consumer positions](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html).

## Decide whether to duplicate

Use on-demand joins when the read workload is modest or decisions require the same authoritative view as writes. Use a transactional summary when immediate freshness matters and its additional write and lock cost fits. Use a materialized or asynchronously maintained view for repeated expensive reads whose contract tolerates lag. Benchmark against the same workload and compare read latency, source commit cost, projection throughput and repair time. A customer summary that takes one lookup can still be a poor choice if every source write must recompute an expensive aggregate.
