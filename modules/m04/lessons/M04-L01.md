# Relational invariants and query-driven models

Two checkouts race for the last unit of stock. At the same time, a support job tries to delete the buyer's customer record. The orders page needs to show the buyer's recent orders without loading invoice PDFs. Each operation places a different demand on the model. Design the transaction that protects the order, then design the access paths around it.

- **M04-L01-LO1.** Trace relational constraints, concurrent writes and query access paths in an order model.
- **M04-L01-LO2.** Defend a normalized model and attachment boundary using data ownership, query requirements and failure behavior.

## Give each invariant an enforcement point

Model customers, orders, line items and stock as separate tables with stable keys. An order belongs to one customer. An item belongs to one order. A stock row represents the quantity available for one SKU. A primary key identifies a row, a foreign key checks the relationship, and a join follows that relationship to fetch fields for a read. Joining orders to customers on `customer_id` produces the current customer name. Joining a line item to its order by `order_id` gives the order metadata. [PostgreSQL 18 primary keys](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-PRIMARY-KEYS), [foreign keys](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK), [joins](https://www.postgresql.org/docs/18/tutorial-join.html).

Declare `orders.customer_id` non-null with a foreign key to `customers.id` and restrictive deletion. If the deletion commits first, an order referencing the deleted customer fails. If the order commits first and still references that customer, the delete fails. A separate application lookup would leave a gap between the check and the insert. The line item's foreign key checks that its parent exists. The transaction that creates an order must also enforce the rule that a confirmed order has its line items. The foreign key alone permits a parent with zero children. [PostgreSQL 18 foreign keys](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK).

Apply ACID to the checkout boundary. Atomicity groups the stock claim, order header and all line items into one commit or rollback. Consistency means the committed state obeys the enforced database constraints and business rules. Isolation governs interactions with concurrent operations, so protect the stock claim at the write. Durability covers a commit acknowledged under the selected durability settings and failure model. The API reports checkout success after that commit. [PostgreSQL 18 transactions](https://www.postgresql.org/docs/18/tutorial-transactions.html), [transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html).

## Walk a checkout race

Assume PostgreSQL 18 Read Committed and one stock row with one unit. Both clients previously saw one unit. In each checkout transaction, decrement the row only while its quantity is at least the requested amount. This is a single conditional update against the current value, with the number of updated rows as the result.

| Event | Checkout A | Checkout B |
| --- | --- | --- |
| Both attempt to claim one unit | Updates the row to zero and holds the write lock | Waits on A's update |
| A inserts its header and lines, then commits | Can report success | Rechecks the predicate on the updated row, changes zero rows and rolls back |
| Alternative if A's line write fails | Rolls back the claim and order | Can claim the restored unit and attempt its own order |

The conditional write protects this one stock row. For an order with multiple SKUs, claim every required row and roll back the entire transaction if any claim fails. PostgreSQL rechecks the targeted row's predicate after a concurrent update commits under Read Committed. A cross-row rule, such as a per-customer limit across active orders, needs its own enforcement design. [PostgreSQL 18 Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED).

## Shape reads around ownership

Keep the customer's current name in the customer record. A correction then updates one authoritative value. Keep the agreed purchase price on the order line, because the value at purchase time and today's catalogue price are different facts. Joining to the current catalogue to reconstruct a receipt would silently change its total after a price update.

For `listRecentOrders(customer, limit)`, start with a B-tree on `(customer_id, created_at DESC, id DESC)`. The leading equality groups one customer's rows. The remaining fields order the results and break timestamp ties. For order details, look up the order by primary key and fetch its lines by an order-leading key. This targets the two read shapes while preserving the checkout transaction. Verify the plan and the extra index maintenance under the measured write mix before adding more indexes. [PostgreSQL 18 multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html), [indexes and ORDER BY](https://www.postgresql.org/docs/18/indexes-ordering.html).

## Put large attachments on their own path

An invoice PDF that is generated after checkout can live in object storage. The order is confirmed after its database commit while the invoice is `pending`. Store the invoice state, published object key and current attempt token in one database row. Give each attempt a unique, never-reused token and object key. After uploading an immutable object, the worker changes the row to `ready` and records its key only if the row is still pending and its current token matches that attempt.

To retire an attempt, atomically change that same row only if it is still pending and the token still matches. The change revokes the token and records the attempt as retired before a retry gets a new token. Both the publish and retirement updates compete on the invoice row. If publication commits first, retirement's predicate fails and cleanup retains the published key. If retirement commits first, a delayed publisher's predicate fails and it cannot make its old key visible. Cleanup may delete the retired key after the retirement commits. A delayed upload can finish after that deletion and leave another unreferenced object, so retain the retired attempt record and repeat cleanup until the upload is known to have finished or its ability to write has been revoked. Never reuse its key. A failed upload leaves the invoice pending and retryable. PostgreSQL Read Committed rechecks the competing update's predicate after a concurrent updater commits. The database update and the object upload remain separate operations even with strong object read-after-write. [PostgreSQL 18 Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED), [AWS S3 object consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

Small bytes that must share the same commit and lifecycle as the order can stay in the database if measurements support the read and backup cost. External storage fits large attachments with a separately observable pending state. Confirm the design with two concurrent last-unit claims, a customer delete racing checkout, a failed line write and a worker crash after upload. Measure order-list and attachment access separately because each uses a different path.
