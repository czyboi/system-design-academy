# SQL tuning as an evidence loop

A warehouse dashboard reads the latest 25 orders for a tenant, then loads line counts. At peak, its slow statements compete with order creation. A faster single query can improve the dashboard while an added index increases write cost. Choose the change by measuring both workloads under the same conditions.

- **M04-L05-LO1.** Read a representative query plan and connect its dominant work to a schema, index or query-shape change.
- **M04-L05-LO2.** Defend a tuning or scaling choice using bottleneck evidence, write cost and the affected transaction boundary.

## Find the expensive work

Collect frequent and slow statement shapes and their calls, time, rows and buffer activity. Use application telemetry for original operation latency and error counts. PostgreSQL 18 `pg_stat_statements` aggregates planning and execution statistics for normalized query entries. Use a representative parameter distribution, including hot and small tenants, and sample plans with `EXPLAIN (ANALYZE, BUFFERS)` on a safe representative environment. `ANALYZE` executes the statement. Cost estimates are planner units. Actual rows and time are measured by execution. For repeated nodes, multiply average actual rows by loops to estimate total rows emitted at that node, and avoid summing nested times as independent work. [PostgreSQL 18 Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html), [pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html).

## Walk two plans under one workload

The endpoint returns recent order headers and each selected order's line count. In a hypothetical baseline, the database scans 600,000 order rows, filters to 4,000 tenant rows, sorts them, joins all 4,000 orders to their lines and only then keeps the newest 25 grouped orders. An inner line lookup emits three rows per execution over 4,000 loops, or about 12,000 rows. This is expensive because the endpoint discards most orders after enrichment.

Preserve semantics by selecting the newest 25 headers first, then joining only those order IDs to their lines and preserving zero-line headers. Use deterministic ordering by creation time and order ID. This rewrite fits because the line count does not affect eligibility or ordering. If a filter requires at least one matching line, apply that filter before limiting. A candidate B-tree `(tenant_id, created_at DESC, id DESC)` can read the desired prefix in order. An order-leading line index supports targeted lookups. With a plan that uses them, the same average of three lines and 25 loops gives 75 emitted rows. These are plan assumptions. Measure actual plans, buffer reads and end-to-end success under the same data and traffic before accepting a gain. [PostgreSQL 18 multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html), [indexes and ORDER BY](https://www.postgresql.org/docs/18/indexes-ordering.html).

## Tighten storage and account for index cost

Choose types by range, nullability and domain semantics. A count known never to exceed an integer type's limit can use that type. Order IDs require range for growth. A required tenant or timestamp should be non-null. Use exact `NUMERIC` with explicit scale and rounding policy for money when decimal arithmetic is required. PostgreSQL 18 pads fixed-width `CHAR`. `VARCHAR(n)` imposes a length bound and `TEXT` fits variable text with an independent domain check when needed. PostgreSQL gives no general speed advantage to `CHAR`. Keep large invoice bytes off the narrow order-list path if their lifecycle allows a reference, with the recovery rules from M04-L01. [PostgreSQL 18 numeric types](https://www.postgresql.org/docs/18/datatype-numeric.html), [character types](https://www.postgresql.org/docs/18/datatype-character.html).

Each index consumes storage and cache space and can add maintenance to writes. Compare plans and writes with and without the proposed index. For an isolated bulk load into a new table, loading before building indexes can be cheaper. Plan rebuild space, locks, recovery and validation before touching a live table. Dropping an index that enforces uniqueness changes correctness. [PostgreSQL 18 populating a database](https://www.postgresql.org/docs/18/populate.html).

## Separate pruning, scaling and caching

Time-range partitioning can prune partitions when predicates constrain the partition key. It can simplify dropping old data. A query that omits that predicate may touch many partitions, and writes to the latest range can still concentrate in one partition. A hot row remains hot within that partition. In PostgreSQL 18, a unique or primary key constraint on a partitioned table must include all partition key columns and meet the documented key restrictions. Check whether that can enforce the existing invariant before changing the schema. [PostgreSQL 18 partition pruning](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITION-PRUNING), [partitioning limitations](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS).

MySQL 5.7 had a server-side query-result cache with table-dependent invalidation. MySQL 8.0 removed it. Tuning that old cache is product history. An application result cache instead requires a key, invalidation or expiry, authorization scope and a freshness contract. It changes the observed workload but cannot enforce a transactional invariant. [MySQL 5.7.44 query cache implementation](https://github.com/mysql/mysql-server/blob/mysql-5.7.44/sql/sql_cache.cc), [MySQL 8.0 removals](https://dev.mysql.com/doc/refman/8.0/en/mysql-nutshell.html#mysql-nutshell-removals).

## Decide by the measured bottleneck

| Observed constraint | Candidate and transaction cost |
| --- | --- |
| Crawler queue query scans most rows for a small eligible set | Tune its predicate and index before adding nodes. Keep claims on the transaction owner. |
| Large read volume remains after tuning an order-status or rank display | Route stale-tolerant reads to replicas. Preserve leader writes and proof for fresh reads. |
| Social graph reporting repeatedly joins several tables for the same summary | Consider a derived view. Measure source write amplification, lag and repair. |
| Unrelated billing or hosted application workloads contend for one database | Federate ownership when each invariant stays within its owner. Cross-domain composition gains explicit failure modes. |
| Writes or data exceed one owner and independent tenants can be routed | Shard along an invariant boundary. Measure hot tenants, migration and scatter. |
| Repeated identical query-service requests have a safe freshness policy | Cache at the application layer with keys scoped to the input and caller when needed. A cold miss still reaches the database. |

After each candidate, replay the same arrival mix and fault schedule. Report the timely success share of original requests and the latency of successful work separately, with a fixed cohort window and deadline. Count errors, rejections, timeouts and late results against timely success. Also record write latency, locks, WAL, buffer activity and storage. Select a change only if the results support the bottleneck diagnosis without sacrificing the relevant write or freshness contract.
