# Distributed social-graph traversal

“Find a connection between two people” can mean **reachability**, **a shortest path in a defined graph snapshot**, or **a path the viewer is allowed to see**. Those are not interchangeable contracts. A fast heuristic can return a plausible chain while failing the shortest-path requirement; a correct shortest-path algorithm can still leak a private edge unless authorization is part of the traversal boundary.

- **M10-L05-LO1:** trace breadth-first and bidirectional graph search, including frontier, visited sets, predecessor reconstruction, partitioned adjacency fetch and one worked shortest path.
- **M10-L05-LO2:** choose placement, batching, caching and search limits while defending shortest-path proof, privacy and resource budgets.

## Define the graph and the answer

For the lesson's core worked example, relationships are **undirected, unweighted and visible to the requesting viewer at one declared consistent graph revision**. The objective is a minimum-edge-count path between two person IDs. A directed “follows” graph or weighted relationship strength would require a different neighbor relation and, for nonuniform weights, generally a different shortest-path algorithm. A path is not permitted to traverse an edge the viewer cannot inspect.

Assume a synthetic service with 100 million person vertices, 2 billion undirected relationships stored as one canonical edge plus any adjacency projections, and a peak of 5,000 path queries/s. If we materialize both endpoints' adjacency, there are roughly 4 billion directed neighbor references. With an illustrative eight bytes per reference alone that is about 32 GB decimal before IDs, metadata, indexes, replication, tombstones, compression and access-control fields. High-degree vertices make mean degree (~40) a misleading bound on expansion work. The numbers are exercise assumptions, **not** benchmarks of a named graph database.

API `GET /paths?from=a&to=g` accepts an authenticated viewer, hop cap, original-operation ID and deadline. Its response includes path IDs and readable person cards only after final authorization, the graph revision (or a declared best-effort freshness label), and a completion status. **“No path found within four hops or 800 ms” is not the same as “the vertices are disconnected.”** If the application requires proof of no path in the entire graph, a bounded real-time endpoint may be unsuitable.

## Start with BFS and reconstruct the path

Breadth-first search uses a FIFO frontier of layers and a per-search visited set:

```text
visited = {source}
queue = [source]
parent[source] = none
while queue not empty and under resource budget:
    u = pop_front(queue)
    if u == target: reconstruct parent chain and return
    for v in visible_neighbors(u) at one graph revision:
        if v not in visited:
            visited.add(v)
            parent[v] = u
            queue.push_back(v)
return budget-exhausted or no-path depending on full exploration
```

For an unweighted static graph, marking vertices visited **when enqueued** ensures the first discovered predecessor provides a minimum-hop route; the FIFO layer order proves all paths of length less than `d` are considered before a length-`d` path. A visited set prevents cycles and redundant expansion. The `parent` map is **per request** so one request cannot accidentally inherit another viewer's visibility, snapshot or predecessor chain. A shared global “visited” bit would make unrelated searches incorrectly skip vertices.

Worst-case BFS visits `O(V+E)` of the explored graph plus memory for its visited/frontier/parent state, assuming adjacency access time is proportional to edges read. It is **not** `O(b^d)` under every graph model without constraints; `b^d` is a useful branching approximation where expansion resembles a tree, while graph revisits and high-degree skew change the actual work. A hop cap bounds path depth, not necessarily visited-edge count.

## Trace a shortest path across three person servers

Our original example has the following undirected edges:

```text
a--b--d--f--g
 \      /
  c--e
```

To remove diagram ambiguity, the **canonical edge set** is `(a,b), (a,c), (b,d), (c,e), (d,f), (e,f), (f,g)`. There are two equally short four-hop routes, `a→b→d→f→g` and `a→c→e→f→g`. A deterministic tie break by sorted person ID returns the first; the correctness condition is minimal length, not a particular tie break.

Person-ID directory maps vertex ownership to partitions: **P1 {a,b}, P2 {c,d}, P3 {e,f,g}**. The coordinator requests adjacency in **batches per partition**. If a frontier contains `b, c`, it can send one batch to P1 for b and one to P2 for c, rather than serially crossing the network for every edge.

| BFS layer from a | Distinct frontier | Newly found parent | Partition RPC grouping |
| --- | --- | --- | --- |
| 0 | `a` | — | P1 fetch a |
| 1 | `b,c` | `b←a; c←a` | P1 {b}, P2 {c} |
| 2 | `d,e` | `d←b; e←c` | P2 {d}, P3 {e} |
| 3 | `f` | `f←d` (ignore repeat from e) | P3 {f} |
| 4 | `g` | `g←f` | target reached |

Reconstruct parent pointers `g←f←d←b←a` to produce the path in source-to-target order. If P2 times out at layer 1 and the algorithm simply skips `c`, it may still find a path through b, but it has **not proven** there is no shorter route through c. A strict shortest-path result must require complete eligible expansions for all layers below the returned length, or a sound lower-bound proof.

A person server stores adjacency by person ID and may group IDs onto a shard or geographically located replicas. Directory lookup must have a version/routing mechanism so a stale owner after shard migration does not silently omit neighbors. Use bounded retries with the same search/snapshot identity; avoid treating a server timeout as an empty neighbor list.

## Bidirectional search changes the shape of work

When both endpoints are known and adjacency can be traversed in both directions, search from `a` and `g` simultaneously. The forward search finds `{b,c}` at depth 1, then `{d,e}` at depth 2. The backward search finds `{f}` at depth 1, then `{d,e}` at depth 2. They meet at `d` or `e`, giving a four-edge path after reconstructing forward and backward parent chains.

One conservative **distributed stopping certificate** makes the bound explicit. For a fixed authorized graph revision, discover a complete forward BFS ball through radius `r_s` from the source and a complete backward ball through radius `r_t` from the target. A radius is complete only after every adjacency batch and page needed to expand all vertices at smaller depths has returned and been incorporated; a pending, failed or clipped page cannot certify it. Each side records its shortest distance and parent for every discovered vertex. Let `μ` be the minimum `d_s(v) + d_t(v)` over **all** vertices in the intersection. If the intersection is nonempty and `μ ≤ r_s + r_t`, the joined parent chains give an exact shortest path. Otherwise expand complete layers further or return `incomplete` when a budget ends; an empty intersection alone is not a no-path proof.

Why is the certificate sufficient? Any shorter path would have length less than `μ`, hence at most `r_s + r_t`. Along such a path there is a vertex no farther than `r_s` from the source and no farther than `r_t` from the target. Both complete balls contain it, and their exact labels yield a candidate no longer than that path, contradicting the chosen minimum `μ`. This is an application-level mathematical derivation, not a graph-vendor guarantee. Directed searches use forward outgoing and backward incoming edges at the same revision and viewer scope.

For the worked graph, complete radii `r_s=r_t=2` give forward ball `{a,b,c,d,e}` and backward ball `{g,f,d,e}`. Both intersections `d,e` have distance sum `2+2=4`; `μ=4 ≤ 2+2`, so the reconstructed path is shortest. To see why partial replies cannot certify a meeting, consider a second undirected graph with routes `a-x-y-z-g` (four edges) and `a-p-q-g` (three). A partial batch may first report candidate `y` of length four while the batch containing `p`/`q` is delayed. Once both radius-2 balls are complete, `q` has distances 2 from `a` and 1 from `g`, giving `μ=3`; stopping at the first message would have returned the longer route. If that delayed page times out, neither completion nor the certificate is established.

Under a roughly uniform branching factor `b` and depth `d`, a naïve one-sided search may explore on the order of `b^d` candidates, while balanced bidirectional search can need roughly `2b^(d/2)`. These are **illustrative complexity approximations**, not latency guarantees under skew or partitioned network cost. [NetworkX's sequential bidirectional implementation](https://networkx.org/documentation/stable/_modules/networkx/algorithms/shortest_paths/unweighted.html#bidirectional_shortest_path) uses its own orderly fringe expansion and first-intersection invariant; it is not a stopping rule for arbitrary distributed partial layers.

For an undirected graph, backward neighbors are the same relation. For a directed graph, backward expansion must follow *incoming* edges if searching for a directed source→target path. That may require a distinct reverse adjacency index with its own consistency contract. A graph mutation during the search can create a path that never existed in any single snapshot: to claim strict shortest-path correctness, pin adjacency reads to one accessible revision or define a weaker “best effort under concurrent updates” API. The lesson's source-of-truth graph revision is an original design choice, not a capability guaranteed by every key-value store.

Neo4j's current [Cypher shortest-path documentation](https://neo4j.com/docs/cypher-manual/current/patterns/shortest-paths/) describes bidirectional BFS optimization for suitable queries and warns that predicates requiring whole-path evaluation can change the planning algorithm. This is an **implementation-specific example**. It doesn't mean every custom partitioned graph or arbitrary business predicate admits the same optimization.

## Make the directory and fetches pay for their network cost

A naïve distributed BFS sends one RPC for each vertex. At depth 3 with 5,000 nodes, it can pay thousands of sequential/parallel setup costs and overload hot partitions. Instead:

1. Partition each frontier by the **owner of the neighbor list** according to a directory or deterministic sharding function with a versioned routing rule.
2. Batch unique person IDs for each owner, with bounded request size and parallelism.
3. Return adjacency lists with source snapshot and response completeness metadata; deduplicate across shards before constructing the next frontier.
4. Apply viewer-visibility checks at the graph authority or a proven authorization boundary **before** using an edge in a result. Perform a final path-edge verification against the promised revision/policy, especially if internal traversal used a cached projection.
5. Keep a per-request budget for visited vertices, remote edge bytes, hop depth, fan-out and elapsed time. If the budget is exceeded, surface `incomplete` rather than a false “no path”.

For this example, P1 and P2 can be queried concurrently for `b,c`. A high-degree person with 5 million neighbors may return far more than a bounded RPC can safely carry; pagination or sharded adjacency blocks are needed, with completeness/watermark rules so a page cutoff cannot silently omit the shortest route. A single “celebrity server” is not a solution to skew if that server becomes overloaded.

**Placement trade-off:** colocating strongly connected communities reduces cross-server edges but increases repartition and hot-spot complexity as the graph evolves. Hash sharding balances average vertex counts yet can scatter most edges; locality-aware partitioning can reduce network RPCs for the common query mix. Measure real cut-edge ratio, high-degree fan-out, migration traffic and read tail latency before moving people purely by geography. A graph store with native traversal may simplify application code but doesn't remove privacy, snapshot and deadline requirements. Meta's historical [TAO graph access architecture](https://www.usenix.org/conference/atc13/technical-sessions/presentation/bronson) illustrates graph-aware social associations, but does not provide this example's strict shortest-path guarantee.

## Treat visibility, caching and precomputation as proof obligations

An edge `(d,f)` may be visible to one viewer and hidden from another. A cache keyed only by `(a,g)` can leak a path derived under another viewer's permissions. Include the viewer's authorized graph/policy scope and graph revision in cached path results, or reauthorize every returned edge at a protected read boundary. A recent cached negative result (`not found`) is especially fragile when a new edge is added. Offline precomputed shortest paths are costly for arbitrary pairs and graph revisions; they fit only stable, well-scoped hot query sets or approximate recommendation use cases, not automatic exact correctness.

A limited search can return a path as soon as a valid one is found if the product asks merely for **some connection**, but an **exact shortest** result needs a layer/lower-bound proof. Pruning high-degree vertices can dramatically reduce work yet remove the only shortest path; if used, label the result approximate or change the contract. Likewise a globally shared visited set can cause a later search from `a` to skip `d` because another request marked it, producing an incorrect “unreachable”.

Query API choices also must not be conflated. **GraphQL** is an API query language and runtime, independent of any graph database; it does **not** inherently implement shortest paths. **Gremlin** (Apache TinkerPop) is a graph traversal language; **Cypher** (Neo4j) describes graph path queries. The choice of GraphQL versus REST on the client side does not answer which graph algorithm or storage representation to use. [GraphQL official introduction](https://graphql.org/learn/introduction/), [Apache TinkerPop Gremlin](https://tinkerpop.apache.org/gremlin.html).

## Choose a contract before calling the service reliable

| Need | Option | Benefit | Critical limit |
| --- | --- | --- | --- |
| One shortest path in a stable snapshot | Layer-complete BFS or correctly terminated bidirectional BFS | Minimum hop count | High-degree explosion and costly full-layer visibility |
| A fast approximate recommendation | Pruned or heuristic traversal | Bounded CPU/RPC | Not an exact shortest-path proof |
| Frequent local community queries | Locality-aware partitioning and batched owners | Fewer remote edges | Repartitioning and skew |
| Dynamic permissions | Scoped path cache + final path validation | Avoids cross-viewer leaks | More read latency and revocation coherence work |
| Analytics across large graph | Offline graph processing | Flexible aggregation | Often not interactive and may be stale |

For a synthetic five-minute cohort of all valid **original** up-to-four-hop queries, measure from first ingress to client receipt within 800 ms, preserving original IDs across retries. A **responsiveness** objective of 99% counts a correct exact path, a justified within-four-hop negative, or a truthful `incomplete` within the deadline. Separately require at least **98% useful exact completion**: count only a correctly authorized exact shortest path or a justified within-four-hop negative received on time. Incomplete, rejected, failed, timed-out, wrong and late results remain in the denominator but cannot enter the useful numerator. A fast truthful `incomplete` can meet responsiveness but cannot meet the useful-completion objective by itself. A complete bounded search showing no path within four hops does not prove graph-wide disconnection. Report admitted-only latency separately; these percentages and deadline are scenario choices, not measured results.

Falsify the correctness claim by injecting a high-degree intermediary, a P2 timeout, a graph revision changing during traversal, a revocation between cache fill and response, and simultaneous searches with different visibility scopes. Validate returned paths against the graph authority under the declared snapshot; a process log that says “BFS finished” is not proof of a shortest authorized result.
