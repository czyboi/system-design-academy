# Crawler and web-search composition

A search result can be wrong even if the query engine correctly intersects postings and merges shards. If a crawler fetched a changed page but the index still serves the prior document version, the result is **complete with respect to an old index** yet stale with respect to the web source. Designing a crawler therefore requires a durable *source-to-index* contract, not just many concurrent HTTP downloads.

- **M10-L03-LO1:** trace URL discovery, frontier scheduling, fetch, versioned page storage, deduplication and index publication through a concrete crawl-to-query example.
- **M10-L03-LO2:** defend bounded recrawl, host limits, content similarity, duplicate handling and query freshness under explicit resource and failure criteria.

## Scope crawl input, output and cost

Assume a synthetic crawl budget of **2 million successful page fetches/day**, average retained response body **50 KiB**, 30 days of versioned source storage, and **3 million search queries/day**. Raw fetched payload is approximately `2,000,000 × 50 KiB ≈ 95 GiB/day` and `≈2.9 TiB` across 30 days before compression, duplicates, metadata, replica copies and retained past versions. Average fetch admission is roughly 23/s and average query load 35/s; a hot host or query burst is not represented by these averages. Egress/ingress bandwidth, DNS requests and host concurrency must be part of the envelope.

The product contract in this example is **not “index every URL on Earth”**. It crawls a declared set of permitted public hosts and links, respects fetched robots rules, keeps one canonical document identity per chosen URL policy, and aims for verified index publication within five minutes of a *successfully persisted* content change. A search export requires a complete result on one readable generation with a source-cut freshness claim; interactive browse may disclose an incomplete or older generation if the caller explicitly accepts it. These thresholds are invented teaching constraints, not Google or AWS product guarantees.

Separate three identifiers:
- **Raw discovered URL:** preserves exactly where a link was found, after a safe URI parse.
- **Normalized fetch key:** a carefully defined URI equivalence policy—scheme/host normalization and conservative handling of default ports—used to avoid fetching truly equivalent addresses twice. Do not silently remove query parameters, fragment-related application state or path case when the origin might distinguish them.
- **Document/version identity:** `(canonical_url_id, fetch_version)`, bound to fetched bytes and metadata, so an old indexing worker cannot overwrite a newer snapshot.

RFC 3986 describes URI syntax and normalization concerns; it does **not** tell every website which query parameters are insignificant. [RFC 3986 §6](https://www.rfc-editor.org/rfc/rfc3986.html#section-6).

## Make the frontier recoverable and polite

The frontier is a durable scheduler, not merely a `visited` set in one worker's memory:

```text
links/sitemaps -> URI parse + domain allow policy
  -> normalized URL key + priority + next_due_at
  -> host-partitioned frontier and robots/politeness gate
  -> leased fetch attempt -> response storage + fetch event
  -> link extraction -> frontier updates
                  -> document index job
```

Each normalized URL has a lifecycle such as `discovered → scheduled → leased → fetched/failed → due-for-recrawl`. Claiming a task should be atomic for the scheduler's selected unit, and leases must be recoverable; a crashed worker's lease eventually becomes eligible for safe replay. A stale worker finishing after a replacement must not promote an older fetch version over the newer committed version. Use a monotone fetch generation or conditional version update in the authoritative page store; an attempt ID alone is not a canonical document order.

A **host budget** limits concurrent connections and requests per time window, with bounded retries, jitter and adaptive backoff for overloaded origins. A global queue that lets a popular host consume all slots violates fairness even when aggregate QPS looks safe. Keep per-origin queues with weighted priority and a global concurrency cap. Cache DNS within resolver TTL and safety constraints, pool connections according to HTTP transport policy, bound response bytes and decompression ratio, and reject private/loopback/link-local or otherwise prohibited destinations after every DNS resolution and redirect to prevent SSRF and DNS rebinding. Don't infer that domain-name normalization alone provides a safe network destination.

For robots rules, apply **RFC 9309**: fetch the origin's `/robots.txt` and honor its applicable User-Agent group and the longest matching allow/disallow path rule, with the standard's behavior on access failures. Robots files help cooperative crawlers decide which paths to request; they are **not authentication or a guarantee that a public page is excluded from search indexing**. Keep the robots cache freshness and error policy explicit, and use actual authentication to restrict protected content. [RFC 9309 §§1–3](https://www.rfc-editor.org/rfc/rfc9309.html), [Google Search Central robots introduction](https://developers.google.com/search/docs/crawling-indexing/robots/intro).

**Transport correction:** switching a crawler's HTTP request from TCP to arbitrary UDP is not a valid bandwidth optimization. HTTP/1.1 and HTTP/2 use their specified transports, whereas HTTP/3 maps HTTP semantics over QUIC. QUIC uses UDP as its substrate with its own transport/security behavior. A crawler must negotiate a supported application protocol; it cannot just send GET syntax in datagrams and expect an HTTP server to understand it. [RFC 9114 §1](https://www.rfc-editor.org/rfc/rfc9114.html#section-1).

## Store versions and deduplicate without deleting meaning

At fetch completion, record response status, final URL, relevant cache validators (`ETag`, `Last-Modified` when supplied), content type, capture timestamp, byte count, canonical raw-body digest, and an immutable page version. A conditional GET can reduce body transfer if the origin chooses a valid `304 Not Modified`; a `304` revalidates a particular stored representation, not “all pages unchanged forever”. [RFC 9111 §4.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3).

**Exact duplicate:** the same byte content may appear at two distinct URLs. A cryptographic content digest is an index hint; verify full content or a trustworthy collision-safe policy before sharing one blob. Retain each URL's document identity, link graph and fetch provenance even if both reference one body. A report asking for “all URLs containing this document” must not accidentally discard the second URL.

**Near duplicate:** token shingles or normalized term vectors can compare similar pages. For shingle sets `A` and `B`, Jaccard similarity is `|A∩B| / |A∪B|`; cosine similarity is `dot(x,y)/(||x|| ||y||)` for nonzero vectors. These scores depend on tokenization, stop-word policy and normalization, and can be high for pages whose legally relevant or monetary values differ in one field. A threshold should *suggest* clustering or one search-result representative, not silently imply two URLs are semantically interchangeable. For access and deletion, treat distinct documents separately unless the application explicitly defines a stronger deduplication contract.

**Loop prevention:** a page that links back to a visited URL should not cause unbounded recursive fetches. A visited record means “known URL with next recrawl schedule”, not “never fetch again”. Cycles through `A → B → A` collapse to one canonical scheduled state per URL, with future recrawl permitted.

An often-misread MapReduce example emits a key only when it appears once in the input. That is **unique-only filtering**, not ordinary *distinct URL* deduplication. If two input records both contain `u1`, a unique-only reducer outputs **zero** copies of `u1`, which is wrong for a crawler that wants one fetch candidate. Correct distinct filtering emits exactly **one** representative for each key, retaining the chosen provenance and due-time policy.

## Walk a duplicate and a changed page to the index

At 10:00, the crawler fetches:

| URL identity | Content at 10:00 | Raw digest relation | Search metadata |
| --- | --- | --- | --- |
| `u1=https://shop.test/item/7` | `Blue kettle, 2 L` | digest H | title `Blue kettle`, snippet from page |
| `u2=https://mirror.test/item/7` | `Blue kettle, 2 L` | same H | separate URL and origin even though body shared |

The crawler may retain one immutable copy of the *body* for digest H but two URL records with different fetch timestamps, link edges, host policy and visibility. The search product may collapse them into one **labeled representative** per content cluster; it must preserve the second URL's provenance for re-crawl and correction.

At 10:10, `u1` changes to `Blue coffee maker, 2 L`. A successful conditional or full fetch writes version `u1:v2` to the page store, but the index worker crashes before publishing it. Generation `g17` still holds `u1:v1`; a query for `coffee maker` can miss `u1`, while a query for `blue kettle` can return a stale reference. The crawler fetch counter alone cannot declare search fresh.

A durable index event `(u1,v2,digest,commit_sequence)` is replayed idempotently. Each shard applies it only if `v2` is newer than its stored `u1` generation and updates title, snippet and inverted postings consistently for that document. It must remove old `kettle` postings and add `coffee`/`maker` postings in the same readable index generation (or with a versioned manifest so queries never see a half-applied doc). A coordinator publishes generation `g18` **only after** affected shards have confirmed the required source cut. Reader requests pin a generation for the entire scatter/gather; mixing `g17` and `g18` shard results cannot prove a complete global top-K. The retrieval mechanics are owned by [M08-L03](../../m08/lessons/M08-L03.md).

```text
10:10 persist u1:v2 ---- durable index event ----> worker crashes
10:11 query at g17 --> old "kettle" posting; index lag measured
10:12 replay event --> update postings/title/snippet --> g18 confirmed
10:12 query pinned to g18 --> "coffee maker" includes u1:v2
```

A page deletion, robots-policy change or legal removal is even more sensitive: commit a tombstone/change event and prevent old versions from being resurrected by a delayed fetch or index worker. “Last finished worker wins” is not a safe version protocol. Define whether an origin `404` retires the index immediately or only after a repeat confirmation to avoid transient removal; that is a product trade-off with disclosure risk.

## Choose recrawl budget and query freshness together

Recrawl is a resource allocation problem: too frequent and the crawler wastes bandwidth or overwhelms origins; too slow and the index becomes irrelevant. Record observed change intervals and error history per URL, and schedule adaptive `next_due_at` with conservative lower/upper bounds. A frequently changing news feed may warrant a shorter interval than an archived document, but don't assume every page is equally expensive to crawl. Cache validators can save bytes while still consuming requests. Host-specific rate limits and Retry-After responses override a greedy freshness schedule.

At query time, use the **inverted index and scatter/gather** from M08-L03. A query needs not just shard coverage and scores but source-cut freshness and document version evidence. Serving a fully ranked list from old `g17` is *complete relative to g17* yet stale relative to observed `u1:v2`. Browsing may show a freshness label; exports with strict freshness should fail or wait within deadline rather than silently claim current results.

Index/crawl partitions and caches should be separated by bottleneck: high crawl bandwidth requires distributed fetchers and politeness by host; large postings need sharded index storage; hot common queries justify cache only with generation-aware keys; a title/snippet hydration cache must be invalidated or versioned with the document. DNS caching and connection pooling reduce repeated setup, but uncontrolled fetch bursts can violate origin constraints. Estimate storage for raw page versions, index postings, URLs/edges and replica overhead separately rather than multiplying raw page bytes by one undocumented factor.

## Test the composed system, not just isolated stages

A useful end-to-end freshness SLI counts **original eligible source changes that the crawler successfully persisted** in a cohort and were fully query-visible within five minutes of their persistence time. Deduplicate retry events by stable change/version ID, observe every event to its five-minute deadline, and count missing, stale, failed and late changes as failures. Report coverage of *not-yet-fetched* pages separately, since the crawler cannot know every origin update. For a client-facing search SLO, denominator is all original valid queries; successful responses must satisfy requested completeness and source-cut contract plus deadline, not only return a 200 quickly.

Run falsifying tests: break a crawler after committing the new page but before index event handoff; replay an old `v1` after `v2`; change robots policy while scheduled jobs are leased; simulate a URL loop and content duplicate; throttle one host; return `304` with a mismatched cached validator; make a slow index shard exceed the query's cutoff. Distinguish fetched-source age, index published cut, query generation and client-received result. A complete design names the first component that can *prove* each stage progressed.
