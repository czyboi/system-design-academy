# Paste storage, short links and expiry

A paste service appears to need only two operations: accept text and return it later. The first design challenge is not choosing a database; it is deciding **which promise a link represents**. Does it expose public bytes to anyone who has it? May its owner revoke it immediately? Can a link expire while a copy remains in a cache? A short-URL service has a related identifier problem but a different payload and response behavior.

- **M10-L01-LO1:** trace the create, read, retry, analytics and deletion paths, with capacity assumptions and failure boundaries.
- **M10-L01-LO2:** choose identifier, storage, caching and retention policies that satisfy the stated privacy, freshness and operational trade-offs.

## Start with a small workload and a precise contract

**Illustrative workload, not a measured service:** 50,000 new pastes/day, an average 2 KiB payload, 14 days of retention, and 1 million reads/day. Treat an “original” create as a client-scoped request ID; retries retain that ID. Limit individual text bodies to 256 KiB for this example. Assume 80% of pastes are unlisted public links (a link is a bearer capability), while 20% are private and require the owner's authenticated authorization check. A public link's entropy is **not** a replacement for a private link's permission check.

At steady state, retained paste payload is approximately `50,000 × 14 × 2 KiB = 1,433,600,000 bytes ≈ 1.34 GiB` before metadata, replication, object-store overhead, indexes and version history. Average create and read rates are about 0.58/s and 11.6/s; design capacity for a **declared** short-lived peak, for example 100 times average reads, rather than assuming average utilization predicts the tail. These are sizing inputs, not demonstrated throughput or service-level guarantees. Short links may require a much longer retained mapping because an active redirect has tiny payload but a very long link lifetime; apply separate retention assumptions.

First establish one correct logical API:

| Operation | Request and contract | Response and failure |
| --- | --- | --- |
| `POST /pastes` | Idempotency key for this creator and byte-identical body/visibility/expiry inputs; authenticated owner for private pastes | Return immutable ID and URL only after the content and readable metadata are durably committed. Conflicting reuse of the key rejects. Timeout means outcome unknown; retry *same key*. |
| `GET /p/{id}` | Resolve metadata, fetch the bound content, then make an authoritative release-admission decision before releasing bytes | Admit exact bytes only when the same generation is active, unexpired and permitted at admission. Otherwise return no content; distinguish errors only as disclosure policy permits. |
| `DELETE /p/{id}` | Authenticated owner or authorized administrator | Commit a tombstone so subsequent authoritative reads reject; physical object and derived copies may be cleaned later under a stated deadline. |
| `GET /r/{code}` | Resolve a short-link mapping, validate safe target and current policy | Redirect to an approved target or return an unavailable response; no arbitrary-URL fetch by the application is needed. |

Separate the **resource lifecycle state** from a storage-object lifecycle setting. An object store's expiration job does not define the moment a public HTTP response must stop serving data.

## Assign an identifier without confusing representation and safety

For an allocated counter `n`, Base62 is a conventional positional representation over digits, lower-case and upper-case letters. It is **not an encryption scheme** and reveals approximate allocation order; a short string does not imply secrecy. For a random ID, choose a cryptographically secure random bit string and encode it using a URL-safe alphabet. The namespace must have an atomic uniqueness check (for example, a unique database constraint). On collision, retry with new randomness; never overwrite an existing record.

Suppose the service chooses **10 uniformly random Base62 characters** for its public identifier. Its namespace has `62^10` possible strings. A collision is unlikely under the example's moderate number of active IDs but is **not impossible**. The unique insert is the final correctness boundary, not a probability estimate. For unlisted links, choose sufficient entropy over the entire expected issuance volume, watch abuse and apply throttling; add a separate private authorization layer for private content. Avoid user-chosen identifiers without namespace reservation and abuse controls.

**Do not conflate encodings.** Standard Base64 uses `+` and `/` in its alphabet; RFC 4648 §5 defines base64url by replacing those alphabet positions with `-` and `_` and discusses padding. Base62 has 62 symbols; base64url has 64, and neither creates entropy. RFC 3986's unreserved URI characters include letters, digits, `-`, `.`, `_` and `~`, so a path-safe identifier avoids delimiter escaping when used as one segment. Always parse the URL before percent-decoding user data that might otherwise be treated as a delimiter. [RFC 4648 §§4–5](https://www.rfc-editor.org/rfc/rfc4648.html#section-5), [RFC 3986 §§2.3–2.4](https://www.rfc-editor.org/rfc/rfc3986.html#section-2.3).

What about hashing paste content and truncating it to generate an ID? It can support **content-addressing** under a carefully defined deduplication policy, but two equal pastes receive the same link and a truncated digest can collide. If the system automatically reuses a hash-derived ID, a caller may learn that another user's exact text exists; if the public payload is secret, content-derived identifiers can leak information. Do not use MD5 where collision resistance is required; RFC 6151 distinguishes that security use from other checksum contexts. When hashing for *integrity or deduplication*, choose a contemporary algorithm and compare full digests plus size/content verification under the domain's trust model. When generating a non-derivable public link, use secure randomness rather than treating deterministic content hashes as access tokens. [RFC 6151 §2](https://www.rfc-editor.org/rfc/rfc6151.html#section-2), [OWASP IDOR: identifier complexity and access verification](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html).

For sequential IDs, an atomic allocated range or an ID-generation service can ensure uniqueness, but retries must not create multiple links for one original create. An idempotency record binds the caller-scoped key to input fingerprint and stable resource ID **before** retryable downstream work; use the same identity on replay. Otherwise retry after a lost response can mint two URLs even when neither storage insert collides.

## Make the first version correct before adding an object store

For a small workload, one transactional metadata/content store can be enough. A create transaction claims the idempotency key, reserves a unique identifier and stores the content with `status=active` and `expires_at`. A read fetches by ID and enforces status, expiry and authorization at the release-admission boundary described below. The storage engine's ordinary transaction semantics must be verified for the chosen product; this example doesn't assert a specific vendor.

As bodies grow, splitting immutable content into object storage can lower the cost of keeping blobs in an indexed metadata database, but introduces a two-system commit problem:

```text
Client --POST + original key--> API
   1. atomically claim key / reserve ID -> metadata pending
   2. write immutable object at versioned key -> object store
   3. verify write success for required durability/visibility contract
   4. atomically flip metadata pending -> active, bind object version
   5. respond ID; retries read same operation receipt
```

The `GET` path reads authoritative metadata first, then uses the *bound* object key/version. If step 2 succeeds but step 4 fails, the pending record is not readable; a recovery worker can safely resume or garbage-collect an orphan only after the operation is terminal under a documented recovery policy. If step 4 commits but the response is lost, the same idempotency key resolves the previously created ID. **Never publish active metadata before its object can be read under the target consistency requirement.** For Amazon S3 specifically, the current documentation describes strong read-after-write consistency for PUT/DELETE and related operations, but this does not make an application-level write spanning S3 and SQL atomic. [AWS S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

For private pastes, authorize the metadata request before releasing a content URL. An Amazon S3 presigned URL is a bearer capability subject to its expiration and underlying credential validity; it may bypass a newly revoked application permission while it remains usable. Therefore either serve through an authorization-enforcing proxy or state a bounded revocation delay. S3 checks expiry when a request starts, and a download already underway may continue: a direct URL alone cannot enforce the application admission boundary below. [Amazon S3 presigned URLs and expiration](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html#PresignedUrl-Expiration). Use distinct credentials, encryption and logging boundaries per [M09-L01](../../m09/lessons/M09-L01.md).

## Trace expiration through caches and cleanup

Consider paste `x7K9`, `expires_at=12:00:00 UTC`, cached at 11:59:50 with a 60-second TTL. A cache that admits a new response from the copy at 12:00:20 violates this exercise's expiry contract, even if the object-store lifecycle job has not yet removed the blob. A soft public expiry with a documented minute of grace would make a different trade-off.

For this exercise, **release admission** is the authoritative, linearizable decision immediately before a response may start releasing content bytes. After a potentially slow object fetch **or a cache hit**, the API sends the observed resource generation and caller to a gate serialized with that resource's deletion/tombstone commits. The gate checks that the current generation is still active, the caller remains permitted, and the expiry has not been reached. Assume its clock is within a known bound of UTC: admit only if the clock's upper possible UTC time is strictly before `expires_at`; if time or authority is unavailable, fail closed. A delete serialized first rejects the read; an admission serialized first may start its response, even if deletion commits immediately afterward. Cached bytes and a prior metadata check cannot authorize that decision.

This contract forbids **new admission** at or after expiry and after a tombstone wins the serialization order. It does not promise to recall a response already admitted, stop its in-flight bytes at expiry, or erase a client's retained copy. Stronger revocation needs a separately specified streaming enforcement boundary and still cannot recover previously delivered bytes. Limit cache reuse by TTL and expiry with clock-skew allowance; a late fill cannot overwrite a newer generation/tombstone. The gate is an application design, not an automatic S3 or HTTP-cache guarantee. See [M06-L03](../../m06/lessons/M06-L03.md), [M06-L02](../../m06/lessons/M06-L02.md) and [RFC 9111 §§4.2, 4.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.4).

```text
11:59:50 GET x7K9 -> metadata check says active; slow object fetch begins
12:00:00 expiry boundary reached
12:00:02 fetch finishes -> gate rechecks before release; rejects even if bytes are cached
12:00:05 sweeper deletes old object, conditional on tombstone/version
A second paste: delete commits first -> its concurrent read admission rejects;
if admission commits first -> that already-admitted response may finish after delete.
```

A production cleanup worker can scan an index on `(status, expires_at, id)` and advance in bounded batches. Commit a tombstone or terminal status before physical deletion, and condition deletion on the metadata version so a delayed sweeper cannot delete a newly reused object path. **Never reuse object keys without versioned identity** when old cleanup jobs can still be running. Rate-limit cleanup so it does not starve foreground storage writes. Prefer observable lag and bounded retention; “object eventually deleted” is a different promise from “no longer publicly retrievable”.

HTTP caches have their own invalidation semantics. RFC 9111 §4.4 requires an intermediary cache to invalidate the target URI on a non-error response to an unsafe request it actually forwards, but this **does not guarantee global invalidation of every alternate URL or every cache**. Private content should avoid shared-cache storage unless its policy is carefully controlled. A separate purge mechanism and conservative `Cache-Control` response policy are necessary for any claimed revocation bound. [RFC 9111 §4.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.4).

## Derive the short-link case and the analytics path

A URL shortener stores a small mapping `code → target URL`; it normally issues a 3xx redirect rather than returning stored text. The target may contain sensitive query strings, and redirect destinations should follow an allow/deny policy to avoid becoming an abuse relay. Mapping identity and retention differ from paste content: a long-lived public redirect might benefit from a cache, but target edits and disabled links must follow a declared consistency contract.

For monthly hit analytics, **do not synchronously increment a global count on every redirect**. A bounded asynchronous event can carry `(event_id, code, timestamp_utc, source)` with a stable identity. With an explicit month boundary, the map phase emits `((YYYY-MM, code), 1)` for each distinct hit event; the shuffle groups equal month/code keys; reduce emits the count. For example:

| Raw hit | Mapped key/value | Monthly result |
| --- | --- | --- |
| `h1` for `aB7`, UTC Jan 31 23:59 | `((Jan, aB7), 1)` | Jan `aB7 = 1` |
| `h2` for `aB7`, UTC Feb 1 00:00 | `((Feb, aB7), 1)` | Feb `aB7 = 2` after `h3` |
| `h3` for `aB7`, UTC Feb 1 00:01 | `((Feb, aB7), 1)` | — |
| retry of `h2` | same `event_id`: deduplicated | Feb remains 2 |

Specify whether a “hit” means an **original redirect request**, an admitted redirect, or a successful client receipt. Server-side 3xx emission cannot prove that the browser reached the destination. For the illustrative dashboard, count distinct admitted redirects, not delivered impressions. An append-only event log can be replayed into a warehouse; protect event retention and exclude raw sensitive targets/identifiers where unnecessary. Analytics can lag without extending the redirect's client deadline. If analytics dispatch is critical, atomically persist durable event intent with the redirect's relevant acceptance record or acknowledge that some analytics may be missing. [MapReduce original paper](https://research.google/pubs/mapreduce-simplified-data-processing-on-large-clusters/), [M08-L01](../../m08/lessons/M08-L01.md).

## Scale only when observations justify it

A hot link can be served by a controlled cache and read replicas while the authoritative metadata store remains the revocation source. Watch cache hit rate, origin read traffic and freshness errors, *not only* cache latency. Horizontal API servers are easy relative to a write bottleneck on a single ID allocator or uniqueness index; partition by ID only after measuring it. Store immutable content in object storage when the read/write/cost profile justifies it, keeping metadata transactional. Move hit-event analytics to a queue/warehouse so a slow aggregation does not delay ordinary GETs. For private content, a strict authorization path may intentionally forgo shared CDN caching.

Three choices expose different costs:

| Need | Reasonable first choice | When to change it |
| --- | --- | --- |
| Small active dataset, simple deletes | One transactional store for metadata and text | Payload volume or blob I/O stresses indexed OLTP work |
| High public read fan-out, bounded staleness | Cache responses with resource expiry and generation guard | Revocation is strict, content is private or hot-key invalidation fails |
| Auditable monthly hit counts | Durable event IDs + offline windowed aggregation | Exact near-real-time totals become product-critical and state/late-event costs are acceptable |

**Verify success on original operations.** Suppose the public paste-read target in this exercise is 99% of valid original GETs in each five-minute ingress window returning correct permitted bytes for a read admitted while active (or the correct unavailable status when expiry/deletion wins the admission decision) received at the client within 500 ms of first ingress. Count each original once across retries; rejected, wrong, timed-out, failed and late originals remain in the denominator. Track whether a request was correctly denied separately from active-content success, so a service cannot “meet latency” by returning fast errors for active links. The numerical target is a made-up design exercise, not a performance claim.
