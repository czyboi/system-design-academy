# Category sales ranking

A store promises its customers a weekly ranking of the products and categories with the most units sold. A ranking table is simple to query; **the difficult part is defining exactly which sales count and which revision of the result is visible**. A late refund, a duplicate checkout event, a product assigned to two categories or a sale at the midnight boundary can change the result without changing the frontend code.

- **M10-L07-LO1:** trace an input window through filtering, grouping, two MapReduce-style stages, distributed sorting and materialized top-K serving.
- **M10-L07-LO2:** defend batch versus incremental revision handling, category membership, skew and cache freshness under explicit correctness and latency contracts.

## State the ranking contract before selecting workers

The product displays the seven-day half-open window `[2026-11-09T00:00:00Z, 2026-11-16T00:00:00Z)`, ranks by **net units** sold (the sum of positive accepted sales and negative settled returns), and refreshes the public table every hour. It is an illustrative service: 5 million original purchase-line events/day, 100,000 distinct products, 400 categories, 2 million ranking reads/day, and a two-hour permitted correction window for late source events. These figures and deadlines are **exercise assumptions**, not an actual marketplace benchmark.

Record each transaction line with stable base identity `(source, order_id, line_id)` and a separate authoritative, monotonically ordered revision for that base line, plus event time in UTC, signed integer quantity, product ID and category membership. This ordering is an application source contract, not a MapReduce guarantee. Event arrival time determines *when work becomes available*; event time determines the weekly bucket. Within a frozen complete source cut, reconcile duplicate deliveries by base identity and revision, select only the highest authoritative revision for each base line, and emit its signed current value once; a selected tombstone emits no sale. For example +3 at revision 1 then +2 at revision 2 yields +2, not 5, even if revision 1 is replayed after revision 2. A settled return such as `s6` has its own distinct stable base identity and signed negative value, not a revision of the sale. Returns follow the declared financial accounting contract; don't silently use gross item count while labeling the table “net sold”.

An event exactly at `2026-11-16T00:00:00Z` is excluded from this window and belongs to the next. Use a consistent UTC boundary or document a seller-local time-zone conversion; mixing local times and UTC yields off-by-one-window errors. The ranking query key must include `window_id, category_taxonomy_version, source_cut, ranking_policy_version` and explicit status `provisional` or `final/corrected`. If products can be in multiple categories, decide whether a product's units are counted **in each relevant category** or allocated to exactly one primary category. The two policies lead to different per-category totals; neither is an implementation detail.

## Start with one reproducible snapshot

For a small materialized table, a database group-by and sort can be the best first version. Use an input snapshot whose inclusion boundary and transaction revisions are explicit:

```text
Frozen complete source cut: group by base identity, select authoritative latest revision/tombstone
  -> emit one signed current line per surviving base identity
  -> filter event_time in [week_start, week_end)
  -> attach effective product-category membership version
  -> group by (window, category, product)
  -> SUM(signed_units)
  -> rank (category, product) by units desc and deterministic tie-break
  -> publish one immutable revision of ranked table
```

A database with the right indexes may satisfy an hourly refresh with predictable cost. Moving to MapReduce makes sense once the retained input size, skew or isolated batch execution warrants a distributed scan/shuffle. It does not by itself fix duplicate source events or cross-store publication consistency.

For the original worked sample, the product-category map at taxonomy revision `tax7` is:

| Product | Categories |
| --- | --- |
| `pA` (Steel kettle) | `Kitchen` |
| `pB` (Travel mug) | `Kitchen`, `Gifts` |
| `pC` (Notebook) | `Stationery` |

Assume this example **counts a multi-category product in each assigned category**, while the product's total sales counted across unique products remains separate. The input's original line IDs are distinct except the intentional duplicate noted below. All events fall in the current week:

| Original line | Product | Signed units | Intake partition |
| --- | --- | ---: | --- |
| `s1` | pA | +5 | A |
| `s2` | pB | +3 | A |
| `s3` | pA | +2 | B |
| `s4` | pC | +4 | B |
| `s5` | pB | +2 | B |
| retry of `s2` | pB | +3 | B |

Before any late return, unique line contributions yield **pA 7, pB 5, pC 4**. Per-category product pairs are `Kitchen:pA 7`, `Kitchen:pB 5`, `Gifts:pB 5` and `Stationery:pC 4`. Summing category totals gives Kitchen 12, Gifts 5 and Stationery 4: the sum across category totals is 21 units, whereas the unique product total is 16, **because pB appears twice by policy**, not because a sale was incorrectly duplicated.

## Trace two MapReduce jobs and sort safely

**Job 1: filter and aggregate.** Map each **selected current line**, after revision/tombstone reconciliation, to one or more `((week_id, category_id, product_id), signed_units)` pairs according to the selected taxonomy version. Partition by full aggregation key so all contributions for one pair reach one logical reducer. Combine local integer sums where safe, shuffle by key, reduce to `(category, product, units)` records. Each mapper/reducer task should write attempt-scoped output and the coordinator must select only one completed attempt per logical input split. *Execution-attempt deduplication does not replace source-line deduplication*: `s2` arrives in two input partitions and needs a stable source identity reconciliation before aggregation or a canonical revisioned input snapshot.

Job 1's resulting rows:

| Key | Reduced units |
| --- | ---: |
| `(Kitchen,pA)` | 7 |
| `(Kitchen,pB)` | 5 |
| `(Gifts,pB)` | 5 |
| `(Stationery,pC)` | 4 |

**Job 2: order and materialize.** If the product needs per-category top-K, map each Job 1 row to a composite sort key such as `(category_id ascending, -units, product_id ascending)`. Shuffle by category/range so all rows for a category can be correctly ordered. A single reducer is simple for small categories; a massive hot category may need range partitioning or hierarchical local top-K with a correctness proof for global tie-breaking. Merely sorting **within independently hash-partitioned files** does not produce one globally ordered result. For final category leaderboard, use `(-total_units, category_id)` across completed group totals and a deterministic range-sort or one final small reducer. [Original MapReduce paper, §§3–5](https://research.google/pubs/mapreduce-simplified-data-processing-on-large-clusters/).

The two jobs separate the expensive event scan and group-by from the much smaller ordered result set. If the only output is per-category totals, you can aggregate directly to `(week,category)` and sort; product detail is retained here because the UI also needs each category's top products. Avoid storing huge intermediate tables when a bounded local pre-aggregation can save shuffle, but prove that the chosen aggregation function remains associative over exact integer quantities and the source semantics.

## Publish a whole result revision, not visible partial writes

A safe batch output is an **immutable result revision**, such as `weekly_ranking:week_46:tax7:cut108:v1`. Stage all categories and product ranking rows, verify their source cut and completeness, then atomically flip the serving pointer from the prior revision to the new one. If the database cannot atomically flip one pointer and all rows, write a complete versioned result first and switch a small authoritative manifest; readers pin a version for the entire pagination session. Before computation, bind a stable job/manifest ID to an immutable complete source cut, authorized taxonomy/policy generation and input membership; same-manifest retries reuse those inputs and cannot change their payload. Source coverage and taxonomy are independent, not lexicographic revision numbers. At atomic pointer admission, require the manifest to match the currently authorized taxonomy/policy and its complete source coverage to include at least the currently published coverage; otherwise reject and rebuild from an eligible cut. For example, with `(tax7, cut109)` published and tax8 newly authorized, `(tax8, cut108)` cannot replace it because coverage would regress: rebuild tax8 through cut109 or later. After tax8 is authorized, `(tax7, cut110)` is also rejected despite its newer source cut. This is an application conditional-commit contract; a chosen store must actually provide its required atomicity, not be assumed to do so because it supports SQL.

At 2026-11-15 11:05 UTC, the source archive admits a legitimate **return** `s6` for `pA = −3 units` with event time 2026-11-15 11:00 UTC, inside the week. If `s6` is within the permitted correction window and a complete source prefix is available, publish a new revision with **pA 4, pB 5, pC 4**. The Kitchen product order becomes pB 5, pA 4; category totals become Kitchen 9, Gifts 5, Stationery 4. A late retry of `s2` remains ignored. The corrected table must not be overwritten when an older batch job finishes later.

For this example, the correction-admission cutoff is **2026-11-16 02:00 UTC exclusive**, two hours after the weekly end. A correction first durably admitted before it enters the covered source history; one at or after cutoff is recorded and escalated to a separate audited adjustment, not silently included or discarded. At each UTC hour from 2026-11-09 01:00 through 2026-11-16 02:00 inclusive, freeze a complete source prefix covering all accepted eligible inputs admitted before that hour and the authorized taxonomy, then publish that scheduled snapshot by 15 minutes after the hour. The final 02:00 cut includes all admitted pre-cutoff corrections. For `s6` at Nov 15 11:05, the 11:00 cut excludes it and the 12:00 cut must include it, with publication due by 12:15; a successful 11:00 publication cannot stand in for that later scheduled output.

**Watermarks and late-data triggers are execution-model choices, not guarantees that no more events can arrive.** Apache Beam's programming guide describes windows, watermarks, triggering and late input; the Academy scenario additionally requires immutable source prefixes, stable line revisions and whole-result serving barriers. [Apache Beam Programming Guide, Windowing/Triggers](https://beam.apache.org/documentation/programming-guide/#windowing).

## Invalidate readers by result generation

The read-heavy query path is straightforward:

```text
GET /ranking?week=2026-W46&category=Kitchen
 -> lookup authoritative published_manifest (tax7, cut109, revision 2)
 -> cache key (week, category, tax7, revision2, ranking policy)
     hit: serve versioned result
     miss: read complete version2 rows, fill guarded cache, serve
```

A row cache keyed only by `Kitchen` can continue serving pA=7 after the return. A delayed warmup from revision1 must not write under revision2's current key. Make result revisions immutable and pin the manifest/version used at fill; a later manifest change cannot be masked by insertion-time TTL. Whether a product itself is edited also matters: a changed category membership or display name may require a new **taxonomy or hydration version**, even when quantities remain unchanged. See [M06-L03](../../m06/lessons/M06-L03.md) and the service-level cache example [M10-L06](M10-L06.md).

Materialize the top-100 list once per hour and serve it with a read cache rather than recomputing a seven-day group-by on every page view. Separate a **canonical source snapshot** from a cache: cache loss increases origin load but must not change ranking correctness. Measure original API read completion to deadline, cache hit ratio, version age and stale result rejection. An old cache may be used only if the public contract explicitly accepts its staleness.

## Resolve hot categories, boundaries and replays

Job 1 groups by the full `(week, category, product)` key, so many Kitchen products need not all hit one reducer. If `(week, Kitchen, pA)` itself is hot, add a stable salt to **that full key**, compute exact partial sums and remove salt with a final reduce by the original full `(week, Kitchen, pA)` key. Keep pA and pB separate before ranking; reducing only by Kitchen would lose product totals. Job 2 can still face one hot Kitchen ordering group even when Job 1 keys are balanced. Partition its products into disjoint groups, take each group’s exact local top K with the same `(-units, product_id)` order, then merge those candidates using that order for the exact category top K. Any discarded item has K items ahead in its own group, so it cannot be in the global top K. For a full ordered category, use ordered ranges instead. Both options add merge or stage cost and are justified by measured skew.

A late return with original `s6` event timestamp from the prior window does **not** belong to this week even if it arrived today. Time partitioning must be by the business event-time policy. The example counts a return by its own correction event-time; an alternative accounting system may attribute it to the original sale's week, but then that original-week link is part of the event model and needs stable reference identity. Never quietly mix those two policies.

For a product joining a second category midweek, choose between `category-at-sale-time` and `current-taxonomy-as-of-publication` semantics. The former preserves historic category reporting; the latter may restate past rankings after taxonomy edits. Both can work, but the system must snapshot category membership under the selected revision and communicate the restatement. A “product currently has two categories” lookup in a long-running reducer without a frozen version risks mixing old and new policies in one table.

A fixed window + hourly batch is a good fit if the SLA is a known hour and correction publication is bounded. An incremental stream can keep an hour-fresh provisional view if repeated full scans miss the deadline, at the cost of durable state, deduplication and complex late correction. Periodic batch reconciliation remains useful for detecting drift. Do not call an approximate top-K an exact inventory result when the contractual leaderboard requires exact counts. [M08-L02](../../m08/lessons/M08-L02.md).

## Make the result measurable and falsifiable

For this synthetic ranking API, the product's target is at least **99%** of *all original valid ranking reads* in a five-minute ingress cohort receiving the **correct authorized result for the advertised published revision** at the client within 300 ms of first ingress. Count each original once through retries; wrong revision, incorrect tie-break, rejected, failed, timed-out and late requests remain denominator failures. Separately, the scheduled-publication objective is **100% of scheduled hourly snapshots** published by that hour plus 15 minutes with a complete source prefix through the scheduled cut and the then-authorized taxonomy/policy. Count every scheduled hour, including missing, late, incomplete or wrong-policy outputs, in the denominator. For example, if four snapshots are due and three meet both deadline and coverage, the result is 3/4 = 75%, a miss; a fast API serving the old manifest does not change that. A fast but stale query is not success.

Try to falsify correctness by replaying `s2`, injecting a sale exactly at the half-open window's upper boundary, moving pB into/out of Gifts while a batch runs, delivering s6 after provisional publication, crashing between writing rows and flipping the manifest, and finishing an old job after the corrected revision. The useful result is a coherent published window with its source cut and taxonomy version—not a green batch scheduler dashboard.
