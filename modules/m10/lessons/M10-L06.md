# Search query cache at service scale

A search API returns its top results in 30 ms on a warm cache. An index editor then removes a product, yet the API continues returning the removed hit until the entry expires. Adding more cache nodes can make latency look better without fixing correctness; it also changes what happens when a node disappears. The first design decision is **which result a cache is authorized to reuse**, not which eviction algorithm to install.

- **M10-L06-LO1:** trace cache hit, miss, fill, eviction and query routing; estimate memory and origin load under explicit assumptions.
- **M10-L06-LO2:** select invalidation, placement, replication, sharding and failure handling under accuracy, staleness, availability and cost contracts.

## Scope one search result and its budget

Assume a synthetic catalogue search service with 10 million original queries/day, 200,000 distinct normalized queries/day and a 20-result response whose serialized IDs, scores and snippets average **4 KiB**. A query result identifies its index generation, relevance-model version, filters, authorization scope, locale and ordering rule. The cache must not serve a result computed for a different set of inputs. Queries that include viewer-private entitlements must be cached only with an appropriately scoped key or not shared.

If 100,000 hot distinct result keys fit in cache, raw payload storage is roughly `100,000 × 4 KiB ≈ 391 MiB`; memory for key strings, map/list nodes, metadata, expiry structures, fragmentation and replication is **additional**. Two full copies double raw cached payload to approximately 782 MiB before overhead. Ten million/day averages about 116 original queries/s; a 20× peak is about 2,315/s. Test the actual distribution; hit ratio is conditional on key popularity, request composition, freshness and how much memory is allocated. No observed hit ratio or product capacity benchmark is implied.

At `QPS = 2,315` and a measured 90% hit fraction in a *hypothetical experiment*, backend origin sees about `231.5` queries/s, before revalidation and retries. Losing a cold cache for a hot region can transiently push close to all 2,315 requests/s downstream. If the origin can process only 400/s under the same query mix, blind retry and warmup can overload it. The 90% and 400/s figures are scenario inputs that must be tested, not facts about a specific database.

## Start with one correct cache-aside node

The query API normalizes the query and includes **all result-changing inputs** in a stable key, such as:
`(tenant_or_public_scope, normalized_terms, filters, sort, page, model_version, index_generation)`.

The first correct path is simple:

```text
Client original query
  -> query API checks scope + requested completeness/freshness
  -> cache GET by exact key
      HIT: verify entry's source cut, expiry and authorization scope -> release gate
      MISS: query index (same pinned generation) -> merge eligible shards
            -> validate completeness and source cut
            -> atomically cache the result with generation/expiry constraints
            -> release gate (or explicit failure/partial per client contract)
```

A miss must not cache an **unknown or incomplete** result under the key of a verified complete result. If browsing accepts incomplete search, use a separate result class/key and represent missing shards and source cut; never allow a partial top-K to masquerade as a complete export. See [M08-L03](../../m08/lessons/M08-L03.md) for why one missing shard changes the global rank and why mixed generations cannot prove completeness.

**Current authorization is separate from index freshness.** The policy authority maintains a monotone policy epoch and serializes each revocation commit with a protected release-admission decision. After a cache hit, an origin miss, or a coalesced wait, each caller independently confirms its identity, current authorization scope and applicable epoch at that gate immediately before response admission. The gate checks that the result is valid under the current policy and that its complete result view is acceptable for the strict request; an old scope key, a prior check or a fresh TTL alone cannot authorize release. If the required policy authority or confirmation is unavailable, strict requests fail closed. If admission serializes first, that already-admitted response may finish in flight after a revocation; if revocation commits first, the old result cannot be newly admitted. Previously delivered bytes cannot be recalled. This is an application contract, not an automatic property of the cache or index. [OWASP Authorization: per-request validation](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request).

At 12:00:05 a policy revocation removes item X while `g17` remains the readable search generation until `g18` is query-visible at 12:00:08. A `g17` hit or a waiter completing during that interval must pass the new policy gate; a result containing X is refused even though `g17` is still the current readable index. Filtering X from its old top-20 prevents that item leaking but does **not** prove the remaining list is the complete exact current authorized top-20: an omitted candidate may need to move up. Obtain a complete result from a view proven current for that policy and query, or fail the strict request; a browsing response may be explicitly qualified if its contract permits. After the eligible readers can query `g18` through the required source cut, pin its generation and expected shard set through query, fetch and retries. A second revocation can still win at the per-caller release gate.

A bounded per-key in-flight request registry (single-flight) can make concurrent misses for one popular query share *one* origin computation. It needs an upper limit, leader timeout and waiter cancellation; otherwise one hung leader turns every waiter into a deadline miss. When the group cannot fetch a fresh answer, return the explicit error/degraded policy rather than holding clients past the original deadline. Apply the cache-coherence rules from [M06-L03](../../m06/lessons/M06-L03.md), not a new home-grown interpretation of LRU.

The pinned Primer's [query-cache sketch](https://github.com/donnemartin/system-design-primer/blob/ae9bbd7b02d90b9866215de185217d33f39ab733/solutions/system_design/query_cache/query_cache_snippets.py) is incomplete: it refers inconsistently to the initialized lookup attribute and an undefined map, and accesses a missing key without a guarded miss path. A usable design needs one consistent map, an explicit miss result and map/list updates that remain consistent when evicting an entry; the detailed LRU invariants are in M06-L03.

**Eviction ≠ invalidation.** In one node, an LRU map+linked-list index can fetch, insert, update and move an entry in expected O(1) per operation under the assumed data structure and lock regime; a capacity overflow evicts the least recently used candidate. Those operations optimize *which reusable copy to retain*. They do not determine whether a retained copy is fresh. Redis documents memory limits and multiple eviction policies, including approximated LRU in its own implementation; do not claim Redis LRU is exactly the textbook linked-list algorithm. [Redis key eviction](https://redis.io/docs/latest/develop/reference/eviction/).

## The stale-fill race that TTL alone does not fix

Assume a cached result for query `steel filter` was read from index generation `g17` at 12:00:00. At 12:00:05 the authoritative catalogue completes a relevant update. A source-cut proof for `g18` becomes readable at 12:00:08. An origin request that started on `g17` returns slowly at 12:00:10.

If the cache inserts that old response at 12:00:10 with `TTL=30s` measured from insertion, it can extend old result reuse until 12:00:40. More importantly, if the API's contract requires the latest confirmed catalogue generation after 12:00:08, simply invalidating `g17` at 12:00:08 is insufficient when a delayed `g17` fill can repopulate a *current* key.

```text
12:00:00  read g17 begins (old result)
12:00:05  catalogue mutation committed
12:00:08  g18 published with verified source cut; current-generation token becomes 18
12:00:10  delayed g17 fill arrives
           compare captured generation (17) against authoritative current-generation (18)
           reject fill for any current-generation serving key
12:00:11  next query pinned to g18; compute or hit g18 result
```

Use **generation-scoped cache keys** and a durable mapping to the currently required generation. A response tagged `g17` may still be stored under an old-generation key for an explicitly allowed historical-read contract, but must not be returned to a caller demanding `g18`. The cache key alone is not sufficient if a routing layer can return an old generation as though it were current; check the requested generation/token at the serving boundary. Fail safely when the generation map is unavailable and strict freshness is required.

For a time-limited freshness contract, calculate hard reuse cutoff from the **source observation/publication cut** with clock uncertainty and replica lag accounted for, rather than automatically giving a delayed fill a fresh full TTL. An entry's `expires_at` can cap reuse before the hard policy deadline; invalidation on content updates may shorten it further. Absolute wall-clock cutoffs require a known clock-error bound or comparisons anchored to the same authoritative clock. [RFC 9111 freshness and age](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2); that HTTP standard does not automatically implement this application's generation barrier.

## Decide what changed and whether to invalidate

Search results depend on more than document text. For a query `steel filter`, a change can affect results in at least three distinct ways:

| Change | Which cached result can be wrong? | Required decision |
| --- | --- | --- |
| An indexed item is deleted or visibility revoked | Any result containing it, and other pages whose positions shift | Enforce revocation at the current policy gate immediately; use a proven query-visible index cut for exact current ranking, or fail strict requests |
| A new document gains one matching term | A cached top-20 may omit the new high-ranked document even though none of the old 20 changed | Invalidate via generation or a proven dependency index; “none of my cached IDs changed” is insufficient |
| Scoring model or popularity weights change | The same candidates can reorder; pagination and top-K may differ | Include rank-model version or invalidation generation, not only document IDs |
| URL alias/canonical set changes | Old URL may redirect differently or a document may move across representative clusters | Key or invalidate affected alias and result-set generation |
| An unrelated source change is proven to leave result inputs unchanged | Potentially reusable entry | Targeted invalidation can save origin work, but requires a sound dependency proof |

A global generation bump on every catalogue mutation is simple and conservative, but can destroy hit ratio at large update rates. A per-shard/per-topic dependency version may preserve more hits, provided the update pipeline can prove which candidate set and rank inputs influence a cached result. Do not make the dependency index itself less reliable than the cache. A clear freshness SLO may permit short stale windows and event-driven purge rather than synchronous strict-version checks—state this explicitly, since latency/cost are different.

For HTTP caches, RFC 9111 describes request/response freshness and invalidation on a forwarded unsafe method. That is not proof that *all* internal search-result replicas or alternate URLs have been purged; the cache-aside application's invalidation protocol remains its own responsibility. [RFC 9111 §4.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.4).

## Add nodes only after measuring miss and memory cost

Three placements trade simplicity for capacity:

**Independent full caches** on multiple API nodes each hold overlapping hot keys. Routing can use least-loaded replicas or locality; a query may hit on node A and miss on B. This is simple and can continue after one cache node fails, but duplicates memory and leaves inconsistent invalidation windows unless all nodes enforce the same generation/token contract. At 100,000 hot keys and 4 KiB each, each replica needs ~391 MiB raw payload.

**Replicated shared cache nodes** can keep hot data close to more than one request path and survive a cache-node loss; their replication may be asynchronous, so the failover replica can carry an old cache entry. The query API still checks current policy/generation and cannot infer fresh correctness merely because replication succeeded. The extra memory, network traffic and coordination cost should be justified against cache hit gain and failure objectives.

**Sharded cache** routes each key to an owning node, often via a versioned hash-ring or directory. It uses aggregate memory efficiently but makes a node loss invalidate a partition of hot keys, and rebalancing moves key ownership. Owners must have clear epoch/routing versions, and replicas or remote fallback must preserve the same generation-acceptance rule. A cache miss should fall back to an authoritative source, not accept a stale result from an unknown old owner. Key hot spots remain even with perfect hash balance: one search string can consume one shard's QPS.

The unit of partitioning is typically the *whole cached query result*, not its document IDs; splitting one top-20 across arbitrary cache partitions adds an unnecessary merge and weakens hit latency. Search-index sharding from M08-L03 is a separate layer with different completeness semantics.

## Trace one node loss, retry and origin overload

Suppose two cache nodes `C1,C2` normally hold disjoint key ranges, with one shared index-backed origin. Before failure, overall hit fraction is a hypothetical 90%, origin QPS ~232 at peak 2,315. At 12:05 C1 fails and the router directs its keys to C2 or an empty replacement. Assume, purely for illustration, **half** of traffic was mapped to C1; all of that portion immediately misses while the healthy half retains 90% hits. The new hit fraction is `0.5 × 0% + 0.5 × 90% = 45%`; origin load rises to `2,315 × 55% ≈ 1,273 QPS`. If the origin's tested safe capacity is 400 QPS, simply rerouting has created an overload; retries worsen it. If all misses are distinct and uncoalesced, an ideal immediate capacity upper bound is `0.45 × 2,315 + 400 = 1,441.75` query responses/s, about 62.3% of the offered originals before latency failures. This bound does not apply if coalescing changes the miss demand; authorization-gate capacity must also be provisioned and measured separately from expensive origin fills.

A defensible failure policy includes an origin concurrency limiter, per-key single-flight, timeout propagation from the **original** request deadline, bounded warmup and admission control. Under a strict search-completeness contract, shed excess requests with explicit errors rather than fabricate a cached full result. Under an explicitly relaxed browsing contract, a recent but stale generation may be served *only when the caller accepts the labeled staleness* and privacy rules allow it. Partial results must declare missing shards even if cached.

Scale-cache replication can reduce cold misses but adds memory and potential asynchronous staleness. Keep `cache_node_lost`, origin query QPS, per-key hit ratio, stale-generation rejects, source-cut age, client-correct-on-time proportion and rejected originals as separate telemetry. A system that fails fast for 60% of traffic can report beautiful successful-response latency while missing the user-facing SLO.

## Compare choices with the original operations, not only hits

Define a synthetic SLO: in each five-minute window of **all original valid queries** arriving at the API, 99% must return a correctly authorized, complete and current-to-the-requested-generation top-20 (or valid empty result), client-validated within 300 ms. Deduplicate retries by original ID and follow each original through its deadline; rejected, timed-out, unauthorized, wrong-generation, incomplete and late work remain in the denominator but outside the success numerator. Track cache hit ratio, per-node QPS and admitted-success latency separately. A browse API may define a different success criterion permitting explicitly labeled partial results; don't substitute it for the strict export numerator.

Selection rules follow from the constraint:

- Stay with a single cache-aside node while its hit/miss rate and bounded memory meet the actual workload; learn the LRU mechanics from M06-L03.
- Replicate when survival of cache node loss or lower read latency is worth duplicate memory and stale-replica checks.
- Shard when the hot result working set exceeds per-node memory, accepting routing, hot-key and rebalancing complexity.
- Use targeted invalidation only when it can prove its dependency set; otherwise prefer a generation key and explicit freshness contract.

Falsify the design with a late `g17` fill after `g18` publication, a ranking-only change, a revoked result before index refresh (including a coalesced waiter and both gate/revocation orders), C1 failure at peak traffic and a query whose private tenant scope differs. For each failure, inspect the **client's actual answer**, the index generation/cut and origin overload—not merely the cache's hit counter.
