# Iteratively scaling a cloud application

A photo-and-article catalogue launches on one machine. At first, one process and one SQL database can serve every user. After growth, every request goes through an autoscaled web fleet but the checkout API still times out: its **single database writer** has reached its commit and I/O limit. Adding more web nodes increases concurrent pressure and can make the tail worse. The useful design skill is to explain *which observed limit motivates each architectural change*, and which original limit that change does not solve.

- **M10-L08-LO1:** reconstruct request and data flows as a read-heavy service evolves through five stages, including network, data, media and failure boundaries.
- **M10-L08-LO2:** choose scaling, replication, caching, automation and asynchronous processing options using measured workload, SLO, security, recovery and cost trade-offs.

This is an original teaching scenario using AWS products as concrete implementation examples, not a claim that an older AWS reference diagram describes current best practice. Amazon EC2, S3, RDS, an Application Load Balancer (ALB), Route 53, CloudFront, ElastiCache, CloudWatch, SQS and workers each play a specific role. Historical labels such as “ELB” or “EC2 Lambda workers” are **not** interchangeable product contracts. A self-managed implementation could make equivalent choices at different operational cost.

## Stage 0 — One useful service and explicit workload

Assume a synthetic catalogue: 50,000 daily active users, each averaging eight catalogue reads/day and 0.4 content updates/day; an update may add one 1-MiB image. Approximate base demand is **400,000 reads/day (4.6/s average)** and **20,000 updates/day (0.23/s average)**, with up to a 100× short-lived read burst. New image bytes average about **20 GiB/day** before replicas, lifecycle retention or transformations. A higher peak in a single region can be far above the daily average. None of these numbers is a measured cloud benchmark.

The first working system is one EC2 instance running a web application and an ordinary relational SQL engine, with local files for image bytes. Requests arrive at a public DNS name, resolve to a public endpoint, terminate HTTPS at the application or a deliberately configured ingress, authenticate the caller, execute a parameterized SQL query and return HTML/JSON. The server process checks record authorization; merely opening TCP/443 is not access control. Use backups and test a restore before calling the service durable.

```text
Client --HTTPS--> public EC2 web + SQL + local image files
                     |  process, disk, CPU and DB share failure domain
                    backups -> separate protected recovery location
```

On day one this may be the simplest design. An EC2 instance's **static public IP or Elastic IP** addresses reachability, not failover, and Route 53 supplies DNS routing, not a new application replica. For security, don't expose SQL or SSH broadly to the internet: use least-privilege security group ingress and controlled admin access such as Session Manager when supported. A source-era suggestion to open every port to avoid breakage would be unsafe. An S3 object URL or DNS alias does not imply TLS or authorization unless those boundaries are configured.

Before changing architecture, instrument **original user requests**, not only successful database calls. Assume a target of at least **99% of original valid catalogue reads** receiving correct, authorized content at the client within 400 ms in each five-minute ingress window. Each original request is identified across retries and followed to its deadline; rejected, wrong, timed-out, failed and late work remain in the denominator. Measure admitted-success latency separately; fast rejection must not count as a good response.

## Stage 1 — Profile and scale a single host before splitting it

Suppose a load replay using the declared peak mix shows 90% sustained CPU utilization on the EC2 host while SQL latency and disk utilization are near their baselines, with the web process doing expensive image resizing synchronously. A **vertical upgrade** can buy time, but profile first: if image work dominates, moving only the SQL instance to a larger disk is not a justified first fix. A bounded CPU profile and controlled experiment that moves or queues image work would test the hypothesis. If the machine instead spends most time waiting on SQL locks or disk, more web CPU may do little.

A relational engine is justified here by consistent content ownership, visibility, uniqueness and multi-row metadata updates. “NoSQL scales more” is not a decision rule. Compare actual access patterns, transactional invariants, write/read ratios, query shapes and operations against supported SQL/NoSQL products. Starting with one SQL host is not failure by itself. The pressure to **separate failure domains** becomes compelling when a local media write fills the SQL disk, a host restart loses both application and database, or independent resource scaling would reduce measured cost and outage risk.

## Stage 2 — Separate immutable objects, SQL and network boundaries

Move uploaded image objects to S3 and relational metadata to an RDS DB instance or equivalently managed database. Save `image_id`, object key and immutable object-version/reference only when the intended stored object is ready. This is **not one atomic SQL+S3 transaction**: commit pending metadata or an operation receipt, upload/verify object, then publish ready metadata with a guarded transition. A crash between object upload and SQL activation leaves recoverable pending state or an orphan that must be reconciled conservatively. Retrying the original upload uses the same logical identity.

```text
Client -> HTTPS ingress -> web API (application tier)
                               |     \
                      private SQL DB     private S3 bucket/object
                         transactional    object bytes / versions
                         metadata         with scoped access
```

Place the **public ingress** in public subnets with an internet-gateway route; private application/database subnets **lack direct internet-gateway routes**. A private subnet is defined by its routing, not merely by an instance having a private IP address. If private workloads need outbound internet access, supply approved NAT or VPC endpoints where supported; those are explicit egress and cost choices. Restrict the database security group to the application tier's service traffic on its configured listener port; use TLS and authenticate the database server. Do not assume “private subnet” implies encrypted traffic. [AWS VPC subnet configuration](https://docs.aws.amazon.com/vpc/latest/userguide/create-vpc-options.html).

For user-visible images, a private S3 origin can be delivered through CloudFront with **Origin Access Control (OAC)** or a carefully scoped signed-content policy. OAC restricts S3 origin access to the distribution; it **does not by itself authorize an individual application's private photo view**. Choose public asset delivery for genuinely public content, and enforce viewer entitlements/signed distribution URLs or an application-authorized proxy for private content, with an explicit revocation window. The current AWS guide recommends OAC over legacy OAI for supported S3 origins, subject to the stated bucket/origin constraints. [CloudFront S3 OAC](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

This split lets metadata transactions, blob retention and image transfer scale independently, but it introduces two consistency domains and network costs. User-visible **delete** commits an authoritative tombstone and denies further authorized reads according to policy; asynchronous physical object deletion, CDN purge and backup retention have separate completion clocks.

## Stage 3 — Survive one app host/AZ loss without pretending the database is solved

Move from one app instance to at least two healthy targets across Availability Zones, behind an **Application Load Balancer**. An internet-facing ALB can terminate viewer TLS on a configured HTTPS listener; the ALB→app hop has its own security/transport boundary and must be protected according to risk. The target security group permits only the ALB's required application and health-check traffic; the database still permits only app-origin traffic. DNS via Route 53 resolves the configured load balancer name; it does not replace target health checks. [AWS ALB creation](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/create-application-load-balancer.html).

```text
Client -> Route 53 DNS -> ALB (public subnets AZ-A, AZ-B)
                           |                       |
                        App A                   App B
                         \                      /
                          private RDS writer / S3
```

Health checks must represent **readiness**, not merely “process exists”; a slow database can leave two HTTP servers passing shallow health probes while real requests fail. If AZ-A becomes unavailable, the remaining target capacity and database path must sustain the offered load. A load balancer with two targets is not necessarily resilient when both depend on one fragile shared database. Use zone-aware test traffic and monitor rejected/failed original requests during failover.

For RDS, distinguish two products that source-era “Multi-AZ” diagrams can conflate:

- An **RDS Multi-AZ DB instance deployment** maintains a synchronous standby in another AZ for **high availability and failover**; that standby **does not serve reads**. A failover still interrupts in-flight connections and requires application retry with transaction-outcome reconciliation. [RDS Multi-AZ DB instances](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html).
- An **RDS Multi-AZ DB cluster** has a writer and readable DB instances with different replication and failover behavior. A separate ordinary **RDS read replica** can offload reads but uses asynchronous replication in the usual DB instance model; it can be stale. These are not interchangeable with a single-standby instance. [RDS Multi-AZ DB clusters](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/multi-az-db-clusters-concepts.html), [RDS read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html).

A committed write with a lost network reply has **unknown caller outcome**, not proof the transaction rolled back. Use stable request IDs and authoritative receipts for retryable writes; do not blindly replay side effects. Backups and a tested restore are still required, because replicas can reproduce bad application data or destructive changes.

## Stage 4 — Add cache, centralized state and targeted database reads

At greater read demand, measure **which SQL queries** and which application work dominate. Cache public catalogue metadata, rendered pages or image variants only when their authorization and versioning permit reuse. ElastiCache (Redis OSS/Valkey or Memcached products, depending on supported configuration) can provide a managed in-memory cache, but cache hit fraction and size should be validated under the real query distribution. A cache node disappearing should reduce performance, not change a record's permissions or force the primary database beyond safe capacity. Reuse the generation/late-fill rules taught in [M10-L06](M10-L06.md).

The application is now stateless with respect to **routing**: session and authentication state either live in bounded signed tokens or a separate session store. Avoid app-host local sessions unless sticky-session failure semantics are acceptable; the user's next request may land on another AZ. Shared session storage itself needs availability and expiry/refresh rules. A global cache does not remove the need to revoke a server-side session or check access at a protected action boundary.

For read-heavy workloads, a read replica can offload stale-tolerant catalogue reads. Read-after-write requests, payment/ownership checks and other operations requiring current state must route to the writer or use a documented consistency protocol that establishes the required source cut. **Replica lag is not a missing cache entry**: a newly created item can be absent on an asynchronous replica despite having been committed by the writer. A read-routing policy can require a transaction revision/watermark or direct writer read for a bounded session period. [RDS read replica semantics](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html).

In a hypothetical load replay, the database writer can safely sustain **600 relevant write transactions/s**, while a promotion campaign offers **1,000/s**. Adding web hosts from 4 to 16 does not raise the writer limit to 2,400/s. It may queue more connections, increase lock contention and worsen 95th-percentile user latency. Scale web CPU only if web CPU/connection throughput is the bottleneck; for write saturation, inspect transactions, indexes, lock hold times, batchability, contention and data ownership before considering partitioning or a different storage model.

## Stage 5 — Automate within bounds and isolate expensive work

An EC2 Auto Scaling group can increase or decrease app targets using **target tracking**, for example a measured request-per-target or CPU target. Configure **minimum, desired and maximum capacity**, readiness and instance warmup; newly launched hosts have startup/connection/cache-warm phases and are not instantly productive. A scheduled action can anticipate known traffic, while reactive autoscaling may lag a sudden campaign. AWS recommends target tracking or step scaling rather than relying on simple cooldown-only policy for routine scaling. [AWS Auto Scaling target tracking](https://docs.aws.amazon.com/autoscaling/ec2/userguide/as-scaling-target-tracking.html).

A defensible original service scenario:

| Workload stage | Observed signal in a controlled replay | Incremental change | Boundary that remains |
| --- | --- | --- | --- |
| Users (first host) | Image CPU saturates while SQL waits stay modest | Profile and resize CPU or move image work | Single disk/database and host failure |
| Users+ (split storage) | Content bytes crowd SQL disk, independent cost pressure | S3 objects + RDS metadata and separated security domains | SQL+S3 atomicity, origin/cache invalidation |
| Users++ (AZ redundancy) | App-host failure breaks reads | ALB + multi-AZ app fleet + database HA | Writer saturation and AZ failover downtime |
| Users+++ (read workload) | Repeated public reads dominate SQL and replica-safe queries identified | Versioned cache, selective read replicas, central sessions | Cold-miss overload, replica lag, writer ceiling |
| Users++++/+++++ (dynamic load) | Repeatable demand bursts, thumbnail CPU and reporting scans | Bounded Auto Scaling, SQS worker/outbox, analytics/warehouse and measured data partitioning | Startup delay, queue cost, eventual results, database write invariant |

Large thumbnail work becomes **asynchronous**: commit a durable media record and runnable job intent; a worker retrieves an immutable source object, produces a versioned thumbnail and conditionally publishes its result. SQS is a queueing example, not evidence that exactly one external transformation ever occurs. A worker can crash after S3 write and before acknowledging its message; make the effect idempotent and ensure retry can safely confirm or replace the same derived object. Do not mark the original upload fully processed until the user-visible transformation contract has been met. Use DLQ/redrive strategy with bounded attempts and clear recovery decisions. [Amazon SQS dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html).

Similarly, move cross-user trend analytics and long historical scans to a warehouse when necessary. Redshift is one AWS implementation example, not the only way to store historical aggregates. Keep OLTP transaction/current ownership data separate from analytical projections, each with source-cut/freshness metadata. A federation/sharding design addresses a measured write/tenant hotspot only after its cross-shard transactional, routing, backup and rollback rules are defined; an arbitrary split by letter does not preserve all application invariants. A NoSQL alternative is defensible only when its access patterns and consistency/failure semantics match the product. No historic Primer scaling threshold is asserted as a universal switch point.

## Operational evidence is part of the architecture

Collect CloudWatch (or equivalent) metrics, application and infrastructure logs, request traces, external probe results, exception/error rates, security audit events and incident timestamps. Distinguish **host**, **aggregate service**, **database**, **queue**, **outside-in client** and **business correctness** signals. A dashboard reporting healthy CPU on 12 newly spawned nodes cannot prove correct product reads while the shared DB is saturated. Tie incident alarms to user-visible cohort failure, source-age, saturation and queue oldest age. The diagnostic method and recovery objectives from [M09-L02](../../m09/lessons/M09-L02.md) apply; that prerequisite is still in unmerged MS05 Draft PR #100.

Define two independent tests:

1. **Capacity:** repeat identical offered workload, request mix and data size before/after the proposed change; measure original valid-operation successful-on-time fraction, admitted latency, writer commit throughput and CPU/DB/queue saturation. A claim that web autoscaling “fixed scaling” fails when writer backlog and request failures continue rising.
2. **Recovery:** inject one app AZ failure, RDS primary failure and a failed thumbnail worker in distinct drills. Observe valid client operations across their original deadlines; verify writer transaction receipts on retry, S3 object/metadata coherence, and recovered data point/time-to-usable-state rather than only monitoring a load balancer's green status.

For the synthetic read SLO, each five-minute cohort contains **all first-ingress valid reads**, deduplicated across retries. At least 99% must receive correct, authorized content within 400 ms at a managed client. Separate read availability from write durability and transformation completion. If 1,000 originals include 930 on-time correct results, 30 timed out, 20 were rejected and 20 were late, success is **930/1,000 = 93%**, not 930/950 based on selected completed replies. This ratio can deteriorate under deliberate overload shedding; it must remain visible even when the successful requests are fast.

The enduring design principle is to introduce one new distributed boundary only when a measured workload limit or failure policy justifies it, then explicitly teach what correctness work that boundary adds.
