# Financial aggregation and budgeting

A personal budgeting application may display a monthly food total in one query. The difficult question is whether that total is still correct after the bank resends a record, edits its description, replaces a pending charge with a posted transaction, or removes a record entirely. Financial aggregation is therefore an **identity and revision** problem before it is a database-choice problem.

- **M10-L04-LO1:** trace account-linking, staged extraction, durable transaction reconciliation, monthly mapping/reduction and notification side effects.
- **M10-L04-LO2:** choose refresh, categorization, budget-template, storage and privacy approaches for the stated consistency, timeliness and cost constraints.

## Define a bounded feature and its data boundaries

The sample app allows a consenting user to link a supported financial account, import transactions and categorize spending by month, then compare actual amounts against an explicitly configured monthly budget. It **does not move money, guarantee account balances, provide financial advice or claim every institution supports the same API**. Separate read-only transaction consent from bank-login credentials. Assume the customer can disconnect the account and request data deletion under the app's documented policy.

For this original example, 100,000 active linked accounts refresh once/day, with a peak manual-refresh burst of 10,000 triggers in a minute. Each refresh returns an average of 10 changed transaction records. The system must budget for roughly one million changed records/day plus initial-history imports, webhook bursts, provider throttling and retries. A five-year ledger and object/archive copies need a retention and deletion policy; no raw-account volume or legal retention requirement is inferred from these synthetic figures.

The central table contains a stable **provider+item/account+transaction identity**, current source version/state, timestamp, signed amount in exact minor units, currency, merchant description and current category revision. Store both source event time and ingestion time. Different currencies must not be silently summed as though they were the same unit; either report per currency or use an explicitly versioned conversion policy. A transaction's sign convention must be applied consistently (in the lesson's example positive = spending; negative = refund/inflow).

## Connect accounts and keep credentials out of the ledger

A supported delegated-authorization flow grants narrowly scoped, user-approved access through an institution/aggregator. An OAuth-based integration follows current OAuth security guidance, including restricted tokens, appropriate client authentication and refresh-token replay defenses; **not every financial provider is OAuth-based**. Store the resulting access tokens as secrets with encryption, access auditing and a documented revocation procedure. The analytics and budget workers should operate on an internal account ID and least-privilege service credentials, not copy bank access tokens into events or raw dashboards. [IETF RFC 9700 §§2.2–2.3, 4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.2.2), [M09-L01](../../m09/lessons/M09-L01.md).

A **hash of user credentials** is not a safe universal account identifier: password rotation changes inputs; identical passwords can create false linkage; leaking a deterministic derived value may itself increase risk; many integrations never receive a user's password. Use the provider's documented stable account/connection identifiers under a tenant-scoped uniqueness policy, and verify any mapping across reconnects. If an institution changes identifiers, reconcile with explicit user consent/evidence instead of merging account histories by a password hash.

At first link, acquire available initial history using the selected provider's supported pagination/cursor mechanism. Later runs may be scheduled for active accounts, triggered by a provider notification or requested manually. These are **triggers to attempt synchronization**, not proof that the bank has supplied fresh records. The app reports `last_provider_update`, `last_successful_sync` and any unknown gap separately. Failed permission, expired consent or provider outage creates a visible degraded freshness state; do not fabricate a zero-spending result.

## Preserve transaction identity across extraction retries

One supported implementation example is Plaid's `/transactions/sync`: it describes `added`, `modified` and `removed` records with a cursor and paginated updates. **That is a named provider example, not a requirement that all aggregators expose the same interface.** Pending and posted representations can have different transaction IDs; Plaid documents a pending record being removed and a posted record added, with a possible `pending_transaction_id` link. [Plaid Transactions API](https://plaid.com/docs/api/products/transactions/#transactionssync), [Plaid pending/posted states](https://plaid.com/docs/transactions/transactions-data/).

A safe extraction task uses a durable `(connection_id, request_identity)` receipt and a resumable queue:

```text
link/webhook/schedule/manual trigger
   -> atomically claim durable sync intent and stable connection ID
   -> worker claims an app-assigned fenced generation G for this connection, reads cursor C0
   -> fetch pages; stage added/modified/removed under sync run R
   -> if G still owns C0, atomically apply staged set and advance cursor C1
   -> emit committed source change set/outbox with G and coverage state
   -> category/aggregate workers publish coherent budget view revision
   -> on required coverage and committed cursor + view, queue completion intent
   -> notification worker; budget alerts follow their own threshold transitions
```

For a newly linked Plaid Item, **exhausting currently available pages is not proof that initial history is ready**. A successful empty response can report `NOT_READY`: show initializing and wait for a provider update or retry according to its contract. A later sync may reach initial update completion while historical acquisition is still pending; a UI can show available data labelled partial and its known coverage, never a complete spending history. Once `transactions_update_status` reports historical update completion, verify that the provider-supported, requested range for this example has no known coverage gap, apply all available pages coherently, commit the cursor and publish the matching view. Only then is initial required coverage complete for this scenario. Historical completion is a provider status, not a promise that an arbitrary five-year range is available. If the required range exceeds provider support or coverage cannot be established, show the gap and do not claim complete. [Plaid fetching transaction data](https://plaid.com/docs/transactions/add-to-app/#fetching-transaction-data); [sync `transactions_update_status`](https://plaid.com/docs/api/products/transactions/#transactionssync-response-transactions_update_status).

The *exact cursor transaction boundary depends on provider semantics*. For the described Plaid case, the guide recommends gathering all pages of the update before persisting a coherent batch and handling mutation-during-pagination errors by restarting the applicable pagination loop. If the worker crashes after fetching pages but before committing the batch, replay C0 and apply stable identities again. **Never advance the durable cursor past unapplied changes**, and never count two fetch responses as two economic transactions merely because they arrived twice.

Reconcile `added` as insertion or update of one current source ID, `modified` as replacement of its relevant current fields and category evidence, and `removed` as a tombstone/absence in the authoritative current view. For each linked connection/Item, assign an application sync generation and serialize commits. Commit a staged run only if its expected C0 and generation still match the authoritative current state; a superseded worker cannot apply contributions, publish a change set or advance the cursor. A later committed generation therefore prevents an old page from restoring a removed record. Provider cursors are opaque continuation tokens: store and compare them for identity according to the provider contract, never sort them as revision numbers. The app generation is separate from provider fields and the user category revision. When a pending charge becomes posted under a new ID, resolve the provider's relationship; otherwise displaying both can double-count, even if each ID is unique. The raw source event log may retain both for audit under a strict retention policy, while the live spending projection includes exactly the chosen current economic representation. [Plaid integration guide](https://plaid.com/docs/transactions/add-to-app/).

A retry of a refresh should reuse the same logical operation ID. If the app accepts a refresh but crashes before queuing it, durable intent must remain runnable; merely persisting a success acknowledgment is insufficient. Provider rate limits call for bounded retry/backoff and per-account concurrency control. Running two cursor sessions simultaneously for one connection risks out-of-order advancement unless the provider and app explicitly support it.

## Pick categories without disguising uncertainty

Start with a seeded, versioned merchant dictionary and source transaction descriptors. Example: `GREEN MARKET` suggests Groceries, `CITY CAB` suggests Transport. A provider's category is another input, not an unquestionable final answer. Allow user overrides scoped by account/merchant or **individual transaction**; define precedence so a manually chosen transaction category is not silently replaced by a later model update.

A possible deterministic category decision order:
1. Explicit user override for this transaction and current classification revision.
2. User-defined merchant rule, when it applies.
3. Trusted curated merchant mapping with its version.
4. Provider suggestion or privacy-aggregated crowd signal, with confidence.
5. `Uncategorized`—not an invented precise label.

A crowd/manual ranking can help suggest merchant categories, but the app must avoid publishing identifiable user transaction histories as votes. Use consent, minimum-support thresholds and privacy review; a crowd signal is not proof of individual transaction purpose. For a merchant that can sell groceries and electronics, treating every purchase as “Groceries” may be wrong.

Budgets can start from a **user-editable template** selected by a declared income tier, e.g. a configuration for `monthly_income=4,000 USD` may suggest Groceries 100 and Transport 80 solely to demonstrate the data model. These amounts are arbitrary exercise inputs, not sensible personal finance recommendations. Store sparse `(user_id, period, category_id, limit_minor_units, template_version)` overrides rather than duplicating the whole template for every user. User overrides should survive template updates, and template changes should yield a new identifiable budget revision rather than silently rewriting historical comparisons.

## Compute one month and repair it after reclassification

Use an explicit time-zone contract for the user's budgeting month. This example uses UTC, **posted** transactions only, USD and positive numbers for net spending; refunds are negative. Each accepted transaction has one canonical current representation. Map `(user_id, YYYY-MM, category_id, currency)` to amount in **integer minor units**; reduce with exact addition. User-facing display converts cents to dollars after aggregation, not by repeated floating-point rounding. The MapReduce grouping/reduce model is explained in [M08-L01](../../m08/lessons/M08-L01.md).

| Source ID | Original amount | Initial category | Note |
| --- | ---: | --- | --- |
| `t1` | +75 USD | Groceries | posted market purchase |
| `t2` | +40 USD | Transport | posted taxi |
| `t3` | −20 USD | Groceries | posted refund |
| `t4` | +60 USD | Groceries | posted ambiguous merchant |
| retry `t1` | +75 USD | — | same source ID, not another purchase |

Initial authoritative totals: Groceries `75 - 20 + 60 = 115 USD`; Transport `40 USD`. With illustrative budget limits Groceries 100, Transport 80, the Groceries total exceeds its limit by 15. A duplicate of `t1` must not make the total 190.

Now the user explicitly changes `t4` from Groceries to Transport. The app creates a new category revision for `t4`, replaces its contribution and publishes **Groceries 55; Transport 100** under a newer aggregate revision. The prior Groceries alert is no longer applicable; Transport now exceeds its illustrative limit by 20. A delayed old category worker must not republish the old Groceries=115 snapshot after the newer revision is visible. Compare aggregate input version/source cut before replacing a whole materialized total; update affected category rows and revision atomically when the chosen store supports it, or serve a coherent versioned snapshot.

If a transaction modification changes amount, date, posted state or category, remove the prior contribution and add the new one exactly once—either recompute the affected month/category from the canonical transaction view or apply a guarded delta carrying the old and new versions. A late source removal must not be “undone” by replay of an older add. This is why source event identities, cursor progress and materialized-view revisions are different fields.

## Keep notifications and storage subordinate to correct totals

A refresh completion notification is distinct from a budget alert. If the product sends one, persist a versioned, idempotent intent keyed by the original refresh and committed sync generation only after the required coverage, cursor and coherent view are committed; an outbox or recoverable equivalent keeps that intent linked to the commit. A partial, failed or unknown sync is not “completed”; the UI may report its status separately. Delivery retries reuse the intent and do not create another completion.

A budget alert is a side effect of a committed view revision, not a new accounting entry. When a category crosses a threshold, persist notification intent with the aggregate revision or in a recoverable outbox. Deduplicate by `(user,period,category,budget_revision,threshold_transition)`, with a policy for alert retraction when reclassification reverses the condition. Retrying notification delivery is not a reason to add spending again. Distinguish “delivered” from “queued”.

Use a small transactional **OLTP** store for current account connections, canonical transaction states, user overrides and recent revisioned monthly aggregates. Keep protected immutable source logs/exports in object storage when a reproducible replay, audit or repair policy justifies their retention. Move large cross-user analytical scans to a **warehouse** fed from the same audited event stream; it can have intentional lag. A dashboard must display the data's as-of cut so a warehouse delay does not masquerade as a fresh account balance. Large raw logs and credentials need stronger access control, encryption at rest/in transit, secrets separation, careful log redaction and policy-based deletion. This lesson does not assert any particular statutory retention period or rights.

Cache read-heavy budget summaries only with keys including user/period/revision and protect against stale fill after a category edit. Observe app write hotspots—e.g., source cursor/connection state, category aggregation and alert outbox—before sharding. A database read replica can scale read queries but doesn't fix a saturated transactional write coordinator. Batching extraction avoids hammering providers but may sacrifice freshness; immediate synchronous refresh improves perceived recency for a small request at the cost of provider latency/limits.

## Defend the refresh decision with actual outcomes

A design choice table forces the constraint to be explicit:

| Trigger | Option | Benefit | Failure/price |
| --- | --- | --- | --- |
| First account connection | Full initial paginated import | Complete view only for verified requested supported coverage | Initial or historical acquisition can remain incomplete; unavailable ranges and pagination failure |
| Active daily budget view | Scheduled and webhook-triggered cursor sync | Efficient changes, bounded provider load | Freshness lag; webhook isn't proof of complete sync |
| User requests current view | On-demand refresh with stable original key | Explicit user intent and inspectable status | Throttling, timeouts and unknown provider completion |
| Categorization ambiguity | Versioned user override + replay/recompute | Respects user intent and corrects totals | Re-aggregation and notification corrections |
| Historical cross-user reports | Warehouse copy | Isolates expensive analytic scans | Lag, access controls and reconciliation requirements |

Define an SLI for the synthetic integration: of **all original authorized refresh triggers** received in a five-minute ingress cohort, at least 99% must result in a reconciled source-consistent current view with a published sync-cut within fifteen minutes, visible to the managed client and confirmed at receipt. For first link the view must also cover the requested provider-supported range with historical readiness established and no known gap; an initializing or partial view is not a success. Follow each original to its deadline, preserve the same key across retries and include errors, refused/throttled triggers, unknown outcomes and late completions in the denominator. Track provider-unavailable cases separately, but do not silently remove them from the user experience metric. Report accurate categorization separately: a view can be fresh and still incorrectly classified. A “sync succeeded” webhook is not a validated spending total.

Test a successful empty first-link response with `NOT_READY`, then partial initial and historical completion, and verify no complete view or completion notification is claimed early. Also test a stale sync generation attempting commit after a newer one, a crash after provider fetch but before cursor commit, pending-to-posted replacement, replayed t1, a user override racing with a stale classifier, an alert delivered twice and an account disconnect during a queued refresh. Only an observed correct ledger and client-facing view can establish success.
