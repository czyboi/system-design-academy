# Social feed publication and timelines

A timeline seems to be an ordered list of posts. But an author's list and a user's home feed have different **ownership, write amplification and visibility rules**. An author posting once should not wait for two million followers' feeds to update before receiving acknowledgment. Conversely, a reader following a small set of accounts should not need to scan the entire global post table to find ten relevant items.

- **M10-L02-LO1:** trace publication, user-timeline reads, follower fan-out, media handling, hydration and asynchronous failure recovery.
- **M10-L02-LO2:** defend fan-out-on-write, fan-out-on-read or hybrid serving given follower skew, latency, privacy, ordering and bounded resource budgets.

## State the product and workload before the architecture

A **post** has a stable `post_id`, `author_id`, canonical `created_at`, text and optional media reference; a **reply** also has a parent post ID. A **user timeline** lists a single author's posts in a stable order. A **home timeline** combines eligible posts from followed authors, subject to viewer visibility and any stated ranking policy. The two cannot be the same materialized collection unless every user follows exactly one author.

For this synthetic service, assume 100,000 original posts/day, 500,000 home-feed opens/day, a two-KiB average text body, 1% of posts carrying one 1-MiB media object, and an average of 200 followers per author **but a heavily skewed follower distribution**. Text is about 200 MiB/day before copies and indexes; media roughly 1,000 MiB/day. Uniform fan-out-on-write would create about `100,000 × 200 = 20 million` home-inbox entries/day on average—about 231 inserts/s before peaks, edits, deletions and retry overhead. A single celebrity with two million followers can dominate that budget. A mean alone hides the tail: estimate follower-count percentiles and maximum fan-out job duration, and test a burst envelope.

Define two separate contracts. (1) **Publish success:** for each original valid post, either return the durable canonical post ID plus recorded delivery intent or an explicit non-success; don't report a published post whose only copy is in a volatile queue. (2) **Feed freshness:** for each original valid home-feed open, the user receives a correctly authorized set, with eligible newly committed posts visible within a *declared* delay where the product promises it. The example uses 10 seconds for routine authors; celebrity pulls may appear on the next read. These are **design targets**, not observed provider benchmarks. Measure retries against the original request ID; failed, late or stale feed responses are not omitted from the denominator.

## Begin with durable author posts and user-timeline reads

The smallest correct path writes the authoritative post and reads it by author:

```text
Client POST (idempotency key)
  -> Post API: authenticate, validate parent/visibility, reserve post ID
  -> transactional Post Store: commit canonical post + event/outbox intent
  -> Client: stable post ID after required durability
  -> Dispatcher: publish post-created event from outbox
```

Use an input-bound idempotency record so a timed-out client retry does not allocate a second ID. If the post and outbox intent are separate commits, a crash can leave a visible post that never reaches fan-out. Either persist event intent with the post in one atomic write domain, or persist an independently recoverable pending index and prove a scanner can rediscover it. An outbox publisher may deliver duplicates; downstream effects need deduplication by stable `post_id` and recipient ID. The queue design follows [M07-L03](../../m07/lessons/M07-L03.md): producer acceptance, log replay and external side effects require separate boundaries.

A user-timeline read queries `posts_by_author(author_id, created_at desc, post_id desc)`, with stable tie-breaking, visibility checks and pagination. It does **not** depend on completion of a home-inbox fan-out job. Media bytes live in an object store behind authenticated access or deliberately public URLs; the post record references a committed media version. Do not put large blobs inside every recipient's inbox row. Notifications are downstream side effects, not prerequisites for the canonical post's durability.

## Compose home feeds without putting every author on the same path

**Fan-out-on-read (pull):** on each home-feed open, obtain the viewer's current follow set, query recent posts from followed authors, merge them, filter for eligibility and return a page. This avoids replicated inbox writes and naturally respects new following relationships. But a user following many authors can require many read operations; naive N-way scans, per-post author lookups and ranking work threaten read latency. Batch source fetches by shard and hydrate authors/media metadata in groups, not one RPC per post.

**Fan-out-on-write (push):** after canonical commit, a fan-out worker reads a consistent follower snapshot and asynchronously appends `(recipient_id, post_id, author_id, event_version)` to each follower's bounded home inbox. Reads are cheap and predictable. It trades storage and write IOPS for lower read assembly cost and introduces delayed propagation, retries, deletes and follower-graph race handling. Use a unique `(recipient_id, post_id)` key plus version policy so retries cannot duplicate one post. A user who unfollows an author must not continue seeing an old inbox entry merely because materialization happened earlier: the scenario uses the release-admission policy below, even when the inbox or cache still contains the old entry.

**Hybrid:** push ordinary authors' entries, but pull high-fan-out authors' recent posts at read time and merge them with the inbox. Choose the push/pull threshold from measured fan-out queue capacity, follower distribution and feed-read workload, not a magic follower number. For a celebrity, on-read fetch can itself be hot; cache bounded recent public author posts and batch reads, subject to privacy/revocation contracts. A celebrity-only read optimization does not imply that all celebrity posts are eligible for all viewers.

Historical evidence that large social-graph read workloads require careful caching and privacy-aware composition appears in Meta's [TAO engineering explanation (2013)](https://engineering.fb.com/2013/06/25/core-infra/tao-the-power-of-the-graph/) and the original [USENIX TAO publication](https://www.usenix.org/conference/atc13/technical-sessions/presentation/bronson). They describe an **historical Meta system**, not an endorsement of this specific push/pull threshold or modern product semantics.

## Walk two authors through two home timelines

Assume Ben follows ordinary author Ada and celebrity Zee. Cara follows only Ada. Ben's inbox initially contains older post `a09`; Cara's inbox is empty. At 10:00:00 Ada commits `a10`. At 10:00:01 Zee commits `z55`. Both canonical posts are durable. The worker responsible for delivering `a10` to Ben is delayed, but delivery to Cara finishes at 10:00:02.

| At 10:00:03 | Ben | Cara |
| --- | --- | --- |
| Push inbox | `a09` (new `a10` missing) | `a10` |
| Pulled followed celebrity posts | `z55` | None |
| Composed provisional top | `z55, a09` with possible routine-author freshness deficit | `a10` |
| At 10:00:08, after deduplicated worker recovery | `z55, a10, a09` | `a10` |

The system must not silently claim that Ben had the complete feed at 10:00:03 if the routine-author ten-second freshness contract is being evaluated. A queue retry can deliver `a10` twice; the inbox unique key collapses it. A privacy change on `a10` between enqueue and release is checked at the release-admission boundary below. A client whose feed request started at 10:00:03 is counted once whether it retries at 10:00:07.

A separate **author timeline** for Ada returns `a10` at 10:00:03 because it queries the canonical post store rather than the delayed Ben inbox. The two data products have independent freshness and failure characteristics.

## Make ordering, replies and pagination explicit

A reply has `parent_post_id` and its own durable creation record. A reply must not appear as though its parent is visible if the viewer cannot access the parent; a product can show a placeholder or hide the reply according to a documented policy. A fan-out worker that sees a child before a parent should not assign causal order based on *processing time*. It can sort by canonical commit order with stable `(created_at, post_id)` tie-break, or use an explicit parent/child relation when displaying threads. A globally consistent physical-time order requires a much stronger clock/order contract than this example assumes.

For this scenario, a page session pins a **bounded immutable candidate view** containing the ordinary inbox membership, celebrity-author source cuts, follow-set version, ranking version and an upper creation-time cut selected at session start. The cursor binds the viewer, view ID, those source cuts, ordering/ranking version, last exclusive `(created_at, post_id)` key and expiry; the server retains the view until expiry. Its creation watermark alone cannot freeze inbox membership. Ben’s first page at 10:00:03 returns `z55, a09`; `a10` arrives in his inbox at 10:00:08 but is not in that pinned view. A continuation after `a09` cannot promise to include that late entry: silently adding it ahead of the last key would skip it, while widening the continuation can repeat entries. The next page uses only the original membership; a new feed session can include `a10`. If the pinned view is lost or expires, explicitly require a restart rather than stitching a new view into the old cursor. Snapshot stability is separate from freshness: the ten-second promise is checked at the original open, and a source cut too old to meet it fails that open even if pagination is stable.

Each page then checks **current eligibility**; the frozen follow set defines candidates, not permission. Deduplicate by post ID when merging push and pull sets. A highly skewed user might need additional candidates to fill a page after permission filtering. State the maximum fan-in, page size and deadline; when a source times out, return a labeled partial page only if that is allowed by the API contract, otherwise fail without pretending completeness.

Keep an active inbox bounded by recent posts or a time window. For an inactive user, avoid backfilling every missed item by fan-out when they return; rebuild from followed authors' canonical histories and merge with retained inbox entries, applying current visibility. Old canonical posts may be retained longer than the materialized home feed. A rebuild must produce and pin a new bounded candidate view before issuing its cursor; do not combine its continuation with an earlier view.

## Decide visibility when the response is admitted

The worked policy uses an authoritative **release-admission** decision for each page after hybrid fetch, cache lookup and hydration. Serialize that decision with the relevant follow/unfollow and post-visibility changes; recheck the current viewer relationship and post-policy versions, then admit only still-eligible content. If policy authority is unavailable, fail closed rather than trust a stale inbox, cache fill or candidate snapshot. If Ben unfollows Ada before admission, suppress Ada’s entries and refill from the pinned candidate view if possible, or return a permitted short page/fail under the page contract. If admission wins first, the already admitted response may finish even if the unfollow follows; this policy cannot recall bytes already released. The same rule applies to every subsequent page and protected media retrieval, not just page one. A direct presigned media capability can remain usable for its scoped lifetime once issued; constrain lifetime/access or proxy authorization when the product needs a stronger revocation boundary. It cannot retroactively recall bytes. [M10-L01](M10-L01.md); [OWASP per-request authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request). This serialization is the example’s application contract, not a guarantee of the cited systems.

## Cache, search and notifications do not replace the feed contract

Post text, user profile previews and media metadata should be hydrated with **batched** queries, cache the appropriate public/authorized fields, and avoid N+1 request graphs. For mutable relationship or deletion state, a cached value must have a precise freshness boundary; a late fill from an older generation must not reopen a revoked post. Physical media-object cleanup follows durable post tombstones and may have a longer lag than the “no longer visible” policy. Reference the cache invariants from M06.

Keyword search is a **separate index projection**. Consume canonical `post-created`/`post-deleted` events into the index, track a source cut and do not equate queue acknowledgment with query-visible search. Tokenization, shard scatter/gather and ranking live in [M08-L03](../../m08/lessons/M08-L03.md), not in this social-feed case. A home-feed read must not become a full-text search if the use case is followed-author freshness. Notifications may be delayed, coalesced or suppressed and should not block posting.

## Failures, choices and observable success

| Constraint | Choice | Main benefit | Failure / cost to measure |
| --- | --- | --- | --- |
| Few reads per new post; extreme follower skew | Pull for high-fan-out authors | Avoids millions of writes from one author post | High fan-in and hot-author reads at feed open |
| Many home reads, ordinary follower counts | Push with bounded inbox | Fast assembled recent feed | Fan-out lag, retry duplication and storage amplification |
| Changing follow/visibility state | Serialized release-admission check per page/media request | Policy-ordered visibility | Added policy calls and possible empty/short pages |
| Long-inactive reader | Rebuild from canonical author histories | Avoid wasted infinite backfill | Rebuild latency and snapshot stitching |
| Search needs recent posts | Separate index with source-cut progress | Isolates search scaling | Index projection lag, stale deletions and extra storage |

For a sample **home-feed original-operation SLO**, define a five-minute cohort of valid first-ingress opens. At least 99% must return an authorized page of up to 20 correct entries (or a valid empty page) to the managed client within 800 ms, with routine-author posts committed at least ten seconds before ingress present if eligible and within the page's rank range. Rejected, wrong, timed-out, stale and late opens all count in the denominator; measure admitted-only latency separately. A product could choose other numbers, but it must not claim a fast read when it merely dropped incomplete sources. Under this scenario’s release-admission contract, an unauthorized release is a correctness failure even if the timeline appears otherwise full. Earlier admitted bytes and any already issued capability remain subject to their stated limits.
