# M10-L06 assessment — Search query cache at service scale

## Knowledge checks

**Q1 (LO1).** One hundred thousand 4-KiB search result entries are cached. Approximately how much *raw value* memory is needed, before keys, metadata and allocator overhead? What does a second full replica change?

**Answer.** 100,000 × 4 KiB = 409,600,000 bytes ≈ 391 MiB of raw result values. Two full copies need ≈782 MiB raw values. Eviction metadata and object overhead add memory; this is not the cache node's complete sizing requirement.

**Q2 (LO1).** A query misses the cache and the index returns only two of three shards. Can the API insert the partial top-20 under its complete-result cache key?

**Answer.** No. It must return a contract-compliant error or a separately labeled partial response. Missing shard hits may outrank those returned. A partial result's generation, missing-shard set and completeness cannot be represented as a verified complete result.

**Q3 (LO1).** Is a textbook O(1) map+list LRU operation the same thing as proving a retained search result fresh? Does Redis promise exact linked-list LRU semantics?

**Answer.** Neither. LRU chooses eviction victims based on usage, while freshness requires source-cut, expiry, generation and access checks. Redis documents approximate LRU and several alternative eviction policies; it does not guarantee the example's exact local data structure.

**Q4 (LO2).** At peak 2,315 queries/s with 90% cache hits, roughly what reaches origin? Then C1 with 50% of traffic fails while C2 retains its 90% hits and C1's replacement has none. Compute the new origin rate.

**Answer.** Before: 231.5/s. After: overall hits 0.5×0 + 0.5×0.9 = 0.45; origin is 0.55×2,315 ≈1,273/s. If safe origin capacity is 400/s, shedding, request coalescing, bounded warmup or more proven capacity is needed. Rerouting alone does not preserve user SLO.

**Q5 (LO2).** A new high-scoring search document is added, but none of the cached top-20 IDs changed. Can the old top-20 be reused automatically? What if only rank-model weights changed?

**Answer.** No. A new document can enter the top-20 and shift pages despite no old cached document mutation. Weight changes can reorder the same set. Invalidate by a proven dependency set, index generation and rank-model version, or honor a declared stale window.

**Q6 (LO2).** The index publishes `g18` at 12:00:08. A late result computed on `g17` fills at 12:00:10 with 30-second TTL. Why is this unsafe for current-generation requests?

**Answer.** Insertion-time TTL alone extends an obsolete result. Compare the captured generation against the currently required generation and reject the old fill for any current-generation key; if retained for historical use, key it by g17 and never serve as g18. Anchor time-limited reuse to source observation/cut and clock-error budget.

## EX-1 — Ranking change and cache node failure

**Scenario.** The cache serves 10 million original catalogue queries/day, 100k hot keys averaging 4 KiB values, with 2,315 peak QPS. Two cache nodes own disjoint halves. Before failure, the measured hypothetical cache hit fraction is 90%. C1 dies at peak load; C2 retains 90% hits for its half, C1's replacement has none. The origin's safe tested load under this mix is 400 QPS. At the same time, generation `g18` makes a previously lower-ranked document top-ranked, and a `g17` origin fill arrives late. Export demands all-shard complete top-20 from the specified generation within 300ms at the client. Browsing may accept labeled partial results.

**Synthetic strict-query drill.** For all 1,000 valid original strict queries in one five-minute first-ingress cohort, follow retries under the same original ID to client-validated receipt or their 300 ms deadline. The target is at least 99% correct, complete, current-to-requested-generation and currently authorized top-20 or valid empty results received on time. Exclusive client outcomes are 940 qualifying results on time, 15 partial, 10 wrong-generation/stale, five unauthorized, 10 rejected, 10 timed out and 10 otherwise-correct results received late. These are scenario values, not measured product results.

**Deliverables.** Calculate raw cache sizing, before/after origin QPS and overload. Draw hit/miss/fill and routing paths, with correctness keys, generation checks and a separate current-policy release gate. Trace a hit and a coalesced waiter across policy revocation at 12:00:05 before `g18` becomes query-visible at 12:00:08; specify both revocation/admission orderings and what happens when policy authority is unavailable. Explain why removing a revoked ID from an old top-20 cannot prove a complete exact replacement. Choose independent, replicated or sharded cache placement with explicit cost and failure policy. Explain a stale-fill rejection, rank-only change and post-delete invalidation. Calculate the strict original-operation SLI against its target, identify every failure class, distinguish admitted-only latency and origin protection from SLO success, and give two falsifying tests.

### Reference solution

1. Raw 100k × 4KiB ≈391 MiB; with two full replicas ≈782 MiB, before metadata. Ten million/day mean ≈116/s. Two-shard assignment is not full replication, and replacement warmup can create 1,273/s origin load, far beyond 400/s; before the failure the rate was ~232/s.
2. Cache key includes normalized query, filters, authorization scope, result sort/page, rank version and index generation. A miss pins the generation and expected logical shard set through query, fetch and retries; each eligible reader must have a query-visible proven source cut before cutover. Only complete results populate strict export entries. Each hit, miss result and single-flight waiter passes its own current policy-epoch release gate, serialized with revocation; a prior scope check is insufficient. Fail closed if required policy authority cannot confirm. Single-flight reduces identical concurrent fills, but the policy authority has separate capacity needs; origin concurrency limiting and explicit admission errors protect the origin without proving the client SLO.
3. `g17` fill captured before `g18` publication must not be served as current after cutover. If a policy revokes item X at 12:00:05 while `g18` is not query-visible until 12:00:08, a `g17` hit or delayed waiter still needs the new policy gate: revocation-first rejects the old result; admission-first allows the already-admitted response to finish, and delivered bytes cannot be recalled. Filtering X from old top-20 does not establish complete exact top-20. Use a proven current authorized view or fail strict requests; a relaxed browse result must be labeled. Rank-only, content and URL changes can also affect candidates; use scoped generation or a sound dependency proof.
4. Full replicated caches can preserve hits after C1 loss but double hot value memory and still require freshness verification. Sharding saves memory and exposes a cold-miss blast radius; an independent node pair duplicates some hot keys and has inconsistent hit ratios. Select based on observed capacity and SLO, not “Redis is fast.”
5. From first ingress to client-validated receipt within 300 ms, the five-minute cohort gives `940 / 1,000 = 94%`, below the 99% target. Partial, stale, unauthorized, rejected, timed-out and late originals remain in the denominator but not the numerator; retries are deduplicated. Admitted-only latency is a separate diagnostic. Test a revoked `g17` hit and coalesced waiter before `g18` visibility in both gate orders, policy authority outage, delayed fill after cutover, and cache loss. Origin protection can coexist with a failed user SLO.
