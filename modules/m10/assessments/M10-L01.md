# M10-L01 — Paste storage, short links and expiry: assessment

The companion evaluates decisions explained in [M10-L01](../lessons/M10-L01.md). Unless stated, the service uses the lesson's synthetic workload and strict public expiry policy.

## Knowledge checks

**Q1 (LO1).** A request creates an object, updates metadata to active, then the HTTP response times out. The client retries with the same idempotency key. What is the correct create behavior?

**Answer.** Read the durable operation receipt and return the same existing resource ID if the key and input match. Do not create a second mapping. Reject conflicting reuse of the key. A missing response cannot prove the first write failed.

**Q2 (LO1).** The service stores body bytes in an object store. Which ordering permits a readable link without making the metadata+object update magically atomic?

**Answer.** Claim/reserve pending identity; write immutable object and verify sufficient visibility; atomically publish active metadata referencing its exact object version; only then return the link. Repair or garbage-collect pending/orphan work with durable operation identity and conservative terminal checks.

**Q3 (LO1).** A short-link hit processor sees `h2` twice due to event replay, and `h1` at Jan 31 23:59 UTC, `h2` and `h3` at Feb 1. What are the monthly counts for the same code?

**Answer.** January 1, February 2 after deduplicating `h2`. Use the UTC event timestamp for bucket assignment and stable event identity before emitting `((year-month, code),1)` keys.

**Q4 (LO2).** Does a 10-character Base62 ID automatically make a private paste confidential? Is Base62 identical to base64url?

**Answer.** No to both. ID length alone does not prove authorization; private access requires a check. Base62 has 62 symbols and is a chosen positional alphabet; RFC 4648 base64url has 64 and differs from standard Base64 on two characters. Either encoding merely represents bits or numbers.

**Q5 (LO2).** An unlisted paste expires at 12:00. A read checks active metadata before 12:00 but its object fetch finishes at 12:00:20; a cache holds the same bytes. Can either response newly release content, and what if a delete races with another read?

**Answer.** No. After either fetch or cache hit, the authoritative gate must recheck generation, permission and expiry, using its bounded clock, at release admission. At 12:00:20 it rejects. The gate serializes this decision with tombstones: a delete that wins rejects admission; an admission that wins may finish its already-started response after deletion. Purge alone cannot establish this ordering or recall delivered client bytes.

**Q6 (LO2).** A content-derived truncated MD5 string is proposed as the public link for both pasted secrets and ordinary text. Give two independent problems and an alternative.

**Answer.** Truncation can collide; deterministic content-derived identifiers may reveal equal/predictable content and are not access controls. MD5 is unsuitable where collision resistance is required. Use random, sufficiently entropic IDs with an atomic unique insert and separate authorization for private objects. If deduplication is required, define a separate digest-domain policy and verify full content before reuse.

## EX-1 — Paste and redirect service under deletion

**Inputs.** A service receives 50,000 pastes/day, 1 million GETs/day, 2 KiB average content, 14-day expiry, and 100× peak reads. A paste `r7D` was active at 11:59:50, expires at 12:00:00 and sits in an edge cache with an otherwise-valid 60-second TTL. Two concurrent retries with the same caller key arrive during a new create; one response is lost after backend commit. Analytics receives a hit twice under the same `event_id`. A private paste with the same plaintext body as a public paste must remain invisible without permission.

**Synthetic read drill.** The target is at least 99% correct responses received by the client within 500 ms of first ingress, over all valid original GETs in each five-minute ingress window. A correct response is permitted content for an active read admitted by the authoritative gate, or an unavailable response when expiry/deletion wins the gate decision. Follow every original to its own deadline; retries retain the original ID. For one window of 1,000 originals, a controlled oracle independently records the policy state at the relevant release decision for each original: 980 require active content and 20 require an unavailable response. This classification includes requests the system actually rejects or times out. Exclusive client outcomes: among the 980, 970 received correct content on time, five correct content late, three were rejected and two timed out; among the 20, 15 received correct unavailable status on time, one was rejected, one timed out and three incorrectly received content. These numbers are scenario observations, not benchmarks.

**Deliverables.** Produce the minimum correct architecture and a write/read/delete sequence. Estimate payload storage and average/peak request rates. Specify unique-ID construction, collision handling, idempotency and the object-store metadata commit boundary. Explain the expired cached response and optional clean-up, choosing an explicit strict-expiry enforcement. Derive the long-URL redirect changes, including one privacy rule. Show the monthly hit map/reduce keys and duplicate policy. Define the original-operation SLI's population, window, start/end, deadline and correct response classes. Calculate the drill result against the target and distinguish admitted-only latency. Test at least two failure interleavings, including pre-expiry check followed by post-expiry fetch and a deletion race.

### Defensible reference answer

1. At steady state store approximately `50k × 14 × 2 KiB = 1,433,600,000 bytes ≈ 1.34 GiB` of content before redundancy/metadata. Average reads ≈11.6/s and writes ≈0.58/s; the illustrative 100× read spike implies ≈1,160 reads/s. Treat peaks as test inputs, not product guarantees.
2. Use a cryptographically secure random ID with a unique metadata constraint. A transactional operation receipt atomically binds the caller/key/input and chosen ID. Concurrent duplicate attempts return the same pending/committed operation, and the lost response retry returns the committed ID. Collision retries use a new random candidate for *the same logical operation*.
3. Metadata begins pending. Immutable object body is written/verified, then active metadata points to its version. A crash after body write but before activation leaves an unreadable pending record that reconciliation may complete. Never publish active metadata that points to unavailable content.
4. After object fetch or cache hit, the authoritative release-admission gate rechecks `r7D` generation, permission and expiry immediately before permitting response bytes, with its UTC clock error bounded and upper possible time before expiry. A check before 12:00 followed by fetch completion after 12:00 rejects at the gate; cached bytes do not change this. The gate serializes admission with deletion: delete-first rejects, admission-first may finish its in-flight response, and already delivered bytes cannot be recalled. A stale fill cannot reinstall an old active generation. Tombstone precedes asynchronous conditional object removal.
5. A redirect uses `code → validated target URL` and a 3xx response; it need not store paste text. It should not expose private content on the basis of matching plaintext/hashes, and its abuse/redirect policy and lifetime differ. Analytics counts distinct admitted redirect events grouped by `(UTC year-month, code)`; replay of the same `event_id` does not increase totals.
6. SLI: correct permitted content for active admissions or correct unavailable status when expiry/deletion wins, client-received within 500 ms of first ingress, divided by **all valid original GETs in the five-minute ingress window**, deduplicated by original ID and followed to their deadlines. The drill yields `(970 + 15) / 1,000 = 98.5%`, below 99%. Late responses, rejections, timeouts and wrong-content responses stay in the denominator and are not successes; track both classes separately. Admitted-only latency excludes rejected work and cannot prove the objective. Failure tests include a pre-expiry metadata check whose fetch finishes after expiry, both serializations of a read/delete race, and a lost create response followed by same-key retry.

### Rubric — 12 points

| Criterion | Points | Full credit |
| --- | ---: | --- |
| Workload and contract | 2 | Retention/rate math and declared peak, strict policy and private/public distinction |
| Correct create and idempotency | 3 | Unique-ID guard, same-key concurrent/timeout behavior, ordered object+metadata publication |
| Expiry and cache safety | 3 | Authoritative release admission after fetch/cache hit, generation/permission/expiry and bounded clock; serialization with tombstone, explicit admitted-in-flight limit; stale fill and version-safe cleanup |
| Redirect and analytics | 2 | Mapping/3xx separation, abuse/privacy boundary, deduplicated year-month aggregate |
| Measurable success and recovery | 2 | Five-minute original cohort, first ingress to client receipt within 500 ms, both correct-response classes, all failure categories, 985/1,000 = 98.5% versus 99%, admitted-only latency limitation, and two falsifying interleavings |

Equivalent designs receive full credit when they make the same observable guarantees and state what their consistency boundary actually enforces.
