# M10-L01 — Paste storage, short links and expiry: assessment

The companion evaluates decisions explained in [M10-L01](../lessons/M10-L01.md). Unless stated, the service uses the lesson's synthetic workload and strict public expiry policy.

## Knowledge checks

**Q1 (LO1).** A request creates an object, updates metadata to active, then the HTTP response times out. The client retries with the same idempotency key. What is the correct create behavior?

**Answer.** Read the durable operation receipt and return the same existing resource ID if the key and input match. Do not create a second mapping. Reject conflicting reuse of the key. A missing response cannot prove the first write failed.

**Q2 (LO1).** The service stores body bytes in an object store. Which ordering permits a readable link without making the metadata+object update magically atomic?

**Answer.** Claim/reserve pending identity; write immutable object and verify sufficient visibility; atomically publish active metadata referencing its exact object version; only then return the link. Repair or garbage-collect pending/orphan work with durable operation identity and conservative terminal checks.

**Q3 (LO1).** A short-link hit processor sees `h2` twice due to event replay, and `h1` at Jan 31 23:59 UTC, `h2` and `h3` at Feb 1. What are the monthly counts for the same code?

**Answer.** January 1, February 2 after deduplicating `h2`. Use the UTC event timestamp for bucket assignment and stable event identity before emitting `((year-month, code),1)` keys.

**Q4 (LO2).** Does a 10-character Base62 ID automatically make a private paste confidential? Is Base62 identical to base64url?

**Answer.** No to both. ID length alone does not prove authorization; private access requires a check. Base62 has 62 symbols and is a chosen positional alphabet; RFC 4648 base64url has 64 and differs from standard Base64 on two characters. Either encoding merely represents bits or numbers.

**Q5 (LO2).** An unlisted paste expires at 12:00. An edge cache filled at 11:59:50 with 60s TTL returns content at 12:00:20. What violated the strict policy, and what prevents it?

**Answer.** Cache lifetime extended beyond authoritative expiry. On each protected read validate active status and expiry through an authoritative versioned gate or proven equivalent, and bound all cache serving to the earlier of policy expiry and TTL. Purge alone is best effort across caches; an expired byte copy must not authorize a response.

**Q6 (LO2).** A content-derived truncated MD5 string is proposed as the public link for both pasted secrets and ordinary text. Give two independent problems and an alternative.

**Answer.** Truncation can collide; deterministic content-derived identifiers may reveal equal/predictable content and are not access controls. MD5 is not an appropriate contemporary security primitive. Use random, sufficiently entropic IDs with an atomic unique insert and separate authorization for private objects. If deduplication is required, define a separate digest-domain policy and verify full content before reuse.

## EX-1 — Paste and redirect service under deletion

**Inputs.** A service receives 50,000 pastes/day, 1 million GETs/day, 2 KiB average content, 14-day expiry, and 100× peak reads. A paste `r7D` was active at 11:59:50, expires at 12:00:00 and sits in an edge cache with an otherwise-valid 60-second TTL. Two concurrent retries with the same caller key arrive during a new create; one response is lost after backend commit. Analytics receives a hit twice under the same `event_id`. A private paste with the same plaintext body as a public paste must remain invisible without permission.

**Deliverables.** Produce the minimum correct architecture and a write/read/delete sequence. Estimate payload storage and average/peak request rates. Specify unique-ID construction, collision handling, idempotency and the object-store metadata commit boundary. Explain the expired cached response and optional clean-up, choosing an explicit strict-expiry enforcement. Derive the long-URL redirect changes, including one privacy rule. Show the monthly hit map/reduce keys and duplicate policy. Define one client-visible original-operation success SLI and test at least two failure interleavings.

### Defensible reference answer

1. At steady state store approximately `50k × 14 × 2 KiB ≈ 1.4 GiB` of content before redundancy/metadata. Average reads ≈11.6/s and writes ≈0.58/s; the illustrative 100× read spike implies ≈1,160 reads/s. Treat peaks as test inputs, not product guarantees.
2. Use a cryptographically secure random ID with a unique metadata constraint. A transactional operation receipt atomically binds the caller/key/input and chosen ID. Concurrent duplicate attempts return the same pending/committed operation, and the lost response retry returns the committed ID. Collision retries use a new random candidate for *the same logical operation*.
3. Metadata begins pending. Immutable object body is written/verified, then active metadata points to its version. A crash after body write but before activation leaves an unreadable pending record that reconciliation may complete. Never publish active metadata that points to unavailable content.
4. On read, a protected authoritative metadata/policy check rejects `r7D` after 12:00 regardless of the old cached body. Cache fill guards on version/expiry; deletion writes a tombstone before asynchronous object removal. A stale fill must not reinstall a deleted or expired active response.
5. A redirect uses `code → validated target URL` and a 3xx response; it need not store paste text. It should not expose private content on the basis of matching plaintext/hashes, and its abuse/redirect policy and lifetime differ. Analytics counts distinct admitted redirect events grouped by `(UTC year-month, code)`; replay of the same `event_id` does not increase totals.
6. Example SLI: correct content for active permitted original GETs, or correct unavailable response for deleted/expired originals, validated at client within 500 ms / **all valid original GET arrivals in the five-minute window**, deduplicated by original ID and followed to their deadlines. Track class-specific success to prevent “all errors are fast” gaming; include late, rejected and failed originals in denominator. Failure tests: lost create response followed by same-key retry; delayed cache fill after tombstone; uncertain object upload before metadata activation; stale edge after expiry.
