# M10-L04 companion — Financial aggregation and budgeting

## Six checks and explained answers

**Q1 (LO1).** A worker fetched two cursor pages from a transaction API, then crashed before persisting its changes. Can it advance the stored cursor to the final page merely because those HTTP calls returned successfully?

**Answer.** No. Durable cursor progress must not pass unapplied changes. Replay from the last committed cursor with stable source identities, apply a coherent update batch with cursor advancement under the provider's contract, then publish downstream change intent. An HTTP response is not proof the local ledger reflects it.

**Q2 (LO1).** A pending transaction `p7` for 40 USD is removed and a posted `q9` for 40 USD appears. Both have unique IDs. Why can a naïve `SUM(amount)` still be wrong?

**Answer.** The two records may represent one economic purchase at different lifecycle stages. Reconcile pending-to-posted linkage and maintain one selected canonical current representation in the spending view. Raw audit can retain both transitions without counting both as purchases.

**Q3 (LO1).** For January, posted `t1=+75`, `t2=+40`, `t3=-20`, `t4=+60`, with t1 and t3 and t4 in Groceries, t2 in Transport, and `t1` is replayed. What are the totals?

**Answer.** Groceries 115 USD and Transport 40 USD. Deduplicate by stable source transaction identity, not by counting fetch events. Use integer minor units and the same period/currency.

**Q4 (LO2).** A user reclassifies `t4` (60 USD) from Groceries to Transport. What happens to totals and budget alerts?

**Answer.** New totals Groceries 55, Transport 100. Under sample limits 100 and 80, retract or correct the prior Groceries exceedance and consider a new Transport exceedance by 20. Carry a higher classification and aggregate revision, and version alert transitions so delayed messages can't present the old result as current.

**Q5 (LO2).** Is the hash of a banking password a reliable cross-connection account ID? Should refresh tokens or full transaction descriptions be put on the warehouse queue?

**Answer.** No. Passwords rotate, can be shared, and may never be exposed through delegated integration; use provider-documented account identity with tenant scope and consent. Tokens are secrets; avoid copying them into analytics or event logs, and minimize/redact personal fields.

**Q6 (LO2).** Can a warehouse result generated 30 minutes ago be called the user's current bank balance if a webhook was received five minutes ago?

**Answer.** No. Webhook is a trigger, not proof of completed reconciliation or a bank-authoritative current balance. Show as-of/source-cut timestamp and meaningful freshness/error state. OLTP and warehouse have different latency and contractual purposes.

## EX-1 — Replayed refresh and changed budget category

**Scenario.** A consenting user has USD posted transactions t1 Groceries +75, t2 Transport +40, t3 Groceries refund -20, t4 Groceries +60. January Groceries budget is 100 USD and Transport 80. Two manual refresh attempts use the same original key. A provider emits t1 twice; a pending transaction p7 is removed as posted q9 appears, but p7/q9 have not yet been included in the above totals. After the initial monthly report the user changes t4 to Transport. A stale classifier tries to publish an earlier version and two alert-delivery attempts race.

**Deliverables.** Define account consent/token/identity boundaries; draw durable refresh and source change flow through a cursor/canonical transaction store, protected raw log, current aggregate and notification; calculate initial/final totals and active alerts; show why posted q9 must replace p7 rather than add to it twice; justify the OLTP, warehouse and object-store split, and specify an original-trigger SLI and at least two crash/race tests.

### Worked reference

1. Link with supported scope/consent and restricted provider credentials. Never use password hashes as account IDs; only provider-supported scoped identities. Durable intent claims the original manual key before dispatch; a second same-key request returns the same operation state. Store no provider token in budget/warehouse events.
2. Sync from committed cursor C0 and stage provider added/modified/removed pages. On successful coherent application, update current transaction identities and cursor C1 together, emit a recoverable change event. A crash before commit resumes from C0; a duplicate t1 is an update/no-op for one source ID. A pending-to-posted transition replaces the pending representation; account for q9 once when it becomes eligible for the posted-only view.
3. January initial `Groceries=75-20+60=115` and `Transport=40` (USD), so Groceries is 15 over its exercise budget. After category override for t4, `Groceries=55`, `Transport=100`, and Transport is 20 over. The new version's committed totals supersede the old; stale classifier output must fail a version/cut comparison.
4. Notification intent follows the aggregate revision; delivery dedup key includes threshold transition and budget revision. Replaying a “Groceries exceeded” alert after the revision is obsolete and should be suppressed or corrected by policy. No notifications mutate the ledger.
5. OLTP stores live accounts, source IDs, category rules, recent summary; protected object log supports replay/retention; warehouse serves large historical groupings with as-of timestamps. Separate currency domains; do not incorrectly sum USD with other units.
6. Example success denominator: **all original valid refresh triggers** received in a five-minute ingress window, deduped by original ID, with a reconciled view within fifteen minutes. Count failure, throttling, late and unconfirmed as failures; measure classification accuracy separately. Tests: crash after last provider page/before cursor commit; concurrent duplicate refresh; late classifier after user override; pending-to-posted swap; duplicate alert delivery.
