# M10-L08 assessment — Iteratively scaling a cloud application

## Knowledge checks

**Q1 — resource split (LO1).** A web/SQL server runs out of local disk due to uploaded images. What is the first useful decomposition, and which failure does it introduce?

**Answer.** Move durable image objects into separately secured object storage and transactional metadata to a database with clear object-version binding. This removes media bytes from SQL disk but creates a cross-store publication problem: orphaned objects or active metadata pointing to an unavailable object after a crash. Use pending metadata, verified object storage and guarded activation rather than pretending SQL+S3 are one transaction.

**Q2 — public/private network (LO1).** If an app instance has a private IP address, is that proof it is in a private subnet or that DB traffic is encrypted?

**Answer.** No. Public/private subnet classification depends on route tables and direct internet-gateway routes. IP type alone does not establish reachability or encryption. Restrict required inbound traffic with security groups and configure transport and identity per hop, with NAT/endpoints for private outbound needs. ALB HTTPS target connections encrypt but ALB does not validate target certificates; restrict target ingress to the ALB security group and consider AWS’s VPC boundary. Separately configure the application’s RDS client to verify the database certificate and hostname.

**Q3 — high availability vs read throughput (LO1).** An RDS MySQL Multi-AZ **DB instance** has a standby in another AZ. Can the application route read queries to that standby during normal operation?

**Answer.** No. The ordinary RDS Multi-AZ DB instance standby supports HA/failover and is not readable. A separate RDS read replica or appropriately configured Multi-AZ DB cluster can serve reads with product-specific semantics. Do not treat asynchronous replica data as automatically current.

**Q4 — writer bottleneck (LO2).** The writer sustains at most 600 transactions/s in the controlled test, while 1,000/s are offered. Will increasing app servers from four to sixteen necessarily restore end-to-end SLO?

**Answer.** No. More web capacity cannot increase the single writer's sustainable commit rate. It may increase DB concurrency and contention. Measure lock waits, write amplification and transaction cost; address the writer or admission policy, and count refused/late original operations as failures.

**Q5 — autoscaling delay (LO2).** A campaign creates a sudden peak that lasts two minutes. Can target tracking guarantee immediately ready extra capacity from cold instances?

**Answer.** No. Detection, control-loop response, allocation, deployment, application warmup and cache/DB connection warmup take time. Use bounded min/max and scale-out readiness, scheduled capacity for known peaks, and controlled admission; don't equate the desired instance count with productive capacity.

**Q6 — downstream work (LO2).** A thumbnail worker writes an object then crashes before acknowledging the SQS message. Must the queue guarantee exactly one thumbnail write?

**Answer.** No such generic guarantee is assumed. Retry can repeat the message and external effect. Use stable job/media version, idempotent conditional object update and a durable processed receipt. Record transformation completion only when the committed thumbnail version is visible; queue acknowledgment by itself isn't user-visible completion.

## EX-1 — Evolve a catalogue without hiding failed requests

**Scenario.** A catalogue starts at 50k DAU, eight reads and 0.4 updates per user daily, each update averaging one 1-MiB image. It experiences 100× peak reads. An initial EC2 host runs app, SQL and media files. Tests subsequently show (A) thumbnail CPU and disk pressure, (B) host-AZ failure, (C) repetitive catalogue reads and (D) single SQL writer sustaining 600 writes/s under 1,000/s offered, while a two-minute campaign causes a web burst. For one synthetic five-minute first-ingress cohort of 1,000 original valid reads, followed across retries to managed-client receipt or the 400 ms deadline, 930 are correct and authorized on time, 30 time out, 20 are rejected during overload or warmup, and 20 are correct but late. The target is at least 99% correct and authorized on time; these exclusive outcomes are scenario inputs.

**Deliverables.** Calculate average reads/updates and image bytes. Draw the original and final request/data paths and explain five incremental architecture changes, each tied to a measured signal. Compare one RDS DB instance Multi-AZ standby to read replicas or a Multi-AZ DB cluster. Specify security group and per-hop TLS/identity boundaries, private subnet routing, S3/CloudFront origin access and separate private-viewer entitlement, ALB, and Auto Scaling min/max, versioned launch/readiness/warmup and rollback limits. Compare InnoDB buffer-pool work with an external result cache, state replica-lag routing and SQS thumbnail recovery, and explain when to split web and application groups. Diagnose writer saturation. Calculate the original-cohort SLO against its target, distinguish admitted-only latency, and give failure-injection evidence.

### Reference response

1. Initial load is 50k×8 = 400k reads/day (≈4.6/s mean), 50k×0.4 = 20k updates/day (≈0.23/s mean), ~20GiB/day of new 1-MiB images before replication; peaks require separate test capacity.
2. First measure image CPU/disk and move thumbnail derivation to durable asynchronous jobs. Separate S3 objects and RDS metadata, with pending→active guarded activation and protected object identity. Internet-facing ingress sits in public routed subnets, with app/DB private and least-privilege security groups. ALB HTTPS target traffic is encrypted but ALB does not validate target certificates; restrict target ingress to the ALB security group and assess the documented VPC boundary. Separately configure app→RDS certificate/hostname verification. For a private regular S3 origin use distribution-scoped bucket permission and CloudFront OAC configured always-sign; separately check viewer entitlement and issue scoped expiring signed URLs/cookies or use an authorized proxy, with capability revocation limits.
3. Add ALB + healthy app instances in separate AZs. Standard RDS Multi-AZ DB **instance** standby serves failover, not read scale; use separate read replica or multi-AZ cluster with actual semantics when reads need scaling. A failed AZ still needs adequate surviving capacity and recovery checks.
4. Measure MySQL 8.4 InnoDB buffer-pool page reads, query plans and CPU: page hits still execute SQL, whereas a valid external result-cache hit can avoid query work at the cost of stale, miss-load and authorization controls. Route current-state reads to the writer or a replica proven to have applied the required revision; a stickiness timer alone is not proof. Use lag-tolerant replicas only under an explicit stale-read policy. One 600 writes/s DB writer under 1,000/s offered is overloaded regardless of web instance count; address write transaction/partition/invariant and/or reject with visibility rather than claiming SLO success.
5. Pin a numbered launch template, AMI, artifact and nonsecret configuration; assign a scoped role to obtain runtime secrets. Bootstrap and dependency checks precede lifecycle completion and health readiness; failed bootstrap does not serve, and metric warmup is not readiness. Roll a bounded refresh with a previous numbered template and a conditional recovery plan, not an unconditional rollback promise. Keep combined web/app tiers when profiles match; split for measured independent scaling or release needs, accounting for extra routing and operations. Put media intent in a recoverable queue and write derived object versions idempotently. Separate warehouse scans from OLTP and run client/zone/database/worker drills.
6. Success is **930/1,000 = 93%**, below required 99% in the five-minute first-ingress cohort, measured through managed-client receipt within 400 ms. Excluding failures, rejections, late responses or only reporting admitted-success latency would be wrong. Assert recovery only after validated usable service and transaction receipt checks, not after an ALB health signal.

### Rubric (14 points)

| Criterion | Points | Required proof |
| --- | ---: | --- |
| Workload and first viable system | 2 | Correct arithmetic, bottleneck hypothesis and initial request boundary |
| Stage progression and network/data separation | 4 | Each change has its trigger; SQL/S3 pending activation; VPC and ALB/AZ; ALB HTTPS target certificate limitation and restricted target SG, distinct app→RDS certificate/hostname verification; private regular S3 OAC always-sign plus distribution bucket permission and separate viewer entitlement/capability limits |
| Scaling choice and trade-offs | 4 | RDS standby versus replicas and required revision proof, InnoDB page caching versus external results, combined versus separately scaled tiers, numbered template/bootstrap/role/readiness versus metric warmup and conditional recovery, 600 vs 1,000 writer limit |
| Asynchronous/recovery and user SLO | 4 | Idempotent thumbnail queue and failure drills; five-minute original-valid ingress cohort, managed-client receipt within 400 ms, 930/1,000 = 93% misses 99%; timeouts, warmup/overload rejections and late work retained, admitted-only latency separate |

Equivalent managed or self-managed designs earn full credit when they preserve the same observable contract, source-cut assumptions and failure evidence.
