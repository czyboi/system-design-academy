# M10-L03 assessment — Crawler and web-search composition

## Knowledge checks

**Q1 (LO1).** Two URLs on different hosts return byte-identical bodies with hash H. Can the crawler safely discard all metadata for the second URL?

**Answer.** No. It may deduplicate the immutable body after trustworthy collision checks, but each URL retains independent origin, fetch history, links, robots/policy and tombstone state. Search may cluster representatives by a declared policy, not treat the origins as one authoritative URL.

**Q2 (LO1).** A reducer sees URL `u1` twice and `u2` once. Contrast “emit keys with count exactly one” and “emit one copy per distinct key”.

**Answer.** Unique-only filtering emits `u2` but removes `u1` entirely; distinct filtering emits one `u1` and one `u2`. A crawler that wants one fetch candidate per URL needs the latter, with a defined merge rule for priority and source provenance.

**Q3 (LO1).** A fetch of `u1:v2` succeeds, but the index publish event is lost after the page-store commit. What does a successful crawl metric prove and what is required?

**Answer.** It proves only that a page version was persisted. The search index may still serve `v1`. Persist index intent atomically with page-version metadata or recover it deterministically, replay by stable `(url,version)`, update postings/title/snippet and publish a source-cut manifest after required shard acknowledgments.

**Q4 (LO2).** An origin's robots.txt disallows `/private`. Does that enforce secrecy? May an HTTP crawler simply switch to raw UDP to avoid TCP overhead?

**Answer.** No. Robots instructions guide compliant crawlers and aren't authentication; pages need access controls. Arbitrary UDP datagrams do not implement HTTP. HTTP/3 uses negotiated QUIC and HTTP semantics, whereas other versions have their specified transports.

**Q5 (LO2).** Two near-duplicate product pages differ only in a crucial price or legal disclaimer. Is Jaccard similarity above 0.95 sufficient proof they are interchangeable?

**Answer.** No. Similarity is a heuristic dependent on representation and tokenization. A rare legally significant change can leave high overlap. Retain URL/version identity and preserve the exact fields when making search representatives or deduplication decisions.

**Q6 (LO2).** A search response has all shards from generation `g17` but an observed source page version already persisted for `g18`. Is the result complete and fresh?

**Answer.** It may be complete **within g17**, but not fresh relative to the declared source-cut rule. The service should report both coverage and freshness, or fail an export requiring both. Never mix shard generations to claim one complete ranking.

## EX-1 — Crawl a duplicate, process a change, answer a query

**Inputs.** At 10:00, distinct URLs `u1` and `u2` return identical `Blue kettle 2 L` bodies. A 10:10 recrawl of `u1` returns `Blue coffee maker 2 L`; the page is durably stored as `v2`, but its index event times out. Search generation `g17` contains the older version. An origin may return a temporary `503`; a third page links back to `u1`. Crawl quota 2m successful fetches/day at 50KiB average; retention 30 days. A strict search export requires all shards and a verified source cut no older than five minutes.

**Task.** Estimate raw daily and 30-day bytes. Define the frontier key/lifecycle and a per-host scheduling constraint. Trace the two URLs through exact deduplication without losing their identities, then the changed `u1:v2` through page-store event and generation publication. Explain a search for `coffee maker` before/after `g18`, and how a temporary error, robots disallow and URL loop affect scheduling. Correct the unique-only filtering bug. Provide client-facing export and change-to-index SLIs, plus a failure injection.

### Worked solution

- Raw bytes ≈ `2m × 50KiB = 95 GiB/day`, ≈2.9TiB over 30 days (before compression, duplicates, index and replica overhead). Mean ≈23 successful fetches/s, not a burst or host budget.
- Normalize URIs conservatively to a durable `(fetch_key, next_due_at, fetch_generation)` record. Leasing is recoverable. Host-level concurrency and robots policy gate dispatch, and a cycle only updates already-known URL scheduling rather than recursing forever.
- Both `u1` and `u2` retain their own URL identities/provenance. Body H can be stored once if the bytes are verified identical. A distinct reducer emits **one** candidate per URL even when a URL appears multiple times, unlike unique-only filtering.
- `u1:v2` has a durable page version and pending index job. A missing acknowledgment is **unknown**, not proof that the update never committed. Query and/or retry by stable version; only publish `g18` after shard source cuts confirm atomic visibility of the new document's title, snippet and postings and removal of the old terms. A `g17` search for `coffee maker` misses `u1`; `g18` includes it. Strict export against the required cut fails while freshness is unproven.
- Back off on 503, honor RFC9309 rules and failure policy, and never use robots as authorization. A page change is successful by the exercise's change-to-index SLI only if the new version becomes query-visible within five minutes from persisted source time; late, failed and missing versions remain failures. Search export success requires all requested shards from one fresh generation by client deadline across **all original valid export requests**.
- Falsify by crashing after page persistence but before event dispatch, replay `v1` late and check that `g18` does not regress, while measuring wrong/old search results at client.
