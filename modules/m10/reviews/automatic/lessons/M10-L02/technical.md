### M10-L02-T1 — select the concurrent visibility decision boundary

- **Severity:** major. **Status:** resolved in round 1; see resolution evidence below. Quoted passages/locations/problem below preserve the original round 0 record.
- **Locations:** `modules/m10/lessons/M10-L02.md:47`, lines 64, 72, 78, 88 and 92; `modules/m10/assessments/M10-L02.md:44`, lines 52, 55 and 63; evidence C5 at `modules/m10/evidence/M10-L02.md:11`.
- **Exact passages:** “filter against current relationship/visibility policy at the read boundary or enforce a proven bounded invalidation policy”; “according to a specified authorization/version boundary”; “For an alternate stricter privacy contract, missing a revocation boundary is a correctness failure”.
- **Problem:** the lesson recognizes the issue but does not select a boundary for the worked scenario or specify the alternative invalidation bound. The reference consequently cannot determine what a second-page request already in flight at the unfollow is permitted to release. Checking a current relationship, pausing for celebrity fetch/hydration, then releasing after an unfollow or protected-post revocation is not equivalent to authorization at release admission. A late cache fill and a direct media capability add serving paths; an inbox entry/version does not itself authorize them. The actor is also only “A user” in the scenario, while the answer assumes Ben. These missing conditions affect which feed response is correct under the stated authorized-page SLO.
- **Evidence:** [OWASP, Validate the permissions on every request](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request) supports resource authorization on each serving request, but does not define this application's concurrent revocation timing. The [TAO paper §2 and §6.1](https://files.usenix.org/s3fs-public/cdn/atc13-bronson.pdf) describes view-time privacy composition and an eventually consistent graph store; citing TAO does not establish immediate revocation. Accepted prerequisite `modules/m10/lessons/M10-L01.md:71`–73 explicitly distinguishes serialized release admission from older checks and already admitted bytes. Applying that distinction here is an application-design inference, not a vendor guarantee.
- **Bounded fix:** name Ben as the unfollower and choose a scenario contract. One option is an authoritative release-admission decision after hydration/cache retrieval, serialized with relevant relationship/post-policy changes, with observed versions rechecked and failure closed when authority is unavailable. State both orders: change wins → suppress/refill or fail; admission wins → previously admitted response may complete. Explicitly apply the policy to each page and protected media-serving path, using L01's capability caveat where applicable. Alternatively, choose and quantify a bounded-delay policy and grade it consistently. Add one concrete race to the lesson/reference and align the SLO; do not imply recalling already delivered bytes.

### M10-L02-T2 — a creation-time watermark alone does not stabilize hybrid pagination

- **Severity:** major. **Status:** resolved in round 1; see resolution evidence below. Quoted passages/locations/problem below preserve the original round 0 record.
- **Locations:** `modules/m10/lessons/M10-L02.md:72`–74; `modules/m10/assessments/M10-L02.md:36`, lines 46, 52 and 63.
- **Exact passages:** “define a read snapshot or upper watermark and last sort key”; “Rebuild cursors must incorporate stable high-watermark/version semantics or they can intermix incompatible snapshots and repeat/miss items.”
- **Problem:** no cursor is bound to a concrete candidate-set generation/snapshot. An upper creation-time bound plus last key excludes newly created posts, but does not freeze membership below that bound. In the supplied trace, a two-item page at 10:00:03 can return `z55,a09` and save `a09` as its last key. `a10` was committed before the page watermark but arrives in the inbox later and sorts ahead of `a09`. A next page strictly after `a09` misses it; widening the query to recover it risks repeats. Recomputing the follow set or changing push/pull source selection during an inactive-user rebuild creates similar stitching ambiguity. Deduplication cannot recover a candidate that was never selected. The lesson offers “upper watermark” as an alternative without its necessary membership/continuation condition.
- **Evidence:** [Elasticsearch 8.19, search-after pagination](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/paginate-search-results.html#search-after) explicitly distinguishes a sort continuation from a point-in-time view when indexed state changes. This is a named illustration of the constraint, not a requirement to use Elasticsearch for feeds. The counterexample above follows directly from this lesson's delayed-inbox trace. Accepted M07-L03's snapshot/continuation contract likewise distinguishes a saved position from the state it represents; it does not automatically give a newly constructed home-feed cursor that binding.
- **Bounded fix:** choose a bounded serving snapshot/generation or explicitly weaker live-pagination contract. For a stable view, show a cursor/session binding viewer, immutable candidate/source membership and ordering/ranking version, upper cut, last exclusive sort key and expiry. Keep that view stable across pages/rebuild continuation while applying T1's current eligibility policy; expired/lost snapshot state requires an explicit restart, not silently stitching another generation. A creation-time watermark is sufficient only if the selected storage/source contract also fixes the underlying eligible candidate membership. Give a short late-`a10`/second-page trace and reflect it in the reference/rubric. This does not require implementing a global log-replay system or prescribing a vendor.
