## Prioritized findings — original round 0 record, with current status

### M10-L04-T1 — successful first-link pagination does not establish initialized history

- **Severity:** major. **Status:** resolved in round 1; see the resolution evidence below. Locations/passages/problem below record the original round 0 content.
- **Locations:** `modules/m10/lessons/M10-L04.md:33`, extraction flow at lines 44–48, cursor discussion at line 52, first-link table row at line 105 and success definition at line 111; `modules/m10/assessments/M10-L04.md:51` and line 55; `modules/m10/evidence/M10-L04.md:9` (C3).
- **Exact passages:** “atomically apply coherent staged update set and advance cursor C1”; first connection promises “Complete source view under provider's contract”; success requires “a reconciled source-consistent current view with a published sync-cut”.
- **Problem:** the flow has no initialization/coverage gate between fetching all *currently available* pages and publishing the view as successfully reconciled. A newly linked Item can return HTTP success with no data, or a completed initial subset while historical acquisition remains pending. Neither is a failed-permission/outage case of the kind described at line 33. The generic instruction to expose an unknown gap is useful, but the named Plaid example never identifies this normal successful-response case or tells the worker how it affects completion. A learner can follow the shown sequence and label missing historical spending as a complete initial view, while also crediting the refresh SLI.
- **Primary evidence:** Plaid's [Fetching transaction data](https://plaid.com/docs/transactions/add-to-app/#fetching-transaction-data) distinguishes a successful empty initial response, an initial subset and later history readiness; another call is needed as more data arrives. The [`/transactions/sync` response field `transactions_update_status`](https://plaid.com/docs/api/products/transactions/#transactionssync-response-transactions_update_status) distinguishes `NOT_READY`, initial completion and historical completion. Exhausting pagination is not the same boundary as completing source acquisition. These are current publisher documentation observations, independently opened for this review.
- **Bounded fix:** add a short first-link trace: empty/not-ready → retain initializing status and retry/wait for updates → partial initial history with explicit coverage → history complete for the requested supported range → reconciled published view. Define which coverage is required by the example's initial-refresh success contract; a partial result may be displayed as partial but cannot satisfy a promise of full history. Carry that condition into EX-1/reference and evidence C3, and include a successful-empty initialization case in the suggested tests. Do not imply that five years can be backfilled from an arbitrary provider merely because the application retains five years.

- **Problem:** q9 is a separate posted record that is explicitly absent from the four stated transaction totals. Its amount, category and budgeting period are not supplied. The reference says to count it once when eligible but still fixes the exercise's totals/alerts at the t1–t4-only answers. If q9 belongs to January Groceries or Transport, at least one answer changes; if it belongs to another period, those answers can remain correct. The scenario does not choose either condition. This makes the required calculation and full-credit criterion underdetermined, despite the t1–t4 arithmetic itself being correct. Plaid's [Pending and posted transactions](https://plaid.com/docs/transactions/transactions-data/#pending-and-posted-transactions) supports a removed pending ID and a newly added posted representation, and explicitly permits changed details. That lifecycle relationship does not supply the missing financial inputs.
- **Bounded fix:** state that p7/q9 are a separate lifecycle-only trace excluded from the January calculation (for example, q9 posts in February), or specify q9's amount/category/period and update all affected totals, alerts and rubric values. Keep the numeric t1–t4 trace intact if choosing the former. Supply enough explicit data to explain q9's one contribution without guessing.

### M10-L04-T3 — identify the authority for source ordering

- **Severity:** minor. **Status:** resolved in round 1; see the resolution evidence below. Locations/passages/problem below record the original round 0 content.
- **Locations:** `modules/m10/lessons/M10-L04.md:25`, lines 52–56 and line 89; `modules/m10/assessments/M10-L04.md:62`; `modules/m10/evidence/M10-L04.md:11` (C5).
- **Exact passage:** “Track source revisions and transaction state so a late older page cannot restore a removed record.”
- **Problem:** the ordering invariant is correct, and line 56 already recognizes concurrency risk, but “source revisions” is not mapped to an implementation authority. A reader could infer that each Plaid transaction provides a monotonic record revision or that opaque cursors can be numerically ordered. C5 calls revision gating an application choice; the teaching flow should make that boundary equally explicit.
- **Primary evidence:** the [Plaid sync request/response contract](https://plaid.com/docs/api/products/transactions/#transactionssync) provides cursors and change sets, rather than a general per-transaction monotonic revision protocol. Its pagination restart rule is tied to the starting cursor. This does not itself implement the application's stale-worker fence.
- **Bounded fix:** name an application-assigned committed generation for each chosen sync stream, serialize its apply path or require an expected-current-cursor/generation check at commit, and reject an older run after a newer generation commits. Distinguish that generation from category revision and provider fields. State that opaque cursors are stored/compared for identity under the provider contract, not sorted as revision numbers. This can be a few sentences rather than executable code.
