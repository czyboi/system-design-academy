### M10-L03-T1 — the search SLO is not yet a decidable service objective

- **Severity:** major. **Status:** resolved in round 1; see resolution evidence below. Quoted passages/locations/problem below preserve the initial round 0 record.
- **Locations:** `modules/m10/lessons/M10-L03.md:23`, lines 93 and 99; `modules/m10/assessments/M10-L03.md:44`, lines 46, 54 and 64.
- **Exact passages:** “successful responses must satisfy requested completeness and source-cut contract plus deadline”; “Search export success requires all requested shards from one fresh generation by client deadline”; rubric asks only for “Both SLI populations”.
- **Problem:** the original-operation population and failure accounting are useful, but no concrete query response deadline, success proportion or cohort window is defined. The five-minute **source-cut age** in the exercise is not a query latency deadline. The separate persisted-change SLI has a five-minute per-change publication deadline, but an unspecified cohort window and no target proportion. Thus a learner cannot decide whether the proposed service meets its stated SLO, and a rubric can award full credit for a population definition without a measurable reliability decision. Fast admitted-only results must remain separate, as the lesson already recognizes.
- **Evidence:** [Google SRE Workbook, Implementing SLOs](https://sre.google/workbook/implementing-slos/) distinguishes an SLI specification/measurement from a reliability target and explicitly discusses the target's time window. It also distinguishes server-side observations from client experience. The missing example values are application choices, not values to infer from that source or from the five-minute index lag.
- **Bounded fix:** choose explicit original query/export and persisted-change cohort windows and target proportions. Define query timing from first ingress to managed-client receipt with a numerical deadline; retain all original failures/rejections, unknown, wrong, stale, incomplete and late outcomes. State the reference point for source-cut age separately from response latency, and keep unknown not-yet-fetched origin changes outside the persisted-change population with separate coverage reporting. Add a small synthetic outcome cohort to EX-1, calculate each relevant numerator/denominator and compare it with the target in the reference/rubric. Do not claim those exercise counts were observed in a run.

### M10-L03-T2 — distinguish successful-fetch rate from admission rate and correct the binary-unit total

- **Severity:** minor. **Status:** resolved in round 1; see resolution evidence below. Quoted passages/locations/problem below preserve the initial round 0 record.
- **Locations:** `modules/m10/lessons/M10-L03.md:21`; `modules/m10/assessments/M10-L03.md:50` and rubric line 61.
- **Exact passages:** “≈2.9 TiB” over 30 days; “Average fetch admission is roughly 23/s”.
- **Problem:** the daily payload is approximately 95.37 GiB, but 30 such days are approximately **2.794 TiB**, conventionally rounded to 2.8 TiB. Also, the premise gives two million **successful page fetches**, so dividing by 86,400 gives roughly 23.15 successful fetches/s. It does not establish attempts/admissions/s: failed fetches, redirects, robots requests, retries and body-free revalidation can change the request population and bandwidth. The assessment correctly labels 23/s as successful fetches; teaching and reference should agree.
- **Evidence:** [NIST binary prefixes](https://physics.nist.gov/cuu/Units/binary.html) defines Ki, Gi and Ti as powers of two. Direct calculation from the exercise gives `2,000,000 × 50 × 1024 = 102,400,000,000 B/day`; `×30 / 2^40 ≈ 2.794 TiB`. This is arithmetic over synthetic inputs, not a benchmark.
- **Bounded fix:** change the 30-day value consistently to about 2.8 TiB and call 23/s the successful-fetch mean. Explicitly budget request attempts and protocol/retry traffic separately. If showing bandwidth, the declared retained-body volume alone corresponds to about 9.48 Mbit/s averaged over a day; label it as a payload-only derivation, because retained bytes need not equal transferred encoded bytes or total wire traffic.

### M10-L03-T3 — separate HTTP fetch identity from fragment-based application identity

- **Severity:** minor. **Status:** resolved in round 1; see resolution evidence below. Quoted passages/locations/problem below preserve the initial round 0 record.
- **Locations:** `modules/m10/lessons/M10-L03.md:25`–30; companion frontier definition at `modules/m10/assessments/M10-L03.md:51`; evidence C5 at `modules/m10/evidence/M10-L03.md:11`.
- **Exact passage:** under “Normalized fetch key”: “Do not silently remove query parameters, fragment-related application state or path case when the origin might distinguish them.”
- **Problem:** preserving discovered/rendered application state is sensible, but a fragment is not part of an HTTP request target and the origin does not receive it. Placing this warning under the HTTP fetch key without the distinction can lead to separate frontier fetches for `/p#a` and `/p#b`, even though both retrieve the same HTTP target. A client-rendered hash route can need its own rendering/document identity; that is an additional product choice, not an origin-level HTTP distinction.
- **Primary evidence:** [RFC 3986 §3.5](https://www.rfc-editor.org/rfc/rfc3986.html#section-3.5) separates fragments before dereferencing; [RFC 9110 §7.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.1) explicitly excludes the fragment from the HTTP target URI.
- **Bounded fix:** state that the HTTP network fetch key excludes the fragment while raw discovery/provenance retains it. If browser rendering/hash-route crawling is in scope, give that state a separate explicit rendering/document key; otherwise keep it out of network-fetch deduplication. Preserve the existing conservative query/path-case policy and reflect the distinction in the frontier reference/evidence.

- **Robots:** [RFC 9309 §§2.2.2–2.4 and 3](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.2.2) supports applicable groups, most-specific path matching and the access-control caveat. In particular, HTTP 4xx unavailability permits access, while network/server unreachability requires complete disallow under the standard's conditions; these must not be conflated when implementing the lesson's referenced failure policy. Its cache recommendation is normally no more than 24 hours, with an unreachable exception. [Google's robots introduction](https://developers.google.com/search/docs/crawling-indexing/robots/intro) supports the explicitly scoped statement that blocking crawl does not guarantee Google removes a linked URL from its index. The lesson does not claim a robots-based authentication or legal permission grant, or inherit the Primer's robots-as-frequency-control simplification.
- **HTTP and network safety:** [RFC 9114 §§1–3](https://www.rfc-editor.org/rfc/rfc9114.html#section-1) supports HTTP/3 over negotiated QUIC, rather than an arbitrary raw-UDP shortcut. [RFC 9111 §4.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3) binds a 304 to the matching stored representation/validators; the lesson's proposed mismatch test is appropriate. [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3) supports Retry-After delay semantics. [OWASP SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) supports destination/IP validation, DNS-rebinding awareness and controlling redirect bypasses; origin allowance and each resolved/redirected network destination are separate checks. These are app safety obligations, not guarantees of URL normalization.
- **Frontier/versioning:** durable URL lifecycle, recoverable leases, due-for-recrawl state, version-guarded page promotion and stable change identities address cycles and stale workers. Exact body sharing retains both URL identities/provenance. Jaccard's set overlap formula (when the union is nonempty) and cosine for nonzero vectors have the stated meaning; similarity cannot establish semantic or policy equivalence. An implementation should define its empty-shingle-set convention. No similarity threshold or digest is treated as a permission/deletion decision.
- **Distinct filtering:** independently read the pinned Primer crawler README and actual `web_crawler_mapreduce.py`. Its `if total == 1` indeed drops every repeated URL. The lesson's one-representative-per-key correction is valid; it does not reproduce the defective implementation as runnable code.
- **Page-to-index path:** Q3 explicitly requires atomic page metadata/index intent or deterministic recovery; this composes the durable-dispatch prerequisite. The `u1:v2` trace correctly distinguishes page persistence, event timeout/unknown outcome and confirmed query visibility. [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) supports the dual-write and replay concerns. [Elasticsearch 8.19 near-real-time search](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/near-real-time.html) independently confirms the prerequisite's distinction between indexing and search visibility; its refresh semantics are a named implementation example, not a guarantee of the unspecified crawler index. Per-document postings/title/snippet version consistency, stale-version rejection, tombstones and request-pinned generations are correctly required application protocol. The accepted M08 source-side cut also requires proving relay publication and actual visibility through that cut, not merely receiving a worker/broker acknowledgment.
- **Privacy/removal:** the public-host scope does not imply authorization to expose private content or to treat robots as secrecy. Tombstone/version guards avoid delayed-worker resurrection. The lesson distinguishes an immediate versus repeat-confirmed 404 policy as a choice, and does not promise immediate legal takedown propagation or recall of delivered copies. No additional strict revocation timing guarantee was inferred from the memory hint.
