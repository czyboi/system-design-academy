# Source evidence for M09-L02

Checked 2026-11-15. Timeline, saturation values, recovery objectives and drill results are illustrative assumptions, not measured production results.

| Claim | Primary evidence and scope | Verification and limits |
| --- | --- | --- |
| C1. User-facing latency, traffic, errors and saturation help locate a change. CPU, memory, I/O, network and queues discriminate resource hypotheses when measured with the traffic envelope and relevant baselines. | Google SRE [Monitoring Distributed Systems, The Four Golden Signals](https://sre.google/sre-book/monitoring-distributed-systems/#the-four-golden-signals), and Brendan Gregg [USE Method, Linux metrics](https://www.brendangregg.com/USEmethod/use-linux.html). | Verified methods and example resource metrics. High utilization or correlation by itself does not establish a cause. Use Linux sample metrics as examples with workload context. |
| C2. Dapper models distributed requests as trace trees of associated spans, propagates tracing context through common libraries and samples to cap cost. | Sigelman et al., Google Technical Report dapper-2010-1, [Dapper, §§2.1–2.4, authors' report hosted by MIT](https://people.csail.mit.edu/matei/courses/2015/6.S897/readings/dapper.pdf). | Verified historical architecture only. Do not treat Dapper identifiers or sample rates as a modern protocol guarantee. Queue correlation, link topology and timestamp assumptions belong to the worked scenario. |
| C3. W3C Trace Context standardizes distributed HTTP context, including trace ID, parent ID and a sampled flag. Propagation, instrumentation and retention are separate. | W3C Recommendation [Trace Context §§3.2.2 and 4](https://www.w3.org/TR/trace-context/#traceparent-header). | Verified header/context behavior for the named standard. An absent span cannot prove no work occurred. Keep trace sampling separate from the service's request success denominator. |
| C4. Construct falsifiable hypotheses from observations and test them. A repeated controlled load test and a profile can test the suspected resource path and intervention. | Google SRE [Effective Troubleshooting, Theory and Practice](https://sre.google/sre-book/effective-troubleshooting/) and [Monitoring Distributed Systems, The Four Golden Signals](https://sre.google/sre-book/monitoring-distributed-systems/#the-four-golden-signals). | Verified diagnostic method. Offered traffic, request mix, cold versus warm behavior and correctness/error results are scenario controls. Profile collection has cost and may need a bounded experiment. |
| C5. RPO concerns the recoverable data point and RTO the time allowed for recovery. Backup restorability and tested service recovery are distinct from replication. | NIST SP 800-34 Rev. 1 [Contingency Planning Guide, §§3.2.1, 3.4.1, 3.5.1 and 4.4](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf). | Verified planning definitions and test guidance. Scenario grades the gap from the contiguous recoverable committed point to the disruption cutoff and measures usable, validated restoration from a separately recorded outage declaration; no regulatory requirement follows. |
| C6. An SLI implementation must correspond to the user outcome and measurement population. | Google SRE [Service Level Objectives, Indicators in Practice](https://sre.google/sre-book/service-level-objectives/#indicators-in-practice), [Implementing SLOs, Moving from SLI Specification to SLI Implementation](https://sre.google/workbook/implementing-slos/#moving-from-sli-specification-to-sli-implementation). | The managed-client cohort, join identity, deadline uncertainty rule and missing-receipt classification are explicit scenario measurement choices. An edge send is a distinct diagnostic event. |
