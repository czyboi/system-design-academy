# Source evidence — M09-L03

Checked 2026-11-16 from the primary publisher HTML/documentation pages linked below. The writer epochs, tenant projection, quorum layout, target SLO and timeline are **original illustrative design assumptions**. They are not measured results or guarantees of Chubby, ZooKeeper, etcd or Spanner.

| Claim ID and scoped claim | Primary source and exact section | Verification and boundary |
| --- | --- | --- |
| C1: Chubby was designed for coarse-grained locks and small metadata, and describes validation of lock sequencers by protected servers. | Mike Burrows, Google, *The Chubby lock service for loosely-coupled distributed systems* (OSDI 2006), [§§1, 2.4–2.6](https://www.usenix.org/legacy/event/osdi06/tech/full_papers/burrows/burrows_html/). | Verified historical paper, specifically §§2.4–2.6; sequencer validation is a responsibility of the consuming server. Not a modern Chubby cloud product claim. |
| C2: ZooKeeper's lock recipe uses ephemeral sequential children, predecessor watch and GUID-based recovery for uncertain creates. | Apache ZooKeeper [Recipes and Solutions, Locks and Recoverable Errors](https://zookeeper.apache.org/doc/r3.9.4/recipes.html#sc_recipes_Locks), pinned ZooKeeper 3.9.4 documentation, independently checked 2026-11-26. | Verified documented recipe. The [3.9.4 Sessions contract](https://zookeeper.apache.org/doc/r3.9.4/zookeeperProgrammers.html#ch_zkSessions) describes removal of the ephemeral owner marker on session expiry; the documentation does not promise fencing an unrelated database. The epoch-reuse caveat is an application design constraint, not a ZooKeeper API promise. |
| C3: Majority/leader loss can interrupt write availability; an election is not instant. | etcd maintainers, [v3.6 Operations Guide: Failure modes, Leader failure / Majority failure / Network partition](https://etcd.io/docs/v3.6/op-guide/failures/). | Verified for **etcd v3.6**. Three-voter majority arithmetic is used as an illustrative quorum policy; do not apply product-specific election timeout semantics to Chubby or ZooKeeper without separate evidence. |
| C4: Spanner's published system uses a distributed time uncertainty API with externally consistent transactions. | Corbett et al., Google, [Spanner: Google's Globally-Distributed Database, OSDI 2012](https://research.google/pubs/spanner-googles-globally-distributed-database-2/); current Google Cloud [TrueTime and external consistency, External consistency / Timestamps and MVCC](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency). | Verified publisher paper abstract and current official documentation. Current documented external consistency is scoped to transactions with serializable isolation; no claim that an application-side local clock or lock gives that guarantee. |
| C5: Observing only admitted successes hides refused original work; a correct SLI must specify its population and events. | Google SRE, [Service Level Objectives: Indicators in Practice](https://sre.google/sre-book/service-level-objectives/#indicators-in-practice); see prerequisite [M09-L02](../lessons/M09-L02.md). | The 99%, five seconds, ten-minute window, receipt verification and denominator are deliberately specified **scenario policy**, not vendor benchmarks. The SLI construction is a design choice requiring instrumented client reconciliation. |

## Rights and gaps

Original prose, trace table, textual flow and exercise. No copied third-party diagram or code. Chubby and Spanner are cited research, ZooKeeper and etcd are vendor/project documentation. System Design Primer remains the pinned *topic map* (approved coverage IDs PR-ARCH-SPANNER, PR-ARCH-CHUBBY, PR-ARCH-ZOOKEEPER), not the sole factual authority. Full product integration tests, clock-fault experiments, real region correlated-failure data and a live runnable gateway are **not provided** and must not be asserted to pass.
