# Companion assessment for M09-L02

## Practical exercise

**EX-1.** A report service defines success as a correct report returned to the caller within two seconds of the original valid request's first edge arrival. Its target is 99% of originals arriving in each five-minute window. Each original is followed through its deadline, including when that falls after the window. Rejections, errors, timeouts and late results fail the target. In a window of 1,000 originals, 920 finish correctly on time, 30 finish correctly late, 20 are rejected, 20 time out and 10 fail.

For one successful request, synchronized timestamps show edge forwarding at 0–50 ms, API validation and enqueue at 50–100 ms, queue wait at 100–800 ms, worker preparation at 800–850 ms, a database call including network round trip at 850–950 ms, and result assembly and return at 950–1,100 ms. The API span encloses its child work while waiting. Across the same window, oldest-job age rises and workers are continuously busy, while database execution time and disk latency remain near baseline.

Calculate the success result and trace the longest interval. Propose one falsifiable cause, measurements that could refute it, and a controlled load test and intervention. State how sampling and missing instrumentation affect conclusions. Separately, the service has a five-minute RPO and a 20-minute RTO measured from a 12:00 outage declaration until a usable, validated service. A drill restores the newest contiguous committed point at 11:53 and validates service at 12:18. Assess both objectives and name the evidence you would preserve.

## Knowledge checks

### Q1

An API span lasts 1,100 ms and includes a 700 ms queue wait and a 100 ms database call. How should its inclusive duration be used when adding up the request timeline?

**Answer.** Do not add its inclusive duration to the child intervals. Use non-overlapping intervals within the API span, plus the portions outside it, to avoid counting child time twice.

### Q2

A 760 ms enqueue-to-worker-start interval is observed alongside an 80 ms database round trip. What does the trace locate, and what does it leave uncertain?

**Answer.** It locates the larger measured interval before the worker starts. The database interval includes its network round trip, so it does not by itself separate database execution from transit, and one trace cannot establish the incident-wide cause.

### Q3

An HTTP request has propagated a W3C `traceparent`, but the worker span is missing from the retained trace. Does that establish that no worker ran?

**Answer.** No. Propagation carries context, while creating, exporting, sampling and retaining spans are separate steps. Missing instrumentation, loss or sampling can leave work without a retained span.

### Q4

Only 950 of 1,000 original requests eventually return correctly, and 930 of those are on time. Evaluate a 99% original-request target.

**Answer.** The on-time numerator is 930 and the denominator is 1,000, so the result is 93% and misses the target. The 50 originals that were rejected, failed or timed out remain in the denominator, as do the 20 late results.

### Q5

Queue age rises with worker CPU near its limit and stable database execution time. How would you test the worker-capacity explanation?

**Answer.** Collect a bounded worker profile and relevant queue, resource and outcome metrics. Repeat a controlled workload with the same arrival pattern, request mix, data size and starting condition before and after one targeted intervention. Falling worker CPU and queue wait with comparable downstream evidence support the hypothesis for that envelope. A different saturated resource or unchanged queue wait calls for further investigation.

### Q6

An outage begins at 12:00. A drill restores a contiguous commit point at 11:56 and the service passes validation at 12:24. Evaluate a five-minute RPO and 20-minute RTO.

**Answer.** The four-minute gap meets the RPO. The service is usable 24 minutes after declaration, so it misses the RTO. Restoring data earlier would not itself establish the service's usable time.

## Sample solution and rubric

**EX-1 sample.** On-time success is 920/1,000 = 92%, below 99%. All five outcome groups remain in the denominator. The 700 ms queue wait is the longest exclusive interval. The 100 ms database call includes network time, and the enclosing API span must not be added again. Instrument enqueue completion and worker start with job correlation, plus edge outcome counters and worker/database spans. A sampled or absent span is incomplete evidence about an individual path and cannot replace original-request counters.

One hypothesis is insufficient worker capacity for the offered mix. Compare worker CPU, memory pressure, queue age, offered and admitted rates, database execution and network observations with baseline. A bounded CPU profile can identify candidate worker work. Hold offered load, mix, data size and starting condition fixed while changing one measured worker cost, then repeat with correctness, error and original-request success measurements. Unchanged queue age or a newly saturated downstream resource would weaken or qualify the hypothesis.

The newest contiguous recoverable point is seven minutes before 12:00, so the five-minute RPO fails. Usable service at 12:18 meets the 20-minute RTO. Preserve the backup and log identities, continuity and integrity checks, recovered point, declaration and usable timestamps, plus the authenticated read and controlled write/read validation results. The result applies to the tested drill.

| Criterion | Points | Evidence for full credit |
| --- | --- | --- |
| User outcome and timeline | 3 | Computes 92% using all originals, identifies the 700 ms queue wait and avoids double-counting inclusive spans. |
| Diagnosis and instrumentation | 3 | Proposes a falsifiable worker hypothesis, contrasting metrics and a controlled intervention, and explains sampled or missing spans. |
| Recovery | 3 | Correctly assesses both objectives, uses the contiguous recovered point and validated usable time, and records supporting drill evidence. |
| Trade-off | 1 | States a relevant telemetry, experiment or recovery limitation. |

Award partial credit for a correct calculation with incomplete reasoning. Accept other interventions when the measurements and controlled test could distinguish the proposed cause and preserve correctness.
