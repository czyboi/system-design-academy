# M09-L03 — Coordination and multi-data-centre control: assessment

Use the example and assumptions in [M09-L03](../lessons/M09-L03.md). Answers explain a defensible design, not one vendor API.

## Knowledge checks

**Q1 — Trace an expired owner (LO1).** Writer A holds epoch 41. Its lease expires while it is paused; B receives epoch 42. A later sends an epoch-41 update to the projection store. Does the lease expiry alone guarantee rejection?

**Answer.** No. The store must enforce the new authority. Before fence 42 is durably installed, a store relying only on its last installed epoch may still admit the delayed write. Once the barrier is installed, the store's atomic epoch check rejects 41. A lease describes coordinator permission; it does not retroactively cancel a network request.

**Q2 — Order the takeover (LO1).** Put these in the safe order: B writes projection, B obtains epoch 42, the storage gateway durably installs fence 42. Explain why an acknowledgment matters.

**Answer.** Obtain 42 → durably install fence 42 at every relevant authoritative write boundary → receive confirmation → begin B's writes. If installation is unknown, B cannot prove that old writes will be rejected, so it must stop instead of guessing.

**Q3 — Distinguish fencing from deduplication (LO1).** B retries the same update twice with epoch 42. Is checking `epoch >= max_epoch` sufficient to apply it once?

**Answer.** No. Both may carry the currently valid epoch. Use a stable operation ID with atomic idempotency or a version precondition as appropriate. Fencing rejects obsolete ownership; idempotency handles repeated current-owner commands.

**Q4 — Majority and partitions (LO2).** Three voters inhabit independently failing zones. Two become unreachable from the third. Can the isolated singleton safely elect a new writer under the two-of-three rule?

**Answer.** No. It lacks a majority. The two remaining connected voters may maintain progress if the protocol's other requirements hold; the singleton must fail closed for ownership changes. Latency/election timing are additional constraints, not proof that a minority can elect.

**Q5 — Coordination-tool limits (LO2).** A team uses ZooKeeper ephemeral sequential znodes to elect the projection writer. Is it correct to claim that ZooKeeper automatically blocks the old writer's database update after session expiry?

**Answer.** No. The recipe elects/coordinates contenders, but an old process can still send a delayed command to another service. The database gateway must verify current authority or a monotone fencing generation. A sequence suffix requires explicit non-reuse guarantees across restore/recreation before being treated as a durable epoch.

**Q6 — Choosing a transaction system (LO2).** A service must atomically update related records across regions and preserve externally consistent transaction order. Is a worker lease equivalent to Spanner's serializable transactions?

**Answer.** No. A lease elects a writer; it does not supply cross-record atomicity or an externally consistent database transaction history. Spanner's documented serializable transactions use replication and TrueTime-related timestamp rules. Verify supported isolation, availability, latency and workload requirements before choosing it.

## EX-1 — Tenant settlement projection takeover

**Scenario.** Three coordination voters occupy fault domains A, B and C. A tenant settlement projection is stored behind one authoritative gateway; all writes for that tenant are serialized there. Writer W1 owns epoch 17 and has produced v4. W1 pauses after preparing an update. The coordinator considers W1's session expired and grants W2 epoch 18. W2 is in region B; the coordinator voters in B and C can communicate, A is partitioned. Two clients independently retry a rebuild request. The projection must never regress from an accepted newer generation to an older owner generation.

**Task.** Draw or tabulate the paths for ownership, fence installation and mutation. Decide which commands must reject; describe the takeover policy if the fence installation times out. Explain why idempotency still matters and which domain failure modes are not handled by the two-voter majority. Define one original-operation SLI with a denominator that includes rejected/failed/late work. Give one test that would falsify the claimed safety design.

**Reference answer.**
1. W2's coordinator majority (B,C) can grant epoch 18 while A lacks quorum. W2 requests the gateway to persist `max_epoch=18` atomically before any W2 protected mutation. A command from W1 with 17 arriving **after the installed fence** must reject even if W1 never learned its lease expired. W2's epoch-18 mutation may then proceed subject to authorization and version checks.
2. If fence installation is timed out or unacknowledged, W2 does **not** take over. It retries idempotently or diagnoses the gateway; a successful election alone is not enough to prove storage protection. A delayed W1 request before installation remains a documented limitation of the example's policy.
3. Independent retries can repeat the same rebuild even with epoch 18, so use a caller-scoped original-operation ID, a deduplication/commit record in the same write domain, and version checks. Decide how a timeout with unknown commit outcome is reconciled before a replacement attempt.
4. A,B,C are only independent by assumption. Shared WAN, certificate authority, deployment automation or a two-zone regional outage can remove quorum. The coordinator's quorum does not restore the projection database or its backups.
5. For example, on-time-correct SLI = original valid rebuild requests received in each ten-minute ingress window that return a client-validated, durable and current-generation projection within five seconds / all original valid rebuild requests in that window. Deduplicate retries by original ID; rejected, failed, timed-out, late and stale responses remain failures. Validate client receipt and correctness rather than treating the last server send as success.
6. Pause W1, expire its lease, install 18, complete W2's write, and deliver W1's recorded epoch-17 command late. Inspect storage and audit log: if any stale command commits, the safety claim is false. Also inject fence-install timeout and prove W2 does not begin writes.

### Rubric (10 points)

| Criterion | Points | Required evidence |
| --- | ---: | --- |
| Authority and majority | 2 | B/C elect safely; A does not acquire new authority without quorum |
| Fence placement and stale-write trace | 3 | Durable atomic fence at the gateway precedes W2; old request is rejected after fence, with pre-fence limitation acknowledged |
| Uncertain outcomes and repeat work | 2 | Failed installation blocks takeover; idempotency/version conditions handle same-epoch retries |
| Failure-domain and SLO reasoning | 2 | Common-cause risk and original-request denominator with failures/late responses |
| Falsification test | 1 | Paused-owner test inspects accepted commits, not only controller logs |

Equivalent architectures earn full credit if they defend the same external invariant and explicitly state the storage-side enforcement, failure policy and measurable outcome.
