# Coordination and multi-data-centre control

Two report builders may both believe they own the same tenant's end-of-day settlement projection. A coordinator can elect one leader, but an old leader that pauses, loses its lease and resumes may still send an already-constructed write. The business invariant is **one authoritative projection generation per tenant**. A lock holder's belief is not a storage-side guarantee.

- **M09-L03-LO1:** Trace membership, election, lease expiry and resource-side fencing through a delayed write.
- **M09-L03-LO2:** Choose coordination and cross-region placement according to the protected invariant, availability policy, latency and failure evidence.

## Start with the invariant and the smallest owner model

Suppose a tenant has one projection writer. Without automatic failover, an operator appoints writer A and explicitly stops it before starting B. This can satisfy the single-writer invariant if the stop is confirmed by the resource that accepts writes, but operator response is slow. To automate replacement, replicas need a shared, sufficiently consistent view of *who may take over*.

Membership says which candidates participate, not whether their processes are responsive right now. A health check is a fallible observation; delayed packets can make a healthy peer appear dead. Leader election chooses one authority under a protocol's assumptions. A lease gives its holder permission for a bounded term while renewal succeeds. A distributed lock is a higher-level *coordination agreement*; it is not, by itself, a transaction on the external resource.

When a minority loses contact with the coordinator's quorum, it cannot safely elect a new coordinator-backed owner under this policy. It should stop acquiring/renewing authority and reject or defer affected operations. Availability is reduced deliberately to preserve the invariant. Uncoordinated retries across both sides are not a substitute for a quorum decision. [etcd v3.6 failure modes](https://etcd.io/docs/v3.6/op-guide/failures/).

## Follow the paused owner: a lease without fencing fails

This is an **illustrative design**, not a claim that ZooKeeper, Chubby or etcd implements the application's external write checks automatically. The coordinator issues monotonically increasing **owner epochs** for this tenant. A storage gateway serializes installation of each epoch and every protected write against a durable `max_epoch` per tenant.

| Step | Event | What the storage gateway can prove |
| --- | --- | --- |
| 1 | A acquires epoch 41, installs it at storage, and writes projection v7. | Requests from epoch 41 may proceed while that epoch is current. |
| 2 | A pauses before sending its next command. Its coordinator lease expires. | Storage cannot infer that fact from A's old command alone. |
| 3 | B acquires epoch 42 from the coordinator and **installs fence 42 at storage** before it is allowed to write. | Storage durably rejects later commands tagged with epoch below 42. |
| 4 | B writes projection v8 with epoch 42. | Storage accepts the command if its normal authorization, ordering and version checks also pass. |
| 5 | A resumes and sends its delayed epoch-41 command. | Storage rejects it even if A is unaware of lease expiry. |

The core boundary is step 3. **If B merely obtains epoch 42 and writes before the target installs the fence, an old epoch-41 request may still be admitted.** Installing the fence and performing writes must be ordered in the *same* resource-side serialization domain; a cache of an epoch at another proxy is not enough. If multiple independent storage partitions accept this tenant's writes, each relevant partition must enforce a durable fence, or writes must pass through one authoritative gateway. A database conditional update/transaction is one implementation option; the lesson does not assume a particular SQL engine.

```text
Coordinator       Writer A            Writer B           Protected storage
    | -- grant 41 --> |                   |                       |
    |                 | -- write 41 ---------------------------> accept
    |                 X paused           |                       |
    | -- expire 41 -----------------------|                       |
    | -------------------- grant 42 ---->|                       |
    |                                     | -- install fence 42 -> persist
    |                                     | -- write 42 ---------> accept
    |                 | -- late write 41 ----------------------> reject
```

A fence token is a *monotone order* that the resource enforces, not merely a random session ID or an authentication secret. It must be generated under the coordination protocol, survive restarts without reuse and be checked on every protected mutation. Same-epoch retries also need operation IDs and version preconditions: fencing stops an **obsolete owner**, not duplicate commands from the current owner. The resource must authorize the writer identity as well as check the epoch. Chubby's sequencer design illustrates why lock-only coordination cannot protect delayed external requests ([Burrows 2006, §2.4–2.6](https://www.usenix.org/legacy/event/osdi06/tech/full_papers/burrows/burrows_html/)).

**What this model does not promise:** during the interval after A's lease expires but *before* the fence for B is installed, storage may still admit A's old request if it validates only the last installed epoch. This protocol guarantees no old-epoch write *after the new fence is installed* and no overlap with B's accepted writes; it does not guarantee immediate wall-clock revocation at lease expiry. A requirement to reject all old writes exactly at expiry needs a stronger, explicitly modeled storage/coordinator check and changes the availability/latency trade-off. If the fence installation fails or is unacknowledged, B must not start protected writes.

## Chubby and ZooKeeper solve coordination, not arbitrary storage fencing

Google's **Chubby** paper describes a coarse-grained lock service also used for small configuration data and leader discovery. Clients can obtain a lock *sequencer* and pass it to a protected server, which is expected to validate that sequencer. Chubby also describes a lock-delay mechanism for clients unable to validate sequencers; the delay is risk reduction, not a universal guarantee against stale writes. The paper is a **2006 historical system description**, not a current hosted-service SLA. [Chubby §§2.4–2.6](https://www.usenix.org/legacy/event/osdi06/tech/full_papers/burrows/burrows_html/).

Apache **ZooKeeper** exposes ordered updates, sessions and ephemeral sequential znodes. In its lock recipe, contenders create ephemeral sequential children and watch the nearest predecessor; when the predecessor disappears they re-evaluate who is first. This reduces herd wakeups. Session expiration removes ephemeral nodes, but the old process may still execute code or send a delayed network message. A znode deletion does not independently fence a database. If a sequence suffix is used as a proposed epoch, prove it remains globally monotone across parent deletion, namespace recreation and any coordination-service restore; otherwise allocate an independent durable epoch. The recipe also documents ambiguous node creation after a connection failure, requiring a GUID recovery check. [ZooKeeper 3.9.4 recipes, Locks and Recoverable Errors](https://zookeeper.apache.org/doc/r3.9.4/recipes.html#sc_recipes_Locks).

Neither tool turns an arbitrary external database or object store into a linearizable transaction participant. Choose a small coordination plane for leader assignment and metadata. Do **not** send every high-throughput data mutation through that plane when the storage system can enforce the business invariant locally.

## Place the quorum according to failures and latency

Consider three **voting** coordinator replicas in three independent failure domains, one vote each. A two-of-three majority may make a decision if one voter fails; if two are unavailable, there is no safe majority under this configuration. Merely saying “three regions” is not evidence of independence: shared networking, identity infrastructure, power, control planes, or a common operator action can disable multiple domains.

Across geographically distant regions, quorum round trips and leader handoff can add tail latency to ownership changes or coordinated writes. Putting all voters near the hot writer reduces coordination latency but puts their availability in a shared regional failure domain. Geographically distributing votes can tolerate a single *independent* regional failure while increasing WAN dependence. Do not promise an absolute failover time from lease TTL alone: detection, election, session expiry, fencing installation, application reconnection and downstream replay all contribute. For a named implementation, use its documented failure model rather than treating these generic majority calculations as its complete API contract. [etcd v3.6 failure modes](https://etcd.io/docs/v3.6/op-guide/failures/).

A useful runbook tests (1) old leader paused past expiry and later resumed, (2) coordinator majority loss, (3) successful election but failed storage fence, (4) a correlated region/network outage and (5) restoration with a monotone epoch. It records which writes were accepted, deferred or rejected, and whether any accepted operation was overwritten by a stale leader. Separate coordination-plane recovery from the data store's backup and restore evidence ([M09-L02](M09-L02.md)).

## Why Spanner is a different choice

Spanner is an example of coordinating **database transactions**, not simply choosing one worker with an external lock. Its published design combines synchronous replication and transactions with TrueTime, an API that exposes clock uncertainty. Spanner selects transaction timestamps and uses a commit-wait rule so timestamp order reflects observable completion order. Google Cloud's current documentation scopes *external consistency* to Spanner transactions using serializable isolation; it is not a guarantee for an arbitrary application clock, a ZooKeeper lock or a non-serializable isolation mode. [Spanner OSDI 2012](https://research.google/pubs/spanner-googles-globally-distributed-database-2/), [Google Cloud TrueTime and external consistency](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency).

| Workload invariant | Plausible design | Decision cost / failure boundary |
| --- | --- | --- |
| Only one worker may build a disposable, replayable projection at a time. | Coordinator lease plus idempotent writes; add resource fencing if stale output could overwrite current results. | Election/lease overhead, paused writers, fencing installation on take-over. |
| One durable tenant projection must never be replaced by a superseded owner. | Monotone owner epoch with storage-enforced fence and version/operation checks. | Resource-side serialization; write availability pauses if no safe owner or fence cannot be installed. |
| Multiple rows/records need externally ordered atomic transactions across regions. | Database transaction system with documented cross-region isolation, such as appropriately configured Spanner. | Greater cross-region coordination, workload constraints, cost and vendor-specific behavior; not interchangeable with a worker lock. |
| Independent or commutative processing produces mergeable results. | Avoid global leadership if per-key idempotency/merge rules suffice. | Reconciliation complexity but less coordination on the hot path. |

## Define success on original operations

For the sample tenant-projection API, assume a test cohort expects at least 99% of **original valid rebuild requests** in a rolling ten-minute arrival window to return a correct, durable, current-generation projection within five seconds of first ingress. Carry a stable original-operation ID across retries. Follow each original to its five-second deadline; count rejected, timed-out, failed, late or stale-generation responses in the denominator but not the on-time correct numerator. Measure admitted-success latency separately. The 99%, five-second and ten-minute values are **invented exercise thresholds**, not system benchmarks.

During a majority loss, refusing a rebuild may preserve single-owner correctness but worsen the measured availability SLO. Hiding such refusal by reporting only successful calls would confuse a deliberate safety trade-off with an improvement. Track stale-write rejections and epoch transitions as *diagnostic* metrics, and alert on any accepted stale write as an invariant violation.

The design decision is therefore not “always use a distributed lock”: first state which externally visible mutation requires ownership, then choose how the storage target can *prove* that a command still carries valid authority.
