# Measure, trace and recover

A statement service begins returning some reports slowly during a traffic increase. Its edge forwards a request to an API, which places a report job on a queue and waits for a worker to read the database and return the result. The database is on the path, but that alone does not identify it as the bottleneck. An operator needs to locate the delay, test a cause and check whether the service can recover its data after a failure.

- **M09-L02-LO1.** Trace the request and use its telemetry to locate waiting and execution time.
- **M09-L02-LO2.** Choose evidence, interventions and recovery checks using workload, measurement and failure criteria.

## Measure the original request

Assume this example measures a managed test cohort whose origins and valid request inputs are known. Its service objective is that at least 99% of original valid report requests arriving at the edge in each five-minute window produce a correct report received and validated by the client within two seconds of first edge arrival. A stable, caller-scoped original-operation ID is reused across retries. Count each original once and follow arrivals through their two-second deadlines even if those deadlines extend beyond the window. Rejected, failed, timed-out and late originals remain in the denominator and are excluded from the on-time numerator. Latency for admitted or successful requests is a separate diagnostic distribution.

Join the edge's first-ingress record to the managed client's validated-receipt record by that ID. Use a common clock or a known bound on cross-clock error. Count a receipt as on time only when its elapsed-time upper bound is at most two seconds. When the bound straddles the deadline, the result is inconclusive and excluded from the numerator. Missing receipt evidence is also unsuccessful under this measurement policy. An edge send event is a useful server-side proxy, but it cannot establish client receipt or correctness. For example, an edge can finish sending while the client times out and has no validated receipt.

In one illustrative window, the client-reconciled records classify 1,000 original valid requests. Of these, 930 are validated on time, 20 are validated late, 20 are rejected, 20 time out and 10 fail. The result is 930/1,000 = 93%, below the objective. Computing only 930/950 = 97.9% on time among eventual correct responses omits rejected, timed-out and failed originals. A fast admitted-only percentile can improve if requests are rejected and still leave the user objective unmet. A sampled trace is not the denominator. The workload envelope, error rate and saturation signals give context for the latency change. [Google SRE, indicators in practice](https://sre.google/sre-book/service-level-objectives/#indicators-in-practice), [four golden signals](https://sre.google/sre-book/monitoring-distributed-systems/#the-four-golden-signals).

## Follow a request through waiting and work

For one slow successful request, the following synthetic edge, service and managed-client timestamps use a common clock. Each interval is exclusive and their total from first edge arrival to client-validated receipt is 1,200 ms. The API span encloses the queue and worker work while it waits, so its inclusive duration must not be added to its children.

| Time since edge arrival | Instrumented interval | Duration |
| --- | --- | --- |
| 0–40 ms | Edge accepts and forwards to API | 40 ms |
| 40–90 ms | API validates and durably enqueues | 50 ms |
| 90–850 ms | Enqueue completion until worker starts | 760 ms |
| 850–900 ms | Worker preparation | 50 ms |
| 900–980 ms | Database call including its network round trip | 80 ms |
| 980–1,140 ms | Worker assembles and returns result to API | 160 ms |
| 1,140–1,180 ms | API and edge send result | 40 ms |
| 1,180–1,200 ms | Result reaches client and client validates it | 20 ms |

The queue interval is derived from an enqueue timestamp and worker-start timestamp carried with the job, with clock error small relative to this example's interval. It is a queue-wait measurement, not the execution duration of a database span. The 80 ms database interval contains network time, so it alone cannot split database execution from network transit. Here the dominant observed interval is queue wait. It makes queue capacity, arrival rate and worker availability plausible places to investigate. One trace does not establish that every request or the whole incident has the same cause.

A trace connects timed spans for an individual operation. Instrument edge and API work, record job identity and enqueue/worker-start events, and associate worker and database spans with the original request. A metrics series can show the distribution and rate of many operations, including queue age, worker utilization, errors and on-time successes. Structured logs can record discrete outcomes and a request identifier for investigation. Compare all three over the same window and request class. A log or span may be missing because instrumentation, export or retention failed.

Google's Dapper paper describes a historical trace-tree design that propagates context through common infrastructure and uses sampling to manage overhead. For HTTP boundaries using W3C Trace Context, `traceparent` carries a trace ID, parent ID and trace flags including a sampled flag. Propagating context across a queue requires the application or its instrumentation to carry and restore the relevant context with the job. Propagation alone does not create, export or retain spans. A missing sampled trace proves neither that the operation was absent nor that it succeeded. Choose sampling and retention to balance diagnosis, telemetry cost and sensitive data exposure. Avoid placing financial fields, credentials or raw tokens in trace attributes and logs, following the boundaries in [M09-L01](M09-L01.md). [Dapper §§2.1–2.4, MIT-hosted copy](https://people.csail.mit.edu/matei/courses/2015/6.S897/readings/dapper.pdf), [original report mirror](https://zhjwpku.com/assets/201810/dapper.pdf#page=3), [Google Research publication record](https://research.google/pubs/dapper-a-large-scale-distributed-systems-tracing-infrastructure/), [W3C Trace Context](https://www.w3.org/TR/trace-context/#traceparent-header).

## Test a bottleneck hypothesis

Assume the slow-request window also shows rising oldest-job age and continuously busy workers. Worker CPU is near its allocated limit, while database execution time, disk latency and network retransmissions remain near their respective baselines. That pattern supports a worker-capacity hypothesis, but it does not prove it. CPU can be high for work that is unrelated to the queue, and a database span can conceal its own internal wait. A bounded worker CPU profile showing report serialization as the dominant work would make the hypothesis more specific.

Use measurements that could disprove a proposed explanation. Compare offered and admitted request rates and request mix with queue depth and oldest-job age. CPU saturation may imply compute contention. Memory pressure and allocation or garbage-collection pauses suggest a different constraint. Disk throughput and latency, database execution or wait time, and network throughput and retransmissions help distinguish storage or network delay. Compare each against its baseline and resource limit, and check errors as well as utilization. A low average can hide a saturated worker or a long tail. [Google SRE monitoring](https://sre.google/sre-book/monitoring-distributed-systems/#the-four-golden-signals), [USE method](https://www.brendangregg.com/USEmethod/use-linux.html).

Run a controlled test in a safe environment with the same offered arrival pattern, request mix, data size and warm or cold starting condition. Record queue age, worker CPU, database and network evidence, original-request outcomes and admitted latency. Change one factor, such as a measured reduction in serialization work, then repeat with the same load and correctness checks. If worker CPU and queue wait fall while database latency and request mix remain comparable, the result supports that intervention for this envelope. If queue age remains high or another resource saturates, investigate the new evidence instead of declaring the incident solved. Profiles and detailed tracing consume resources and may expose data, so scope their collection and access. [Google SRE troubleshooting](https://sre.google/sre-book/effective-troubleshooting/).

## Check recovery against objectives

Assume the service has a recovery point objective (RPO) allowing at most a five-minute recovery gap between the disruption's data-loss cutoff and the newest contiguous recoverable committed point. Its recovery time objective (RTO) is 20 minutes from a declared outage to a usable, validated service. The cutoff defines the point against which the recovery gap is measured. The declaration starts the restoration timer in this scenario and may occur later than the disruption. A replica can make another copy available, but a shared deletion or corruption can reach that copy too. Keep a recovery copy with an independently usable restoration path and test it. [NIST SP 800-34 Rev. 1, §§3.2.1 and 3.4.1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf).

In an illustrative drill, the disruption and defined data-loss cutoff occur at 12:00, and the outage is also declared at 12:00. Restore a backup and required log segments into an isolated environment. Check integrity and confirm the newest **contiguous** recovered committed point is 11:56, with no earlier missing segment. The recovery gap from 11:56 to the 12:00 cutoff is four minutes, so the five-minute RPO is met for this drill. The service passes a representative authenticated read and a controlled write/read check at 12:17. The elapsed 17 minutes from declaration meets the 20-minute RTO for the stated validation boundary. If the newest recovered record were 11:59 but a required earlier segment were missing, its timestamp alone would not establish a contiguous recovery point. If data restored at 12:12 but the service became usable only at 12:24, the 24-minute RTO result would fail.

Record the input backup and logs, recovery point, disruption cutoff, outage declaration, validation result and usable time. A successful isolated drill is evidence for that tested failure and environment, and repeated drills can expose changes in data volume, credentials or recovery steps. A backup completion message by itself does not demonstrate a usable restore. [NIST SP 800-34 Rev. 1, §§3.5.1 and 4.4](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf).
