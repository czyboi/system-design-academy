# Security by trust boundary

A financial reporting service lets tenant members retrieve payout records. Its API routes through a reverse proxy to a reporting service and a database. A valid signed-in user changes a record ID in the URL to one belonging to another tenant. The request reaches the correct endpoint, but returning the record would expose another tenant's financial data. The design must preserve confidentiality while also preventing unauthorized changes and allowing legitimate members to work.

- **M09-L01-LO1.** Trace the authentication, authorization, data protection and input/output controls for a request across these boundaries.
- **M09-L01-LO2.** Choose and defend controls against a stated threat using their costs and failure boundaries.

## Make the access decision at the record boundary

Assume user Ada belongs to tenant A and may read its payout records. Record `r-42` belongs to tenant B. The request `GET /payouts/r-42` crosses an Internet-to-proxy boundary, a proxy-to-service boundary and a service-to-database boundary. A separate identity provider issues access tokens. This example assumes a JWT access-token profile with trusted issuer and key configuration.

1. The browser establishes HTTPS with the proxy and presents Ada's access token. The proxy terminates TLS, removes client-supplied identity headers and forwards only values it establishes to the service over an authenticated, encrypted connection. The service accepts that identity information only from the trusted proxy. A direct client must not reach an endpoint that trusts those headers.
2. The resource server validates the token's integrity using its configured trusted issuer and allowed algorithm, then checks the required issuer, audience, expiration and scope. A token intended for another API or an expired token fails before record access. An opaque token needs validation through its own configured authorization mechanism rather than JWT parsing.
3. Authentication identifies Ada. Authorization asks whether Ada may perform `read` on the actual record's tenant. The service derives Ada's tenant membership from its trusted policy data, and applies that membership and the requested action to the object. The URL's ID and any client-supplied tenant ID are inputs, not proof of membership. The service denies access if policy data cannot establish permission.
4. The database read binds both the requested record ID and the authorized tenant ID as values in a query restricted by both predicates. With Ada's authorized tenant A and `r-42`, no row matches. The service returns its chosen non-disclosing error and no financial fields. A request for an A record follows the same checks and can return the permitted fields.

The service enforces policy for each request, even when the proxy authenticated the connection. The record predicate makes the tenant scope part of retrieval, so a later code path must not fetch the row by ID alone and assume an earlier check applies. Policy changes concurrent with a request need an explicit decision boundary if the product promises immediate revocation. This example makes no such timing promise. [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request), [RFC 9700, access-token restrictions](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3).

Least privilege applies to both identities and network paths. The reporting service's database identity receives only the operations and data access its job requires, and administrative operations use separate authority. Permit only needed proxy-to-service and service-to-database connections. Segmentation reduces reachable paths after a compromise, while the service still checks the caller's object-level permission. A private subnet cannot identify which tenant Ada is allowed to read. [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final), [OWASP least privilege](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#enforce-least-privileges).

## Protect each hop and stored copy

TLS 1.3 protects a channel between its authenticated endpoints. Server authentication lets the client check it reached the intended server. Mutual TLS can also authenticate a workload to its peer when configured for that purpose. TLS ends at the proxy, so the internal hop needs its own protection and peer authentication. The proxy must strip untrusted forwarding and identity headers before setting trusted ones, because an attacker can otherwise supply a false identity assertion. [RFC 8446 §1](https://www.rfc-editor.org/rfc/rfc8446.html#section-1), [RFC 9700 §4.13](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.13).

Encrypt database storage and backups against exposure of a copied disk or backup, and restrict access to their keys separately from access to stored ciphertext. Where a specific field has a narrower set of authorized readers, consider field encryption with a separately controlled decrypt capability. That adds key management, rotation and query complexity. A running service authorized to decrypt and return a field can still disclose it through an authorization flaw. [OWASP cryptographic storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html#separation-of-keys-and-data).

Give each service its own narrowly scoped credential. Store secrets in a controlled secret-management system, restrict who and what can retrieve them, and rotate them through a planned process that updates consumers without placing secrets in source code. Audit policy decisions with a request identifier, principal, action, target reference and outcome, while excluding tokens, passwords, keys and financial values from logs. A centralized secret system itself needs access control and availability planning. [OWASP secrets management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html#23-access-control), [OWASP logging data exclusions](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude).

## Keep input as data and output in its context

Check that `r-42` has an accepted identifier shape and reject malformed input early. Validation also enforces business rules, but an identifier with a valid shape can still belong to another tenant. Bind values in the database driver's parameterized query. For example, the conceptual statement below binds both placeholders separately from SQL syntax. Its parameter notation is illustrative, and the database driver determines executable syntax.

```sql
SELECT payout_date, amount, display_note
FROM payouts
WHERE record_id = ? AND tenant_id = ?
```

The first value comes from the request and the second from the authorization decision. A value such as `r-42' OR '1'='1` stays one value when bound. It cannot change the predicate into SQL syntax. Parameter binding cannot safely select an arbitrary table or sort identifier, so map any permitted identifier to an application-owned allowlist. It also does not decide whether the user is entitled to the matching row. [OWASP SQL injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html#defense-option-1-prepared-statements-with-parameterized-queries).

A payout's `display_note` can contain user-supplied text. When rendering it into HTML text, encode it for that context so markup-like characters are displayed as text. Attribute, JavaScript and URL contexts have different rules, so use a safe renderer suited to the destination rather than treating one encoding as universal. For a state-changing browser request using automatically attached session cookies, require a CSRF defense such as a server-validated, session-bound synchronizer token. An attacker may cause a victim's browser to send cookies with a forged request, while the attacker lacks that token. XSS prevention remains necessary because script running in the application origin can undermine CSRF defenses. [OWASP XSS prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html#output-encoding), [OWASP CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#synchronizer-token-pattern).

## Select controls for the threat

| Threat or decision | Control and benefit | Cost and boundary |
| --- | --- | --- |
| Valid user requests another tenant's record | Authenticate the caller and enforce action plus tenant-scoped record authorization on each read. | Policy lookup and enforcement add dependency and latency. Failure to establish permission denies the read. |
| Network interception or forged internal identity | TLS on both hops, trusted proxy header handling and authenticated service peers protect those hop boundaries. | Certificate and trust configuration need maintenance. A trusted endpoint with excessive authority can still expose plaintext. |
| Leaked storage snapshot | Encrypt data and backups at rest with separately controlled keys. | Key availability and rotation affect recovery. An attacker with both decrypt authority and ciphertext may still read it. |
| Injection or browser execution | Bind query values, validate business inputs and encode output for its actual rendering context. | Controls must cover each query and output context. They do not supply tenant authorization. |
| Forged state change in a cookie session | Validate a session-bound CSRF token on the mutation. | The client and server must maintain and verify the token. A separately authorized API operation still needs its own access decision. |

The right combination follows the asset, actor and reachable boundary. The original cross-tenant request requires an object-level decision even when every network connection and stored copy is encrypted.
