# Review a statement service under exposure, overload and stale leadership

A merchant-portal statement service crosses three networks: browser → TLS-terminating proxy → statement API → SQL database. A separate API job path enqueues report requests for workers; a coordinator assigns a single writer for each tenant's consolidated reporting projection. The service runs in multiple failure domains, but that does not make its database, control plane and identity provider independent.

## Scenario facts and authority

- A client presents a configured user-delegated JWT to the statement API through an authenticated proxy. Under the example token profile, validated issuer + subject identify **Bo**. Bo belongs to tenant C and has the general `statements:read` scope. Statement `s-9` belongs to tenant D. The database account can read multiple tenants. The membership service may fail. Neither a valid token nor database encryption grants Bo access to D's row.
- The queued report is **not** an authorization shortcut: it may read only statements authorized for the original issuer-scoped requester and requested action at **worker execution time**, and the result must be access-checked again on retrieval. Tenant membership may change while a job waits. Only the authenticated Statement API may produce report jobs, and only an authenticated report-worker workload may consume them. The API constructs a durable, integrity-protected envelope with a stable job ID, validated requester reference, **server-established** tenant, authorized action and bounded record selection; client-supplied tenant IDs or a bearer token copied into the job are not authority. Define the queue permissions, worker-side fail-closed reauthorization, protected worker-to-database hop, dedicated least-privilege database principal, worker-to-result-store and API-to-result-store transport and workload permissions, and safe result/log data handling in the review.
- The browser-to-proxy, proxy-to-API and API-to-database hops each need an explicit transport/peer identity policy. The API uses its own restricted database principal. The browser also submits tenant-provided statement notes, and a cookie-authenticated edit endpoint exists.
- For report-generation requests, the API enqueues and synchronously waits for a result. In a **synthetic slow request** the exclusive intervals from first edge ingress until managed-client validated receipt are: edge 40 ms; API enqueue 50 ms; queue wait 760 ms; worker preparation 50 ms; database network-call 80 ms; result assembly 160 ms; response send 40 ms; client receipt/validation 20 ms. Total **1,200 ms**. An API parent span encloses the queue and worker spans and cannot be added to them again. This interval pattern is a clue, not proof of a causal bottleneck.
- In a five-minute arrival cohort of **1,000 original valid** report requests, 930 arrive correct and client-validated within the **two-second** deadline, 20 are correct but late, 20 are rejected, 20 time out, and 10 fail. Repeated attempts retain the same original ID. Every original is followed to its deadline. The service target is at least **99%** correct and on time over each original ingress cohort. These are scenario values, not production measurements.
- For tenant C's projection, writer W1 originally installed epoch 41 at an authoritative storage gateway. W1 pauses, its coordinator lease expires, W2 obtains epoch 42 from a surviving quorum, and W1 may later deliver an old command. B and C coordinator voters remain connected; voter A is partitioned. Assume a two-of-three voting quorum. A protected write and fence installation for this tenant serialize at one durable gateway. A newly elected W2 cannot safely write until storage **confirms installation of fence 42**.
- The three coordination voters occupy different stated zones, but an identity/secret-distribution outage or shared WAN failure may affect more than one. The report database and backup restore path have **not** been shown to survive a region outage. Recovery objectives require separate testing.

## M09-EX1 — An evidence-based design review

Produce a review report for the following objectives. Distinguish source-backed behavior from the scenario assumptions.

1. **Trust boundaries.** Draw the complete browser, proxy, API, database and API → queue → worker → database → result-retrieval paths. For Bo's attempt to read `s-9` and a tenant-C queued report, locate identity validation, tenant/object authorization **at enqueue, execution and result retrieval**, envelope provenance, producer/consumer permission, network peer verification, the separate API/worker database principals, parameterized tenant-scoped queries and non-disclosing denial. For both result-store connections, specify encrypted transport, intended-peer verification, distinct authenticated worker and API principals, tenant/job-scoped worker write and API read permissions, and fail-closed behavior before transfer when transport, identity or permission checks fail. Include fail-closed membership-service failure, revoked membership while queued and the cookie-authenticated notes edit path. Specify a defense and its limit for each exposed boundary.
2. **Operational diagnosis.** Reconcile the sample 1,200 ms trace without double counting nested spans, propose two *falsifiable* hypotheses, and name measurement evidence that distinguishes queue saturation from database/network delay. Score the 1,000-original cohort against the 99% target; explain how a success-only latency chart can mislead.
3. **Stale writer and correlated failure.** Tabulate W1 expiry, W2 election, durable fence installation, W2 write and W1 delayed write; state the safe response if fence installation times out. Show which side of the A–(B,C) partition may appoint the next owner. Identify at least two shared dependencies that could invalidate simplistic “independent region” claims.
4. **Recovery.** Propose a bounded drill that observes the client-visible report SLO, projection monotonicity, restoration of durable data and time-to-usable-service. Distinguish evidence of a coordinator election from evidence of a restored statement database and client correctness.

The deliverable is one coherent design critique: a boundary diagram, measured-decision table, chosen availability/consistency policy, and a test plan that could falsify your claims. Do not infer that a technical mechanism is correct just because its control plane reports “healthy.”
