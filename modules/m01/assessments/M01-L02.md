# Assessment for Performance versus scalability

## EX-1 · Size a museum admission API for opening time

The API checks timed-entry tickets. It receives 85 requests/s normally and 180 requests/s during a three-second opening burst. Each check needs a CPU stage and one read from a shared store. The store supports 220 reads/s, and waiting for a read leaves the CPU slot free. The request mix is fixed. Every replica can serve every ticket, and traffic splits evenly when both replicas are available.

| Option | CPU capacity | Operating cost |
| --- | --- | --- |
| A · One faster server | One CPU slot, 6.25 ms per request | 10 units/hour |
| B · Two slower servers | One CPU slot on each server, 10 ms per request | 12 units/hour total |

The budget is 12 units/hour. Over repeated opening bursts and their recovery, successful-request p99 must be at most 100 ms and failures, rejections and timeouts must stay within 0.5%. Outside the burst, the service must keep up with 85 requests/s during the loss of one API server. Use an initially empty FIFO queue, constant rates within each interval and negligible routing overhead. All figures are scenario assumptions.

**Deliverable.** Estimate CPU capacity for both options, backlog at the end of the burst and the approximate wait for a request that arrives near its end. Recommend what to load-test first and name one observation that would reverse your choice. Then reassess if the store can complete only 150 reads/s. Give a measurement plan and explain how the outage and error requirements affect the decision.

### Sample solution

- **A.** The CPU completes `1 ÷ 0.00625 = 160 requests/s`. The burst builds `(180 − 160) × 3 = 60` queued requests. A late arrival waits about `60 ÷ 160 = 0.375 s` for CPU. The queue drains in `60 ÷ (160 − 85) = 0.8 s`. The single-server outage leaves zero API capacity.
- **B.** Each CPU completes `1 ÷ 0.010 = 100 requests/s`. Each sees 90 requests/s in the evenly split burst, so the fluid model predicts no growing CPU queue. A survivor can handle the normal 85 requests/s in the model. B fits the budget and is the first candidate to test. If routing skew sends more than 100 requests/s to one replica, its queue grows. That would invalidate the recommendation as configured until traffic can be redistributed or capacity changes.
- **With a 150 reads/s store.** The two healthy replicas can issue 180 reads/s under the overlap assumptions, so the store queue grows at 30 reads/s and accumulates about 90 reads by the end of the burst. Extra API replicas leave that ceiling in place. Investigate reducing store work per check or increasing the store's capacity. Prompt rejection can protect admitted requests and still consume the 0.5% error budget.
- **Verify.** Replay the arrival schedule and request mix on both options. Record client-side p99 for successful responses, the error fraction, goodput and per-stage waiting for CPU and store reads. Include normal traffic with one replica down and check that the survivor sustains it. Use per-replica arrivals to verify the split. Evaluate the 100 ms and 0.5% targets from the observed burst and recovery windows.

### Rubric

Award 0, 1 or 2 points per row for missing, partial or complete reasoning. Accept other recommendations that respect the budget and outage requirement and explain how the candidate would meet the service targets.

| Criterion | Full credit |
| --- | --- |
| Capacity and queue | Uses per-server rates and units. Estimates A's burst backlog and wait and explains the even-split result for B. |
| Decision and failure | Uses the cost and outage constraints to choose a candidate, identifies a condition that invalidates it and distinguishes modeled capacity from measured service targets. |
| Shared dependency | Locates the new limit at the store, explains the queue growth and proposes a change that reduces pressure there. |
| Verification | Tests a matched burst and single-server loss. Checks p99, errors and stage-level signals that can confirm or refute the diagnosis. |

## Knowledge checks

### Q1 · Service time and fleet capacity

In the parcel API model, which deployment spends less CPU time per request at low load, and which has the higher aggregate CPU capacity under balanced traffic? Explain how both results can hold.

**Answer.** A needs 5 ms of CPU time and B needs 8 ms per request. B can do that work on two CPUs in parallel, for 250 requests/s in aggregate versus 200 requests/s for A. Each request in B still runs on one CPU.

### Q2 · Rising throughput and slower requests

Use the parcel model with a **one-second** burst at 230 requests/s and the 300 reads/s store. A previously handles 120 requests/s. What happens to its CPU completion rate and queue, and how long does a late arrival wait for CPU?

**Answer.** The CPU completion rate rises to 200 requests/s as the slot stays busy. The queue still gains `(230 − 200) × 1 = 30` requests. A late arrival waits about `30 ÷ 200 = 0.15 s` before service under the stated model. Completions rise because the CPU processes more work per second. Waiting grows because even more work arrives.

### Q3 · Match the measurement boundary

A steady API run admits and completes 140 requests/s. The mean number of requests inside the API, including requests waiting for its store, is 4.2. Estimate mean API time. What additional measurement would you need to check p99?

**Answer.** `4.2 ÷ 140 = 0.030 s`, or 30 ms within the API boundary. Little's Law uses means for a stable system. Measure individual latencies or a sufficiently resolved histogram over the target population to estimate p99. A client-facing target needs client-side timing.

### Q4 · State placement and a hot replica

The parcel API uses two 125 requests/s replicas. Local sessions pin 60% of the 230 requests/s burst to one replica. Would buying another replica fix that overload if the original clients remain pinned? Which change would you test?

**Answer.** The hot replica gets 138 requests/s and accumulates 13 requests/s even with spare capacity elsewhere. Keeping the same affinity leaves that replica overloaded. Test making those requests serviceable by any replica and redistributing them. Check per-replica arrivals and include any external session-state work in the test.

### Q5 · The bottleneck moves

In the balanced two-replica parcel design, traces show that all 230 burst requests/s reach the shared store with one read each, and the store can complete 180 reads/s. Where does work accumulate? Would a faster API CPU help?

**Answer.** Work accumulates at the store at about 50 reads/s in the model. The API already supplies enough reads to saturate it. Profile the store or reduce the read work per request. A faster API CPU leaves the 180 reads/s store ceiling in place.

### Q6 · A misleading p99 improvement

At the same offered burst rate, a bounded queue lowers successful-request p99 from 105 ms to 55 ms. The combined failure, rejection and timeout rate rises from 0.2% to 2%. The targets are p99 ≤ 75 ms and at most 0.5% errors and timeouts, including rejections. Can you ship either configuration? What would you measure on the next run?

**Answer.** The original misses the latency target and the bounded queue misses the error target. Track timely successful completions, client-observed failures, and where requests wait. Replay matched offered traffic after changing the constrained stage or the queue limit. Quick rejection can improve the latency of admitted requests while leaving too many clients without a successful response.
