# Assessment for Consistency and partition decisions

## EX-1 · Account preferences and spending authority

A service has East and West replicas and clients in both regions. A network partition blocks every message between the regions. At the start, both replicas show a customer's `display_name = Nia` and confirmed balance of 60 credits. East acknowledges a profile edit to `Noor` and then acknowledges a balance update to 35 credits. Both updates finish before a West client reads. West has received neither update.

The product requires public profile reads to remain usable locally, with possible stale values. A customer who just edited a profile must never receive a successful session read that omits their acknowledged edit. A balance endpoint promises the current confirmed balance. West can reach neither the East authority nor any other component that can establish the latest balance. For the session mechanism, assume profile updates use a single ordered history and isolated West cannot acknowledge new profile writes. For the conflict question, consider a separate design that permits independent concurrent profile edits in both regions during the partition.

**Deliverable.** For each of the three read operations, propose a response and explain its client contract. Design a concrete session-token eligibility rule for a single shared ordered profile history, including what happens if West cannot satisfy it. Give a deterministic rule for conflicting edits, the conditions required for convergence, and one user-visible cost. Explain what the balance endpoint should do and which additional invariant a payment operation would need. Describe how the application could communicate these outcomes.

### Sample solution

- An ordinary public profile read can return `Nia` under the stated stale-data contract. The application can mark the value as possibly stale. It must eventually propagate the acknowledged edit and resolve all conflicts to obtain convergence.
- A read-your-writes request carrying the `Noor` edit cannot successfully return `Nia` merely because West has a local copy. For a common totally ordered profile log, the writer returns the edit's position as a token. An eligible replica serves a snapshot whose contiguous applied prefix contains that position. If West cannot access such a replica before the deadline, return `unavailable` and offer a retry. Independent regional counters cannot establish inclusion in the common history.
- If both regions edit the same field, choose the edit with the largest unique edit ID under an agreed total order. On reconnection, deliver all edits to both replicas and apply the same deterministic rule. Both then select the same value. This rule can discard a user's edit. An alternative merge or conflict workflow is valid if its semantics and convergence conditions are explicit.
- The current-balance read must wait for a reachable authority or return `unavailable` within the client deadline. Returning 60 as current would violate the promised linearizable read because the update to 35 completed before the read. A separate last-known-balance endpoint could expose 60 with an explicit stale-data contract.
- A payment needs an atomic authorization and debit rule that prevents concurrent spenders from violating the balance constraint. A current read followed by an uncoordinated update is insufficient. The UI can distinguish an unavailable current value from a possibly stale profile.

### Rubric

Award 0, 1 or 2 points per criterion for missing, partial or complete reasoning. Accept alternatives that satisfy the stated contracts and specify their assumptions.

| Criterion | Full credit |
| --- | --- |
| Operation contracts | Separates stale public profile reads, read-your-writes session reads and current balance reads, and gives an appropriate result under the partition. |
| Session mechanism | Checks inclusion of the acknowledged edit in the served snapshot and uses a common contiguous history for a scalar token. States a deadline failure path. |
| Convergence and trade-off | Specifies a deterministic conflict rule, eventual delivery and an application-visible consequence of resolution. |
| Balance safety | Explains why stale success violates the current-balance contract and why authorization plus debit needs a coordinated atomic invariant. |

## Knowledge checks

### Q1 · Classify a completed history

East acknowledges `display_name = Lin`. A subsequent West read returns the earlier value `Mira` because replication has not arrived. No later write occurred. Which of the weak, eventual and linearizable contracts described in the lesson can allow the result?

**Answer.** A weak contract can allow it, as can eventual consistency during propagation. It violates a linearizable read/write contract because the acknowledged write finished before the read started. Eventual convergence still depends on delivery and consistent conflict resolution after updates stop.

### Q2 · Overlapping operations

A field initially holds `Mira`. A read begins, a write of `Lin` starts and finishes, and then the read returns `Mira`. No other operations occur. Can this history be linearizable?

**Answer.** Yes. The read overlaps the write, so the legal sequential history can place the read before the write. Returning `Lin` could also be legal if the read is ordered after the write. The specific invocation and response times constrain this choice.

### Q3 · A session read moves regions

A user receives a successful response to their `Lin` profile update at East. They then request a read-your-writes session read at West. West returns `Mira` successfully before receiving the update, with no later write. Which promise is violated, and does eventual consistency alone rule out this result?

**Answer.** Read-your-writes is violated because the successful session read omits the user's acknowledged update. Eventual consistency alone permits the temporary stale value, subject to its eventual propagation and reconciliation assumptions.

### Q4 · Interpret an unavailable response

During an East–West partition, an isolated West node returns `unavailable` for a current linearizable balance read. Explain what this does for the data contract and how it relates to CAP availability.

**Answer.** The response avoids reporting an unverified stale value as current. The requested read did not complete with a valid balance, so this outcome does not satisfy availability for that operation in the CAP model. A real service should also measure errors and latency against its own operational objective.

### Q5 · Check a scalar token

East acknowledges a profile update at position 12 of a shared total order and gives the client token 12. West reports its own independent regional counter is 15. Is that enough to serve a read-your-writes request? What evidence would be enough in the lesson's single-history model?

**Answer.** An independent regional counter says nothing about whether West applied East's update. West can serve the request from a snapshot that includes the contiguous applied prefix of the same ordered history through position 12. Otherwise it must route, wait or return unavailable within the deadline.

### Q6 · Reconcile concurrent edits

While disconnected, East writes `Lin` and West writes `Ari` to the same display-name field. You want replicas to converge after the network recovers. Propose a rule, state the delivery assumption, and identify a cost.

**Answer.** Assign each edit a unique ID and select the greatest ID under a fixed total order. Deliver both edits to both replicas and apply the same deterministic rule. They converge on the same winner, but one user's edit can be discarded. A different deterministic rule or an explicit conflict-resolution workflow is also valid when its assumptions are stated.
