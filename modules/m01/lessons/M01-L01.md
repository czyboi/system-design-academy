A team is designing an activity feed with a 30-day retention window. It needs an initial storage allocation and a latency budget before production measurements exist. Estimate the workload at each boundary, then use the estimates to choose what to measure and where to provision capacity.

## Learning outcomes

- **M01-L01-LO1.** Convert a stated workload into request rates, storage, bandwidth, working-set size and a request-path latency estimate.
- **M01-L01-LO2.** Choose and defend capacity and latency assumptions using peak demand, access patterns, trade-offs and measurement.

## Estimate demand from an activity feed

Assume a mature service creates 864,000 feed events every day and serves 8.64 million feed reads every day. A day has 86,400 seconds. Each event has a 1,000-byte stored payload, and each feed read returns 4,000 payload bytes to the client. These are hypothetical inputs for estimating, rather than observations or product benchmarks. Each event generates one API write and each feed view generates one API read. A peak interval reaches four times each daily average. These inputs describe one combined peak scenario. Use a different mix if reads and writes peak at different times. [Google SRE, Demand Forecasting and Capacity Planning](https://sre.google/sre-book/introduction/#demand-forecasting-and-capacity-planning)

| Quantity | Calculation | Estimate |
| --- | --- | ---: |
| Writes, average | 864,000 / 86,400 | 10 requests/s |
| Reads, average | 8,640,000 / 86,400 | 100 requests/s |
| Writes, peak | 10 × 4 | 40 requests/s |
| Reads, peak | 100 × 4 | 400 requests/s |
| Writes in 30 days | 864,000 × 30 | 25.92 million events |
| Reads in 30 days | 8,640,000 × 30 | 259.2 million requests |

The averages describe a hypothetical 30-day month with constant daily totals. The fourfold peak is an assumption about the rate within a shorter interval. For example, a launch might have a higher multiplier even when its daily average is unchanged. The combined peak has 440 API requests/s. It is an input for testing, since a request rate alone does not determine CPU or database capacity.

## Budget storage, bandwidth and the working set

Define units before multiplying. One byte is eight bits. `1 MB = 10^6 bytes` and `1 GB = 10^9 bytes`, while `1 MiB = 2^20 bytes` and `1 GiB = 2^30 bytes`. Thus `1 GiB = 1,073,741,824 bytes`, approximately 1.074 GB. Use decimal network units for Mbit/s and identify binary units when reporting memory or storage. [NIST, Prefixes for binary multiples](https://physics.nist.gov/cuu/Units/binary.html)

For this model, the retention window is full, each event expires completely at 30 days, and each stored event has three full copies. Indexes and metadata add 20% of the three-copy payload footprint. Provision an additional 25% of that subtotal for growth and operating margin.

1. Logical payload is `25.92 million events × 1,000 B = 25.92 GB`.
2. Three full copies use `25.92 × 3 = 77.76 GB` of payload.
3. Add index and metadata overhead, then margin. `77.76 × 1.20 × 1.25 = 116.64 GB` provisioned.

The 25% margin here means an addition equal to 25% of the subtotal. If a disk must instead remain 25% free *after* allocation, divide the required subtotal by `0.75`. Backups, temporary copies during repair, compression and future growth have their own assumptions and are excluded from this allocation.

At peak, client-to-API write payload is `40 × 1,000 × 8 = 320,000 bit/s`, or **0.32 Mbit/s**. API-to-client read payload is `400 × 4,000 × 8 = 12,800,000 bit/s`, or **12.8 Mbit/s**. These are separate interface directions. They exclude headers and retransmissions. If each write also sends its full payload once to two additional replicas, the primary's inter-node outgoing replication payload is `40 × 1,000 × 8 × 2 = 0.64 Mbit/s`. A design with different internal calls or replication mechanics needs a new per-link budget.

For a working-set estimate, suppose the normal write rate stays at 10 events/s for two hours, every new event in that period is accessed at least once, and no older events are accessed. The distinct event payload touched is `10 × 7,200 × 1,000 = 72,000,000 B`, or **72 MB**. Repeated reads increase traffic but do not increase this distinct set. Real access to older events, item sizes, cache metadata and eviction can change the memory required. A working set is tied to a chosen access interval. [Denning, The Working Set Model, §3](https://denninginstitute.com/pjd/PUBS/WSModel_1968.pdf#page=4)

## Budget the latency of a request path

Draw the dependency chain before adding times. For one hypothetical feed read, assume 3 ms for the client-to-edge path, 2 ms for API routing and processing, 12 ms for a profile lookup, 8 ms for a feed lookup, and 3 ms for the response path. If the feed lookup depends on the profile result, this single trace takes `3 + 2 + 12 + 8 + 3 = 28 ms`. If both lookups are independent, start together and have no extra contention, their overlap takes `max(12, 8) = 12 ms` and the corresponding trace takes `3 + 2 + 12 + 3 = 20 ms`. Parallel work can add concurrent load and use extra connections. Verify both the latency and resource cost under peak load.

Scale matters when deciding which parts warrant measurement. For this same feed, consider a hypothetical path where one local memory access takes 100 ns, one small device read takes 10 µs, and one remote request and response takes 1 ms. These are stipulated durations for an illustration, with no queueing or extra work included. A device read is 100 times the assumed memory access, and the remote round trip is 100 times the device read. Even 100 serial memory accesses total only 10 µs under these assumptions, while one remote round trip takes 1 ms. If the feed path has several dependent remote calls, investigate their count and individual durations first, while also checking device reads and memory access in the actual profile. Hardware, topology, request size, caching and contention can change these figures. Historical latency tables, including Patterson's 2004 comparison, provide dated intuition. Measure the current system under the intended workload before allocating a deadline. [Patterson, Latency Lags Bandwidth](https://pages.cs.wisc.edu/~markhill/restricted/cacm2004_latency.pdf)

For storage, a sequential scan reads nearby blocks and can benefit from locality and prefetch. A random access pattern reads scattered locations and can have different cache behavior and I/O costs. A batch may improve throughput while increasing the time an individual request waits to fill the batch. Benchmark both patterns using the intended block size, cache state, concurrency and device, then apply the relevant result to the path. [fio documentation, I/O type](https://fio.readthedocs.io/en/latest/fio_doc.html#i-o-type)

## Choose assumptions and refine the budget

Run a low and a high case for the assumptions that dominate the decision. If the same 30-day feed has a twofold to sixfold peak, its peak read input ranges from 200 to 600 reads/s. Provisioning from the average alone would miss both cases. Record how the range was chosen and check whether peak traffic, larger payloads and reduced capacity can occur together. Carry the resulting workload into a load test, measure per-stage latency and saturation, and revisit storage, network and compute allocation as actual access data arrives.

The 28 ms and 20 ms examples describe individual traces. Adding component p99s does not generally produce an end-to-end p99. Measure the client-facing distribution for the target population and time window, with errors and timeouts alongside it. This keeps a fast average from concealing a slow tail. [Google SRE, Worrying About Your Tail](https://sre.google/sre-book/monitoring-distributed-systems/#worrying-about-your-tail-or-instrumentation-and-performance)
