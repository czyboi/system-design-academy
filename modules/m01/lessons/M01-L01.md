# Capacity and latency budgets

## Learning outcomes

- M01-L01-LO1: Model traffic, retained storage, bandwidth, working set and the latency of a request path from stated inputs.
- M01-L01-LO2: Choose and defend an allocation or path change using peak load, failure margin and measurement criteria.

## Problem and motivation

An activity feed works in a small demonstration, but a machine sized from the daily average may run out of network or storage during a burst. A capacity estimate turns traffic, retention and request-path assumptions into quantities to test. It gives a team a starting allocation and identifies the assumptions most likely to change the design. Forecast growth and event spikes separately, and validate the chosen capacity under a representative workload. [Google SRE, Demand Forecasting and Capacity Planning](https://sre.google/sre-book/introduction/#demand-forecasting-and-capacity-planning).

## Core concepts and mechanisms

State the window, operation mix and units. Divide operations per day by 86,400 seconds for an average per second. A 30-day total can be divided by 30 before applying that conversion when activity is assumed uniform across days. Multiply each average operation rate by a stated peak factor. Peak traffic may differ by operation, customer, hour and region.

With constant daily ingest and full copies, retained payload bytes are daily events × retention days × bytes per event × number of copies, including the primary. Indexes, logs, backups and per-record overhead require separate estimates. Add a stated margin to estimated used capacity, or divide by the desired maximum utilization when the margin is stated as a share of provisioned capacity. For example, 25% added to use means multiply by 1.25. Reserving 25% of provisioned capacity means divide use by 0.75.

For network payload, multiply peak requests per second by bytes per request or response and by eight to obtain bits per second. Count ingress, egress and replication separately, then allow for framing, retries and uneven distribution. One kilobyte (kB) is 1,000 bytes, whereas 1 KiB is 2^10 = 1,024 bytes. A MiB is 2^20 bytes, and a GiB is 2^30 bytes. [NIST, Prefixes for binary multiples](https://physics.nist.gov/cuu/Units/binary.html).

The working set for a stated window estimates the **distinct** objects accessed during that window and their size. Repeated reads of an object may reuse the same cached bytes. This service-cache approximation applies the window and distinct-reference idea from the working-set model to application objects. Cache metadata, eviction and access skew change the practical allocation. [Denning, *The Working Set Model for Program Behavior*, definition](https://denninginstitute.com/pjd/PUBS/WSModel_1968.pdf#page=4).

## Worked example

Assume a feed creates 864,000 events and serves 8,640,000 reads per day. Each event occupies 1,000 payload bytes and each read response carries 2,000 payload bytes. Retain events for 30 days in three full copies. Assume a fourfold peak for reads and writes, and add 25% to the resulting stored payload for explicitly modeled growth and overhead.

| Quantity | Calculation | Estimate |
|---|---|---|
| Average writes | 864,000 ÷ 86,400 | 10 writes/s |
| Average reads | 8,640,000 ÷ 86,400 | 100 reads/s |
| Peak | average × 4 | 40 writes/s and 400 reads/s |
| Stored payload | 864,000 × 30 × 1,000 × 3 | 77.76 GB |
| Payload plus modeled margin | 77.76 GB × 1.25 | 97.2 GB |
| Peak read payload egress | 400 × 2,000 × 8 | 6.4 Mbit/s |
| Peak write payload ingress | 40 × 1,000 × 8 | 0.32 Mbit/s |

Replication traffic, backups and protocol overhead are additional. If the only distinct records read in a two-hour window are those created at the average ingest rate, the raw working set is 10 × 7,200 × 1,000 = 72,000,000 bytes, or 72 MB. This is a scenario-specific access assumption. A hot older item or a different event rate changes it.

## Latency and the request path

The original scale below uses **assumed values** solely to illustrate relative magnitudes. It is a sketch, not a benchmark or a promise for a machine, cloud or network. CPU cache access can be shorter than main-memory access. A sequential scan can transfer adjacent data efficiently, while random disk access may incur repeated positioning on a rotating disk. Solid-state devices have different mechanics. Read size, queue depth and cache behavior affect both patterns. Test the actual storage pattern. Suppose a request first fetches an ID over an assumed 1 ms local round trip, then uses that ID for a second 40 ms remote round trip. The second starts after the first completes, so these two intervals contribute about 41 ms to that individual trace before other work. If independent data can be requested together, overlap or batching may shorten the critical path. Confirm ordering, data dependencies and the resulting end-to-end distribution in traces. A sum of component p99s does not generally equal the end-to-end p99. HTTP/1.1 pipelining is one protocol-specific mechanism for eligible requests and still preserves response ordering. [RFC 9112 §9.3.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3.2).

## Trade-offs and failure modes

Choose a range for peaks and storage overhead when inputs are uncertain. A larger allocation absorbs more modeled variation at greater cost. A short retention period lowers storage while reducing the history available to users. An extra full replica consumes another copy's storage and replication bandwidth and may improve resilience depending on the topology.

Use the estimate to choose a starting allocation, then compare measured peak rates, latency distributions, saturation and physical overhead against assumptions. A cache needs sufficient memory for the observed working set and a policy for stale or evicted data. A path change helps only when it removes or overlaps work on the path users actually wait for. Repeat the test after the change.
