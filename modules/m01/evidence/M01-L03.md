# Evidence for M01-L03 — Consistency and partition decisions

Checked 2026-11-12. The profile and balance histories are original models. This lesson follows the approved [outline](../../../curriculum/revision-1/CURRICULUM_MASTER.md#m01-l03).

| ID | Claim and boundary | Primary source | Status |
| --- | --- | --- | --- |
| CP-01 | A weak read contract can admit stale reads after an acknowledged write. Eventual consistency requires convergence after updates stop and pending changes propagate and reconcile. A freshness bound or session guarantee requires a separate contract. | Werner Vogels, *Eventually Consistent — Revisited* (2008), [Client-side Consistency](https://www.allthingsdistributed.com/2008/12/eventually_consistent.html). | Verified |
| CP-02 | In this lesson strong consistency means linearizability for a read/write object. A legal sequential history must respect the order of nonoverlapping calls. In a two-operation history with an overlapping write, the read may see either value if its placement makes the history legal. | Herlihy and Wing, ACM TOPLAS 12(3), 1990, [§2.2 and §5.1](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf#page=6). | Verified |
| CP-03 | In the asynchronous CAP model with partition message loss, guaranteeing both a linearizable object and completion of every request at a non-failing node is impossible. A stale read can satisfy a weaker operation contract. An unavailable response fails to complete a stipulated current read. CAP availability has no response deadline or percentage target. Apply partition policy at the operation boundary. | Gilbert and Lynch, ACM SIGACT News 33(2), 2002, [§§2.1–2.3 and §3.1](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer6.pdf#page=3). Eric Brewer, *CAP Twelve Years Later* (2012), [Why “2 of 3” is misleading and Partition Mode](https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/). | Verified |
| CP-04 | A successful read-your-writes session read must include its prior writes, subject to subsequent updates. A scalar minimum version demonstrates inclusion when the served snapshot has applied a contiguous prefix of the same totally ordered history. Regional counters from independent histories lack that implication. | Terry et al., PDIS 1994, [§3.1](https://pages.cs.wisc.edu/~remzi/Classes/739/Papers/bayou-sessions94.pdf#page=3) and [§5](https://pages.cs.wisc.edu/~remzi/Classes/739/Papers/bayou-sessions94.pdf#page=7). Scalar threshold is a derived simplification of the inclusion check under the stated invariant. | Verified |
| CP-05 | With eventual delivery, a common total order and deterministic conflict handling, replicas can reconcile to the same state. Choosing one winner may discard a concurrent edit. Profile-field rules are application decisions. Balance authorization and debit require a separately specified atomic invariant. | Terry et al., SOSP 1995, [§5, Replica Consistency](https://www.scs.stanford.edu/nyu/01fa/sched/bayou.pdf#page=4). Business examples are original applications of the mechanism. | Verified |
| CP-06 | BASE stands for basically available, soft state, eventually consistent. Replica-derived state can change as queued updates arrive. Specify freshness, conflict handling and failure responses per operation. | Dan Pritchett, ACM Queue (2008), [An ACID Alternative and Consistency Patterns](https://web.stanford.edu/class/cs245/spr2019/readings/base.pdf#page=4). BASE is an architectural approach. | Verified |
| CP-07 | DynamoDB global tables version 2019.11.21 in MREC mode replicate changes asynchronously. Same-item conflicts use AWS's internal timestamp ordering. A regional strongly consistent read can still miss a write made in another Region. | AWS DynamoDB Developer Guide, [Versions and Multi-Region eventual consistency (MREC)](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html). Keep all examples mode-specific. A fixed lag, field-wise merge, application-time ordering or global transaction guarantee would require separate evidence. | Verified |
