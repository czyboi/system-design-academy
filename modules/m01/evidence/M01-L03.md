# Evidence for M01-L03 — Consistency and partition decisions

Checked 2026-11-11. The lesson traces original read/write histories and uses the Primer as its topic map.

| ID | Claim | Publisher, version and section | Scope and confidence |
|---|---|---|---|
| C1 | A weak consistency contract may permit a post-write stale read. Eventual consistency adds convergence once updates stop and communication and reconciliation can make progress. Linearizability requires a legal single-object history ordered by real-time precedence between nonoverlapping operations. | Werner Vogels, *Eventually Consistent – Revisited*, [Client-side Consistency](https://www.allthingsdistributed.com/2008/12/eventually_consistent.html), author version (2008). Gilbert and Lynch, *Brewer’s Conjecture*, ACM SIGACT News (2002), [§2.1 and §3.1](https://www.cs.princeton.edu/courses/archive/spr22/cos418/papers/cap.pdf#page=2). | Verified. A stale read after a completed nonoverlapping write and with no intervening write disproves linearizability for that history. Convergence has no generic deadline. |
| C2 | Under arbitrary message loss, an asynchronous replicated read/write object cannot guarantee both linearizability and eventual completion with a valid response for every request at a non-failing node. | Gilbert and Lynch (2002), [§2 and §3.1, Theorem 1](https://www.cs.princeton.edu/courses/archive/spr22/cos418/papers/cap.pdf#page=2). Eric Brewer, *CAP Twelve Years Later*, IEEE Computer (2012), [Why “2 of 3” Is Misleading and Partition Mode](https://sq4007-2025.github.io/website/pdfs/Brewer%20-%202012%20-%20CAP%20twelve%20years%20later%20How%20the%20rules%20have%20changed.pdf). | Verified. CAP availability concerns operations in the model. An error can be operationally preferable and still fail CAP availability for the requested operation. CP and AP can describe operation choices during a partition. |
| C3 | Reads in a read-your-writes session reflect preceding writes in that session. A minimum version and suitable routing or waiting can enforce it in a single-writer example. | Terry et al., *Session Guarantees for Weakly Consistent Replicated Data*, IEEE PDIS (1994), [§3.1 and §4](https://classes.cs.uchicago.edu/archive/2026/spring/23380-1/papers/terry_sessionguarantees.pdf). | Verified. Other sessions can lag. If a suitable replica is unreachable, the example must decline or delay the read to preserve the guarantee. |
| C4 | BASE refers to basically available, soft state and eventual consistency. A view can change as queued updates arrive even without a new user request. | Dan Pritchett, *BASE: An Acid Alternative*, ACM Queue (2008), [An Acid Alternative and Consistency Patterns](https://web.stanford.edu/class/cs245/spr2019/readings/base.pdf#page=3). | Verified as design terminology. Service targets, merge rules and transactions require separate contracts. |
| C5 | DynamoDB global tables in multi-Region eventual consistency mode replicate item writes asynchronously, resolve conflicting writes by internal last-write timestamp per item, and can return an older cross-Region version on a locally strongly consistent read. | AWS, DynamoDB global tables Version 2019.11.21, [How DynamoDB global tables work](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html), Multi-Region eventual consistency. | Verified for MREC. Whole-item resolution can discard a concurrent field edit. Generic cross-Region lag and availability figures remain unresolved. |

Donne Martin's *System Design Primer* at `ae9bbd7b02d90b9866215de185217d33f39ab733` maps [PR-H036–PR-H039 and PR-H041–PR-H044](https://github.com/donnemartin/system-design-primer/blob/ae9bbd7b02d90b9866215de185217d33f39ab733/README.md#L438-L493). Millisecond convergence and required synchronous replication are unsupported as universal claims. Teach operation policy with an older public profile, an author session with a minimum version, and a balance read requiring reachable authority.
