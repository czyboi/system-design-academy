# Wide-column and graph stores

A monitoring team reads one device's recent measurements, and a community team explores friends of friends. Both start with a known identifier. One wants contiguous time ranges with predictable bounds. The other follows edges discovered during execution. The storage model determines which data remains local as each query grows.

- **M05-L02-LO1.** Trace a wide-column range read, timestamped cell versions and a bounded adjacency traversal.
- **M05-L02-LO2.** Choose a key and placement strategy based on hot partitions, retention, traversal fan-out and required query semantics.

## Design wide rows for their range queries

In Bigtable, rows sort lexicographically by row key. Column families group qualifiers and provide settings such as retention. Rows can have different qualifiers, so sparse data need not have a cell for every possible attribute. A cell is identified by row key, family and qualifier and can contain values at multiple timestamps. For example, `device-18#20261113#081500` may have `metrics:temp` at 21.0 with timestamp 100 and a correction of 21.3 with timestamp 105, while `metrics:humidity` is absent. The event time in the row key identifies the measurement. The cell timestamp identifies its stored version. [Bigtable schema design](https://docs.cloud.google.com/bigtable/docs/schema-design), [Chang et al., Bigtable](https://research.google/pubs/bigtable-a-distributed-storage-system-for-structured-data/).

A row key beginning with the timestamp sends adjacent new readings into the newest key range. Use `device#day#time` with fixed-width or order-preserving time fields to keep a device's readings together and distribute different device prefixes. A high-rate device can still saturate one range. If its readings are independent, add a bounded bucket prefix derived from event identity. Read one range per bucket for the requested day and merge by event time. If the query spans two days, both day ranges are needed for each bucket. Verify distribution with per-range read and write load, and bound fan-out by the supported time window. [Bigtable row-key design](https://docs.cloud.google.com/bigtable/docs/schema-design).

## Separate retained versions from conflict timestamps

In Cloud Bigtable, a family can retain the newest versions or retire data by age. Garbage collection runs during compaction, so an eligible old value may remain readable until cleanup. Filter for the latest version or the required time range if the API depends on that behavior. HBase also stores timestamped cell versions and exposes family version settings, with product-specific defaults and read controls. [Bigtable garbage collection](https://docs.cloud.google.com/bigtable/docs/garbage-collection), [HBase Reference Guide, data model](https://hbase.apache.org/book.html#datamodel).

In Cassandra, a schema such as partition key `(device, day, bucket)` and clustering keys `(event_time, event_id)` puts that slice on one logical partition, with rows ordered by the clustering columns. Cassandra maps partitions by the partition key instead of exposing one Bigtable-style lexicographic range across all keys. Its normal write conflict resolution uses mutation timestamps per column. A winning timestamp chooses the visible value. If old corrections must remain queryable, model them as separate records. [Apache Cassandra CQL primary keys](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/ddl.html), [Dynamo architecture and versioning](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html).

## Walk two hops from an indexed seed

A graph represents accounts as vertices and follows as directed edges. Look up the starting account by indexed ID, then expand its outgoing adjacency. If A follows B and C, B follows D and E, and C follows D and A, the second-hop candidates are D, E, D and A. Exclude the seed, exclude direct follows where the product requires it, and deduplicate to return D and E. The index locates A. The expansion cost comes from the edges examined after that lookup. [Neo4j Cypher indexes](https://neo4j.com/docs/cypher-manual/current/indexes/performance-indexes/using-indexes/), [bounded variable-length paths](https://neo4j.com/docs/cypher-manual/current/patterns/variable-length-paths/).

A supernode with 50,000 outgoing edges can dominate a two-hop query even at small depth. A distributed placement can keep many common neighborhoods local or route each remote adjacency lookup to its owner. A cross-partition edge can add remote work. To bound requests, filter eligible edges early, cap expansion and make truncation explicit. If the endpoint requires exhaustive results, return an explicit incomplete response or offer asynchronous enumeration instead of silently dropping neighbors. For stable known traversals, a precomputed neighbor list is another read path with its own freshness and update cost.

## Choose using locality and query promises

Use a wide-column time-series model when a bounded set of row-key ranges answers the important requests. Measure hottest range, reads per logical query and the cost of repairing or expiring stored versions. Use a graph model when relationships drive which records to visit next. Measure nodes and edges visited, remote hops and completeness for the requested traversal. A two-hop graph query on a degree-skewed graph needs a different budget than a fixed time range on one device.
