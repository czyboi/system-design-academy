# Wide-column and graph stores

A monitoring team reads one device's recent measurements, and a community team explores friends of friends. Both start with a known identifier. One wants contiguous time ranges with predictable bounds. The other follows edges discovered during execution. The storage model determines which data remains local as each query grows.

- **M05-L02-LO1.** Trace a wide-column range read, timestamped cell versions and a bounded adjacency traversal.
- **M05-L02-LO2.** Choose a key and placement strategy based on hot partitions, retention, traversal fan-out and required query semantics.

## Design wide rows for their range queries

In Bigtable, rows sort lexicographically by row key. Column families group qualifiers and provide settings such as retention. Rows can have different qualifiers, so sparse data need not have a cell for every possible attribute. A cell is identified by row key, family and qualifier and can contain values at multiple timestamps. For example, `2#device-18#20261113#081500#event-0042` may have `metrics:temp` at 21.0 with illustrative version timestamp 1000000 microseconds and a correction of 21.3 at 2000000 microseconds, while `metrics:humidity` is absent. These distinct timestamps respect Bigtable's millisecond granularity. The event time and immutable event ID identify the measurement. The cell timestamp identifies its stored version. Two events sharing an event time retain distinct IDs and rows. [Bigtable schema design](https://docs.cloud.google.com/bigtable/docs/schema-design), [Bigtable Data API](https://docs.cloud.google.com/bigtable/docs/reference/data/rpc/google.bigtable.v2), [Chang et al., Bigtable §2](https://www.usenix.org/legacy/event/osdi06/tech/chang/chang.pdf#page=2).

A row key beginning with the timestamp sends adjacent new readings into the newest key range. Use `bucket#device#day#time#eventId` with fixed-width UTC day and time fields and the full immutable event ID as a tie-breaker. Derive the bounded bucket from that original event ID, and send every correction to the same row and qualifier. A high-rate device can still saturate a range, but independent event IDs can spread its readings across buckets.

For four buckets and the half-open UTC interval [2026-11-13 23:45:00, 2026-11-14 00:15:00), issue one cross-midnight range per bucket. For bucket 0 and `device-18`, the lower-inclusive key is `0#device-18#20261113#234500#` and the upper-exclusive key is `0#device-18#20261114#001500#`. All event IDs at the start time fall inside, while the end time is excluded. Repeat the bounds for buckets 1–3, then merge the four streams by event time and event ID. Day fields sort consecutively within each fixed bucket and device prefix. Verify actual per-range load and bound fan-out by the supported time window. [Bigtable row-key design](https://docs.cloud.google.com/bigtable/docs/schema-design#row-keys), [Data API RowRange](https://docs.cloud.google.com/bigtable/docs/reference/data/rpc/google.bigtable.v2#rowrange).

## Separate retained versions from conflict timestamps

In Cloud Bigtable, configure the family retention policy to preserve all versions needed for the audit period, including the expected correction rate. An audit read explicitly requests the retained versions in its required version-time interval. A latest-value read instead selects the newest version for each cell. Garbage collection runs during compaction, so an eligible old value may remain readable until cleanup. Apply the read filter even after the retention threshold. HBase also stores timestamped cell versions. Its family version limits and Get/Scan version and time-range controls have their own documented behavior and defaults. [Bigtable garbage collection](https://docs.cloud.google.com/bigtable/docs/garbage-collection), [HBase Reference Guide, data model and versions](https://hbase.apache.org/book.html#datamodel), [HBase version controls](https://hbase.apache.org/book.html#versions).

In Cassandra, a schema such as partition key `(device, day, bucket)` and clustering keys `(event_time, event_id)` puts that slice on one logical partition, with rows ordered by the clustering columns. The same two-day request addresses each day and bucket partition separately, unlike the Bigtable range above. Cassandra maps partitions by the partition key instead of exposing one Bigtable-style lexicographic range across all keys. Ordinary conflict reconciliation uses mutation timestamps per column. If old corrections must remain queryable, model them as separate records. These references are the Cassandra project's living documentation. [Apache Cassandra CQL primary keys](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/ddl.html), [data versioning](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html#data-versioning).

## Walk two hops from an indexed seed

A graph represents accounts as vertices and follows as directed edges. Look up the starting account by indexed ID, then expand its outgoing adjacency. If A follows B and C, B follows D and E, and C follows D and A, the second-hop candidates are D, E, D and A. Exclude the seed, exclude direct follows where the product requires it, and deduplicate to return D and E. The index locates A. The expansion cost comes from the edges examined after that lookup. [Neo4j Cypher indexes](https://neo4j.com/docs/cypher-manual/current/indexes/performance-indexes/using-indexes/), [bounded variable-length paths](https://neo4j.com/docs/cypher-manual/current/patterns/variable-length-paths/).

A supernode with 50,000 outgoing edges can dominate a two-hop query even at small depth. A distributed placement can keep many common neighborhoods local or route each remote adjacency lookup to its owner. A cross-partition edge can add remote work. To bound requests, filter eligible edges early, cap expansion and make truncation explicit. If the endpoint requires exhaustive results, return an explicit incomplete response or offer asynchronous enumeration instead of silently dropping neighbors. For stable known traversals, a precomputed neighbor list is another read path with its own freshness and update cost.

## Choose using locality and query promises

Use a wide-column time-series model when a bounded set of row-key ranges answers the important requests. Measure hottest range, reads per logical query and the cost of repairing or expiring stored versions. Use a graph model when relationships drive which records to visit next. Measure nodes and edges visited, remote hops and completeness for the requested traversal. A two-hop graph query on a degree-skewed graph needs a different budget than a fixed time range on one device.
