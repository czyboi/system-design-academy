# Key-value and document stores

A commerce application checks a session by token and lists active products by category and price. Session validation starts with the exact identity of a record. Product discovery starts with predicates over data. The access paths, failure semantics and unit of update differ.

- **M05-L01-LO1.** Trace exact-key, ordered-key and indexed document access for sessions and product aggregates.
- **M05-L01-LO2.** Choose a key-value or document model by queries, aggregate ownership and required write and read semantics.

## Start with the access path

For `validate(token)`, hash the presented token to derive a lookup key and fetch that session. In an illustrative hash-partitioned store, hashing the key chooses an owner and a keyed lookup obtains the value. The value might contain an account ID, expiry and session flags. The application checks expiry and interprets a missing record according to policy. A product query such as category `helmets` and price under 80 cannot derive a product ID from that key alone. Maintain a secondary access path or scan an explicitly bounded dataset. Application-maintained relationships need their own update and repair rules.

An ordered access path is different. A key model that groups records by a partition key and orders them by sort key can serve a range within one group. DynamoDB exposes this with a composite primary key. For example, model active listing entries with `category#active` as the partition key and `price#productId` as the sort key, using fixed-width price encoding and a tie-breaker. Only active products belong in that listing. Query the exact partition key and the price range in the sort key. A change of category, status or price changes membership or key. If the design also has an authoritative product item, updating the access path needs a defined transaction or freshness and repair policy. A popular category can also become a hot key range. [DynamoDB core components and primary key](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.CoreComponents.html), [Query key conditions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Query.KeyConditionExpressions.html).

## Trace an indexed product document

A product aggregate can embed fields that the product page reads and changes together, such as title, status, display price and a bounded set of variants. Reference separately owned or independently updated data such as a seller profile or unbounded review history. For MongoDB 8.0, a matching compound index over category, active status and price can direct category and status equality plus a price range query toward candidate documents. The index leads to the documents that supply the embedded fields. Check the actual plan and index maintenance cost with representative data. [MongoDB 8.0 data modeling](https://www.mongodb.com/docs/v8.0/data-modeling/best-practices/), [equality, sort and range guideline](https://www.mongodb.com/docs/v8.0/tutorial/equality-sort-range-guideline/).

Suppose product P18 has two variants, category `helmets`, status `active` and price 72. A category and price query finds P18 through that index. A single-document update changes price to 84 and adjusts both embedded display labels together. MongoDB 8.0 provides single-document write atomicity. A matching read of the updated indexed state then excludes P18 from the under-80 result. A separate seller balance or inventory document needs an explicit cross-document transaction or an acceptable independent workflow. [MongoDB 8.0 write atomicity](https://www.mongodb.com/docs/v8.0/core/write-operations-atomicity/).

During a schema rollout, preserve a `schemaVersion` so readers can decode the old and new product shapes. An old reader querying only top-level `price` would miss a nested-only document. An old writer updating only that top-level field would also leave a nested copy stale. While either old reader or old writer remains, keep top-level `price` present and authoritative for every document and use it for browse and current-price reads. Deploy compatible readers and writers, then retire or upgrade the old writers before relying on both representations. Thereafter, if both fields are maintained, update them together in one atomic document write. Backfill nested values, verify them against the canonical field and migrate readers and browse access paths. Retire the old field and index only after old dependents are gone and backfill and verification finish. A dual-path query helps only readers actually changed to execute it. [MongoDB 8.0 schema versioning](https://www.mongodb.com/docs/v8.0/data-modeling/design-patterns/data-versioning/schema-versioning/), [single-document atomicity](https://www.mongodb.com/docs/v8.0/core/write-operations-atomicity/).

## Compare concrete product contracts

Redis `GET` reads a string value by exact key. A sorted set and `ZRANGE` can give score-ordered access if the application maintains the membership. Memcached's basic text protocol exposes keyed `get` and `set` with expiration. Design cache misses and evictions explicitly. If a session must survive a cache failure, validate through a durable authority or fail closed under the contract. Do not turn a miss into authorization. [Redis GET](https://redis.io/docs/latest/commands/get/), [Redis ZRANGE](https://redis.io/docs/latest/commands/zrange/), [Memcached basic text protocol](https://docs.memcached.org/protocols/basic/).

For a concrete revocation contract, keep session state in one regional DynamoDB base table. Confirm revocation only after the write succeeds. Every validation whose authoritative check starts after that confirmation must deny the revoked token. Perform that check with `GetItem` and `ConsistentRead=true` on the same regional table. Treat cache hits, including positive entries, as hints and fail closed if the authority cannot answer. For example, a cache may still say active after revocation commits. A subsequent authoritative read sees the revoked state and denies the token. An unavailable table also yields denial under this contract. [DynamoDB strongly consistent reads](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html#HowItWorks.ReadConsistency.StronglyConsistentReads), [GetItem](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_GetItem.html).

A validation whose authoritative check overlaps the revocation may read active before the write commits and finish afterward. This contract permits that overlap. If a protected action must itself be prevented after revocation commits, coordinate its admission with revocation at an authority that enforces that stronger ordering.

MongoDB provides a document model and single-document atomic updates. DynamoDB uses item keys, sort keys and secondary indexes with resource-specific read semantics. For example, a strongly consistent read can be requested on a DynamoDB table or local secondary index, while global secondary index reads are eventually consistent. For a product browse page, choose the index and freshness policy with that distinction in mind. BASE describes a family of design choices around availability, changing replica state and convergence. Read consistency, failover and transaction guarantees come from the selected product, operation and configuration. [MongoDB 8.0 write atomicity](https://www.mongodb.com/docs/v8.0/core/write-operations-atomicity/), [DynamoDB read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html).

## Choose by lookup, invariants and change rate

Pick keyed access for sessions when the API already has the key and the value fits one independent record. Pick an indexed document aggregate when queries enter through several attributes and the application mostly reads or updates a bounded aggregate. If attribute queries are predictable and narrow, an ordered key design can also fit, with explicit maintenance for every access path. Before deciding, trace the cost of adding a new predicate, a price update, a token revocation, a stale index read and a schema migration. Check that the chosen authority can enforce the required write scope.
