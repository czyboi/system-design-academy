# SQL versus NoSQL and distributed-store guarantees

A shopper can keep editing a basket when regions lose contact. At checkout, two shoppers compete for the last unit. A reporting view can catch up later. The same system needs three contracts. Model the queries, define what each operation promises during failure, then choose a store or combination that can deliver those promises.

- **M05-L03-LO1.** Trace replica overlap, concurrent versions, repair and coordinated reservation in one commerce workload.
- **M05-L03-LO2.** Defend a data model and concrete product contract by access path, invariant, failure behavior and operating cost.

## Choose an access path by workload

| Model | Query and schema fit | Transaction and scaling question |
| --- | --- | --- |
| Relational | Typed tables and keys fit an account ledger where operators join adjustments, invoices and customers and ask new questions. | Keep inventory and reservation in one transaction where possible. Measure contention and plans before splitting the owner. |
| Key-value | A content ID can address snippet metadata or a query-result key directly. Token lookup and short-lived cached results have known access paths. An ordered structure can retrieve a leaderboard by score. | A cache miss needs an authoritative fallback. Ranking updates may contend on one board or require merging partitions. Verify how writes and expiry behave. |
| Document | A basket or product record contains a bounded aggregate. Index stable fields for additional read paths. | Confirm the unit of atomic change. Separately updated records require a defined cross-record contract and migrations must preserve index visibility. |
| Wide-column | A crawler can look up seen-URL metadata by key. Clickstream or log ingestion can group time ranges by source and bucket. A feed can store per-user timelines for bounded scans. | A new access pattern may need another maintained view. One popular user or newest time range can dominate writes even with many nodes. |
| Graph | Edges and adjacency match follower and relationship traversal. An indexed user can seed the walk. | Popular vertices can dominate work. Bound hops and fan-out, and define what an incomplete response means across partitions. |

Match schema flexibility to actual changes and determine which joins or traversals the system needs to execute. Isolate a hot status table only once the measured bottleneck and its partition key are understood. Preserve ownership for any rule spanning that table and another. Compare throughput at the same skew, read/write mix and failure schedule. Count loss or staleness separately from latency. Include backup and restore, migrations, observability, operational skills and reporting integrations in the decision.

## Specify what a response promises

ACID groups atomicity, invariant preservation, isolation and durability. State the invariant and isolation and durability conditions explicitly. A successful reservation must leave stock non-negative and persist its receipt in the same authoritative operation. The consistency in ACID concerns valid state transitions. A read consistency contract concerns what a particular reader can observe.

BASE is shorthand for basically available, soft state and eventual consistency. For a basket design, accept qualifying local edits, let state evolve as updates propagate or reconcile, and define the conditions under which replicas converge. Eventual convergence alone supplies neither a deadline nor a merge rule. During a partition, name which actions can continue, which results can be stale and which actions must fail or wait to protect an invariant. Store categories supply query and data models. Concrete APIs and configurations supply transaction and replication guarantees. [PostgreSQL 18 transactions](https://www.postgresql.org/docs/18/tutorial-transactions.html), [Dynamo, SOSP 2007 §§2 and 4.4](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf#page=6).

## Follow a write through replicas and repair

In a strict fixed replica set, let N be the number of replicas and let W and R be the required acknowledgements for a write and responses for a read. If N = 3 and W = R = 2, any two responding replicas intersect any two acknowledging replicas. For example, a write acknowledged by A and B intersects a read from B and C at B. The arithmetic establishes set overlap. The protocol must still define version selection, concurrent writes and what an acknowledgement means.

The Dynamo paper uses a preference list, sloppy quorums, versions and reconciliation. Distinguish the preferred replicas, nodes contacted and the subset whose replies satisfy the required count. Suppose A, B and C are preferred, B and C are unavailable, and A and fallback D are the only eligible reachable nodes contacted. Both acknowledge the write, and D holds a hint for B. Assume no other copy received this write. If A and D later become unreachable before handoff and B and C are reachable, B and C can supply the two read responses without seeing it. The write acknowledgers and read responders are disjoint even though both counts are two. Hinted handoff transfers D's copy to B when D can reach it. Anti-entropy compares replica ranges using Merkle trees and repairs differences when a copy containing the update is reachable. If every such copy is permanently lost, these mechanisms cannot reconstruct the update. Causal metadata can distinguish concurrent branches but the application still chooses the meaning of a merge. [Dynamo §§4.4–4.7](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf#page=6), [request execution and repair](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf#page=8).

For a basket, assume an add-only set of uniquely identified additions. Two isolated regions add different items against the same base. Their versions are concurrent and union can preserve both additions after reconciliation. If removals are allowed, define their relationship to adds and retain necessary deletion information before adopting a merge rule. A union of the visible item sets could restore a removed item.

## Reserve stock under a concrete contract

With stock = 1, each region could read one and promise the unit independently. A merge after both promises cannot honor both. Keep one coordinated reservation authority. It conditionally decrements available stock and records the stable reservation ID in one transaction. If the reply is lost, look up or retry the same ID under the same authority and durability contract. The reporting projection can consume committed reservation records and expose its freshness separately. It never authorizes stock.

DynamoDB is the AWS product. For example, same-Region `TransactWriteItems` can atomically update a stock item only if enough stock remains and put a distinct receipt item only if that operation ID does not already exist, within one AWS account and Region. Bind the receipt to immutable request inputs such as item, quantity and buyer. Two different operation IDs racing for the last unit cannot both satisfy the stock condition. A duplicate of one ID cannot perform the decrement again once its receipt exists.

Suppose the reply is lost. A strongly consistent base-table lookup that finds the matching receipt returns its recorded outcome. A receipt with different request inputs is an identity conflict. An absent receipt does not prove failure while the first transaction may still be in flight. Return pending or unknown, and, if retry is permitted, submit the same guarded transaction under the same operation ID and inputs. A transaction conflict or cancellation alone does not prove a seat denial. Recheck the receipt and establish the authoritative stock outcome after competing work resolves, or keep the outcome pending.

For this example, accept retries for 24 hours and retain receipts beyond that window. DynamoDB's native `ClientRequestToken` has a ten-minute idempotency window, so the application receipt and its conditional create protect a delayed duplicate after that window. A global secondary index has eventual reads. Do not assume that a transaction in one Region is exposed atomically through a stream, an index or another Region. [DynamoDB TransactWriteItems](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html), [transaction conflicts](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html), [read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html).

As a contrasting design, use one Cloud Spanner database and a serializable read-write transaction to check and update inventory and create the operation receipt together. A later strong receipt read that begins after a successful reservation commit observes that commit. The Spanner paper assigns a commit timestamp and waits until TrueTime guarantees it is in the past before exposing the commit. If a competing transaction begins after that completed reservation, external consistency orders it after the reservation, so it cannot also claim the last unit. An overlapping transaction still must obey the serializable transaction and receipt rules. Strong status reads do not settle an operation that is still in flight merely because its receipt is absent. [Cloud Spanner serializable isolation](https://docs.cloud.google.com/spanner/docs/isolation-levels#serializable_isolation), [external consistency and strong reads](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency), [Corbett et al., Spanner §§4.1.2 and 4.2.1](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf#page=7).

That design pays replication, coordination and commit-wait costs. Geographic availability depends on the selected configuration. Verify that the required participants and replica capacity survive the stated failure and measure latency under that placement. A single transactional owner can suffice when the invariant fits locally.
