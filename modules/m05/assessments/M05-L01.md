# Companion assessment for M05-L01

## Practical exercise

**EX-1.** An outdoor store validates session tokens, shows a product detail page and lists active boots in a category under a price threshold. A revoked token must never be accepted after a confirmed revocation. A cache may lose entries or contain an old positive result. Product browse can lag, while one product's price and bounded set of display labels must change together. During a migration, old readers look for a top-level `price` and new readers can decode a nested price.

Propose a model and access path for each operation. Trace session cache loss and the stale positive result, one product price change across the threshold, and coexistence of old and new documents without dropping browse results. State a freshness or transaction question to verify for each product option.

## Knowledge checks

### Q1

Why can a token lookup route before knowing the user's account ID?

**Answer.** The token derives the session key. The account relationship is a field of the returned value.

### Q2

What must change when a product indexed by category and encoded price moves from 72 to 84?

**Answer.** The old access-path entry must be removed or invalidated and the new one added under the index's consistency contract. A product ID alone cannot answer the category range query.

### Q3

Which read needs extra work if the field indexed as `price` moves to a nested path?

**Answer.** Browse using the old indexed path can miss new documents. Keep a common indexed field or query both compatible indexes through the migration.

### Q4

Should a positive cache entry by itself authorize a session when revocation must be immediate after confirmation?

**Answer.** No. Check a durable authoritative state or an equivalent strictly coordinated validation mechanism that can rule out the revoked version.

### Q5

When would embedding product variants stop being a good fit?

**Answer.** An unbounded or independently owned set can make the document expensive to update and read. Give it a separate access path and define the relationship.

### Q6

Can a DynamoDB global secondary index be asked for a strongly consistent read?

**Answer.** No. Use the documented eventual GSI semantics or choose an eligible table or local index access path if the requirement permits it.

## Sample solution and rubric

Look up a hash-derived session key. Use cache results as hints and confirm authorization with the durable owner whose read semantics honor committed revocation. A missing cache entry falls back to that authority. A stale positive cannot authorize a request, and an unavailable authority fails closed. Check consistency of the exact read and write endpoints, and keep cache eviction outside the authority contract.

Store product price and bounded labels in one document and update it atomically. Use a category, active-status and price index for browse, verify the plan and define how stale reads are exposed. A price of 84 stops matching the under-80 query once the chosen read path includes that change. Keep `price` as an indexed compatibility field until old readers are gone and both shapes are verified, or maintain and query both indexes during the rollout. A composite-key design can serve the known browse shape if it protects or repairs the separately maintained entries.

| Criterion | Points | Full credit |
| --- | ---: | --- |
| Session access and revocation | 3 | Routes exact keys and traces eviction, stale positive and authority failure while preserving revocation. |
| Product access and update | 3 | Traces the attribute query and one aggregate update, and states the visibility contract for browse. |
| Migration | 2 | Keeps both document generations readable and indexed throughout rollout. |
| Contract and trade-off | 2 | Distinguishes application semantics from selected product guarantees and identifies meaningful verification questions. |

Award partial credit for correctly explained mechanisms with incomplete traces. Accept alternatives that meet the same constraints.
