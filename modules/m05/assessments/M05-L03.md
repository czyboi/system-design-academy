# Companion assessment for M05-L03

## Practical exercise

**EX-1.** A ticket platform accepts add-only favorites in two regions during a link failure. It also sells numbered seats, with at most one confirmed buyer per seat. A ranking view can lag and must expose its freshness. A three-replica favorite system normally prefers A, B and C with R = W = 2. With B and C unreachable, A and fallback D are the only eligible reachable nodes contacted. Both acknowledge an add, and D holds a hint for B. Assume no other copy received the add. Before handoff, A and D go offline and B and C return. Reservation retries are accepted for 24 hours, and receipts are retained beyond that window.

Trace the favorite read and repair during and after the failures. Then show how two buyers racing for one seat are handled, including a lost reply while the first transaction may still be in flight, a receipt lookup and a delayed duplicate. Compare an in-Region DynamoDB transaction with a serializable Cloud Spanner transaction across placement boundaries. Assign an access model to rankings and give one test and one product evidence question for each strict operation path.

## Knowledge checks

### Q1

What does R = W = 2 prove for a fixed set of three replicas?

**Answer.** Every set of two read responders intersects every set of two write acknowledgers. This is a set property. Exact read semantics still depend on versions, acknowledgements and concurrency rules.

### Q2

Why can B and C miss the add acknowledged by A and D?

**Answer.** Fallback placement changed the participating set. The two pairs are disjoint until the missing data reaches an intended owner.

### Q3

Why is an add-only union unsuitable for arbitrary favorite removals?

**Answer.** Another replica may still hold the removed item. Merging visible sets can restore it unless the design represents and reconciles the removal.

### Q4

Which condition matters more than traffic volume when choosing the seat reservation store?

**Answer.** Whether a single operation can claim the seat and persist its confirmation identity with the required isolation, durability and failure behavior. Measure throughput under that exact contract.

### Q5

Can a DynamoDB transaction be assumed atomically visible through the product's global secondary index?

**Answer.** No. Index propagation and reads have their own contract. A strict check should use an eligible authoritative access path.

### Q6

Why use an ordered projection for rank while keeping the reservation authority separate?

**Answer.** The ranking path can optimize ordered reads and tolerate lag. It cannot decide whether authoritative stock or a seat is available.

## Sample solution and rubric

B and C are the preferred replicas that return the two read responses. They can return an older set despite satisfying the read count because the write was acknowledged by contacted nodes A and D. D's hint names B, and handoff can restore it if D recovers and the hint remains available. Anti-entropy can repair divergent replicas when a surviving copy containing the add is reachable. A concurrent add-only merge can preserve independent additions. If all copies containing the add are permanently lost, repair cannot reconstruct it without another retained source.

In one AWS account and Region, use a DynamoDB transaction that conditionally changes a free seat to claimed and conditionally creates a distinct receipt keyed by operation ID only if that receipt does not exist. Store the immutable seat and buyer inputs with the outcome. Competing operations cannot both claim the same free seat. A duplicate ID cannot claim again after its receipt commits.

After a lost reply, a strongly consistent base-table read that finds the matching receipt returns its outcome. A mismatched input is an identity conflict. If the receipt is absent while the original may still be in flight, report pending or unknown. A permitted retry uses the same operation ID and guarded transaction. A conflict or cancellation alone cannot prove seat denial. Recheck the receipt and establish the seat outcome after competing work resolves, or remain pending. Retain receipts beyond the 24-hour retry window. DynamoDB's native client token covers ten minutes, while the conditional receipt prevents a delayed duplicate from applying again after that window.

For Cloud Spanner, place the seat and receipt in one database and use a serializable read-write transaction. A later strong receipt read after a completed commit observes it. TrueTime commit wait makes the chosen commit timestamp safely past before the commit is exposed, preserving real-time order for a later transaction. An absent receipt while the first transaction is still in flight remains unknown. Verify configuration, participant and replica availability during the specified failure and latency under the same workload. Test an in-flight lookup, delayed duplicate and lost response for either design.

Maintain the ranking as an ordered projection of committed reservations. Publish an observed checkpoint or freshness indicator with it and test the lag when delivery stalls. Retain enough committed input for recovery.
