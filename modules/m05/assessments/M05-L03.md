# Companion assessment for M05-L03

## Practical exercise

**EX-1.** A ticket platform accepts add-only favorites in two regions during a link failure. It also sells numbered seats, with at most one confirmed buyer per seat. A ranking view can lag and must expose its freshness. A three-replica favorite system normally prefers A, B and C with R = W = 2. With B and C unreachable, an add is acknowledged by A and fallback D. Before handoff, A and D go offline and B and C return.

Trace the favorite read and repair during and after the failures. Then show how two buyers racing for one seat are handled, including a lost reply after potential commit. Compare an in-Region DynamoDB transaction with a database offering externally consistent transactions across placement boundaries. Assign an access model to rankings and give one test and one product evidence question for each strict operation path.

## Knowledge checks

### Q1

What does R = W = 2 prove for a fixed set of three replicas?

**Answer.** Every set of two read responders intersects every set of two write acknowledgers. This is a set property. Exact read semantics still depend on versions, acknowledgements and concurrency rules.

### Q2

Why can B and C miss the add acknowledged by A and D?

**Answer.** Fallback placement changed the participating set. The two pairs are disjoint until the missing data reaches an intended owner.

### Q3

Why is an add-only union unsuitable for arbitrary favorite removals?

**Answer.** Another replica may still hold the removed item. Merging visible sets can restore it unless the design represents and reconciles the removal.

### Q4

Which condition matters more than traffic volume when choosing the seat reservation store?

**Answer.** Whether a single operation can claim the seat and persist its confirmation identity with the required isolation, durability and failure behavior. Measure throughput under that exact contract.

### Q5

Can a DynamoDB transaction be assumed atomically visible through the product's global secondary index?

**Answer.** No. Index propagation and reads have their own contract. A strict check should use an eligible authoritative access path.

### Q6

Why use an ordered projection for rank while keeping the reservation authority separate?

**Answer.** The ranking path can optimize ordered reads and tolerate lag. It cannot decide whether authoritative stock or a seat is available.

## Sample solution and rubric

B and C can return an older set despite satisfying the read count. Hinted handoff can eventually restore intended placements if D recovers and retained hints are available. Anti-entropy can repair divergent replicas when a surviving copy is reachable. A concurrent add-only merge can preserve independent additions. If all copies containing the add are permanently lost, repair cannot reconstruct it without another retained source.

Use a single reservation authority. Conditionally change the seat from free to claimed and save the operation ID together. One competing attempt wins and the other fails the condition. If the response is lost, retry under the same identity and check the authoritative receipt. In one AWS Region, a DynamoDB transaction can operate on distinct seat and receipt items in the same account and Region. Test lost replies, duplicates and the read used to recover the receipt. When strict transactions actually span placements, an externally consistent transaction system is a candidate. Verify its read mode, placement, failure availability and latency with the same workload. Neither option can be selected on throughput claims alone.

Maintain the ranking as an ordered projection of committed reservations. Publish an observed checkpoint or freshness indicator with it and test the lag when delivery stalls. Retain enough committed input for recovery.

| Criterion | Points | Full credit |
| --- | ---: | --- |
| Replication trace | 3 | Shows fixed-set overlap versus the disjoint sloppy pair, names repair conditions and explains safe add-only merge. |
| Reservation and retry | 3 | Protects one winner through an authoritative transaction and traces a lost reply using one operation identity. |
| Product choice | 2 | Scopes DynamoDB and external consistency to actual operations, placement and failure behavior. |
| Projection and verification | 2 | Chooses an ordered reporting path, defines freshness visibility and proposes observable failure tests. |

Accept equivalent designs that preserve the same guarantees. Award partial credit for correctly explained mechanisms with incomplete traces.
