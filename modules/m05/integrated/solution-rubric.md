# Reference design and rubric

## Match the query to the invariant

| Path and recommendation | Mechanism, trade-off and failure response | Two product evidence questions |
| --- | --- | --- |
| Session key in a durable store | Use a hash-derived token key and commit revocation in a single-Region DynamoDB base table before acknowledging it. A same-Region `GetItem` with `ConsistentRead=true` begun after acknowledgement reads revoked and denies despite a stale positive cache. If the read cannot verify state, fail closed and report authority unavailable. An earlier overlapping check follows the specified timing contract. A relational key lookup is also viable if its deployment meets the read and write contract. | Can the exact endpoint observe a previously acknowledged revocation? Which failure or failover modes make the authority unavailable or weaker, and how does the caller recognize them? |
| Indexed product document | Store price and bounded labels in one aggregate and update them together. Query an index with category and state equality followed by price range. A price of 84 eventually removes a former 72 listing from the under-80 result. Keep a canonical compatible price while fixed old readers and writers deploy out. After old writers are gone, update both representations in one document operation, backfill and verify before retiring the old field. A relational transaction and indexed join offer another option, with join and deployment cost to measure. | What is the atomicity scope of the update under the selected configuration? Which actual index and read route supports the browse query while meeting its 15-second freshness target? |
| Wide-column telemetry | Use one authoritative Bigtable row per event, keyed by stable bucket, device, date, time and immutable event ID. Derive the bucket from that ID. Two events at one timestamp are distinct rows. Within the bounded row store the original, all accepted correction payloads and input-bound receipts, current revision and lifecycle state. One single-cluster-routed app profile serves both conditional mutations and complete audit/latest reads. Query one half-open range per bucket and merge by event time and event ID. A time-partitioned relational table can also work if measurements meet its load and retention targets. | How do encoded bounds, partitions and key distribution affect a cross-midnight read and hot device? How do the selected routing, conditional mutation, row-size bounds and cleanup timing preserve complete audit and latest results? |
| Graph adjacency with a bound | Find the seed by ID, traverse two directed hops, exclude seed and direct neighbors, and deduplicate. When a required remote expansion misses the budget, return a marked partial result. An asynchronous endpoint can offer exhaustive enumeration. A relational adjacency table or derived neighborhood view fits a fixed traversal if its fan-out and freshness can be measured. | Does the selected execution plan use the seed index and where does remote adjacency work occur? How does the chosen API report timeouts or truncation, and can it distinguish partial from complete results? |

Prefer one operating stack when it meets all four contracts with manageable cost. Add a specialized store where a measured query or scaling requirement warrants the additional migration, restore, monitoring and repair work. Validate read paths under the same traffic and failure assumptions before comparing costs. The store model does not resolve the authority contract.

## Score the drills and test repair

Browse timely freshness is 196/200 = 98%, below 99%. The two late and two unavailable commits remain in the original commit cohort. For each isolated fixture, start probes from commit through 15 seconds inclusive at one-second intervals. Count a success only if the full ordered A, C response from the actual browse route and the evidence for that response are observed by the deadline. The fixture starts at A, B, C and fits one page. For pagination, exhaust the pages in one consistent browse view.

For a database-backed browse path, read B's canonical revision and the complete membership in the same database snapshot. For a separate search index, record B's committed revision and event ID in a durable source log. Publish a searchable index generation whose manifest proves that generation incorporated the event. Record the actual generation used by the browse response, including the serving generation for every required shard in a distributed index. Verify the event through a revision-bearing indexed record, a removal receipt, or a gap-free applied-through position on its source partition. Tie that evidence to the serving view used for the whole response. A publisher's receipt, a canonical point read, or progress from a different generation or replica cannot prove that this response incorporated the edit. Test a delayed update, an older serving replica, a partial response and a replay, then verify field compatibility during rollout. [MongoDB 8.0 snapshot read concern](https://www.mongodb.com/docs/v8.0/reference/read-concern-snapshot/) · [Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#using-an-outbox-table-with-a-relational-database).

Relationship completion is 91/100 = 91%, below 95%. A correctly labeled partial reply satisfies the truthfulness requirement and misses the completeness objective. Late full replies and timeouts also miss. Keep the original trace identity across retries. Report latency for complete successful replies separately from completeness. Compare normal seeds with remote high-degree seeds under the same budget.

Inject revocation while the cache has an active entry. Start a same-Region strongly consistent base-table check after acknowledgement and verify a revoked-state denial. Separately make the authoritative route unavailable and verify fail-closed behavior.

For telemetry, route each event to one authoritative Bigtable row using an app profile configured for a single cluster, and use that same route for writes and strict reads. A correction has an immutable ID and input payload. Read the complete row and check the ID. If absent, use a single-row conditional mutation that requires the lifecycle to be open and the current revision to equal the value read. On success it atomically writes the next revision, correction payload and receipt binding the ID and inputs. Two simultaneous corrections that read the same revision cannot both update it. The loser rereads and, if still eligible, retries with the new revision. A retry after a lost reply rereads the row. A matching receipt returns the saved outcome, a reused ID with different inputs is rejected, and an absent ID can retry the same guarded mutation. A missing or incomplete authority response remains pending or unavailable.

Audit reads obtain the full row from the same authority and return its original plus every accepted correction and receipt. A latest read selects the payload at the row's current revision from that same atomic snapshot. A truncated or unverified response cannot establish either result. If the designated cluster is unavailable, return unavailable until a recovery route is proven to contain the complete authoritative row. Do not substitute an unverified replica. The scenario's limit of 100 corrections of at most 2 KiB bounds this representation. Verify row size and read costs for the actual deployment. [Bigtable Data API](https://docs.cloud.google.com/bigtable/docs/reference/data/rpc/google.bigtable.v2), [Bigtable routing](https://docs.cloud.google.com/bigtable/docs/routing).

Retain the original and all accepted corrections until at least original event time plus 30 days. Configure no count-based trimming or automatic age-based deletion that could remove them early. A cleanup process waits until a trusted clock's earliest possible current time exceeds that deadline, accounting for maximum clock error. It then uses a conditional single-row mutation to atomically change the lifecycle from open to closed at the current revision. A racing correction either commits before that fence and appears in the row or loses its condition and is rejected after rereading. Cleanup can delete retained payloads only after the closed state commits. Keep a durable terminal marker and prevent creation from recreating any expired event identity, including after cleanup. Corrections mutate only an existing open event row. Test concurrent corrections, an ambiguous retry, two same-timestamp events in one bucket, cross-midnight endpoints, and full audit reads immediately before and at the 30-day boundary under maximum clock error. Test delayed correction and retry attempts against the closed marker. Exercise restore or rebuild for each derived path while its authoritative data remains available. [Bigtable garbage collection](https://docs.cloud.google.com/bigtable/docs/garbage-collection), [Bigtable Data API](https://docs.cloud.google.com/bigtable/docs/reference/data/rpc/google.bigtable.v2).

## Rubric

| Criterion | Points | Full credit |
| --- | ---: | --- |
| Access paths and alternatives | 3 | Compares viable models for all four operations using keys, queries, failure behavior and ownership. |
| Guarantees and failure traces | 3 | Preserves the post-acknowledgement revocation boundary, distinguishes revoked denial from unavailable fail-closed, and preserves atomic product changes and rollout compatibility. Defines an atomic correction acceptance contract that binds the payload, input identity and revision to a durable outcome so concurrent writes and retries preserve accepted history without duplication. Proves complete audit and latest results under the stated read contract or reports them unavailable. Retains all required records for 30 days from event time and prevents late writes or retries from recreating expired data during or after cleanup. |
| Cohorts and repair | 2 | Computes 98% and 91% with the stated denominators and deadlines. Defines a reproducible probe that proves the complete ordered result and required revision on the actual browse serving view by 15 seconds. Tests simultaneous corrections, lost replies, cleanup races, audit boundaries and partial traversal. |
| Product evidence and cost | 2 | Gives two scoped verification questions per operation and justifies the operational cost of the proposed split. |

Accept alternative models and fewer stores when their access paths and verified guarantees meet the same requirements.
