# M11-L04 assessment — CDN and global serving

## Six checks

**Q1 (LO1).** Origin gen9 replaces gen8 and purge of `/logo.png` begins. An old gen8 fill arrives after purge processing. Can a cache insert it under a strict current-generation key?

**Answer.** No. Purge alone may not fence already-running fills. Use versioned URLs or an authoritative generation barrier/check at serving, and reject old fills under current gen9. A plain insertion-time TTL does not prove freshness after origin update.

**Q2 (LO1).** Does CloudFront OAC make a private group image authorized for a specific viewer? Does CDN invalidation erase a previously downloaded browser copy?

**Answer.** No. OAC is authentication from the CDN to supported S3 origin, not end-user policy. Invalidation changes future CDN fetch behavior, not bytes already stored by external clients; private content needs an appropriate viewer gate and revocation contract.

**Q3 (LO1).** Is a 304 response proof that the origin object is immutable or that every user has the latest version?

**Answer.** No. A valid conditional response states the selected stored representation still matches the request's validator at that interaction. Another variant, path or client cache may differ. Versioned immutable URLs and explicit source cuts can be stronger reuse evidence.

**Q4 (LO2).** Region A serves 6,000 QPS, B serves 4,000. Tested capacity A=7,000, B=5,000. After A fails, can routing 6,000 more to B keep all 10,000 requests successful?

**Answer.** Not under the tested capacity: B would need 10,000 QPS while sustaining 5,000. Provision warm spare, shed with counted original failures or change the SLA. DNS success alone does not create compute/DB capacity.

**Q5 (LO2).** A committed object gen9 but failed before B received it. B has gen8. May B claim “current gen9” on read merely because it is healthy?

**Answer.** No. Its replication source cut does not prove gen9. It may serve a clearly labeled allowed-stale public value or return an appropriate failure/pending state, or fetch from another authoritative source. A privacy deletion must not be bypassed using a stale permission copy.

**Q6 (LO2).** Does one DNS failover health-check event ensure all clients instantly use B and old writer A cannot write on restart?

**Answer.** No. DNS caching, existing connections and propagation delay matter; write authority must be separately fenced, and RPO/recovery point verified. A route change is not coordinator write fencing.

## EX-1 — Origin update under regional failover

**Scenario.** The CDN serves `/logo.png` gen8, origin A stores gen9 at 12:00 and begins invalidation. B still has gen8 at 12:00:02, when A fails. A normally receives 6,000 QPS with capacity 7,000; B receives 4,000 with capacity 5,000. DNS/traffic router redirects new connections to B, but old CDN cache fills and an old A writer may resume. The product allows a 60-second stale window for public logos, but **does not allow stale private-content authorization after revocation confirmation**.

**Deliverables.** Draw edge cache+origin and global read/write replication paths. Compute required B failover headroom; show one safe gen9 publication or labeled stale-gen8 policy; distinguish public logo TTL versus strict private deletion. Choose active/standby vs active-active placement, with data failover and fencing. Define an original-read client SLO and explicit test plan.

### Reference answer

- An immutable `/logo.v9.png` path plus versioned metadata is simplest for public new bytes; a mutable path needs validation/invalidation with an explicit stale window and delayed-fill guard. A CDN purge does not erase external caches or prove a protected private photo gone.
- B's new offered load `4k+6k=10k QPS` against capacity `5k` is 2× its tested capacity. At least 5k/s additional sustainable B capacity is needed **for this demand**, not counting retries/cache misses; otherwise reject excess and keep them in user SLO denominator. Scale app, database and origin together.
- B can serve gen8 as **labeled stale** to public logo clients within the 60-second budget if correct permissions and source-cut limits allow, but cannot claim gen9. For strict private revocation a final authoritative permission check or fail-closed policy blocks stale B/edge copies.
- A→B write promotion must validate committed recovery point and install a new write epoch/fence, then reconcile unknown client writes. DNS health/TTL controls traffic routing but not writer authority.
- SLI counts all original valid client image requests at edge ingress, deduplicated through retries, correct permitted advertised version at client within 250 ms. Timeouts, wrong/stale beyond allowed bound, rejected and late requests fail. Test old fill after purge, replication lag, 10k load on B and resumed stale A writer.

### Rubric (12 points)

| Area | Points | Full evidence |
| --- | ---: | --- |
| CDN origin/TTL | 3 | Version/purge and old-fill race, origin protection separate from viewer auth |
| Region failover | 4 | 10k demand vs 5k B, warm capacity, source cut and fenced writer |
| Mutability/privacy | 3 | Public stale budget distinct from strict revocation, no false global purge claims |
| Measurement/tests | 2 | Original-operation SLO and targeted interleavings |

Alternative designs may satisfy the problem if they defend the same observable constraints.
