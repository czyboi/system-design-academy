# M11-L01 companion — File sync and collaboration

## Knowledge checks

**Q1 (LO1).** A uploads v8a from base v7 and CAS advances the file head. B also uploaded v8b from v7 before reconnecting. Can B safely claim its update is current without conflict detection?

**Answer.** No. A head CAS from v7 to v8b must fail after v8a is active. Preserve B's immutable v8b, identify common ancestor v7 and return an explicit conflict or merge path; never silently lose one branch.

**Q2 (LO1).** Does a matching weak rolling block checksum alone prove identical content? Does transferring only changed blocks solve concurrent head updates?

**Answer.** No to both. The weak checksum only locates candidates; a stronger verification/final reconstructed file hash is required. Delta transfer optimizes bandwidth, while a separate guarded head update preserves revision correctness.

**Q3 (LO1).** The server committed the new head, but A lost the HTTP response and retries the same upload key. What should happen?

**Answer.** An input-bound durable receipt returns the same result/revision, not a second head or duplicate conflict. If the outcome is unknown, reconcile the canonical receipt before issuing new independently keyed operations.

**Q4 (LO2).** A and B simultaneously insert x and y between A and B in original text `AB`. Why can applying both raw offset-1 inserts in arbitrary arrival order diverge?

**Answer.** Offsets shift as inserts occur. Without transformation or stable element-ID ordering, each replica can apply its local insert first and produce differing `AxyB`/`AyxB`. OT transformations or a defined sequence CRDT rule must determine the same position/order at every replica.

**Q5 (LO2).** Does CRDT eventual convergence imply every collaborative edit preserved author intent or that permission revocation instantly removes offline copies?

**Answer.** No. Convergence is about replicas applying the same compatible operations under the algorithm; semantic intent can still conflict, and already downloaded offline bytes cannot be retracted. Server authorization and client resync policies are separate.

**Q6 (LO2).** A file version contains an arbitrary video; two users change unrelated regions offline. Should a text-sequence CRDT automatically merge the binary file?

**Answer.** Not without a semantic binary merge model. Whole-file immutable revisions, chunk reuse and explicit conflict resolution are the appropriate baseline; text CRDT identifiers and delete operations do not define valid video-file merging.

## EX-1 — Reconnect two editors

**Scenario.** Tenant T has file `/notes.txt` with v7 = `HELLO`. A uploads v8a = `HELLO!` from base v7; B was offline and uploads v8b = `Hi HELLO` from base v7. A's successful response is lost once, and B's upload content arrived before its CAS. In the collaborative editor (different product contract), initial text `AB` receives two concurrent inserts x and y between the characters, identified `(A,1)` and `(B,1)`.

**Deliverables.** Model metadata/manifest and chunk object keys, durable upload/receipt, head CAS and conflict response. Reconstruct safe v9 and show what happens under A retry. Propose a block-delta optimization with correctness verification. Contrast OT transformed offsets and an illustrative sequence CRDT deterministic tie break for x/y, and state one concurrency/permissions limitation of each. Define an original-operation client SLO and two failure tests.

### Reference response

- Head v7→v8a succeeds. v8b is stored but its CAS from 7 fails. A retry obtains the original v8a receipt. With a defensible three-way merge of disjoint edits, commit v9 = `Hi HELLO!`, explicitly retaining parents v8a and v8b and guarding against a head change during merge.
- Manifest binds ordered verified chunks to the complete file hash; a weak rolling checksum can find shifted common blocks but requires strong content verification. A failed activation produces an orphan/pending object, not a visible broken head.
- OT serializes or transforms the two offset-1 inserts; a policy placing x before y yields `AxyB`. A sequence CRDT can independently attach IDs after element A and deterministically sort two concurrent child positions to the same rendered order, with full algorithm rules for deletes/causality left explicit. Neither model implies all human intent is preserved.
- Permissions are checked on synchronization and protected reads; offline already-downloaded bytes remain. Sync conflicts are correct, visible outcomes rather than silent successes.
- All original authorized upload requests are counted once; success is a durable adopted revision or correct durable conflict response within the declared deadline. Test two offline writers with reordered arrival, response loss, chunk/meta crash and opposite collaborative operation delivery.
