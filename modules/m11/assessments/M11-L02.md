# M11-L02 companion — Messaging and media sharing

## Six checks with explanations

**Q1 (LO1).** Ada receives a durable `accepted(seq41,m100)` response while Ben is offline. Can the UI honestly mark “Ben read”?

**Answer.** No. Accepted means the server persisted the room message and durable delivery intent, not that any recipient device received or displayed it. Device delivery acknowledgments and user read receipts are distinct events with separate populations and timing contracts.

**Q2 (LO1).** Ada retries the same `client_message_key` after losing a response. The worker also retries a push to Cara. What prevents duplicate logical messages?

**Answer.** An input-bound sender receipt returns the same `message_id, room_sequence`. Workers and recipients deduplicate the same event ID, while replay may legitimately resend an already-persisted event. Deduplicating notifications does not substitute for stable canonical message identity.

**Q3 (LO1).** Ben syncs from `last_seq=40` after losing group membership. Should the room log simply return seq41 because it exists?

**Answer.** No. The protected sync must enforce the room's history-visibility policy and current/per-message entitlement before release. An offline cursor is not authorization. The product must state whether removed members retain access to earlier events.

**Q4 (LO2).** The image object exists in S3, but the moderation/thumbnail job is not complete. Is publishing `public` metadata immediately safe?

**Answer.** Not under a “verified/policy-ready media” contract. Keep pending private, verify object and required transformations/checks, then publish an authorization-checked metadata revision. Retry must bind to source/media version, not blindly overwrite later policy.

**Q5 (LO2).** Does CloudFront OAC authenticate each end user for a private group photo? Does a 5-minute signed URL automatically support immediate revocation?

**Answer.** No. OAC secures origin access by the distribution, not membership. A bearer signed URL can remain usable until expiry unless there is an additional protected revocation mechanism. Immediate confirmed non-disclosure requires an authoritative read/release gate or a weaker explicitly bounded contract.

**Q6 (LO2).** A photo changes public→private. The object is protected, but a stale feed thumbnail and search snippet still show private details. Is the privacy change complete?

**Answer.** No. Derived views may disclose the protected title/thumbnail/URL. They need generation-aware invalidation or final permission filtering, and the confirmation boundary must cover any promised protected content path.

## EX-1 — Offline group message and public/private media

**Scenario.** At 10:00, Ada, Ben and Cara belong to private group g4. Ben is offline. Ada submits m100 with key k1; server appends room seq41 and loses Ada's response. Cara's phone acknowledges delivery; Ben reconnects five minutes later with cursor40. At 10:04 Ben's membership is revoked. Ada also uploads p7 privately to g4, publishing the verified source at 11:01, making it public at 11:02 (revision5), and private again at 11:03 (revision6) while an old CDN cache fill is in flight.

**Deliverables.** Draw sender acceptance/room-log/outbox, offline replay, device and read receipts; trace Ben's protected sync after revocation. Draw photo pending→checked→visibility version and object/CDN paths, choose a strict or bounded revocation policy, and explain late fill and feed/snippet leaks. Quantify illustrative text and photo raw daily bytes and define two original-operation SLIs with denominators. Give three falsifying race/fault tests.

### Reference solution

- Commit `(room g4, seq41, m100, sender key k1, outbox)` durably. Retry k1 returns seq41, not a new event. Cara's device ack proves only delivery to that device. Ben sync after 10:04 must satisfy g4's history-visibility rule; in a strict revocation policy it is denied despite message retention. A read receipt is a separate user-view event.
- Photo p7 starts pending private. Verify object/version and required moderation/derivatives before publishing metadata, then use revision5 for public. Revision6 is authoritative private; a late revision5 worker/cache fill must not override it. Public CDN direct URLs must be purged within the documented grace, or eliminated/gated for a strict acknowledgment contract.
- Raw text ≈3m × 300 B = 900 MB decimal ≈858 MiB/day. Photos ≈20k × 2MiB = 39,062.5 MiB≈38.1GiB/day (≈39GiB rounded). Separate metadata, copies, CDN traffic, derivatives and retention.
- Sender SLI counts *original valid send requests*, deduplicated by client key, receiving durable accepted receipt before 500 ms; rejections, errors, timeouts and late replies fail. A separate photo-read SLI counts original authorized reads and correct permitted data within a specified bound; wrong private access is failure even if fast. Run crash-after-log-before-outbox (if no atomic intent), duplicate delivery, Ben reconnect after revocation, pending moderation timeout, late CDN fill after revision6 and snippet leakage.

| Dimension | Points | Required reasoning |

| Message states and replay | 4 | Accepted vs delivered vs read, stable seq/key, durable outbox and Ben's protected replay |
| Media lifecycle and access | 4 | Pending/verify/revisions, public/private/CDN gate, no late stale fill or snippet disclosure |
| Capacity and measurements | 2 | Correct raw bytes and distinct original-operation SLI denominators |
