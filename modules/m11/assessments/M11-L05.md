# M11-L05 assessment — Unique-ID service

## Six explained checks

**Q1 (LO1).** In the toy layout `[42ms][8worker][2seq]`, how many unique tuples may one exclusive worker emit for a single millisecond bucket? What if it emits a fifth?

**Answer.** Four, sequence 0 through 3. The fifth must wait for a proven new bucket/namespace or fail with explicit capacity; wrapping to 0 in the same bucket/slot duplicates an existing tuple.

**Q2 (LO1).** Worker 3 emitted `(5000,3,0)`. Another process restarts as worker 3 at bucket 5000, seq0. Can a coordinator lease expiry alone prove this safe?

**Answer.** No. The old process or an in-flight ID may remain active. Use nonoverlapping namespace generations/persisted watermark with a safe exclusive slot plan, or an authoritative resource-side fence/unique insert before external acceptance. A lease doesn't erase already generated values.

**Q3 (LO1).** Why is a random UUIDv4 not a mathematical proof of zero collisions? How can accepted-record uniqueness still be guaranteed?

**Answer.** It samples a finite random namespace; collision has nonzero probability (UUIDv4 normally has 122 random bits). Enforce a unique acceptance constraint and retry new randomness on collision for the same logical operation.

**Q4 (LO2).** Are UUIDv7 or Snowflake-like IDs guaranteed to represent a global transaction commit order?

**Answer.** No. Their time/worker fields give time-based sort tendencies or local monotonicity under stated algorithms, but different clocks, stalls and uncommitted operations can break correspondence to a linearized commit sequence. Use a transaction/consensus sequence when that property is required.

**Q5 (LO2).** A central allocator reserves IDs 1000–1999 to A. A crashes after 1002; should another worker immediately reuse 1003–1999 to avoid gaps?

**Answer.** Not unless an authoritative protocol proves old issuer cannot still publish and the range is safe. Gaps are allowed in this exercise; never recycling an uncertain range is a simpler uniqueness policy than unsafe reuse.

**Q6 (LO2).** The allocator generated an ID and committed a receipt, but HTTP response was lost. Client retries with the same key. Is allocating a second new ID correct?

**Answer.** No. Return the durable input-bound ID receipt. Atomic counter increments alone are not idempotent; retries without identity can consume extra IDs or create duplicate resources.

## EX-1 — Slot overlap, rollback and ID reservation

**Scenario.** Workers A and B hold slots 3 and 4 in a toy 42/8/2 layout. At bucket 5000, A emits seq0,1,2,3. Its next request arrives before the clock advances, and then its clock moves backward to 4999. A crashes; process A2 is incorrectly assigned slot3 and resumes at bucket5000 seq0. Separately a client request `k7` loses an HTTP response after a durable reservation. The application requires unique accepted resource IDs for ten years, a sortable format if cheap, and original request success within 100 ms.

**Deliverables.** Compute sequence capacity and tuple collision, show correct overflow/rollback/restart policies. Compare secure random IDs with unique acceptance, range leasing and timestamp/slot/sequence. Explain whether UUIDv7 solves global order and when to require a transactional assignment/receipt. Define an original-operation SLO and three fault tests.

### Reference solution

- A owns exactly four tuples `(5000,3,0..3)`. Fifth in same bucket must wait until an advanced bucket or reject. If local time regresses, preserve durable last-used logical bucket/sequence and refuse to reuse prior tuple; do not blindly reset on process restart.
- A2 at `(5000,3,0)` collides with a previously generated value. Prevent reuse through durable slot identity/epoch+watermark and no overlap with stale issuer, or enforce resource-side unique acceptance/fencing. A coordinator lease by itself does not stop A from outputting bytes after expiry.
- Worker B `(5000,4,0)` is distinct. A central reserved range can waste unused IDs but maintain uniqueness if never reissued while old client could publish; random IDs need collision guard and can have no order guarantee. UUIDv7 sorts by embedded timestamp under algorithm's clock assumptions, not commit order or secrecy.
- The original `k7` request returns the same persisted ID on retry. Count all original valid requests in the SLO; correct accepted IDs with on-time client receipt are successes, collisions rejected safely but late responses still reduce availability. Measure no duplicate **accepted** ID independently.
- Tests: two generators assigned slot3, clock rollback 5000→4999, sequence wrap, response loss and uncertain range reallocation.
