# M11-L08 assessment — Memory reclamation

## Knowledge checks

**Q1 (LO1).** A rooted A points to B, while X points to Y and Y points back to X. There is no path from a root to X or Y. Which can tracing GC reclaim and why?

**Answer.** X and Y are unreachable even though both have incoming edges. Tracing GC can reclaim both; a naive reference-counter that only uses nonzero incoming counts cannot identify this cycle.

**Q2 (LO1).** Trace the lesson graph R1→A, A→B,D, B→C,E; X→Y, Y→X,Z. Name the marked and reclaimed sets.

**Answer.** Marked = {A,B,C,D,E}; reclaimed = {X,Y,Z}, assuming the declared only-root and strong-reference model. Traversal order does not change reachability.

**Q3 (LO1).** Why does mark-sweep not automatically guarantee a compact heap after collection?

**Answer.** Sweep makes unreachable allocations reusable, potentially leaving holes. Physical compaction requires moving objects or another allocator mechanism plus safe pointer updates; it is not inherent to mark-sweep.

**Q4 (LO2).** With a mutator running during marking, a live white N is moved from an unscanned B to an already scanned A. What is wrong with a concurrent collector that does nothing on reference writes?

**Answer.** N might no longer be reachable through the unscanned edge when B is traced, while A was already scanned, so N could be wrongly reclaimed. An appropriate write barrier and marking invariant (e.g. incremental update or SATB under its own rules) is necessary.

**Q5 (LO2).** Two services allocate equally with 4 GiB heaps; one has a 0.5 GiB live set and the other 3.2 GiB. Can you infer exact pause times or guarantee less GC CPU for the former?

**Answer.** No. Live-set size affects trace work and headroom, but edge topology, allocator, sweeps, concurrent phases, hardware and collector settings also matter. Measure rather than assert a pause duration or ratio.

**Q6 (LO2).** An in-process cache holds 2 GiB of reachable entries the business no longer needs. Will switching to a concurrent tracing collector reclaim them?

**Answer.** No. Strongly reachable cache entries remain live; the application must implement an expiry/size eviction policy and remove references. GC reclaimability and cache policy are different responsibilities.

## EX-1 — Collector design under two live sets

**Scenario.** A synthetic service has a 4 GiB heap and a 100 ms response deadline. Its object graph is R1→A→B→C, A→D, B→E and a disconnected cycle X→Y→X with Y→Z. The mutator concurrently moves the only reference to a white object N from an unscanned node to an already scanned black node. The service is evaluated under two live-set sizes (0.5 and 3.2 GiB) at the same allocation rate. In five minutes 9,600 of 10,000 original valid requests complete correctly under 100 ms, 150 time out, 100 are shed and 150 complete late.

**Task.** Show root traversal and sweep; explain cycle collection and fragmentation; trace why the concurrent mutation requires an invariant/barrier; compare a simple STW collector with a bounded concurrent marker, including headroom, CPU and latency trade-offs. Give a test plan and define a client-outcome metric rather than only GC pause statistics.

### Reference solution

- Start mark at R1; visit A, B, C, D, E through strong reference edges. Sweep X, Y, Z, including the X–Y cycle, because no root path reaches it. A sweep-only allocator can have holes.
- During concurrent marking, without an adequate barrier the path to N can shift behind the marking frontier, causing false reclamation. A correct algorithm chooses a snapshot/incremental invariant and records relevant mutations; exact barrier requirements are collector-dependent, not one universal recipe.
- STW avoids mutator-mark race but suspends requests. Concurrent mark trades barrier and CPU overhead, possible conservative retention, and residual pauses for lower marking-pause pressure. The larger 3.2 GiB live set generally leaves less free space, but figures alone do not determine exact pause cost.
- Valid original request timely success = 9,600/10,000 = 96%, retaining rejection, timeout and late work in denominator. A benchmark must log end-to-end p99, GC phases, live occupancy, CPU and allocation under comparable loads. Test unreachable cycles, graph mutation during mark, retained reachable cache, and high-occupancy fallback.
