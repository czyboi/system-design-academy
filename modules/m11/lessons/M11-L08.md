# Reachability, tracing garbage collection, and memory pressure

A service keeps running but its heap grows and pauses become unpredictable. The team blames two objects that reference one another: “they still have references, so they can never be released.” That diagnosis is correct for a naive reference-count-only collector, but false for a **tracing** collector. The design question is what is *reachable from roots*, how an object graph is traversed safely, and how the cost of reclaiming garbage changes latency and available memory.

- **M11-L08-LO1:** trace roots, mark, sweep and collection of an unreachable reference cycle on an explicit object graph.
- **M11-L08-LO2:** choose tracing, reference counting and bounded concurrent collection under pause, live-set, headroom and mutation constraints.

## What makes an object live?

A root is a reference that the runtime treats as externally reachable for a collection—for example an active stack local or a relevant static field. The exact root set and reachability classes depend on the runtime; this lesson uses **strong references only**. A heap object is *reachable* if a directed path from a root reaches it. It is not enough for an object to have an incoming edge from another unreachable heap object.

Consider this original graph at a collection safepoint:

```text
Roots: R1 -> A -> B -> C
              |    |
              v    v
              D    E

Unrooted region: X -> Y -> X
                       |
                       v
                       Z
```

For precision, `A -> B`, `B -> C`, `A -> D` and `B -> E` are the reachable edges. The separate region has `X -> Y`, `Y -> X`, `Y -> Z`. Only R1 is a root. Assume no other hidden or native references. The reachable set is **{A, B, C, D, E}**. X and Y each have a nonzero incoming reference count, but neither is reachable from R1. Z is also unreachable despite its incoming reference from Y.

This is why a tracing collector can reclaim cycles that simple reference counting cannot: reachability is a graph property relative to roots, not the mere existence of an incoming reference.

## Mark and sweep step by step

A simple **stop-the-world mark-sweep** collector briefly prevents application threads from mutating the graph. It starts from runtime roots and traverses strong references, marking each visited object only once. An explicit worklist avoids infinite loops on cycles:

```text
worklist = all root targets
while worklist not empty:
    obj = pop(worklist)
    if not obj.marked:
        obj.marked = true
        push all strong children of obj
for each allocated object:
    if obj.marked: obj.marked = false
    else: reclaim obj's storage
```

For the graph above, the worklist visits A then B,D and then C,E, in some order. It marks A–E. X–Z are never reached and are reclaimed in sweep, even though X and Y point to each other. This pseudocode models *one conceptual collection*, not a production memory allocator or a Java GC implementation.

The mark phase costs roughly O(reachable objects + traversed reference edges); a plain whole-heap sweep examines allocated heap slots or allocation metadata. A free-list allocator must make reclaimed memory reusable; mark-sweep does not inherently compact objects, so fragmentation may remain. A moving/compacting collector can address fragmentation but must safely update pointers, with further work and pause implications.

### A mutation can defeat a naive concurrent mark

Suppose an application thread continues running as the collector marks. The collector has already scanned a black object A and has not yet scanned a white object N. A mutator moves the **only** path to N from an unscanned B into an already scanned A, then removes B's edge. Without synchronization or a remembered mutation, N may never be traced although it is reachable at the end of marking.

That is the key reason production concurrent marking cannot be implemented by simply “turning off the pause.” A concurrent collector needs a *marking invariant* and a barrier/remembered-state mechanism to account for mutations. An incremental-update barrier may record a newly created reference from an already-scanned object; a snapshot-at-the-beginning (SATB) approach may preserve deleted references that belonged to the initial logical snapshot. These are **different invariants**, not interchangeable barriers.

Oracle's Java 25 G1 documentation states that its concurrent marking uses SATB and may conservatively retain objects that became unreachable during marking until a later cycle. It also has pause phases; “concurrent” does **not** mean no pauses. [Oracle JDK 25 G1: Marking](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html). OpenJ9 documents concurrent mark and write-barrier/card-table work, illustrating another implementation, not a universal Java requirement [OpenJ9 GC overview](https://eclipse.dev/openj9/docs/gc_overview/).

## Pause time is not proportional to allocated heap alone

The **live set** is the amount of reachable data a collector must preserve. Compare two synthetic instances with a 4 GiB heap and identical allocation rate:

| Scenario | Reachable live data | Dead space before collection | Consequence |
| --- | ---: | ---: | --- |
| A | 0.5 GiB | 3.5 GiB | More reclaimable space; generally less reachable graph to trace |
| B | 3.2 GiB | 0.8 GiB | More references to trace; less room for bursts, promotion or copying |

One cannot derive an actual pause duration solely from these two numbers. Edge count, object shape, fragmentation, collection algorithm, parallelism, remembered sets, available CPU, NUMA and runtime settings also matter. With a copying collector, sufficient free/evacuation space is an additional constraint. With a mark-sweep collector, sweeping allocation metadata can remain costly even when the live set is small. A 4 GiB configured heap with 3.2 GiB live is not equivalent to 3.2 GiB of guaranteed contiguous free space.

Stop-the-world collection simplifies graph consistency by preventing mutation while tracing/sweeping, but makes users wait for collection work. Concurrent collection reduces some long pauses by sharing the work with application threads at the cost of CPU, barriers, coordination and possibly extra retained memory. If the collector cannot keep up with allocation, it may require more aggressive or fallback work, depending on the runtime. Oracle documents G1 evacuation failures and concurrent phases as product-specific examples [G1 documentation](https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html).

## Retained is not necessarily leaked; unreachable is not evicted

A map intentionally holding all recent sessions may be fully reachable and consume most of the heap. A garbage collector **must not** reclaim those sessions until the application removes their strong references, even if operators describe the growth as a “memory leak.” That is an *application retention policy* defect, not failed cycle detection.

Conversely, a cache with a memory budget can explicitly evict a *reachable but replaceable* entry; eviction is an application decision that can invalidate references or remove ownership, not tracing collection itself. An expired key in an external key-value service is governed by that service's expiry/eviction contract (M11-L09), not by this process's root graph. Distinguish object finalization, external resource cleanup and memory reclamation: collecting an object does not by itself prove a remote lock, file or database transaction was safely released.

## Choosing a collector under latency and memory pressure

Suppose an interactive service has a 100 ms response deadline, but observed end-to-end latency sometimes spikes. Define a five-minute SLI over **all 10,000 valid original requests**: 9,600 finish with the correct response under 100 ms, 150 time out, 100 are rejected under memory-pressure shedding and 150 finish late. On-time user success is **9,600/10,000 = 96%**. A lower GC pause percentile alone does not prove user success if CPU competition, queuing or shedding grows. These figures are synthetic.

Choose a simple stop-the-world tracing design when pauses are within the real deadline and throughput/cost simplicity matters. Consider concurrent marking if measurement shows marking pauses dominate deadlines at the observed live-set sizes and CPU/headroom can afford barrier and concurrent work. Track allocation rate, post-GC occupancy, live set, time-to-reclaim, GC pause distribution, CPU share, fragmentation and **the original-operation SLI**. Establish the failure hypothesis first; do not migrate collectors because “concurrent” sounds faster.

Reproduce the A–E, X–Z graph and verify the cycle is reclaimed. While a mark is in progress, mutate references across scanned/unscanned objects and test the collector's declared invariant. Grow the reachable map without changing allocation rate; verify that GC does not reclaim objects still rooted. Finally use controlled load to see whether a smaller measured pause helps or merely transfers cost to CPU and missed service deadlines.

The central principle: trace from roots to decide *what may be reclaimed*, then choose a collection/concurrency policy based on what the service can afford to pause, retain and recompute.
