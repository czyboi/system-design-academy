# Unique-ID service

Two workers generate numeric IDs at high speed. Both return `ID=128034` after a restart: the second worker inherited the same worker identity and started its local sequence counter at zero while the logical clock was still in the old timestamp bucket. Generating *fast* IDs was easy; proving a **non-reused namespace across failures** was the real requirement.

- **M11-L05-LO1:** trace random, coordinated-range and timestamp/worker/sequence ID generation, including collision, counter rollover and clock rollback.
- **M11-L05-LO2:** choose namespace allocation, coordination, durable state and failure policy based on uniqueness, sortability, secrecy, load and recovery constraints.

## Do not combine three different promises

**Uniqueness:** no two accepted logical resources are assigned the same ID in the specified namespace and retention horizon. A random string offers a *probabilistic collision bound* unless a unique insert/collision check enforces actual accepted-record uniqueness. **Order:** an ID may sort approximately by creation time, monotonically within one process, or correspond to a linearized commit history. These are **different** properties. **Unguessability:** an outsider cannot feasibly enumerate valid identifiers; timestamps, counters and Base62 representations do not provide this property automatically.

For this original exercise, a multi-region service receives 200,000 original ID requests/second at peak across 16 generators. IDs are unique within one application namespace for ten years; time order is helpful for indexing but no caller may use the ID to prove a database transaction committed before another. A private resource needs separate authorization, even if its ID is random.

The API is `POST /id-reservations` with a caller-scoped idempotency key and declared resource input. A retry after an unknown reply must return the **same accepted ID**, not consume and publish a new ID each time. Gaps in a sequential allocation are acceptable under this design; duplicates are not. Do not equate an allocation call returned by a volatile process with an externally committed business resource unless the caller's contract explicitly says so.

## Random identifiers and bounded collision risk

A cryptographically secure random generator can sample a 128-bit UUIDv4 or another appropriately sized namespace. RFC 9562 standardizes UUID formats and entropy properties, including v4 and time-based v7. A UUIDv4 has version/variant fixed bits and **122 random bits** in its normal layout, not 128 independent random bits. For (n) random draws from a space of (N) equiprobable candidates with (n) well below the square-root scale, the birthday approximation is:

The approximation is not a *guarantee of zero collisions*. Handle an observed collision using a unique constraint or a source-defined namespace reservation and retry with fresh randomness for the **same original operation**. Check selected ID and input binding in one transactional acceptance boundary. Random ID data may be sortable only by creation metadata, not by ID.

UUIDv7 includes a millisecond Unix timestamp in its most significant bits, with random and optionally monotonic counter fields. It can improve locality/sortability, but a timestamp visible in the ID leaks approximate creation time and does **not** establish a universal causal/commit order across unsynchronized writers. RFC 9562 discusses handling counter rollover and clock rollback, and its stated monotonicity methods carry algorithm-specific constraints. [RFC 9562 §§5.4, 5.7, 6.2–6.4](https://www.rfc-editor.org/rfc/rfc9562.html).

For externally exposed URLs needing confidentiality, do not use a sequential Snowflake ID as the bearer security control. Use authorized lookup and, when link secrecy is genuinely required, a separately generated sufficiently entropic capability with expiry/revocation. URI encoding only changes characters; it adds no entropy. See [M10-L01](../../m10/lessons/M10-L01.md).

## Coordinated counters and range leasing

A single durable atomic allocator can reserve `next_id`, returning a unique number after a committed increment. This centralizes one contention point, but a **range lease** amortizes coordination: under a guarded atomic operation, give worker A IDs 1000–1999 and worker B 2000–2999. Each worker can then allocate locally inside its nonoverlapping range. If A crashes after issuing 1002, unused IDs 1003–1999 may remain permanently skipped; gaps are fine if the product wants uniqueness rather than a gapless accounting sequence.

A range allocator must never **reissue an uncertain reserved range** to another worker simply because it stopped receiving heartbeats. If A might still publish an ID from 1003, assigning that same range to B can cause duplicates. To reclaim safely, either fence all old issuers at a mandatory authoritative acceptance gateway before reassigning, use durable proof that the entire range was not used and can no longer be used, or never recycle ranges within the uniqueness horizon. “Lease expired” at the coordinator does not cancel bytes already produced by A.

An allocator that increments on every request but loses the reply raises another problem: if the client retries as a *new* operation, it receives a new value despite the first value possibly being assigned. A durable idempotency receipt mapping caller key/input to accepted ID solves the API contract, independent from allocation gaps. AWS DynamoDB documents atomic counters as **not idempotent** for blind retries; that example motivates the receipt distinction, without forcing DynamoDB as the selected backend. [DynamoDB atomic counters](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/WorkingWithItems.html).

## Timestamp / worker / sequence layout

A “Snowflake-like” ID is a composite of a timestamp bucket, a worker identifier and a local sequence. Historical Twitter Snowflake is a relevant architecture pattern, but its archived 2010 implementation and exact bit layout are **not current Twitter service guarantees**. [twitter-archive/snowflake](https://github.com/twitter-archive/snowflake).

Build a **toy** 52-bit logical ID for teaching:

```text
[42-bit nonnegative millisecond bucket][8-bit worker slot][2-bit sequence]
```

This encoding permits 256 worker slots and **four** sequence values (0–3) per worker per time bucket. It can allocate at most 4 per millisecond *per slot*, provided the worker slot is exclusive and time advances as required; theoretical maximum 256×4×1000 = **1,024,000 IDs/sec** across all slots ignores networking, durability, process overhead and contention. The toy is not a real production capacity plan. Its limited counter is chosen so overflow can be traced.

The generated value is `(bucket << 10) | (worker_slot << 2) | sequence`. For worker 3 at bucket 5000, sequences 0–3 yield four distinct integers; worker 4 at the same bucket uses a different slot and cannot collide if both slot allocations are valid. The **full tuple** `(bucket,worker,sequence)` is the uniqueness identity. Never overflow sequence from 3 back to 0 while the bucket and worker remain unchanged.

## Trace two workers, overflow, rollback and reuse

| Event | A: slot 3 | B: slot 4 | Safe behavior |
| --- | --- | --- | --- |
| Bucket 5000 begins | Emits `(5000,3,0)`, then 1,2,3 | Emits `(5000,4,0)` | Distinct slots prevent collision |
| A asks for fifth ID in bucket 5000 | Sequence space exhausted | — | Wait for bucket advancement with a bound, use a new proven disjoint namespace or return capacity error; **do not wrap** |
| A's clock reports 4999 | Last emitted bucket remains 5000 | — | Detect rollback; reject/wait or use a durable logical-clock policy that cannot reuse old tuples |
| A crashes and another process starts as slot 3 at bucket 5000 with seq0 | Old A may still be alive or IDs remain accepted | B remains on 4 | New process must not blindly restart at seq0; retain durable watermark / unique new generation, or deny activation |
| A's old request arrives after replacement | Potential old tuple in flight | — | Authoritative resource accepts only unconsumed, correctly fenced identity under the chosen protocol |

A slot-assignment **lease alone is not sufficient** when old process A can continue minting bytes after the coordinator considers it dead. If every ID must be valid independently of a central service, use a namespace plan where slot IDs/epochs cannot overlap across old and new generators for the entire time horizon; persist last bucket/sequence and do not reuse the slot while an old issuer can still be active. Alternatively require a central acceptance boundary that **fences the old generation and enforces uniqueness before an ID becomes an accepted external resource**. These choices trade latency and offline generation for stronger global proof. [M09-L03](../../m09/lessons/M09-L03.md) explains fencing at the protected resource.

A timestamp's `5000→4999` rollback can happen due to wall-clock correction, VM migration or bad time source. Holding the last logical timestamp and increasing sequence may be safe within a bounded, persisted scheme, but its clock will not reflect actual wall time until caught up. Simply “sleep one millisecond” without proving the clock advanced **past the last used bucket** can repeat the same ID. On restart, an in-memory last timestamp is not durable evidence. A monotonically assigned worker generation may require extra bits and changes the layout; make that engineering cost explicit rather than inventing a free guarantee.

## Failure and throughput criteria before product selection

| Constraint | Option | Benefit | Failure / cost |
| --- | --- | --- | --- |
| No dependency on time or worker coordination, collision guard allowed | Secure random ID + atomic unique insert | Simplicity and distributed generation | Random-space collision/retry, no chronological sort |
| Need sortable IDs with standards ecosystem | Carefully implemented UUIDv7 | Approximate chronological locality | Clock/counter treatment, timestamp leakage, no causal order |
| Large numeric monotonically allocated IDs | Durable central counter + never-reused ranges | Simple global disjointness, easy auditing | Allocator availability, range waste, hotspot |
| Need very compact time/worker/sequence IDs | Correctly fenced generator slots and durable watermark | Local high-rate generation under assumptions | Rollback, slot lease reuse, generation fencing and restart |
| Need strict cross-service commit sequence | Database/consensus-backed committed sequence | Observable order under the chosen transaction contract | Coordination latency; ID alone doesn't substitute for write receipt |

For the synthetic API, define a user-visible SLO: at least 99.9% of **all original valid ID reservation requests** arriving in each five-minute cohort must receive the same correct durably accepted ID on retry (or an explicit correct input-conflict result) at the managed client within 100ms. Track no duplicate **accepted** IDs as a separate safety invariant. A request that times out, is rejected for no available slot, or returns an unconfirmed ID is a failure of availability, even if the allocator's successful IDs look monotone. A system that returns errors on every request does not pass.

Falsify uniqueness by simultaneously assigning slot 3 to two workers, restarting with last bucket 5000, rolling the clock back to 4999, exhausting a two-bit sequence, reusing an uncertain reserved range and replaying a client original request after a lost response. Check **persisted accepted ID records and writer generations**, not just samples from an in-memory ID generator.
