# Distributed API rate limiter

An API promises a tenant no more than three admitted expensive requests in any rolling six-second interval. Two gateways each keep an independent counter and each admits three requests: the tenant gets **six**, even though both counters look correct locally. The problem is not which algorithm has the fastest counter. It is where the global **admission decision is serialized**, what time interval the product actually means, and what to do if that authority is unreachable.

- **M11-L06-LO1:** trace fixed/sliding-window counters, token and leaky buckets through the same burst, including state, decision and departure time.
- **M11-L06-LO2:** choose a distributed quota scope, atomicity and partition-failure policy, defending fairness, burst behavior, cost and original-operation outcomes.

## Define the protected operation and the quota

In this original exercise a tenant is assigned a rate budget, and the API's limiting key is `(tenant_id, operation_class, policy_revision)`. Authenticate before deriving tenant identity; trusting a client-supplied tenant header permits bypass. Keep distinct service, user, endpoint and IP limits if the product needs them; do not let an IP-level limit masquerade as a tenant's global quota.

A limiter can count **request attempts**, **accepted original operations**, or **concurrently running work**. Those contracts are different. Here the policy budgets **new original work admitted**, with one stable original-operation ID across retries. An accepted retry cannot consume another quota slot while its original admission is still valid: the rate-limit decision and an input-bound operation receipt must be coordinated at the relevant acceptance boundary. Rejecting an original before any durable work is admitted is safe; a timeout after admission leaves an **unknown** outcome and requires receipt reconciliation, not a new-ID retry.

Assume all timestamps below come from one trusted limiter clock for the example. In deployment, client clocks are untrusted; distributed gateways need a shared authoritative time source or bounded clock-error policy. A completed 429 response indicates a rate-limit refusal but is **not** the same as an admitted expensive operation that later fails. RFC 6585 §4 defines 429 and permits a `Retry-After` field, but deliberately does not specify the counting algorithm. [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4).

## Trace four algorithms on one original burst

To make the mechanisms comparable, the **same five distinct original requests** arrive at `t=0.0, 0.1, 0.2, 0.3, 2.0` seconds. Each algorithm starts empty or full as declared:

- Fixed window: limit **3 admissions** in fixed buckets `[0,6), [6,12)`.
- Exact sliding-window log: limit **3 admissions in (t−6,t]**; records accepted-event times, not every denied retry.
- Token bucket: capacity **3 tokens initially full**, refill at **1 token per 2 seconds**, cost 1 token per admitted original.
- Leaky-bucket shaper: **three waiting slots**, initially empty, **one job departs every 2 seconds** after `t=2`; a request is *queued* if a slot is free, not immediately executed. A separate leaky-bucket **policer** can instead reject arrivals above its rate; do not confuse shaping with policing.

| Original arrival | Fixed window | Exact sliding | Token bucket | Leaky queue (three slots) |
| --- | --- | --- | --- | --- |
| t=0.0, r1 | admit (1/3) | admit (1/3) | admit, tokens 3→2 | enqueue r1, first departure t=2 |
| t=0.1, r2 | admit (2/3) | admit (2/3) | admit, ~2.05→1.05 | enqueue r2, depart t=4 |
| t=0.2, r3 | admit (3/3) | admit (3/3) | admit, ~1.10→0.10 | enqueue r3, depart t=6 |
| t=0.3, r4 | reject | reject | reject (~0.15 tokens) | reject: three slots occupied |
| t=2.0, r5 | reject | reject | **admit**: refill reaches one token | r1 departs at t=2; enqueue r5, depart t=8 |

The token-state numbers are rounded for exposition; a real implementation computes state atomically with a consistent high-resolution time. The leaky queue's r5 acceptance at t=2 assumes the departure is processed **before** the same-time arrival. If the application reverses that tie-break, r5 could reject; ordering must be part of the contract. Shaping means r3 is accepted into the queue at 0.2 but cannot claim *completed at 0.2*. If the client deadline is 5 seconds from first ingress, r3's scheduled t=6 departure is already too late—buffering is not automatically user-visible success.

For fixed and sliding counters, each new original admission is immediate in this model; business work can separately fail. For token buckets, the refill governs *average admitted rate* with a bounded burst but does not cap in-flight concurrent work; add a semaphore/concurrency limit if that is the scarce resource. The leaky queue enforces a smooth processing rate at the price of wait time and buffer overflow. [Redis rate limiter algorithm comparison](https://redis.io/learn/howtos/ratelimiting/).

## Expose the fixed-window boundary burst

A fixed window with quota 3 per six-second bucket may admit `a1,a2,a3` at `t=5.80,5.90,5.99`, then `b1,b2,b3` at `t=6.00,6.10,6.20`. All six fall in a rolling interval shorter than one second, yet each fixed bucket contains only three. A literal guarantee of **no more than 3 in any rolling six seconds** is violated.

An exact sliding log checks accepted timestamps in `(t−6,t]`. Having admitted three requests at 5.80–5.99, it must reject the next three until entries leave the rolling interval. A sliding **counter approximation** can blend counts from two adjacent buckets and save memory but does not prove exact no-boundary-burst behavior. Choose it only if an explicitly bounded approximation error is acceptable.

Exact sliding logs need O(number of accepted events still in the window) per identity for storage plus efficient pruning. Redis describes sorted-set/window approaches; implement prune-count-conditional-add as **one atomic decision**, not separate non-transactional RPCs. Retaining every denied attempt in the admission count is a different policy and can self-DoS the client. [Redis rate limiting](https://redis.io/docs/latest/develop/use-cases/rate-limiter/).

## Local counters cannot enforce a global per-tenant invariant

Suppose gateway G1 and G2 each have a local fixed-window counter of 3. A tenant directs three distinct originals to each during the same six seconds. Both gateways return “allowed,” resulting in **six** admitted originals. A sticky load balancer is not a correctness proof: connection migration, failover, multiple devices and regional routing can break affinity.

Three credible distributed implementations:

1. **Authoritative per-key decision service:** route all a tenant's quota checks to a *serializing* owner or a shared atomic data store. One decision must atomically read eligibility, charge the quota, and record a stable admission receipt. Redis Lua scripting can make read/modify/write operations atomic *within one Redis execution context*; a Redis cluster's cross-slot distributed transactions are not thereby magically atomic. Map related quota and receipt keys into the same supported atomicity domain or use a transactional store with the required semantics.
2. **Quota leasing / escrow:** a central authority allocates disjoint batches of quota units to gateways. For a policy like **100 admissions per minute globally**, it may give 40 to G1 and 40 to G2, reserving 20 centrally for rebalancing. If G1 disappears after issuing 10 of its 40, do **not** reissue the remaining 30 merely because the gateway disappeared unless an authoritative fence proves G1 cannot still admit them. A partially utilized grant reduces short-term availability; reuse without fencing can violate the global cap. This is a quota/epoch problem resembling ID range leasing in [M11-L05](M11-L05.md), but unlike ID allocation, fairness across continuously refilling windows and burst timing also matter.
3. **Approximate local caps:** deliberately partition an allowed error budget across gateways and reconcile usage periodically. This can reduce sync latency, but do not advertise exact rolling global fairness. A gateway outage or uneven traffic can leave assigned capacity stranded while another gateway rejects an entitled client. Specify maximum allowed overshoot and clock skew.

Envoy documents a global rate-limit service and per-route descriptors, useful for multi-proxy configurations; its filter can return 429 for over-limit decisions. Whether a failed rate-limit service request fails open or closed is an **explicit configuration/policy**, not an inherent property of all gateways. [Envoy global rate limiting](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/other_features/global_rate_limiting.html), [HTTP rate-limit filter](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/rate_limit_filter.html).

## Make the decision and runnable work coherent

A naive gateway calls the counter, receives `allow`, and crashes before persisting the accepted operation. The quota was consumed without useful work; that can be tolerable if explicitly charged as an admission attempt, but the API must not lie that a business operation completed. A more serious failure occurs if it acknowledges a durable accepted expensive request **before** making it runnable: the retry sees “already accepted” while no worker can ever find the operation.

One reliable business-command design uses `(tenant, original_id, input_fingerprint)` as a stable receipt, atomically links quota admission with durable operation intent inside a **common transactional domain** where feasible, then dispatches asynchronously:

```text
Gateway -> Authenticate and canonicalize original_id
  -> quota+operation authority:
        if same admitted key and same input -> return existing receipt (no extra charge)
        if key reused with changed input -> reject conflict
        else check policy window/bucket; atomically charge + persist runnable intent
  -> worker consumes stable operation_id, deduplicates effect
  -> client sees accepted, or reconciles unknown reply using original_id
```

When quota state and business outbox live in separate systems, there is **no general atomic transaction** across them. Either design an explicit compensating/reconciliation protocol with known failure windows, move protected acceptance into one authority, or define “quota is advisory admission” rather than claiming exactly-once business execution. A Redis limiter script by itself cannot guarantee a PostgreSQL order table and SQS enqueue are atomic. This is the distinction from algorithm-only rate limiter tutorials.

Clock leaps and retry identity changes can also create unfair decisions. On a monotonic clock policy, store the limiter's last effective time and disallow negative refill when physical time moves backwards; multi-node migrations need a trusted time/epoch source. On an original replay, deduplicate the receipt *before* charging another token. Do not incorrectly treat an expired idempotency receipt as proof an earlier command is terminal if its effect can still arrive.

## Choose a partition-failure policy deliberately

At 12:00 the shared quota authority becomes unreachable, but the API receives new requests:

- **Fail closed:** reject or return an explicit dependency error before admitting protected work. Preserves the strict global cap, but decreases availability. Useful when the quota enforces a hard financial, abuse or safety boundary. Rejects stay in the user-visible success denominator.
- **Fail open:** admit without authoritative counting (possibly under a local emergency bound). Improves availability but **violates the exact global cap**, which must be acknowledged as an explicit degraded mode. Useful only when uncontrolled extra work is safe and abuse risk is priced.
- **Bounded preleased quota:** gateway spends already fenced, exclusive local grants and rejects when exhausted. Preserves a defined global cap under the lease protocol, but can strand units at failed gateways and reduce fairness. Replacement must not reuse uncertain grants.

If two availability zones both believe they own the same global quota partition, a network partition can double admission. Electing an owner is not enough: the **resource that accepts operations** must enforce the new epoch or use nonoverlapping grants, just as M09-L03 fences a stale writer. Explain what a client can conclude after a lost response: “not received” is not the same as “not admitted.” A rejected rate-limited request should not be asynchronously applied later unless the API explicitly models that as queued acceptance.

A strict global limiter is not a guarantee of *fair scheduling*: one tenant can use all its own quota at once, and multiple API classes may contend. Decide key dimensions and per-tenant/per-user limits, weighted costs for expensive operations, and whether unused grants can be reassigned safely. Monitor cardinality and memory of per-identity state; unlimited client-supplied keys can exhaust your Redis memory.

## Measure original user outcomes separately from quota compliance

In an illustrative five-minute cohort there are **1,000 original valid expensive-operation requests**. Suppose 760 receive correct durable acceptance within 200ms, 140 receive a policy-appropriate 429, 50 time out, 30 fail, and 20 are accepted late. The *successful accepted-work SLI* is **760/1,000 = 76%**, not 760/780 or a low p95 on the admitted set. A service can respect a quota while intentionally rejecting 140 originals; those are excluded from the acceptance-success numerator even when the 429 is the correct policy action. Separately monitor **decision correctness** (accurate 429 versus allowed) and **quota safety** (no more than specified originals admitted in the rolling window), so honoring limits is not misreported as high user work availability.

If the product explicitly promises **timely rate-limit decisions** rather than accepted business work, it can count correct 429s as successful *decision responses*, but that is a different SLI with an explicitly defined population and semantics. Keep both metrics visible to avoid optimizing by refusing everything.

Reproduce the original burst on two gateways, inject a simultaneous boundary burst, crash between rate decision and durable operation intent, simulate store partitions, make an old quota lease holder resume, roll the limiter clock backward and try the same original key after response loss. Inspect authoritative admitted-operation receipts and client timing, not only Redis counter graphs. The key design decision is **what a quota violation means**, then which algorithm and state boundary implement that meaning.
