# File synchronisation and collaborative documents

Two laptops edit the same offline file, then reconnect. A naive sync service asks “which timestamp is newer?” and overwrites the other change. A collaborative editor also has concurrent updates, but operates at **character or semantic-operation granularity** rather than whole-file version granularity. A solution that preserves every uploaded file version does not automatically make two concurrent insertions converge to the same editable document.

- **M11-L01-LO1:** trace metadata, chunks, change detection, offline version upload and conflicting parent revisions through one file-sync example.
- **M11-L01-LO2:** compare whole-file conflict policies to operational transformation (OT) and CRDT-style collaborative document propagation, explaining ordering, convergence and failure limits.

## Define the two distinct products

A **file synchronizer** keeps a namespace of paths, permissions, file objects and revision histories in a consistent user-visible state. Reads may restore a specific file version. Updates commonly refer to a previous version/ETag, but two disconnected clients cannot both claim exclusive ownership merely because their local wall clocks advance. A shared **collaborative document** instead accepts concurrent insert/delete operations and transforms or merges them into a convergent logical document, potentially while editing occurs offline.

For one synthetic tenant with 100,000 files averaging 2 MiB, initial logical content is about **195 GiB** before replication and versions. If 1,000 clients each change a 4-KiB part of one 2-MiB file in an hour, retransmitting the entire file costs ≈1.95 GiB of upload traffic for changes totaling ≈3.9 MiB. The difference is an *input assumption*, not a measured compression gain. Small files and highly entropic changes may not justify complex chunk-delta protocols.

A service contract separates:
- **Durable upload**: the server persisted an immutable content revision, bound to an owner/path.
- **Visible head**: a guarded namespace pointer adopted that revision as the path's current version.
- **Converged document**: participants applying the same valid set of collaborative operations to a compatible starting state yield the same rendered document.
- **Authorization**: revoked users cannot fetch new protected versions after the declared server-side revoke boundary; an offline client may retain bytes previously downloaded, which the service cannot retroactively erase.

## Start with immutable file versions and conditional metadata

A minimal metadata record might be `(tenant, path_id, current_revision, parents, file_hash, chunk_manifest, size, rights_version, deleted_at)`. Store content chunks by immutable object identity and a manifest binding chunk order and exact byte lengths. An upload can reserve a pending revision, put chunks, verify full file content, then conditionally update `current_revision` **only if it still equals the client's declared base revision**. This is a compare-and-swap (CAS) on a *namespace head*, not a distributed lock on a user's laptop.

```text
Device A/B -> authenticates and downloads file v7 + base revision 7
Device A offline edits -> uploads chunks / manifest v8a (parent v7)
Device B offline edits -> uploads chunks / manifest v8b (parent v7)
Server CAS path head 7 -> v8a succeeds
Server CAS path head 7 -> v8b fails: conflict, do not discard v8b
```

At conflict, preserve both immutable v8a and v8b with their common ancestor v7. The product may produce an explicit conflict copy, offer a three-way merge for suitable text formats, or ask the user to resolve. It must not falsely report B's edit as the current head. A last-writer-wins (LWW) policy can be a valid deliberate choice for disposable metadata, but for editable user files it can silently lose one user's changes. Using “later wall-clock timestamp” as a total order is unsafe when client clocks are skewed; even a server-ordered winner needs a version history and an explicit product policy for the losing branch.

The API should bind a stable original upload key to input/base revision and operation receipt so a lost successful response does not create another revision. A chunk may upload twice; content-addressing can reuse identical bytes, but use a collision-resistant digest with verification and tenant/privacy rules. A temporary orphan chunk after metadata failure is garbage-collected only when no retained manifest references it. Tombstone and version permissions before physical deletion; late garbage collection must not remove a chunk newly referenced by a committed revision.

## Reduce retransmission with chunk signatures, not just hashes of full files

A **whole-file hash** cheaply detects that *some* bytes changed but cannot specify which region changed. Fixed-size chunks permit uploading changed blocks but shift all downstream boundaries when inserting at the front. Content-defined boundaries or a signature-search algorithm can reduce that effect at additional CPU/index cost.

Tridgell and Mackerras's original **rsync algorithm** uses a weak rolling checksum to quickly find likely matching blocks and a stronger checksum to verify a candidate match. It can identify unchanged portions even when matching blocks shift offset. The weak checksum alone does **not** prove byte equality; the stronger check and final file integrity validation are separate. The report is historical protocol evidence, not a guarantee that every cloud-sync vendor uses rsync. [rsync technical report, rolling checksum and checksum searching](https://rsync.samba.org/tech_report/tech_report.html).

Example: file v7 consists of blocks `[ABCD][EFGH][IJKL]`. Client A inserts `xy` before `EFGH` to create `ABCDxyEFGHIJKL`. Fixed 4-byte client blocks now group differently, while rolling matching can locate old `EFGH` and `IJKL` beyond the insertion. The server must still verify the final reconstructed content hash and **head CAS**; delta efficiency does not solve concurrent revision ownership.

Do not use a public content hash as an authorization token for a private file; an outsider guessing the bytes should not learn whether that file exists. Chunk identity may be scoped to a tenant and use private storage keys even if two file versions share a blob.

## Trace two offline edits and choose a file conflict rule

Start v7: text `HELLO`. Device A, offline, changes it to `HELLO!`; Device B changes it to `Hi HELLO`. Both upload with `base=v7`.

| Event | Server state | Safe client-visible outcome |
| --- | --- | --- |
| A uploads v8a | Immutable content stored; CAS head v7→v8a succeeds | A sees v8a as current |
| B uploads v8b | Content stored; CAS head v7→v8b fails | Server returns version-conflict and the two heads/ancestor |
| Merge | For text, user/tool merges v7, v8a, v8b into `Hi HELLO!` | Commit v9 with parents v8a and v8b after current-head condition |
| Restart | Client retries B's original upload key | Stable receipt points to stored v8b; no duplicate revision or silent overwrite |

This merge is straightforward only because the changes do not overlap semantically. If both changed the same sentence or one renamed/deleted the file while another edited it, automatic character merge may not preserve intent; make conflict resolution a product feature. A file name and folder move can be modeled as versioned metadata, but path aliasing and permission ownership must remain coherent.

RPO and RTO apply to both revision metadata and chunk objects. A backup that restores the head pointer but loses chunks referenced by that head is not a successful file restore. Record which complete manifest/version can be read, not just a backup job's completion.

## Collaborative text: represent intent as operations

Now users A and B edit the **same logical text** `AB` concurrently at the position between A and B. A inserts `x`, B inserts `y`. If a server simply applies insert-at-offset-1 in arrival order without transforming positions or stable identity, replicas may display different order depending on message delivery.

**OT-style approach:** a server or agreed control plane serializes an authoritative operation history. A client submits `insert(x, position=1, base_revision=7)`; a concurrent `insert(y,position=1,base_revision=7)` must be **transformed against operations accepted since its base**, with a deterministic tie-break for the same position. In one example, policy `x before y` produces `AxyB` on all replicas. Position transforms also need correct insert-vs-delete and delete-vs-delete cases; a working two-insert trace is not a proof of a complete OT algorithm. Clients can optimistically apply local edits, then transform/acknowledge remote changes and reconcile the server's revision order.

**CRDT-style approach:** encode each inserted character or sequence element with a stable operation/element identifier and predecessor/ordering metadata; apply a deterministic ordering rule for concurrent insertions at the same logical anchor. For this *illustrative* sequence CRDT, both x and y independently point after element A. IDs `(A,1)` and `(B,1)` determine one repeatable tie-break, so both replicas eventually render `AxyB` once they have applied the same valid operations. A delete addresses an element ID, not “current offset 1”. The algorithm must explicitly define how successors, tombstones, causal dependencies and garbage collection work; these are not automatically supplied by any ad hoc ID sort.

CRDT convergence means replicas receiving compatible operations under a specified algorithm eventually agree when all required operations are delivered and accepted. It **does not automatically preserve human editing intent, enforce server-side authorization, eliminate storage growth or guarantee real-time latency**. Automerge is a documented modern CRDT implementation that can merge offline concurrent changes; its precise sequence semantics must be checked before copying an algorithm into production. [Automerge documentation](https://automerge.org/docs/), [Kleppmann et al., Local-first software (2019)](https://martin.kleppmann.com/papers/local-first.pdf).

## Decide whether whole-file sync or collaborative operations fit

A file-sync engine usually treats arbitrary binary formats (photos, archives, spreadsheets) as opaque versioned blobs. It can detect conflicts, preserve versions and offer replace or application-specific merge; it cannot safely merge two arbitrary images by “inserting characters.” Collaborative editors specialize in structured operations and may pay for operation histories, per-element identifiers, tombstones, causal buffering, access changes, and snapshot compaction. Network partitions and offline peers require a retention horizon or explicit full-state resynchronization.

| Requirement | Candidate | Benefit | Limitation / failure |
| --- | --- | --- | --- |
| Offline opaque file updates | Immutable chunks + head CAS + conflict copy | Safe upload and restores without lost head | Does not auto-merge arbitrary binary edits |
| Text collaboration with server order | OT with authoritative history and transformation rules | Responsive editing and explicit total order | Transform correctness and server-order dependency |
| Offline-first peer text editing | Sequence CRDT with stable IDs/causal delivery | Merge independent operations after partition | Metadata/tombstone growth and intent ambiguities |
| Large similar file version transfer | Delta/rolling signature or chunk-dedup | Less bandwidth on small edits | CPU and index cost, no guarantee of head ownership |
| Sensitive file deleted/revoked | Authoritative metadata policy check + protected storage | Server can prevent new authorized reads | Cannot retract offline/downloaded copies |

For a synthetic original-operation success SLO, measure **all original authorized file-update requests arriving in a five-minute cohort**, deduplicated across retries: within 5 seconds each must receive an acknowledgment of either a durable successfully adopted new head or a **correctly explained conflict with the safely retained candidate revision**. Do not count silent overwrite as success. Track an independent **collaborative convergence** test: after a bounded sync period with delivery resumed, every authorized active replica holding the same accepted operation set reaches the same document hash. These are different guarantees.

Falsify the design by pausing B offline during two edits, losing A's successful response, crashing after chunk upload before metadata CAS, replaying an outdated head update, delivering two inserts in opposite orders, and deleting a character referenced by a delayed operation. For each case inspect revision graph, reconstructed bytes, authorization state and rendered document—not only whether the sync RPC returned 200.
