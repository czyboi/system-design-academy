# Messaging and media sharing

A sender taps *Send*. The chat server records the message and returns 200, but the recipient's phone is offline. The response can truthfully mean “durably accepted” without meaning “delivered to a device” or “read by a person.” A photo uploaded to the same service may move from a private group to a public profile, introducing an independent **object/CDN access transition**. These two features share storage and notifications but do not share one simple “done” state.

- **M11-L02-LO1:** trace connection/presence, message identity, per-room sequencing, offline replay and delivery/read receipts through a concrete group.
- **M11-L02-LO2:** choose safe media-upload/moderation/visibility/CDN policies and compare receipt, retention, privacy and failure trade-offs.

## Draw the boundaries before optimizing the socket

Assume a synthetic service with 200,000 active users, 3 million original chat messages/day, each carrying an average 300-byte text payload, and 20,000 newly uploaded photos/day at 2 MiB before derivatives. Raw original text is roughly **858 MiB/day** and raw photos ≈**39 GiB/day**, before replicas, headers, indexes, thumbnails, CDN and retention. Presence updates can be far more frequent than messages; never write every heartbeat into the durable message log. The numbers are workload inputs, not claims of scale from any particular chat platform.

Define product-visible states:

| State | Proven fact | What it does **not** prove |
| --- | --- | --- |
| `accepted` | Gateway validated the request and the durable message log/receipt is committed under room membership policy | Any remote device received bytes |
| `enqueued_for_delivery` | Recipient delivery intent is durably discoverable | Recipient is connected |
| `delivered_to_device` | A specified authenticated device acknowledged receiving a particular event | User opened/read it on every device |
| `read` | The user's client explicitly signaled viewing under stated UX policy | Human comprehension or a universal guarantee |
| `expired/deleted` | A tombstone and authorization policy prevent *new protected* reads | Already received/offline copies are erased |

Do not use one generic `sent=true` boolean for all states. The Matrix client/server specification explicitly distinguishes event synchronization from read receipts and ties a read marker to plausible viewing, not merely network delivery. Use it as **protocol evidence**, not a claim this example is an implementation of Matrix. [Matrix Client-Server API, sync and receipts](https://spec.matrix.org/v1.16/client-server-api/).

WebSocket can carry low-latency bidirectional frames over a long-lived connection, but the socket is a **transport**. It does not turn an ephemeral presence connection into durable message storage or a read receipt. HTTP request/reconnect and replay endpoints are still needed when a mobile device sleeps or changes networks. RFC 6455 defines the WebSocket handshake/framing and does not prescribe chat storage semantics. [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455).

## Commit one message and retain its original identity

An original sender request uses `(sender_id, room_id, client_message_key)`, with input and membership version. One authoritative room sequencer or guarded log append assigns `room_sequence` when accepting the event. A read can page by stable sequence; cross-room global order is not promised. A retry after a lost response returns the original `message_id/room_sequence`, not a second message.

```text
Sender device -> auth gateway -> check membership + message shape
    -> atomic room log append + sender's idempotency receipt
    -> durable fan-out/outbox intent -> delivery workers
    -> accepted(message_id, room_sequence)
Recipient device online? -> push wakeup + event -> device ack
Recipient offline? -> retain per-room cursor/event history -> replay on sync
```

The log and recoverable dispatch intent must be committed together or be reconstructible from the same durable record. Otherwise a crash between `accepted` and enqueue can strand a message that will never reach an offline device. Delivery workers and push notification systems may retry; deduplicate by stable message ID at recipient and on display. A `notification sent` event is not proof the device received the full message.

Room membership must be an **authorization fact**, not a cached assumption. If a user leaves at room revision 19 while a message at revision 20 is appended, the service must define whether access is decided at message-commit time, at protected replay time, or both. A safe private-room default is: only members entitled to the event under the room's **history-visibility policy** can fetch it, and removed users cannot fetch new messages after revocation confirmation. Already downloaded message copies cannot be retroactively wiped.

## Trace an offline group recipient and reconnect

Group `g4` initially contains Ada, Ben and Cara. Ben is offline at 10:00. Ada sends `m100` with original key `k1`; the server durably appends room sequence 41 at 10:00:01. Cara's connected phone acknowledges `m100` at 10:00:02. Ben reconnects at 10:05 with `last_received_room_sequence=40` and has a verified current membership entitlement.

| Time | Durable log | Cara | Ben |
| --- | --- | --- | --- |
| 10:00:01 | `seq41: m100` committed, dispatch intent durable | Push pending | Offline |
| 10:00:02 | No new event | Device ack for seq41 | Offline |
| 10:00:03 | Sender retried `k1`; same stored receipt | May receive duplicate push, dedup by ID | Offline |
| 10:05 | Log still contains seq41 | Optional user read receipt if viewed | Sync asks for events after seq40 |
| 10:05:01 | Event replay authorized | — | Ben receives, persists cursor seq41 and sends device acknowledgment |

At 10:00:01, the gateway may return `accepted` to Ada even though Ben is offline. At 10:05:01, Ben's **device** delivery is established; a read receipt appears only under a separate user-view event. If Ben has two devices, define whether “delivered” means any one device or every currently registered device. The product must not silently turn a per-device acknowledgment into a person-level read guarantee.

What if Ben's membership was revoked at 10:04? The **room-history visibility policy** decides whether he may retrieve older seq41 after removal; under a strict no-history-after-revocation policy the sync must deny. Replaying a log is not permission to bypass current entitlement. A message can be retained for other authorized members while no longer fetchable by Ben.

## Respect order without a global sequencer

For each room, a stable `room_sequence` orders accepted events. Concurrent sender messages may be accepted in either order according to the room's sequencer; the client must use the **committed sequence**, not local device time, to display canonical room order. Across rooms there is no need for one global order. For a distributed room service, assign a room to a serialized partition/leader with a fenced term or transaction guard, so old leaders cannot append after a replacement becomes active. The coordination mechanics are in M09-L03; the chat case uses the invariant without reteaching the whole consensus protocol.

When an app host crashes during fan-out, rerun delivery from the durable log. When a recipient's cursor is stale, page forward from a retained point and use a server-issued continuation token bound to room/member/snapshot. If messages older than a retention horizon have been deleted, return an explicit `history_unavailable`/resync status rather than pretending there were never older messages. A per-room message ordering guarantee can coexist with a best-effort notification order.

Presence is a soft signal: authenticated connections hold short-lived leases in an ephemeral presence registry and renew periodically. A missing heartbeat suggests offline, not proof the recipient saw nothing; an online indicator can lag during network transitions. Do not gate message durability on the presence service.

## Photo upload is a versioned publication process

A photo first enters a **private pending** state. Its owner obtains a scoped upload intent and transfers bytes into a restricted object-storage key. The server verifies object version/size/type and runs policy-required checks (e.g., malware and content moderation if relevant), then commits a metadata revision that says what derivative(s) can be accessed, by whom and when. Thumbnail/format transformation jobs are idempotent by `(photo_id, source_version, transform_version)`, with retries and a terminal or retryable error state.

```text
Owner POST upload -> photo_id pending_private + scoped upload intent
    -> restricted object store (versioned source)
    -> verify complete object -> scan/moderate -> derivatives
    -> authorize metadata publication (private_group or public)
    -> feed post event / optional CDN delivery
```

If metadata says `public` **before** the policy-checked object and derivatives are ready, a reader can see a broken or prohibited asset. If a moderation job finishes after the owner changes visibility, its old “approved for public” result must not override a newer private revision: compare source/content and policy versions at the metadata transition. Do not expose public URL endpoints that allow bypassing group authorization while the photo is private. [AWS S3 data consistency and object versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

For a genuinely public image, CloudFront can reduce origin load, with a secured S3 origin and OAC where supported. **OAC authenticates CloudFront's access to S3, not the viewer's entitlement to a private group photo**. Signed URLs or cookies can restrict viewer access for a bounded lifetime, but already-issued bearer links may remain valid until expiry; for strict immediate revocation, use a protected read gateway or a deliberately weaker documented revocation bound. [AWS CloudFront: private content and OAC](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

## Trace private-to-public then revocation

Photo `p7` is uploaded at 11:00 as **private to group g4**. At 11:01 the source verifies and thumbnails are ready, but Ben—no longer a group member—must not fetch `p7`. At 11:02 Ada publishes a new metadata revision `visibility=public, revision=5`; eligible public readers may now obtain the published version through the chosen CDN. At 11:03 Ada reverses visibility to private (`revision=6`).

A policy that promises **bounded CDN cache purge** can acknowledge the visibility change with a documented grace window; it cannot claim an instantly unusable public copy. For a **strict acknowledged private** policy, stop content release at the authoritative gateway before confirming revocation and ensure no direct public object/CDN URL bypasses that gate. In-flight authorization checks and already-issued download links need an explicit contract. Deleted/purged objects can continue to exist in backups until retention/deletion completes; that does not authorize serving them.

Tie the social feed to media metadata, not the raw upload key. Feed cards and search snippets can leak a private photo's title, thumbnail or URL even after the binary object is protected; invalidate or re-check every derived presentation. A group membership change can invalidate access to the post and its media independently of a global public-search index update. This is the cross-feature consistency problem, not an image-format optimization.

## Choose receipt, retention and privacy contracts explicitly

| Trigger | Choice | Benefit | Cost / failure boundary |
| --- | --- | --- | --- |
| Offline recipient | Durable room log + replay cursor | No dependence on live connection | Retention horizon, replay authorization and cursor history |
| Long-lived connected app | WebSocket for push, HTTP sync fallback | Low-latency events | Connection churn, backpressure and no built-in delivery proof |
| Sender retry / worker replay | Stable client-message key and message ID | Prevents duplicate logical events | Receipt state and input conflict checks |
| Many members in one group | Per-room serialized append, bounded worker fan-out | Clear room order and throughput | Hot room partition and downstream lag |
| Public media | Versioned object and CDN after policy ready | Cheap read distribution | CDN invalidation/egress and public copies |
| Private group photo | Authoritative viewer/room policy at protected read | Prevents cross-group leakage | Additional read latency, limited CDN sharing |
| Expired history | Tombstone + retention/purge plan | Bounded cost, explicit unavailable state | Offline devices may miss old content permanently |

Define two independent synthetic SLOs. (1) For **all original valid sender message requests** in each five-minute arrival cohort, 99% must receive a durable accepted receipt with stable message ID **within 500 ms of ingress**; rejected, timed-out, failed and late requests count as failures. Recipient delivery/read metrics have their **own denominator**, eligible recipients/devices and deadlines, not the sender receipt's numerator. (2) For **all original authorized photo reads**, 99% must deliver correct *currently permitted* bytes or correct non-disclosure after a visibility transition at the client before a declared deadline; do not count “fast 403 for everything” as content availability. Separate active-public and private-authorized classes.

Falsify the claims by crashing after log commit before fan-out, replaying a duplicate client key, disconnecting Ben for longer than the event-retention horizon, racing membership revocation with sync, publishing photo metadata before moderation, racing public→private with a CDN fill and serving a stale thumbnail/search snippet. Inspect actual device receipts and protected content release, not only HTTP 200.
