# Authoritative card games and price-time order books

Two very different products have the same dangerous shortcut: accepting a client's view of mutable shared state as truth. In a turn-based game, two players disagree about whose turn happened. In an exchange, a cancellation and a marketable order race for one resting order. Network arrival order, UI timestamps, and database commit time cannot independently define both results. The design must name **one authoritative sequence per state machine**, and every replica or reconnected client must reconstruct the result of that sequence.

- **M11-L07-LO1:** trace a duplicate/out-of-order game action and a single-instrument order/cancel race through authoritative state, receipts and deterministic replay.
- **M11-L07-LO2:** choose, compare and defend per-game versus per-instrument serialization, failover and client-visible uncertainty under explicit invariants.

## One turn-based card game: make the server authoritative

Consider an original two-player trick-taking game. A match has an authenticated membership list, a fixed shuffled deck, a current player, hands that may be private, and a sequence number. In this simplified ruleset a turn consists of playing exactly one card owned by the current player; do not infer poker or tournament rules. A client is an **intent producer**, never the authoritative hand or deck owner.

The match owner holds state such as:

```text
Match { game_id, epoch, last_seq, next_player, phase, private_hands, trick }
Command { game_id, player_id, action_id, expected_seq, card_id }
Receipt { action_id, canonical_input, accepted, result_seq, public_result }
```

Authentication binds the command to player identity; membership and turn ownership are checked against current server state, not a locally cached client copy. For one accepted move, the owner verifies card ownership and phase, removes the card, advances the turn and commits the resulting state transition with a stable receipt. Players receive a filtered public event plus their allowed private view; sending the full state log to clients would disclose hidden hands. An untrusted client cannot select the result of a shuffle or forge the opponent's cards. PlayFab's managed multiplayer lifecycle illustrates that allocating and connecting clients to a server are **separate from implementing game rules** [Microsoft: server lifecycle](https://learn.microsoft.com/en-us/gaming/playfab/multiplayer/servers/multiplayer-game-server-lifecycle), [client connection](https://learn.microsoft.com/en-us/gaming/playfab/multiplayer/servers/connecting-clients-to-game-servers).

### Duplicate and reordered action trace

At authoritative sequence 17 it is Alice's turn, and her hand contains C7. She sends `action_id=A42, expected_seq=17, play C7`.

| Event order at the authority | Decision | Durable change |
| --- | --- | --- |
| A42, seq 17, Alice plays C7 | Accept after rule checks | Append event 18; C7 leaves hand, Bob becomes next player, receipt A42→18 |
| Response for A42 lost | Client cannot infer failure | None |
| Alice retries identical A42 | Return the original receipt and permitted view | **No** second play |
| Alice sends new A43, seq 17, play C8 | Reject as stale/not Alice's turn | None |
| Bob sends B11 with expected seq 18 | Accept if he owns card and rules permit | Append event 19 |

The duplicate path checks the **stable action ID and canonical input** before validating the action against the now-changed turn, otherwise an accepted retry might wrongly appear illegal. Reusing A42 with a different card is an input conflict, not a retry. Reconnect is `last_seen_seq` plus server-authorized snapshot/delta: if Alice's latest known event is 16, the server returns a current permitted snapshot and/or events through 18, never trusting her claimed hand. Resend may be at least once; application requires deduplication and monotonic sequence application.

For an operational design, persist a committed event/receipt and its state version together (or an equivalent durable transactionally coherent record). An in-memory authoritative process without durable checkpoints may deliberately lose unfinished games; that is a **different availability/durability contract**, not an invisible implementation detail. On restart, load a versioned snapshot, apply committed commands/events above its watermark in deterministic order, and verify a state digest. A snapshot must reference the same committed history it summarizes.

## A single-instrument order book: define priority precisely

Now consider an **original simplified continuous limit-order book for one instrument**. Orders are authenticated and validated at ingress, but one matching authority decides order sequence. Limit buy orders match resting sells at prices no higher than the buy limit; limit sells match resting buys no lower than the sell limit. Among eligible orders, choose the best price first, then oldest resting acceptance sequence at the same price. Partial fills reduce remaining quantity; a remainder may rest according to its stated time-in-force. This is a deliberately bounded example, **not** a claim that every exchange uses these exact rules: real venues have display, reserve, auction, self-match and regulatory variants. Nasdaq rules describe price/display/time ranking and priority conditions [Nasdaq Equity Rule 4757](https://listingcenter.nasdaq.com/rulebook/nasdaq/rules/nasdaq-equity-4).

Define integer ticks and units—never binary floating-point money comparisons in the matching core. The canonical event input includes `instrument, participant, order_id, side, limit_ticks, quantity_units, time_in_force, request_id`. The state contains live book levels, per-order remaining units, an accepted-command sequence, and a durable execution/cancellation ledger. Client timestamp does **not** determine matching priority; the authoritative acceptance order does.

### Trace the order/cancel race

At sequence 80, a sell order `S1: 5 units @ 101 ticks` rests, ahead of any later sell at that price. At roughly the same external time, the seller sends `cancel S1` and a buyer sends `B1: buy 4 units @ 102`. Both network messages are valid; the resulting contract depends on **serialization**, not which user's clock appears earlier.

| Canonical input order | Event 81 | Event 82 | End state |
| --- | --- | --- | --- |
| Cancel then buy | Cancel S1's 5 unfilled units, mark terminal | B1 finds no S1; may rest or expire by TIF | No trade against S1 |
| Buy then cancel | B1 matches 4 with S1 at resting 101; S1 has 1 left | Cancel remaining 1 of S1 | Fill of 4 is final; cancel cannot undo it |

A cancellation is a request to remove **remaining eligible quantity**, not a guarantee that no concurrent fill existed. The response must carry final order status plus executed and canceled quantities; an order with original 5 can have 4 executed and 1 canceled. Retries of either command use stable request IDs, and the matching core stores the resulting receipt. A lost execution acknowledgment must not generate another buy order. Define cancel of an already fully filled or canceled order as an idempotent status response under a stable ID, rather than inventing a retroactive execution reversal.

An actual price/time book may use distinct display-priority classes; the example deliberately uses one fully displayed price/time class. Published Nasdaq rules are evidence for a **specific venue policy**, not a universal source of truth for all matching engines. Quoting this simplified example must retain its assumption.

## Serialization boundary, log and recovery

One game is independent of another game until cross-game ranking, wallets or tournament constraints are introduced. One instrument can usually serialize its order book independently of another *only if* account-level risk checks, shared positions and cross-instrument atomic obligations have an explicitly separate authoritative boundary. Do not claim that sharding by instrument automatically solves global risk or cross-book orders.

A simple initial architecture for either domain:

```text
Client -> Auth/normalization -> Router(game_id or instrument_id)
         -> fenced authoritative owner(epoch)
         -> deterministic command executor
         -> durable ordered events + input-bound receipts
         -> snapshots/read views -> authorized clients
```

**Why fencing matters:** during failover old owner O1 can keep processing buffered commands after O2 has recovered. Merely electing O2 does not prevent two histories. A durable log or guarded resource must reject O1's outdated epoch at **the write boundary**, and O2 must start from a safe committed prefix. The log sequence and execution side effects must be tied to that prefix. If the system cannot prove exclusive authority, pause new decisions instead of accepting possibly incompatible histories. The lesson [M09-L03](../../m09/lessons/M09-L03.md) introduces storage-side fencing; here its application is per-state-machine order.

For deterministic replay, capture the accepted canonical commands, rule-engine version, initial shuffle seed or committed deck allocation where appropriate, tie-break order, and every external decision that affects results. A game must keep secrets protected even when an audit log exists. The order-book reducer should not call wall-clock time, random number generators or external services to decide matching unless those outputs were recorded as immutable inputs. Test that replayed fills and state hashes match committed results. Outbound notifications are **derived delivery**, not an independent execution of a fill.

Snapshotting reduces recovery latency but must not advance beyond the committed log prefix. A stale read view can show an earlier game turn or order quantity; clients must use an authoritative receipt or sequenced stream for finality, not treat read projection lag as proof a command failed. Under partition, a strict game may suspend moves; a strict order book should stop matching for the affected instrument rather than accept split-brain executions. Both sacrifice availability to preserve their stated ordering invariant, but their acceptable restart delay, confidentiality and compensation policies are product choices.

## Worked capacity and success boundary

Suppose a deliberately **illustrative** deployment carries 2,000 active turn-based games averaging 0.2 accepted moves per second per game (400 moves/s overall), and 80 instruments with a heavily skewed command distribution. Partitioning game instances across owners helps the first workload; evenly hashing 80 instruments does **not** remove a single very hot instrument's serialized bottleneck. The correct capacity test measures maximum sustained **one-partition** decision rate, log commit latency, recovery prefix replay time and cross-domain risk-gate cost. These are workload assumptions, not measured product benchmarks.

For a five-minute cohort, assume 1,000 valid **original** player moves arrive, 920 receive durable accepted/rejected-by-rules outcomes within the 300ms contract, 30 are denied for capacity, 25 time out and 25 complete late. The timely decision SLI is 920/1,000, not 920/950. Legitimate rule rejection can count as a correct timely *decision*, but not as a successful *play*, if the latter is separately promised. For an exchange, separately count original order intents with definitive accepted/rejected status by deadline, executed trades confirmed from the committed matching log, and cancel requests acknowledged with remaining quantity. A late cancel that follows a fill is not automatically incorrect; **an unreported committed fill or a double fill is**.

Rehearse client replay, duplicate actions, conflicting ID reuse, action reordering, double ownership on failover, a snapshot behind committed events, and both order/cancel serializations. Compare state digests and authoritative receipts—not only UI consistency. Choose the serialization key and durable acceptance boundary before optimizing transport latency.
