# Recommendation and graph search

A recommendation endpoint says product `p3` is “related” to `p1`. A graph search endpoint says that person `a` is connected to `c` through a permitted two-hop path. Both can return ranked IDs, but they answer **different correctness questions**. A recommendation can be uncertain and evaluated by relevance; a claimed shortest path must satisfy graph and permission constraints. A stale *feature* damages relevance, while stale *permission* can disclose a private entity even if relevance scoring is numerically perfect.

- **M11-L03-LO1:** trace recommendation event collection, candidate generation, feature production, ranking, serving and feedback for a realistic user/product example.
- **M11-L03-LO2:** combine authorized graph traversal with index filters and ranking, choosing precomputation or online evaluation with explicit freshness, cold-start and failure contracts.

## Establish two products and one authorization boundary

**Related products:** `GET /products/p1/recommendations` returns a ranked list of eligible products under a specific catalogue, price/stock and model version. The ranking seeks user value—e.g. useful click or purchase—subject to hard eligibility. It does not promise a mathematically unique optimal result.

**Friends in a city:** `GET /people/a/friends-in-city?city=DaNang&max_hops=2` returns people reachable through at most two permitted social edges from a under the viewer's visibility scope and a declared graph snapshot. “Within two hops” can be computed by bounded traversal or a suitable index/projection. A top-10 rank may order eligible people by a stated preference score, but must not *invent* a path for a high-scoring non-neighbor. If the endpoint promises a shortest-path explanation, that proof uses the BFS/layer conditions of [M10-L05](../../m10/lessons/M10-L05.md).

For a synthetic product catalogue of 10 million active items, 1 million interaction events/day and 100,000 recommendation requests/day, the system should not score every item on each read unless that cost is justified. Average request rate (~1.16/s) is misleading about peaks and long-tail candidate skew. A scalable first design retrieves a bounded candidate pool, applies eligibility filters and ranks it. All numbers are invented workload inputs, not neural-network benchmark claims.

## Move from interaction events to candidate features

A durable interaction may include `(event_id, user_scope, item_id, event_time, event_type, source_version)`. Instrument displayed impressions and actual user actions separately. Without impression logging, a model trained only on clicks cannot know which unseen items were actually offered. Retry of the same original event should not duplicate an interaction count; an anonymous user/session may require opt-out and retention limits. Feedback events flow asynchronously into a protected log, aggregation and offline feature store; an online feature store serves bounded per-user/item representations where needed.

```text
View/click/purchase -> consent + stable event ID -> durable feedback log
      -> batch/stream features + versioned catalogue/availability
      -> candidate indexes and/or online feature store
Client query -> candidate retrieve -> hard eligibility and privacy checks
             -> rank versioned features -> diversity/business filters
             -> final authorization/availability check -> client
      -> attributed impression/outcome events for evaluation
```

Some candidates can come from item-to-item co-occurrence, followed-author interests, category affinity or a vector retrieval model; each source needs a documented training cut and eligible item universe. TensorFlow Recommenders describes a common **retrieval stage** that narrows millions of items to candidates and a separate **ranking stage** for the shortlist. Google's historical YouTube paper likewise describes candidate generation and ranking as separate stages; this lesson does not inherit their model architecture or performance as a requirement. [TensorFlow Recommenders retrieval](https://www.tensorflow.org/recommenders/examples/basic_retrieval), [Google, Covington et al., 2016](https://research.google/pubs/deep-neural-networks-for-youtube-recommendations/).

## Work a small product example

A user has just viewed `p1` (running shoes). Candidate retrieval produces `p2` (sports socks), `p3` (running shoes), `p4` (travel adapter), `p5` (private seller's unlisted listing). A toy ranking function for this example is:

`score = 0.6 × item_similarity + 0.3 × recent_interest + 0.1 × popularity`

All features lie in [0,1] under a **declared synthetic normalization**. They are not calibrated click probabilities.

| Item | Similarity | Interest | Popularity | Toy score | Eligibility |
| --- | ---: | ---: | ---: | ---: | --- |
| p2 | 0.8 | 0.7 | 0.5 | 0.74 | Public, in stock |
| p3 | 0.9 | 0.8 | 0.3 | 0.81 | Public, out of stock |
| p4 | 0.2 | 0.1 | 0.9 | 0.24 | Public, in stock |
| p5 | 1.0 | 0.8 | 0.8 | 0.92 | Private, viewer not permitted |

Hard filters remove p3 for stock policy and p5 for authorization. The response ranks `p2 (0.74)` above `p4 (0.24)`, **not p5** despite its larger score. Relevance score never overrides permission. A subsequent restock of p3 can change the eligible set without retraining the model; an updated private listing can require immediate policy changes while old feature embeddings still exist.

A cache may store public item-to-item candidates for p1, but viewer-specific filters and dynamic stock/rights are applied at the protected response boundary. Keying by only p1 and serving the old ranked list to a different viewer risks leaking p5. Cache correctness and query-generation constraints follow [M10-L06](../../m10/lessons/M10-L06.md).

## Graph search: traverse eligible edges, then rank eligible people

Consider a static graph snapshot `g12`, with directed or undirected edge semantics stated explicitly. For this example use **undirected friendship**:
`(a,b), (a,d), (b,c), (d,e), (b,f)`.

Locations: `b=DaNang`, `c=DaNang`, `d=Hue`, `e=DaNang`, `f=DaNang`. Viewer V may see edges `a-b,b-c,b-f` but cannot see `a-d` or `d-e` because d's profile is private to another group. Under V's permitted graph, a two-hop traversal from a yields:

| Candidate | Permitted path | Hops | Eligible? |
| --- | --- | ---: | --- |
| b | a→b | 1 | Yes |
| c | a→b→c | 2 | Yes |
| f | a→b→f | 2 | Yes |
| e | a→d→e | 2 in global graph | **No**, path uses hidden edge |

The city filter retains b/c/f; e cannot appear even if location and a global recommender rank highly. A people search index might quickly retrieve all users with `city=DaNang`; it still must intersect with the **authorized two-hop reachable set**. Conversely, BFS can compute reachable people and then query location for those IDs. Choose the plan based on candidate cardinality, index selectivity, graph degree, permission storage and a bounded remote fetch budget. A global index returning e does not prove a permitted relation.

If the caller requests “a few socially relevant people” rather than *all* within two hops, it may rank b/c/f by shared interactions or recency and cap top-K; a ranking score is not a proof of completeness. If the API promises exhaustive eligible results under two hops, all necessary adjacency expansions must finish under a coherent version or it must return an explicit partial/incomplete status. Do not turn an adjacency timeout into an empty neighbor set.

## Separate stale features from stale permissions

Suppose p2's popularity feature is 24 hours old. The user may receive a lower-quality but authorized recommendation. A product contract can label model/feature cuts and choose freshness bounds. But suppose p5 became private at 10:05 while an index and candidate cache still list it as public. Serving it at 10:06 is a **security correctness violation** under a strict revocation policy, not merely a stale relevance score. A correct design filters through an authoritative permission/version gate before exposing the item and prevents a delayed old fill from restoring stale visibility. Use similar authorization logic for graph edges, profiles, and location-derived private attributes.

Cold-start users have no personalized interaction history; they can use declared context, explicitly permitted popular items, onboarding selections or content-based features. Cold-start items have little behavioral data; use taxonomy/text attributes and exploration budgets. **Popularity-only** can amplify exposure inequality, so monitor per-group and long-tail coverage alongside clicks and conversions, without treating a model score as a fairness guarantee. A safe empty eligible set is an honest result; do not reveal a private candidate just to fill top-10.

Offline training can operate on large histories without impacting online latency, but its feature cut may lag current stock/permissions. Real-time streaming updates reduce lag at state/operational cost. Store feature schema/model version, training cut, online freshness, experiment assignment and result provenance so regressions are attributable. Privacy-sensitive raw events require consent/scope minimization, access control and retention that matches product obligations; embedding vectors can still encode sensitive information and should not automatically be declared anonymous.

## Design for latency without weakening hard rules

A sample endpoint budget might allocate 25 ms candidate retrieval, 20 ms feature hydration, 15 ms ranking and 20 ms final policy/response, totaling 80 ms **as a synthetic target**. A cache hit might skip retrieval/ranking, but it cannot skip current permission where strict authorization applies. Parallelization may help if dependency ordering permits; adding individual percentile figures is not a valid end-to-end percentile guarantee. Instrument actual client receipt, request class and stage waits.

| Decision | When useful | Cost / failure |
| --- | --- | --- |
| Offline item-to-item candidates | Stable public item similarity | Stale candidates and retraining |
| Online two-tower/ANN retrieval | Large eligible item corpus with appropriate embeddings | Index refresh and approximate recall, model ops |
| Precomputed authorized graph neighborhood | Stable small follow graph and controlled policy versions | Permission revocation/invalidation and per-viewer storage |
| Online BFS/filter intersection | Dynamic permissions, explicit hop proof | RPC/fan-out and deadline risks |
| Final authority/policy filter | Any sensitive or revocable result | Added latency or safe refusal under policy outage |

For a synthetic user-visible success SLI, include **all original valid recommendation requests**, deduplicated across retries, in each five-minute ingress cohort. To count success, a client must receive a correctly authorized eligible list (which may be empty) within 200 ms; count failed, rejected, leaked, timed-out and late originals outside the numerator. Report relevance quality **separately** using controlled experiments/attributed outcomes and guard against the trivially “fast empty list” strategy with a coverage metric. For graph search, report exact/complete eligible reachability separately from ranked top-K quality.

Falsify by revoking a listing while a precomputed vector candidate remains cached, injecting a hidden graph edge, failing one adjacency shard, delivering an old feature update after a new model revision, replaying an impression event, and issuing the same query under two viewers with different permissions. Source freshness and access decisions must be observable at the client answer, not inferred from a batch-job green dashboard.
