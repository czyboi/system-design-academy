# Durable key-value stores and disposable caches

Two services both answer `GET(key)` and `SET(key,value)` in a few steps. One is the **source of truth** for a user's state; the other is a replaceable copy of that state. They have similar commands, but after a crash the first must recover acknowledged data under a declared durability contract, while the second may forget everything and safely refill. Choosing a product name before this distinction hides the most important design decision.

- **M11-L09-LO1:** trace key routing, expiry, memory-pressure eviction and node restart through a bounded key-value design.
- **M11-L09-LO2:** choose a durable store versus disposable cache, defending acknowledgment, replay, recovery and missing-data semantics.

## Define what an acknowledgment promises

For this original scenario, the authoritative database contains `profile:42 = {name:"A"}`; a cache may store the same value for faster reads. A second independent workload uses a key-value service as the **only** owner of `session:42`. A response `SET OK` means different things:

- In a **disposable cache**, `SET OK` means the cache stored the item for best-effort future reads. It may be evicted, expire or vanish on failure. On a miss, the caller must fetch an authoritative copy or safely compute the item.
- In a **durable store**, an acknowledged write should survive the stated failure class. If the contract promises machine-loss survival, writing only to volatile memory or an unreplicated asynchronous buffer is insufficient. Define exactly which failures count; machine restart, host loss, region loss and data corruption are not interchangeable.
- In a **recoverable but lossy store**, explicitly disclose the recovery point objective. A process may acknowledge in memory yet lose its latest writes after a crash; do not market that as zero-loss durability.

This is an application contract, not an inherent truth of the word “Redis.” Redis Open Source provides RDB snapshots, append-only files with configurable sync, both, or no persistence. Its durability depends on selected configuration, workload and failure boundary [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). Memcached is typically disposable; its warm-restart feature preserves cache in certain **clean restart** conditions, but is not a crash-safe durable database [Memcached warm restart](https://docs.memcached.org/features/restart/).

## Build a small Redis-like key-value service

Start with a process that owns a map of `key -> {value, revision, expire_at}`. A client `SET key value` updates one entry; `GET` returns the currently allowed value or a miss. In a multi-node service, route each key to its designated owner using a deterministic partition map and a versioned routing epoch. Two owners must not both acknowledge incompatible writes to the same key.

A minimal write/read trace:

```text
Client -> router(key, placement_epoch)
       -> current owner: check TTL and command preconditions
       -> apply key mutation at authoritative sequence
       -> durability boundary for promised acknowledgment
       -> return stable revision/receipt
GET -> current owner/read replica under named consistency policy
```

A read replica may lag; a caller who needs read-after-write semantics must use the correct owner or wait for a known committed revision. Rebalancing changes placement and demands an authoritative cutover protocol; merely switching hash functions while old requests are inflight can split histories. A single-key conditional update can protect a revision, but atomicity across keys or shards requires a separate contract. Do not treat a faster lookup as proof of safely replicated state.

Expiration means a key becomes **logically unavailable** at a deadline. Physical memory reclamation may be lazy or background-driven, so an expired entry can occupy bytes until accessed or swept. Reads must not return logically expired data just because an object still sits in memory. Exact TTL interpretation, clocks, and replication of expiry decisions are version-specific; if a source of truth uses expiration as a business event, record what must happen exactly once and how it survives failover.

## Bound memory: expiry and eviction are not the same

Assume an illustrative 4-entry cache budget. At t=0, cache contains A, B, C, D. B has deadline t=10, while A,C,D have later deadlines. At t=12, a `GET(B)` is a **miss** because B is expired, regardless of whether its bytes have already been reclaimed. Inserting E may reuse B's space. If there is no expired candidate, an eviction policy chooses a *still-valid* resident entry for removal. The application must tolerate that subsequent reads of an evicted key miss before its TTL.

| State change | Logical visibility | Why item disappears | Recovery of a cache miss |
| --- | --- | --- | --- |
| B expires at t=10 | Not returned after deadline | TTL policy; physical reclaim can lag | Reload from authority if still valid there |
| D evicted at t=12 due to capacity | Not cached despite unexpired TTL | Memory pressure and replacement policy | Recompute/refetch D |
| Cache node fails at t=13 | All its cached entries may disappear | Node replacement/lost volatile state | Refill gradually with load controls |

An expiry is not a throughput guarantee: clearing millions of keys at the same instant has different costs from rejecting logically expired reads. An eviction policy such as LRU or LFU is chosen to improve hit rate under budget; it is not a data-retention guarantee. Redis documents multiple `maxmemory` eviction policies, including `noeviction`, which refuses qualifying new writes instead of choosing a victim. The selected policy must match the durability contract [Redis key eviction](https://redis.io/docs/latest/reference/eviction/).

For a disposable cache, do not store its **only** copy of an important command receipt, purchase confirmation or user's unreplaceable data. Eviction would silently erase a business invariant.

## Design a Memcached-like disposable cache

Let the authoritative database store `profile:42`. A cache uses `GET(profile:42)`, `SET(profile:42, value, ttl)` and optional invalidation on update. The simplest read-through arrangement:

```text
GET profile:42
  -> cache hit: return cached value if acceptable freshness
  -> miss: fetch database; conditionally populate cache with TTL
  -> if database fails: explicit error/stale-mode policy, not invented data
```

A writer updates the database, then invalidates/replaces cache state. The two operations are not automatically atomic. An older concurrent reader can repopulate an out-of-date value after invalidation:

```text
R1 reads old version v1 from DB, pauses
W commits v2 to DB and invalidates cache
R1 puts v1 back in cache
R2 now sees stale v1
```

Versioned cache entries and conditional installation based on a source revision, or a bounded staleness policy plus TTL, can address the named requirement. A TTL alone bounds stale residence under a functioning clock but does not eliminate all stale reads. A cache miss storm after node replacement can overload the database; request coalescing, bounded concurrency, jitter and overload policies are part of user-facing reliability. [Memcached user guide: expiration and invalidation](https://docs.memcached.org/userguide/).

Memcached's own documentation describes eviction of still-valid items when slab-class free space is exhausted, and expiry via access/background reclamation [Memcached performance guide](https://docs.memcached.org/serverguide/performance/). It also documents warm restart for supported versions, which **does not** turn ordinary cache acceptance into a zero-loss database commitment [Memcached warm restart](https://docs.memcached.org/features/restart/).

## Crash/replay trace: what survives acknowledged writes?

Assume the owner receives `SET K=v2`, replies success, then its host loses power before the next persistence point:

| Configuration/contract | What was acknowledged? | Crash consequence | Safe client response |
| --- | --- | --- | --- |
| Disposable cache with authority elsewhere | Best-effort cached copy | K may be absent on new node | Miss then rebuild/refill from authority |
| KV with periodic RDB snapshot only | In-memory mutation, not zero-loss durable commit | Latest acknowledged writes after snapshot can be lost | Explicitly accept bounded-loss contract or change acknowledgment mechanism |
| KV with AOF `everysec` | Mutation may precede disk sync | Recent writes can be lost on abrupt failure | Declare nonzero RPO; never claim each reply was durably fsynced |
| KV with sync-before-ack and safely persisted recovery record | Contractually durable under the specified local disk-failure model | Replay committed records after restart | Reconcile by stable operation ID/revision; test storage and fault model |

The final row is a *design requirement*, not a claim that a product automatically survives disk destruction, region outage or asynchronous replica promotion. For host-loss durability, the actual acknowledgment boundary may require replicated committed records on independent failure domains, with old-owner fencing and a checked committed prefix. Backups are for recovery from logical corruption or disaster, not a substitute for immediate replication. Redis documents AOF synchronization choices and snapshot trade-offs, not universal durability across all deployments [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

A particularly dangerous design returns an acknowledged `SET` from old primary P1 and fails over to a replica P2 that never received it. If the API promised zero loss, this is a contract breach even if P2 quickly starts serving. If the contract permits bounded recent loss, clients still require a reconciliation policy for uncertain operations. Replica promotion must not resurrect a history that conflicts with later accepted writes; apply epoch fencing and explicit consistency semantics.

## Choose based on failure, not brand

| Decision question | Durable key-value contract | Disposable cache contract |
| --- | --- | --- |
| Can an acknowledged value be forgotten? | Only within explicitly declared RPO/failure exclusions | Yes, anytime |
| Who repairs a miss? | Store recovery/replay, or product-level explicit absence | Authoritative database or deterministic recomputation |
| Memory budget | Avoid silent loss of source-of-truth keys; reject/grow/tier by policy | Evict/expire replaceable entries |
| Restart objective | Restore committed prefix and prove retained revisions | Warm refill while protecting origin |
| Correctness bottleneck | Serialized mutation, sync/replication, failover | Freshness, miss amplification, origin capacity |

For a synthetic five-minute cohort of 10,000 valid original profile reads, suppose 9,100 return correct current data within 100 ms, 400 return stale data outside the product bound, 250 time out and 250 are rejected while origin is overloaded. **Timely correct read success is 9,100/10,000 = 91%**. Do not report 9,100/9,500 by excluding rejected and timed-out originals. Observe read freshness and refill load separately from cache hit rate.

Test TTL expiry while the entry remains physically allocated, pressure eviction before TTL, crash just after an acknowledged write but before sync, failover to a lagging replica, write/invalidate/read race, and a whole-cache restart under load. Compare actual receipts and origin revisions. The architecture choice is complete only once you can say precisely **which acknowledged value may disappear, under which failure, and what makes the customer whole**.
