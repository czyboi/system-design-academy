# CDN as a service and global data serving

A product changes the logo at its origin while a region goes offline. Users are redirected to the remaining region, but some still see the old logo and others receive errors: the CDN had cached the previous bytes, the surviving application cluster lacks spare capacity, and the global database replica has not applied the latest metadata. **Edge caching, region failover and data replication are different mechanisms with different clocks.**

- **M11-L04-LO1:** trace origin registration, edge lookup/fill, TTL/versioning/purge, origin access and a changed object during a regional outage.
- **M11-L04-LO2:** choose geographic placement, replication, active-active/standby and failover rules from latency, staleness, egress, privacy and capacity constraints.

## Start with one origin and a cache contract

Assume a public product-catalogue site has 5 million **original image reads/day**, an average image of 250 KiB, and a hot logo fetched by 20% of requests. Average raw uncached bytes are about `5m × 250KiB ≈ 1.16 TiB/day`, but actual origin bytes depend on cache hit ratio and variant sizes. A globally distributed edge cache can reduce origin fetches and deliver from locations nearer users, at the cost of replication, purge propagation and per-region egress economics. These numbers are invented for this case.

The origin registers a canonical hostname and resource path. A CDN distribution selects an origin and maps incoming viewer URLs to cache behavior. For a fresh public hit, serve an authorized cached representation. For a miss or stale entry, fetch from the origin under declared TLS/authentication, cache the representation with the response's freshness rule and return to the client. The key includes the URL and every variation field that changes bytes or access (content encoding, safe locale/transform variant, appropriately handled authorization). A public edge cache should not accidentally store per-user financial data.

```text
Viewer -> CDN edge (DNS/routing)
       hit -> version/TTL and response-policy check -> client
       miss/stale -> configured origin fetch -> content / ETag
                         -> edge fill -> client
Origin storage metadata + object version = source of truth
```

HTTP caching semantics in RFC 9111 distinguish freshness, conditional validation and invalidation; a `304 Not Modified` on a conditional request can update an existing cached representation without resending its body. An HTTP `max-age` describes reuse under a cache policy; it does not promise that every client cache has received a global purge signal. [RFC 9111 §§4.2–4.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2).

## Origin protection is not viewer authorization

An origin should be reachable from the intended CDN/authorized application path, not publicly bypassable for content that requires controlled distribution. On AWS, **CloudFront Origin Access Control (OAC)** for supported private S3 bucket origins authenticates CloudFront's origin requests; OAC does not inspect business-level “is this viewer a member?” permissions. Dynamic private images require signed viewer capabilities with a documented lifetime, a policy-enforcing gateway or another explicit authorization scheme. Direct S3/public aliases must not bypass the promised gate. [CloudFront OAC](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

At deployment, the origin's public status and CDN behavior are different resources. Validate origin responses and headers, TLS certificate identities and health, cache `Vary` or cache-policy selection and supported methods. A CDN with correct edge TLS but plaintext or unauthenticated origin requests still has an unprotected hop. A private origin may also require allowing CDN service identities and disabling direct anonymous reads; never assume that merely setting a bucket name to “private” proves all routes are blocked.

For a mutable authenticated API response, a shared CDN cache may be inappropriate. Serving personalized JSON under a path-only cache key can disclose another user's result even when the origin did the original authorization check. Versioned public media is much easier to cache safely than frequently changed private policy data.

## Change an object without letting an old fill win

Object `/logo.png` at origin generation 8 contains blue logo bytes. At 10:00 an edge caches gen8 with TTL 60 seconds. At 10:10 the origin commits gen9 with green bytes, and a purge request for the old path begins propagating. A delayed origin read that started before gen9 may reach another edge **after** it processed the purge.

```text
10:00   edge E1 caches /logo.png version8, TTL=60s
10:10   origin stores version9 and marks it current
10:10:01 CDN purge begins; E2 processes purge for version8
10:10:02 delayed in-flight version8 fill arrives at E2
10:10:03 user requests current logo
```

A protocol that merely clears the cache at 10:10:01 but allows any later old fill to reenter the *current* cache key is unsafe for strict post-purge freshness. Options:

- **Versioned URLs:** publish `/logo.v9.png` in a metadata page and leave `/logo.v8.png` immutable. The new HTML/source cut names v9; old cached v8 can still exist but is not misrepresented as v9. It is the simplest path for public, immutable assets. CloudFront recommends versioned file names for frequent changes because external/browser caches may not honor CDN invalidation instantly. [CloudFront invalidation vs versioned files](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html).
- **Mutable path with conditional revalidation:** use ETags, bounded TTLs and CDN invalidation, and define a real permitted stale interval. A purge API acknowledgment is not automatically proof that *every external browser and corporate proxy* stopped serving old bytes.
- **Strict current-generation contract:** require an authoritative current-version check or an enforced generation barrier at the actual protected serving boundary; every fill must carry the version observed and be unable to republish an older generation as current. This costs latency and coordination, and is not a default CDN feature.

A deletion or privacy reversal is stronger than a cosmetic logo update. A presigned public link already issued may remain usable and bytes already downloaded cannot be retracted. The product must avoid promising instantaneous worldwide erasure without a revocable read gate and a carefully defined confirmation event.

## Add regions with explicit consistency rules

A CDN's many edges need not contain the durable authoritative business state. A global data-serving application chooses where original writes are accepted and which regional read copies may answer. Three common arrangements:

1. **Single writer, geographically distributed reads:** one primary region accepts mutations; replicas and edges serve allowed stale reads. Easier to preserve one write order, but a region failure may pause writes and remote reads can lag.
2. **Active/standby:** standby region is kept capable of takeover with an explicit source-cut/RPO proof and fenced write authority. The standby might need scaled capacity *before* takeover; promotion and DNS/traffic switch do not make missing data appear.
3. **Multi-writer/active-active:** regions accept concurrent writes under a chosen per-key conflict resolution or transaction protocol. A last-writer-wins timestamp policy may discard a user's write, so use it only when that loss is explicitly acceptable. Writes with global financial invariants may require regional ownership, quorum coordination or a database that documents the necessary consistency.

Do not equate “two regions” with independent failures if they share global identity, a control plane, a data replication pipeline or one DNS provider. An old region must be **fenced** from protected writes before the new owner begins writing, and retries after failover must preserve original operation IDs. The coordination details are taught in [M09-L03](../../m09/lessons/M09-L03.md).

For S3, replication can be asynchronous; its metrics report pending bytes, operations and failures. The optional S3 Replication Time Control has a **specified product scope**, not a promise that every S3 object exists immediately in every region. If a serving decision requires a version that has not replicated, return a correct not-yet-ready status or use an authoritative source rather than silently serving a prior version. [S3 replication metrics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/repl-metrics.html), [S3 Replication Time Control](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-time-control.html).

## Trace a regional outage during an origin update

Assume two application regions:
- Region A normally serves **6,000 QPS** and can sustainably serve **7,000 QPS** under the scenario's identical user/request mix.
- Region B normally serves **4,000 QPS** and can sustainably serve **5,000 QPS**.
- Together the offered traffic is **10,000 QPS** before any additional retries.
- A is the elected write authority; B holds an async copy of the object metadata. At 12:00 A stores logo generation 9, but B has only version8. At 12:00:02 region A fails. The global router can direct future clients to B.

Moving all 6,000 QPS onto B would require B to serve `4,000 + 6,000 = 10,000 QPS`, **twice its tested sustainable 5,000 QPS**. Correct routing and an available replica are not sufficient. The route switch must either keep warm additional capacity, admit only an explicit bounded subset with truthful error reporting, or meet a different SLO. Retrying rejected requests without coordination may double downstream load. A load test with B at 10,000 and real cache-miss fractions is required before claiming failover capacity.

B's metadata remains gen8. It cannot truthfully serve gen9 as “current” when it has not confirmed a source cut containing that version. It may serve a **clearly stale** public asset if the client contract permits, fetch from another authoritative replica, or fail until data is recovered. CDN edges that already hold gen8 may be technically reachable while business freshness is violated. A private-content deletion that has not replicated requires an authoritative denial path; a stale B permission replica cannot be treated as safe revocation proof.

A writes may have been acknowledged just before the crash. Promotion of B needs a clear recoverable point, and callers must distinguish a write timeout from definite non-application. A new writer epoch/fence prevents A's delayed update from corrupting accepted B history if A returns. Routing DNS records with health checks can move clients away from A, but cached resolver answers/connection lifetimes mean no single instant when all clients switch. AWS Route 53 describes TTL and health-based DNS failover; do not infer instantaneous transition. [Route 53 failover](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/dns-failover.html), [Route 53 DNS TTL best practices](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/best-practices-dns.html).

## Price latency, egress and origin pressure together

| Decision | Benefit | Cost and failure signal |
| --- | --- | --- |
| Long TTL for immutable public versions | Lower origin traffic and edge latency | Old references persist until manifest changes; no revocation by TTL alone |
| Short TTL / origin revalidation | Faster mutable-path updates | Higher origin QPS/egress, risk of overload during cache miss storm |
| Distributed read replicas | Closer reads and failover candidates | Cross-region replication lag, cost and source-cut evidence |
| Hot standby capacity | Safer failover under A loss | Pay for unused/warm capacity and ongoing tests |
| Active-active writes | Local write latency in both regions | Conflict/transaction semantics, increased coordination |
| Strict global current read | Strong freshness/disclosure proof | May require origin/generation gate and refuse reads under partition |

Optimize the **system**, not solely CDN hit ratio. An edge hit that returns an expired private image is a correctness failure. A low average latency among successful requests can improve while admission shedding destroys the original user-visible success fraction.

Define a synthetic client SLI: at least 99% of **all original valid image reads** in a five-minute edge-ingress cohort return the correct **permitted and advertised version** to the managed client within 250 ms, deduplicating retries and including wrong, stale, rejected, failed, timed-out and late responses in denominator. Separately record the *fraction of public requests* whose source cut meets the product's freshness budget and the *fraction of failover attempts* with surviving application+database capacity. During privacy revocation, use a separate zero-leak safety invariant; never mask a private disclosure by a healthy average.

Falsify by delayed old cache fill after version9, deleting an object while edges still have old snippets, failing A with B already at 4k QPS, losing replica progress, briefly restarting A while B is writer, and disabling shared identity/DNS dependencies. Inspect original request client receipt, routed region, manifest generation, permission checks, replica cut, resource saturation and accepted writes—not just the edge's green status.
