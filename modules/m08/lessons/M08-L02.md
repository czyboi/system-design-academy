# Streaming aggregation, trends and top-k

A marketplace wants its most requested products for each hour while that hour is still underway. The batch approach in M08-L01 can recompute a completed hour from an archived snapshot. A continuously updated result responds sooner, but must decide which hour owns a delayed request, when to stop revising the result and how long to retain identity and count state.

- **M08-L02-LO1.** Trace event-time aggregation, duplicate and late-event handling, and ranking in a worked scenario.
- **M08-L02-LO2.** Choose and defend processing, ranking accuracy and recovery policies against stated freshness and resource constraints.

## Update an hourly result

Each request has a stable globally unique event ID, product ID and immutable event timestamp. A retry carries the same ID and payload. A different request has a different ID. The service counts one unit per event. For this example all times are UTC and the event-time hour is `[10:00, 11:00)`, including 10:00 and excluding 11:00. The following durable-intake-time rule is an explicit application contract, with a serialized intake per hour and a trusted intake clock.

- Publish provisional counts after each newly accepted event. At 11:00 publish the current ranking as provisional, even if no new event arrived at that instant.
- Atomically append each arrival to durable intake with a sequence, first durable intake time and live-or-correction classification. An arrival durably admitted before 11:05 is live-eligible, including one processed after recovery. The close transition at 11:05 is serialized with admissions, so an arrival at exactly 11:05 is a correction. During an intake outage, an uncommitted arrival receives no earlier eligibility merely because a client sent it earlier.
- Repeated IDs with the same payload do not increment the count. A conflicting payload for an existing ID is quarantined for investigation. Process the live sequence through the durable close barrier before publishing a final live result. The barrier marks the admission cutoff, not a guaranteed publication time during a failure. Retire counts and seen-ID state only after final publication is durably confirmed. An independently retained authoritative archive contains all admitted original and correction records, including IDs, through each published archive cut.

| First durable intake time | Event `(ID, event time, product)` | Live count and output for the hour in the no-failure run |
| --- | --- | --- |
| 10:03 | `(e1, 10:02, pen)` | pen 1, pencil 0, provisional |
| 10:50 | `(e2, 10:49, pencil)` | pen 1, pencil 1, provisional |
| 10:58 | `(e3, 10:57, pen)` | pen 2, pencil 1, provisional, pen leads |
| 11:00 | Timer | pen 2, pencil 1, provisional |
| 11:02 | retry of `e1` | pen 2, pencil 1, unchanged |
| 11:03 | `(e4, 10:54, pencil)` | pen 2, pencil 2, revised provisional tie |
| 11:05 | Durable close barrier, then drain | pen 2, pencil 2, final live version |
| 11:06 | `(e5, 10:30, pencil)` | routed to correction stream, live result unchanged |

The 11:03 arrival belongs to the earlier hour because its **event time** is 10:54. Its durable intake time decides live eligibility. For a top-one result, use product ID ascending to break ties. Pen leads before e4 and remains first in the tie because `pen` sorts before `pencil`. Final means the service has drained all live-eligible intake through the close barrier and stopped adding new IDs to that live version. It does not mean every event has arrived.

Consider a crash immediately after e4's 11:03 admission but before its count commits. Intake retained its sequence and live classification. On recovery after 11:05, the processor reuses that classification, processes e4 before the already recorded close barrier and finalizes pen 2, pencil 2. The processor commits progress, dedup state, counts and an output intent atomically in one durable transaction, or uses an equivalent recoverable protocol. It retries the intent idempotently, so a crash between state commit and external publication neither drops nor increments e4 twice. A close observed before that drain cannot publish a final result. This transaction and barrier are assumptions of the design, not automatic guarantees of a processing engine.

For repair, assume the archive exposes immutable, complete and nested cuts of its ordered records. Each cut includes every admitted live record through the close barrier and all corrections through its declared archive position. A coordinator durably assigns each distinct cut one revision in increasing cut order **before** computation. A retry reuses that cut and revision. It starts repair only from a cut that is confirmed complete and includes the close barrier. Repair deduplicates all records in the cut by ID and resolves conflicts before publishing a full replacement. For cut A through e5, the corrected result is pen 2, pencil 3. Suppose a later cut B also includes e6, another pen request, yielding pen 3, pencil 3. B receives revision 2 after A receives revision 1. If B finishes and publishes first, the sink atomically accepts its replacement and rejects A's later revision 1. A same-cut retry uses the same revision and payload, so it has no additional effect. A conflicting same-revision payload is rejected and investigated.

The sink orders provisional live updates within a live generation, makes final live publication idempotent, and ranks any accepted correction above live writes for that hour. A late live or final retry therefore cannot overwrite an accepted correction. A visible `corrected` status distinguishes repair from the final live result. These ordering rules require the archive cuts to be complete and nested, and the source to retain all records needed by each cut. Replaying increments into the live total would count retries again.

Event-time windows decide membership. A trigger decides when to publish. A heuristic watermark estimates event-time progress and can help govern when a system closes or cleans up a window, but it does not prove that all earlier events have arrived. A perfect watermark can have a stronger guarantee when source knowledge supports it. The fixed intake-time cutoff above is a separate scenario policy and is not a claimed watermark implementation. [Akidau et al., The Dataflow Model, §§2.1–2.3 and 3.1](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf#page=2).

Keeping counts per product and seen IDs until the cutoff costs memory proportional to active product keys and unique accepted IDs. A longer cutoff admits more delayed events into live results but retains state longer. If source retries can recur after that horizon, route them through the same ID-aware correction process. Checkpointing a processor's progress addresses reprocessing, while a repeated business event under a new source offset still needs event-ID deduplication. Spark 4.0.1 documents watermark-bounded deduplication with a bounded guarantee. Its replay and output semantics depend on the source and sink. [Spark Structured Streaming, streaming deduplication](https://spark.apache.org/docs/4.0.1/streaming/apis-on-dataframes-and-datasets.html#streaming-deduplication), [Spark fault tolerance](https://spark.apache.org/docs/4.0.1/streaming/getting-started.html#fault-tolerance-semantics).

## Rank exact counts or bound the memory

An exact top-k keeps an exact count for each distinct product in the window and ranks those counts. It can resolve a close tie, provided accepted events have been deduplicated. Its state grows with the number of distinct products. A fixed-size summary bounds its counter state but may leave close ranks uncertain.

Consider the Space-Saving summary for one whole window of insert-only unit events, with two counters. When an observed item already has a counter, increment it. When a free counter exists, start at count 1 and error 0. When full and an untracked item arrives, replace a minimum counter with the new item, set its estimate to that minimum plus 1, and record the old minimum as its error. Break a tie between minimum counters alphabetically for this example. The true frequency of a retained item lies between estimate minus recorded error and estimate.

| Input so far | Counter state `(item, estimate, error)` |
| --- | --- |
| A | `(A, 1, 0)` |
| A, B | `(A, 1, 0)`, `(B, 1, 0)` |
| A, B, A | `(A, 2, 0)`, `(B, 1, 0)` |
| A, B, A, C | `(A, 2, 0)`, `(C, 2, 1)` |

C replaced B's minimum. A is known to have count 2, while C has a bound of 1 through 2. The summary cannot establish whether C ties A or trails it, even though the exact sequence gives C 1. A is first under an ascending-ID tie-break, but the summary does not establish a strictly greatest frequency. Retrieve exact counts when that distinction matters. One summary here represents the complete window. Arbitrary removal of expired events and merging separately truncated shard rankings need additional algorithms and guarantees. [Metwally, Agrawal and El Abbadi, Efficient Computation of Frequent and Top-k Elements, increment-counters algorithm](https://www.cs.emory.edu/~cheung/Courses/584/Syllabus/papers/Frequency-count/2005-Metwally-Top-k-elements.pdf).

## Measure popularity and change separately

Top-k by count identifies the largest request volumes in the chosen window. A trend compares current volume with a stated baseline. Suppose topic Harbor has 100 requests this hour versus an average of 80 in comparable prior hours. Topic Kite has 20 versus a baseline of 4. Harbor is more popular this hour, while Kite grew fivefold versus Harbor's 1.25-fold. A policy might require at least 10 current requests before applying `current / baseline`, and handle a zero baseline as a separate new-topic case. The threshold, baseline period and zero rule are product choices. They affect which small bursts are displayed and should accompany the ranking.

## Match recovery to the processing system

In Storm Core 2.8.1, a spout emits a source event as a root tuple, and bolts process tuples and can emit derived tuples. For example, a spout emits e4, a parsing bolt emits an anchored `(pencil, 1)` child, and a counting bolt applies that child. Anchoring links the child to e4's root. The bolts acknowledge their processed tuples. Storm considers the root fully processed only after its anchored descendants have also been acknowledged. If a descendant fails or the tree times out, the root fails and Storm notifies the spout. A reliable spout must retain or recover the root and re-emit it on failure to provide at-least-once processing. If the counting bolt wrote an external effect before failure, replay can write it again unless the sink has an idempotent or transactional contract. The event-ID and revision policy above is an application design, not a default guarantee of every Storm topology. [Storm 2.8.1, Guaranteeing Message Processing](https://storm.apache.org/releases/2.8.1/Guaranteeing-message-processing.html).

Spark Structured Streaming 4.0.1 can process a stream as incremental micro-batches, checkpoint progress and recover using replayable sources and compatible sinks. The source, sink and output mode determine the supported end-to-end effect. A checkpoint cannot deduplicate two separately delivered source records that represent the same business request without an appropriate ID rule. Choose an implementation after specifying the event-time cutoff, acceptable correction delay, source retention, state budget and sink behavior. The two systems expose different processing and recovery boundaries, so the chosen source and sink must satisfy the application's own contract. [Spark 4.0.1, Structured Streaming programming model and fault tolerance](https://spark.apache.org/docs/4.0.1/streaming/getting-started.html#fault-tolerance-semantics).
