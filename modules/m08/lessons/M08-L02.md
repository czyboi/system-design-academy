# Streaming aggregation, trends and top-k

A marketplace wants its most requested products for each hour while that hour is still underway. The batch approach in M08-L01 can recompute a completed hour from an archived snapshot. A continuously updated result responds sooner, but must decide which hour owns a delayed request, when to stop revising the result and how long to retain identity and count state.

- **M08-L02-LO1.** Trace event-time aggregation, duplicate and late-event handling, and ranking in a worked scenario.
- **M08-L02-LO2.** Choose and defend processing, ranking accuracy and recovery policies against stated freshness and resource constraints.

## Update an hourly result

Each accepted request has a stable globally unique event ID, product ID and immutable event timestamp. A retry carries the same ID and payload. A different request has a different ID. The service counts one unit per event. For this example all times are UTC and the event-time hour is `[10:00, 11:00)`, including 10:00 and excluding 11:00. The following processing-time rule is an explicit application choice.

- Publish provisional counts after each newly accepted event. At 11:00 publish the current ranking as provisional, even if no new event arrived at that instant.
- Accept new unique IDs for the hour only if processed before 11:05. Repeated IDs with the same payload do not increment the count. A conflicting payload for an existing ID is quarantined for investigation.
- At 11:05 publish a final live result, discard that hour's live counts and seen-ID state, and send later arrivals to a correction stream. The retained source independently archives all original and correction events, including their IDs, long enough to support repair.

| Processing time | Event `(ID, event time, product)` | Live count and output for the hour |
| --- | --- | --- |
| 10:03 | `(e1, 10:02, pen)` | pen 1, pencil 0, provisional |
| 10:50 | `(e2, 10:49, pencil)` | pen 1, pencil 1, provisional |
| 10:58 | `(e3, 10:57, pen)` | pen 2, pencil 1, provisional, pen leads |
| 11:00 | Timer | pen 2, pencil 1, provisional |
| 11:02 | retry of `e1` | pen 2, pencil 1, unchanged |
| 11:03 | `(e4, 10:54, pencil)` | pen 2, pencil 2, revised provisional tie |
| 11:05 | Timer | pen 2, pencil 2, final live version |
| 11:06 | `(e5, 10:30, pencil)` | routed to correction stream, live result unchanged |

The 11:03 arrival belongs to the earlier hour because its **event time** is 10:54. The processing time decides whether this example still accepts it. For a top-one result, use product ID ascending to break ties. Pen leads before e4 and remains first in the tie because `pen` sorts before `pencil`. At 11:05, final means the live service has stopped accepting new IDs into that version. It does not mean every event has arrived.

A repair job can read the archived source including e5, deduplicate all records by event ID and replace the hour's result with a higher authoritative revision, now pen 2 and pencil 3. A durable coordinator assigns a monotonically increasing revision per hour, and the sink atomically accepts only a higher revision for that hour. This prevents a delayed older repair from overwriting a newer result. The source must retain all original events and corrections needed for that repair, and ID conflicts must be resolved before a trustworthy replacement is published. A visible `corrected` status distinguishes this later revision from the final live result. Replaying increments into the live total without deduplication would count retries again.

Event-time windows decide membership. A trigger decides when to publish. A watermark estimates event-time progress and can help govern when a system closes or cleans up a window, but it cannot prove that all earlier events have arrived. The fixed clock cutoff above is a deliberately simpler scenario policy and is not a claimed watermark implementation. [Akidau et al., The Dataflow Model, §§2.1–2.3](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf#page=2).

Keeping counts per product and seen IDs until the cutoff costs memory proportional to active product keys and unique accepted IDs. A longer cutoff admits more delayed events into live results but retains state longer. If source retries can recur after that horizon, route them through the same ID-aware correction process. Checkpointing a processor's progress addresses reprocessing, while a repeated business event under a new source offset still needs event-ID deduplication. Spark 4.0.1 documents watermark-bounded deduplication with a bounded guarantee. Its replay and output semantics depend on the source and sink. [Spark Structured Streaming, streaming deduplication](https://spark.apache.org/docs/4.0.1/streaming/apis-on-dataframes-and-datasets.html#streaming-deduplication), [Spark fault tolerance](https://spark.apache.org/docs/4.0.1/streaming/getting-started.html#fault-tolerance-semantics).

## Rank exact counts or bound the memory

An exact top-k keeps an exact count for each distinct product in the window and ranks those counts. It can resolve a close tie, provided accepted events have been deduplicated. Its state grows with the number of distinct products. A fixed-size summary bounds its counter state but may leave close ranks uncertain.

Consider the Space-Saving summary for one whole window of insert-only unit events, with two counters. When an observed item already has a counter, increment it. When a free counter exists, start at count 1 and error 0. When full and an untracked item arrives, replace a minimum counter with the new item, set its estimate to that minimum plus 1, and record the old minimum as its error. Break a tie between minimum counters alphabetically for this example. The true frequency of a retained item lies between estimate minus recorded error and estimate.

| Input so far | Counter state `(item, estimate, error)` |
| --- | --- |
| A | `(A, 1, 0)` |
| A, B | `(A, 1, 0)`, `(B, 1, 0)` |
| A, B, A | `(A, 2, 0)`, `(B, 1, 0)` |
| A, B, A, C | `(A, 2, 0)`, `(C, 2, 1)` |

C replaced B's minimum. A is known to have count 2, while C has a bound of 1 through 2. The summary cannot establish whether C ties A or trails it, even though the exact sequence gives C 1. Treat the tie as uncertain and retrieve exact counts when the decision requires a definitive order. One summary here represents the complete window. Arbitrary removal of expired events and merging separately truncated shard rankings need additional algorithms and guarantees. [Metwally, Agrawal and El Abbadi, Efficient Computation of Frequent and Top-k Elements, increment-counters algorithm](https://www.cs.emory.edu/~cheung/Courses/584/Syllabus/papers/Frequency-count/2005-Metwally-Top-k-elements.pdf).

## Measure popularity and change separately

Top-k by count identifies the largest request volumes in the chosen window. A trend compares current volume with a stated baseline. Suppose topic Harbor has 100 requests this hour versus an average of 80 in comparable prior hours. Topic Kite has 20 versus a baseline of 4. Harbor is more popular this hour, while Kite grew fivefold versus Harbor's 1.25-fold. A policy might require at least 10 current requests before applying `current / baseline`, and handle a zero baseline as a separate new-topic case. The threshold, baseline period and zero rule are product choices. They affect which small bursts are displayed and should accompany the ranking.

## Match recovery to the processing system

Storm Core 2.8.1 represents processing as tuples flowing through spouts and bolts. With correctly anchored tuple trees and acknowledgements, Storm can track when a root is fully processed and notify the spout of success or failure. A reliable spout must retain or recover the root and re-emit on failure for the at-least-once contract. A failed attempt may have already written an external effect, so the sink still needs idempotent or transactional handling. The event-ID and revision policy above is an application design, not a default guarantee of every Storm topology. [Storm 2.8.1, Guaranteeing Message Processing](https://storm.apache.org/releases/2.8.1/Guaranteeing-message-processing.html).

Spark Structured Streaming 4.0.1 can process a stream as incremental micro-batches, checkpoint progress and recover using replayable sources and compatible sinks. The source, sink and output mode determine the supported end-to-end effect. A checkpoint cannot deduplicate two separately delivered source records that represent the same business request without an appropriate ID rule. Choose an implementation after specifying the event-time cutoff, acceptable correction delay, source retention, state budget and sink behavior. The two systems expose different processing and recovery boundaries, so the chosen source and sink must satisfy the application's own contract. [Spark 4.0.1, Structured Streaming programming model and fault tolerance](https://spark.apache.org/docs/4.0.1/streaming/getting-started.html#fault-tolerance-semantics).
