# Indexes and scatter-gather search

A catalogue holds more descriptions than one server can scan for every query. Users need matching documents in a useful order even as catalogue edits arrive. An index makes candidate lookup cheaper, while splitting the index across servers adds a decision about slow or unavailable shards. An answer can be complete across responding shards and still omit a recent source edit.

- **M08-L03-LO1.** Trace analysis, lookup, sharded ranking and index updates through a worked search.
- **M08-L03-LO2.** Defend partitioning, deadline and repair choices using relevance, completeness, freshness and cost.

## Find candidates from terms

A document store maps an ID to the original searchable content and fields. A forward representation can list terms per document. An inverted index instead maps each term to a posting list of document IDs, optionally with field and frequency information. For a two-term AND query, intersect the term lists to find eligible IDs, then score the candidates and retrieve the requested fields. OR takes the union instead. Authorization and other filters must be applied consistently before returning a candidate.

Assume a toy analyzer splits on spaces and lowercases ASCII letters at both indexing and query time. It turns `Blue MUG` into `blue`, `mug`. If an index analyzer and a query analyzer produce incompatible terms, a relevant document may never become a candidate. Real analyzers may use token filters and language-specific rules, so choose and test the pair together. Elasticsearch 8.19 describes its own analyzer components and boolean query clauses. [Elasticsearch 8.19 text analysis](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/analysis.html), [boolean query](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/query-dsl-bool-query.html).

## Trace a search across three shards

Assume the current searchable snapshot contains the following documents. Each ID is owned by exactly one document shard. Each occurrence contributes one point and every shard uses the same formula, score descending, then ID ascending for ties. This deliberately simple score makes the ordering reproducible. Production ranking may use field weights, frequency and other signals, which must be comparable across the merged candidates.

| Shard | Documents and normalized terms | Postings relevant to `blue mug` |
| --- | --- | --- |
| A | `d1: blue mug`, `d2: blue blue mug` | `blue → {d1,d2}`, `mug → {d1,d2}` |
| B | `d3: blue mug mug`, `d4: blue plate` | `blue → {d3,d4}`, `mug → {d3}` |
| C | `d5: blue blue blue mug` | `blue → {d5}`, `mug → {d5}` |

The coordinator analyzes `BLUE mug`, scatters the same AND query and `k=2` to A, B and C, and merges the local top two under the shared order. A intersects its postings and returns `d2:3, d1:2`. B returns `d3:3`. C would return `d5:4`. If all respond, the global top two are `d5:4, d2:3`. The ID tie-break puts `d2` before `d3`.

Suppose A and B respond within a 100 ms shard budget and C times out. With an explicit partial-results policy, the coordinator returns `d2:3, d3:3`, labelled incomplete with C identified as missing. It cannot say those are the global top two or that there are no other matches. Under a full-results policy, it returns an error when the budget expires and exposes no search result as complete. A request deadline must reserve time for coordinator merge and network response as well as shard work. Elasticsearch 8.19 documents a choice to allow partial results on shard timeout or failure. [Search API](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/search-search.html#search-search-api-query-params).

With disjoint shards, identical eligibility and a single total order, asking each shard for its local top `k` is sufficient for the global top `k`. Any omitted document has at least `k` documents ahead of it on its own shard, so it cannot enter the global top `k`. This inference fails if the coordinator changes ordering with a later reranker, removes duplicates, or uses incompatible local scoring. In Elasticsearch 8.19, `query_then_fetch` uses local term and document frequencies, while `dfs_query_then_fetch` gathers global frequencies at additional request cost. Select a scoring contract rather than assuming independently calculated scores have identical meaning. [Elasticsearch 8.19 search types](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/search-search.html#search-search-api-query-params).

## Choose the work and failure boundary

Document sharding puts each document's postings on its owner shard. A general query may fan out to all owners, so more shards can increase parallelism and coordination cost. A term-partitioned index instead groups postings by term. It can target queried terms, but a multi-term query must combine the selected term partitions and deal with large or hot posting lists. Choose based on query distribution, skew, update path and expected fan-out, rather than shard count alone.

An all-shard response waits for the slowest required shard. A timeout bounds waiting but leaves unknown results. A bounded hedge sends a duplicate read to another eligible replica after a delay. An eligible replica serves the same logical shard, requested generation and read view under the same scoring contract. The coordinator accepts at most one compatible response per logical shard. A replica unable to serve that view is unavailable for this request. A hedge consumes extra capacity, should be limited and cancelled when no longer needed, and can worsen a shared overload. Latency events can be correlated across shards sharing a network or storage dependency, so independent-shard probability calculations require an explicit model and cannot establish the real tail. [Dean and Barroso, *The Tail at Scale*](https://barroso.org/publications/TheTailAtScale.pdf).

Choose partial results when the user can act on a clearly labelled incomplete answer and accepts missed matches. Choose full results when omitted matches would make the decision unsafe. Monitor missing-shard rate and the original requests that meet the chosen contract. For example, over one hour count every original valid search once from arrival at the service to a complete response received by the client within 200 ms. An illustrative target is 99%. Rejected, failed, timed-out, late and partial responses count against that complete-response target, even if a partial response is useful. Record partial-result rate and successful-response latency separately. The target and budget are example design choices, not product guarantees.

## Keep the index current and repairable

The source of truth commits catalogue edits and emits durable change intent. An asynchronous indexer applies them to a search projection. Index receipt, durable application and query visibility are separate boundaries. In Elasticsearch 8.19 a refresh makes indexed operations searchable, so a successful write may precede visibility. A complete response across all shards can therefore still be stale. Conversely, a fresh responding shard cannot establish completeness when another shard timed out. Measure source-commit-to-search-visibility lag and shard completeness separately. [Elasticsearch 8.19 near-real-time search](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/near-real-time.html).

Use the full-value version and retained-log contract from [M07-L03](../../m07/lessons/M07-L03.md) to repair a lost projection. Capture and protect a consumer-readable end position per partition before taking a consistent source snapshot. Build a separate generation from the snapshot, including durable deletion revision markers, then replay from those earlier positions. The relay publishes committed changes only, and each full replacement carries a monotonic source revision. A conditional apply preserves the newest revision, so overlap and repeated records cannot resurrect a deleted document. Retain the continuation throughout the rebuild. Deltas need additional ordering and gap handling.

Before cutover, fence old generation writers at the index store and settle writes already admitted. Capture an exclusive log-end barrier for each partition after the fence, assuming all old-generation served effects came from that log. The new generation must durably process all required records before each barrier position. It must then make those effects visible through the actual search path on every required shard and every replica eligible to serve the new generation. For example, if the old generation already made D's deletion at offset 42 searchable, a replacement that applied the deletion durably but still has an older search reader could return D after a switch. Wait until that reader exposes the deletion, verify the search path and readiness on all required shards, and keep the old generation active if a required reader cannot establish the boundary. In Elasticsearch 8.19, a successful refresh after application can make operations searchable, followed by application readiness checks on the actual serving path. [Elasticsearch 8.19 near-real-time search](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/near-real-time.html).

Once the replacement passes these checks, atomically switch the read alias. Each request resolves and pins one generation and its expected logical shard set for query and document fetches, including retries and hedges. Requests already pinned to the old generation finish against that generation or fail according to their deadline. This avoids combining generations during a switch and makes a missing required shard visible to the completeness policy. Keep the replacement's own checkpoint and continue processing after the switch. If the protected continuation is lost, restart from a new protected snapshot and continuation instead of silently advancing. These are application-level conditions, with ordering and fencing details explained in M07-L03.

The post-fence log barrier prevents regression of effects already visible in the old generation under these assumptions. It does not cover every source commit. A delete committed after the snapshot may still be waiting in the outbox when the barrier is captured, leaving D visible in both generations until the relay and indexer catch up. To guarantee visibility through a chosen source cut, establish a source-side cut and prove the relay has published every relevant committed change through it before capturing the log barrier. Then apply and expose that barrier on every eligible search reader before cutover. Alternatively, an authoritative read-time policy can enforce a separately defined freshness boundary. A wall-clock wait or the fact of source commit alone proves neither relay publication nor search visibility. [AWS transactional outbox, issues and considerations](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#issues-and-considerations).

For a small dataset, a database query can be simpler if its latency and search capabilities meet the workload. Add sharded retrieval when measured needs justify index maintenance, routing, repair and partial-result policy. The scoring example and operational targets above are illustrative assumptions.
