# MapReduce and distributed file storage

A marketplace wants a daily ranking of product categories by units sold. The input is a closed, replayable snapshot of individual sale records. A single database aggregation may be sufficient while it meets the deadline. When the scan exceeds one machine's practical resources, splitting the scan lets workers process separate input ranges, but matching categories must be brought together before a correct total can be calculated. A second ordering step is needed to rank those totals across categories.

- **M08-L01-LO1.** Trace the map, partition, shuffle, reduce, retry and storage mechanisms in a worked batch.
- **M08-L01-LO2.** Choose and defend a processing and storage approach using workload, failure and resource trade-offs.

## Trace a category from input to ranked output

Assume each source record has a unique sale ID, one category and a nonnegative integer quantity. The snapshot contains each sale once and does not change during the run. It is split into two mapper inputs. These small records stand in for a much larger scan.

| Input split | Sales `(ID, category, units)` | Mapper output `(category, units)` |
| --- | --- | --- |
| A | `(s1, Books, 2)`, `(s2, Games, 4)` | `(Books, 2)`, `(Games, 4)` |
| B | `(s3, Books, 3)`, `(s4, Tools, 4)` | `(Books, 3)`, `(Tools, 4)` |

**Job 1 groups and sums.** Each map task emits one pair per record. The partitioner assigns all pairs with the same category to the same reducer. For this example the mapping sends Books and Tools to reducer R0 and Games to R1. During the shuffle, each reducer fetches its partition from every completed map output. The framework sorts and groups the received keys so the reducer sees a category and its values together. R0 receives `Books: [2, 3]` and `Tools: [4]`, then writes `(Books, 5)` and `(Tools, 4)`. R1 writes `(Games, 4)`. Sorting the keys within each reducer does not order the totals across reducers. [Dean and Ghemawat, MapReduce, §§2.1 and 3.1](https://www.usenix.org/legacy/publications/library/proceedings/osdi04/tech/full_papers/dean/dean_html/).

**Job 2 ranks completed totals.** Its map reads each category total and emits `((-total, category), category)`. The negative total gives descending numeric order in an ascending composite-key sort, and category breaks ties consistently. For two ordered range partitions, choose an assumed boundary `(-4, "M")`. Keys before the boundary go to R0 and the rest to R1. R0 receives `(-5, Books)` and `(-4, Games)`, and R1 receives `(-4, Tools)`. Each reducer writes its sorted keys in order. Reading R0's file followed by R1's file yields Books 5, Games 4, Tools 4. The partition ranges must be non-overlapping, cover all keys, and use the same comparator as the reducers. Hash-partitioned files, or range files read in arbitrary order, do not supply this global order. A single reducer is a simpler option for a small number of category totals, at the cost of one sorting bottleneck. [Dean and Ghemawat, MapReduce, §§4.1 and 5.3](https://www.usenix.org/legacy/publications/library/proceedings/osdi04/tech/full_papers/dean/dean_html/).

## Make retry outputs safe

Suppose the worker holding split A's intermediate output dies after completing its map. The scheduler reruns that input and reducers obtain the selected replacement output. Under the example's contract, each attempt writes private files and the coordinator selects one successful output per logical map task. Reducers use one selected output for each input split. If a selected map output disappears while a reducer is running, the affected reducer must discard or replace the lost attempt's contribution before it can publish a correct result. For Books, the successful inputs remain 2 from A and 3 from B, so the total is 5 rather than 7. Reducers similarly write attempt-scoped results and publish one winning output per logical task. The original MapReduce implementation used atomic rename for its reduce output and re-executed maps whose local output was lost. [Dean and Ghemawat, MapReduce, §3.3](https://www.usenix.org/legacy/publications/library/proceedings/osdi04/tech/full_papers/dean/dean_html/).

This contract assumes deterministic map and reduce functions, stable input and a publication mechanism that enforces one chosen result. A duplicate sale already present in the source would still be counted twice. Likewise, a reducer that charges a customer as a side effect needs its own idempotency or transactional protocol. Selecting a file does not undo an external effect. M07-L03 describes replay-safe effects when processing retained logs.

## Place work near data and address skew

If a worker can read split A from a replica on its own host, the initial scan can avoid transferring those bytes across the network. The scheduler may instead use another host when local capacity is busy or unavailable. Intermediate values still cross the network during shuffle. For summation, a mapper can locally combine several Books values into a partial sum before sending it. This reduces intermediate traffic when a split contains repeated categories, while the reducer still adds all partials. The combining function must preserve the final result under repeated or absent combining. [Dean and Ghemawat, MapReduce, §§3.4 and 4.3](https://www.usenix.org/legacy/publications/library/proceedings/osdi04/tech/full_papers/dean/dean_html/).

Now assume Books accounts for most sales. Sending every Books pair to one reducer makes that reducer a long-running bottleneck even if other reducers are idle. One remedy for an associative sum is to assign records to deterministic salted keys such as `(Books, 0)` and `(Books, 1)`, sum each independently, then run a second aggregation that removes the salt and sums those partial totals. This adds a stage and more intermediate data. Its benefit depends on whether the first stage's work was actually dominated by that key. The subsequent ranking job still operates on the final category totals. For non-decomposable computations, splitting requires a different correct merge rule.

## Store inputs as replicated blocks

In the published 2003 Google File System design, a master kept the namespace and the mapping from files to chunks and replica locations. Chunkservers stored the replicated chunk data. A client obtained metadata from the master and transferred data directly with a chunkserver. A different replica could serve a read after a chunkserver failure, subject to available metadata and surviving replicas. This is the historical design, not a claim about today's internal Google storage. [Ghemawat, Gobioff and Leung, The Google File System, §§2.3–2.6](https://web.mit.edu/6.1800/www/readings/papers/gfs.pdf#page=2).

In Apache Hadoop 3.4.2 HDFS, the NameNode manages namespace and block mapping, while DataNodes store and serve blocks. Heartbeats and block reports inform the NameNode, which can initiate re-replication when a replica is lost. Replicas make multiple read locations possible, but data replication alone does not establish metadata-plane availability. The design must also provision and recover that control plane. [HDFS Architecture, NameNode and DataNodes and Robustness](https://hadoop.apache.org/docs/r3.4.2/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html#NameNode_and_DataNodes).

## Choose a processing model

For a large one-pass, replayable snapshot with a relaxed completion deadline, a MapReduce-style batch makes independent map work, shuffle and durable result publication explicit. Compare the scan volume, network shuffle, hot-key distribution and operational overhead against a database aggregation that already meets the workload. A small result set may justify a single sorting reducer even when the input scan is distributed.

For repeated analysis over the same intermediate data, Spark's RDD model offers persisted partitions that can be reused and reconstructed from their transformation lineage after loss. Persistence consumes resources and may require recomputation or storage reads when partitions are unavailable. Spark can also shuffle for wide dependencies, so an iterative job's choice depends on actual reuse, memory pressure and recovery cost. The cited RDD paper describes that model and its trade-offs, not a guarantee that every Spark workload stays in memory. [Zaharia et al., Resilient Distributed Datasets, §§2–4](https://www.usenix.org/system/files/conference/nsdi12/nsdi12-final138.pdf).
