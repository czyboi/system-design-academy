# Source evidence for M08-L01

Checked 2026-11-15. The sample product data, job contract and calculations are original. References support the mechanisms, and sample workload sizes are assumptions.

| Claim | Primary evidence and scope | Verification and limits |
| --- | --- | --- |
| C1. A mapper emits key-value pairs. The partitioner directs each intermediate key to a reducer, which gathers mapper partitions, sorts/groups keys and receives each group's values. Range partitioning can support a global sort if partition boundaries and the final output order follow the same sort order. | Dean and Ghemawat, Google, OSDI 2004 [MapReduce, §§2.1, 3.1 and 4.1 and §5.3 Sort](https://www.usenix.org/legacy/publications/library/proceedings/osdi04/tech/full_papers/dean/dean_html/). | Verified for the original implementation. For the two-job example, job 1 groups by category and job 2 orders completed totals by a deterministic composite key. Global order across files requires reading the range partitions in order. |
| C2. Worker loss can rerun tasks, including completed maps whose output was on the lost worker. The original design accepts one map completion and publishes reduce output with atomic rename. | Dean and Ghemawat [MapReduce, §3.3 Fault Tolerance](https://www.usenix.org/legacy/publications/library/proceedings/osdi04/tech/full_papers/dean/dean_html/). | Verified for deterministic operators and the published historical implementation. Teach attempt-scoped staging and a single selected output identity as a design contract. External effects, duplicate source records and non-deterministic work need separate semantics. |
| C3. Input locality can save network reads. Local partial aggregation can reduce shuffle for a decomposable operation. A single hot key cannot be spread over the same key partitioning rule merely by adding workers. | Dean and Ghemawat [MapReduce, §§3.4 Locality, 4.1 Partitioning Function and 4.3 Combiner Function](https://www.usenix.org/legacy/publications/library/proceedings/osdi04/tech/full_papers/dean/dean_html/). | Verified for the mechanisms. Splitting a hot category into explicit salted subkeys and recombining their sums is an example-derived inference. Locality does not remove shuffle or guarantee slots are available on a replica host. |
| C4. GFS separated metadata at a master from data on replicated chunkservers, and clients transferred bytes directly with chunkservers. | Ghemawat, Gobioff and Leung, Google, SOSP 2003 [The Google File System, §§2.3–2.6 and 4.3](https://web.mit.edu/6.1800/www/readings/papers/gfs.pdf#page=2). | Verified historical architecture. The MIT link hosts the authors' original paper. No current Google service or benchmark claim follows. |
| C5. HDFS NameNode manages the filesystem namespace and block mapping. DataNodes serve bytes and store blocks. Heartbeats, block reports and re-replication address node/data loss. | Apache Hadoop 3.4.2 [HDFS Architecture, NameNode and DataNodes, Data Replication and Robustness](https://hadoop.apache.org/docs/r3.4.2/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html#NameNode_and_DataNodes). | Verified for the pinned documentation. A replica of bytes offers a read location and does not guarantee metadata-plane availability. |
| C6. Spark's RDD model retains reusable partitions via persistence and can reconstruct lost partitions from lineage. Wide dependencies can require shuffle. | Zaharia et al., UC Berkeley, NSDI 2012 [Resilient Distributed Datasets, §§2.1, 3.1 and 4.3](https://www.usenix.org/system/files/conference/nsdi12/nsdi12-final138.pdf). | Verified for the original RDD model. Persistence depends on configuration and storage level. Avoid claiming Spark is memory-only or never shuffles. The suggested engine choice is workload-dependent. |
