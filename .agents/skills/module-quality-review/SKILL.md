# Automatic per-lesson QA and final module synthesis (parent orchestrator)

Standing user authorization: run independent **Technical + provenance** and **Pedagogy + curriculum coverage** reviews **immediately after each completed lesson draft handoff**; separately review module-wide integration/consistency at module close, without repeating individual lesson audits. Automatically correct actionable findings with limited, targeted re-review. Do **not** modify agent profiles, specs, approved curriculum or skills to fix content. Do not publish/merge; the first review is round 0. The limits are **two corrections per lesson** and separately **two module-synthesis corrections per module**.

## Stage A — Mandatory review immediately after each lesson

1. Identify the lesson ID (e.g. `M01-L02`), approved Story/outcomes and canonical evidence, lesson and assessment paths. Start after this lesson's scoped validation/Git handoff; **never wait for other lessons or the integrated Story**. For an existing unreviewed draft, run the missing Stage A review at the next authorized workflow invocation. Check `python scripts/review_cycle.py status M01-L02` when a cycle exists; do not restart `ready` or `blocked`, and resume an existing `revising` round without incrementing attempts.
2. Parent selects at most three topic-matched verified lessons learned for each reviewer with `learning_memory.py suggest --tags ... --role technical_reviewer|pedagogy_reviewer --limit 3`. Delegate **independent existing** `technical_reviewer` (Sol High) and `pedagogy_reviewer` (Terra Medium). The former combines `technical-review` and `provenance-review` on the selected lesson/assessment/evidence; the latter combines `pedagogical-review` and `curriculum-coverage-review` on that lesson pair and its outcomes. Do not inspect unrelated lessons or let a reviewer edit the draft or call the other reviewer.
3. Each reviewer writes **only** its own artifact: `modules/mXX/reviews/automatic/lessons/MXX-LYY/technical.md` or `pedagogy.md`. Require an independent verdict (`block`, `revise`, `ready-for-human-review`) and location-specific findings with stable IDs, severity, exact primary/curriculum evidence, suggested fix, and `open`/`resolved` state. An open blocker or major cannot be a ready verdict; silence, missing reports and broken source links do not count as PASS.
4. Parent records both actual verdicts: `python scripts/review_cycle.py record MXX-LYY --technical VERDICT --pedagogy VERDICT`. The lesson's dedicated `cycle.json` holds its own attempts, independent of other lessons and the module. Update the affected task's explicit scoped `taskctl.py review-status --scope technical|pedagogy`; being drafted/validated never means reviewed.
5. If the lesson needs actionable fixes, run `python scripts/review_cycle.py begin-revision MXX-LYY` **before** assigning Author, no more than **two author rounds for this lesson**. Provide precise findings, use `taskctl invalidate TASK-ID author --reason "Finding IDs ..."` without cascade, patch only the affected lesson/assessment/evidence, complete the author step and run `draft_handoff.py TASK-ID` with scoped validation. Reinvoke **both** reviewers to recheck changed sections, companion effects and regressions, preserving finding IDs and exact resolved evidence; update the same reports and record verdicts again. Reuse old sources; research again only when needed. A run interrupted in `revising` resumes the reserved attempt. Stop at `blocked` or evidence/reviewer uncertainty and do not silently proceed to downstream authoring.
6. Hand off both reports and cycle with `python scripts/draft_handoff.py TASK-ID --review-report modules/mXX/reviews/automatic/lessons/MXX-LYY/technical.md --review-report modules/mXX/reviews/automatic/lessons/MXX-LYY/pedagogy.md`. This works for **one lesson even when the module is incomplete**. If a corrected cycle is ready and its final report explicitly marks findings resolved with verified evidence, record only reusable lessons with `learning_memory.py record --module mXX --lesson MXX-LYY ...`; new lessons can immediately reuse the compact feedback. There is no AI skill auto-update.

On multi-lesson requests, complete Stage A for a lesson before drafting dependent lessons to prevent repeating discovered errors. No new task-graph step or extra test/model is added; the **parent** invokes the two reviewer agents and Python only records/ships reports.

## Stage B — Module synthesis only (no second full lesson QA)
### Scope and triggering

1. Read the module's lesson and integration Stories in `delivery/backlog.json`. A module qualifies only if **every lesson has a `ready` Stage A review cycle** and its integration Story has finished authoring, files exist and scoped validation/feature-branch handoff succeeded. If any lesson is blocked or unreviewed, module synthesis must not declare ready.
2. Check `modules/mXX/reviews/automatic/cycle.json` through `python scripts/review_cycle.py status mXX`. If `ready` or `blocked`, do not restart automatically. If `revising`, **resume that existing round** from the task state/worklog; never spend another revision attempt for a restart. If no cycle record exists, run initial review.
3. Before delegating, derive 1–8 relevant lowercase hyphenated topic tags from the approved module Story/outcomes, and call `python scripts/learning_memory.py suggest --tags tag-a,tag-b --role technical_reviewer --limit 3` and separately `--role pedagogy_reviewer`. Give each reviewer only its own matched compact prevention reminders (possibly none), never the entire history. Treat stored reminders as context to check, **not** as primary evidence or permission to override the approved spec. The parent delegates two independent reviewer agents using the existing profiles **unchanged**: `technical_reviewer` (Sol High) and `pedagogy_reviewer` (Terra Medium). They cannot review their own authored fixes, edit lessons, or trigger the other agent. They can run in parallel on separate output paths. Python scripts do **not** invoke LLMs.

## Initial synthesis review: integration and cross-lesson connections only

**Technical + provenance:** apply `technical-review` and `provenance-review` to the integrated brief, solution and decision summary, plus **only** cross-lesson contradictions, mismatched assumptions, consistency of references and failure semantics. Start from accepted Stage A reports; do not redo detailed source/answer audits of untouched lessons. Write `modules/mXX/reviews/automatic/technical.md`.

**Pedagogy + coverage:** apply `pedagogical-review` and `curriculum-coverage-review` to module-wide coverage, sequencing, prerequisites, overlap, synthesis and the integrated exercise/rubric. Reuse Stage A outcome maps and verdicts; do **not** rescore each accepted lesson's exercises or reread unchanged lessons. Write `modules/mXX/reviews/automatic/pedagogy.md`.

Both synthesis reports must identify the reviewed integration and any affected cross-lesson connections, not issue a second full verdict on every unchanged lesson. Locate each finding by path, section/line, ID, severity (`blocker`, `major`, `minor`, `note`), evidence and concrete fix. On later re-review, retain original finding IDs and add a compact explicit line such as `| T-1 | resolved | https://primary-source.example/path |` for fixed findings. Include the exact source URL or approved curriculum path that actually supports the correction, and distinguish sources from the reviewer's own assertion. The final verdict is `block`, `revise` or `ready-for-human-review`. An open blocker/major is never a clear verdict. Store reports even if they contain blockers.

## Automatic correction loop (maximum two author rounds)

1. Verify both reports are present and sufficiently specific; do not treat reviewer model silence or partial output as PASS. Record the two **actual** verdicts:
   `python scripts/review_cycle.py record mXX --technical VERDICT --pedagogy VERDICT`.
   This persists the module's review cycle, currently open findings and round count **without** inspecting content hashes. Reconcile per-artifact `taskctl.py review-status --scope technical|pedagogy` against the reviewers' findings; `needs_review` for open blocker/major or significant unresolved issues, `reviewed` only when the corresponding scope is clear. The final public status remains draft pending human approval.
2. If the recorded cycle is `ready`, stop the correction loop and hand off. If `needs_revision` and the findings are actionable, reserve a round **before** spawning Author:
   `python scripts/review_cycle.py begin-revision mXX`.
   The first call reserves revision 1, the second revision 2; a third is prohibited. **Do not regenerate an entire module by default.** If module synthesis changes a previously accepted lesson materially, explicitly flag its task review scopes `needs_review` and carry out targeted independent Stage A re-review of that affected lesson before module QA can become ready.
3. The parent builds a correction plan from the *open findings*, mapping each to affected canonical paths, Story Task IDs, exact sections, source-evidence gaps and linked assessment or integration impacts. Delegate to the original `lesson_author` for affected lesson/assessment pairs, or the integration author for integration artifacts. Give Author the quoted findings, verified evidence, and the current draft; instruct it to patch only implicated sections and their necessary dependencies. A fundamental error may warrant rewriting the **affected lesson**, not unrelated lessons. Reuse source research; invoke `source_researcher` only when the finding actually requires new verification. If evidence is unresolvable, copyright/rights unclear, reviewers contradict with no defensible resolution, or a safe correction cannot be justified, stop using `python scripts/review_cycle.py stop mXX --reason "..." ` and report for human action instead of guessing.
4. For affected completed author tasks, use the owner's standing rework authorization to explicitly `taskctl invalidate TASK-ID author --reason "Module reviewer finding IDs ..."` **without `--cascade`**, then `start` / `complete` that author step after the patch. For unusual historical task graphs use their declared author step rather than inventing one; do not alter completed research unless findings require it. Record which findings were addressed in the existing worklog. Flag material changes for both review scopes as `needs_review`. Do not edit models, skills or the approved curriculum to address teaching content.
5. Run `python scripts/draft_handoff.py` for **only changed completed draft Task IDs**. This reruns scoped deterministic validation, commits/pushes revised content and worklogs, and also persists the active `cycle.json` counter. If it fails, fix only deterministic representation errors in the affected files, then rerun the focused check; do not start a new author/reviewer round merely for validation formatting.
6. Reinvoke **both independent reviewers** in **targeted re-review mode**: verify every originally open finding is either resolved or still open, inspect corrected passages, companion assessment, nearby assumptions and downstream/integrated impacts; look for regressions introduced by changes. Reuse earlier evidence/reports; do not re-research untouched lessons. Each reviewer **updates its own original module report**, retaining finding IDs and history/locations; neither writes to the other's file. Parent records their new verdicts with `review_cycle.py record`. Continue only if cycle is `needs_revision` and the persisted counter permits one more round.
7. **Learn only from corrected, independently confirmed findings.** If the cycle is `ready` **and** at least one corrective round was actually performed, the parent reviews resolved findings in the latest independent reports. Distill only genuinely *reusable* root causes and preventative instructions; do not store one-off wording edits, unsupported reviewer preferences or broad guesses. For each candidate, check the exact evidence is independently adequate and present in the resolved finding's report, then run `python scripts/learning_memory.py record --module mXX --review-role technical --finding-id T-1 --key stable-error-pattern --tags topic-a,topic-b --problem "Specific recurring failure mechanism" --prevention "Precisely what to verify or do next time" --evidence "https://primary-source.example/section" --applies-to lesson_author,technical_reviewer` (or pedagogy equivalents). Use stable keys to deduplicate across modules; inconsistent guidance for the same key must be flagged rather than silently overwritten. The Python helper refuses unresolved/blocked reviews, missing cited evidence and duplicate conflicting advice. When no transferable verified lesson exists, record nothing. **This is repository-level feedback, not model fine-tuning or automatic SKILL.md editing.**
8. At `ready`, or `blocked` after two unsuccessful revisions, stop. The parent hands off the reports, updated learning-memory JSON (if any) and cycle state with
   `python scripts/draft_handoff.py TASK-ID [all completed module Task IDs] --review-report modules/mXX/reviews/automatic/technical.md --review-report modules/mXX/reviews/automatic/pedagogy.md`.
   This selectively commits and pushes the QA evidence and verified prevention notes to the feature branch. A successful handoff does **not** merge or imply human publishing approval.
9. After handoff, run `python scripts/learning_memory.py promotions`. Only if a stable error pattern has **verified occurrences in two different modules**, the parent may propose a narrow Skill change in a **separate reviewable PR** after checking current instructions for conflicts, duplication, source validity and existing pending proposals. Include supporting source links and affected modules; do not auto-merge, silently change Skills or open duplicate proposals. If evidence conflicts, seek human judgment rather than prescribing a global rule. Report outstanding findings and exhausted attempts explicitly.

**Hard stop conditions:** more than two corrective author rounds, missing independent review report, unverified critical claims, unsafe or speculative fixes, irreconcilable reviewer disagreements, or Git/validation failures. An interrupted `revising` cycle resumes its existing round rather than beginning a new one; a completed `ready` or `blocked` cycle requires new user direction to reopen. The module is never reported as ready when it still has open blocker/major findings.

Each lesson QA uses **two independent reviewer calls** plus two per necessary correction round; the module synthesis uses two more reviewers but does **not** repeat comprehensive lesson QA. Re-review is limited to changed content and dependencies. No unbounded self-repair, repeated whole-module audits or additional reviewer roles.
